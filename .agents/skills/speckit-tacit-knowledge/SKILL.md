# Spec Kit 암묵지 기록

## 목적

여러 세션을 거치며 드러난 암묵적인 판단 기준을 검증 가능한 근거와 함께 보존한다. 해석을
상위 규칙이나 확정 요구사항으로 오인하지 않도록 상태, 확신도, 적용 범위와 반례를 함께
기록한다.

## 사용자 입력

```text
$ARGUMENTS
```

입력이 있으면 해석한 내용, 관련 세션·커밋·파일과 사용자가 지정한 기능 경로를 우선
반영한다. 근거가 부족한 부분을 일반적인 관행으로 채우지 않는다.

## 산출물 언어

자연어 기록과 사용자 보고는 한국어로 작성한다. 코드 식별자, 명령어, 파일 경로, 환경
변수, 라이브러리·API 고유 명칭과 오류 식별자는 원문을 유지한다. 비밀, credential,
token과 개인정보는 원문을 기록하지 않고 `<redacted>`로 바꾼다.

## 허용 수정 경로

이 스킬은 활성 기능의 `specs/<feature>/tacit-knowledge.md`만 생성하거나 파일 끝에 새
항목을 추가할 수 있다. 현재 활성 기능이 `001-apple-social-login`이면 대상은 정확히
`specs/001-apple-social-login/tacit-knowledge.md`다.

- 기존 제목, 항목, 표, 순서와 문장을 수정하거나 삭제하지 않는다.
- 기존 해석의 보강, 반증 또는 폐기가 필요하면 원래 항목을 참조하는 새 후속 항목을
  추가한다.
- Constitution, 명세, 계획, 작업 목록, 체크리스트, 소스, 테스트와 설정을 수정하지 않는다.
- 암묵지를 규범·요구사항·설계 결정으로 승격하려면 해당 책임을 가진 Spec Kit 스킬을 별도로
  실행한다.

## 기록 조건

다음 조건을 모두 충족할 때만 기록한다.

- 둘 이상의 독립적인 근거를 종합해 기존 문서에 직접 적혀 있지 않은 판단 기준, 책임 경계,
  반복 패턴 또는 실행 순서를 해석했다.
- 근거 중 하나 이상은 현재 저장소의 파일, Git 커밋·diff, 테스트·명령 결과 또는 사용자가
  확인한 결정처럼 이후 세션에서 다시 확인할 수 있다.
- 해석의 적용 범위와 적용되지 않는 범위를 구분할 수 있다.

단일 세션의 직감, 아직 관찰되지 않은 가능성, 이미 Constitution·명세·계획에 명시된 문장의
복사, 일반적인 업계 관행만으로 만든 주장은 기록하지 않는다. 실제 오류와 해결 과정은
`$speckit-troubleshooting`에 기록하고, 그 사건들에서 일반화한 판단 기준만 이 스킬에
기록한다.

## 권위와 상태

- 암묵지 기록은 참고 근거이며 Constitution, 명세, 계획, 작업 목록과 소스의 현재 사실보다
  우선하지 않는다.
- 상태는 `후보`, `검증됨`, `폐기됨` 중 하나다. 사용자 확인이나 반복 가능한 저장소 증거가
  없으면 `검증됨`을 사용하지 않는다.
- 확신도는 `중간` 또는 `높음`만 기록한다. `낮음` 수준의 추측은 기록 조건을 충족하지 않는다.
- 상위 문서와 충돌하는 해석은 실행 규칙으로 적용하지 않는다. 충돌 근거를 보고하고 필요한
  경우 해당 문서를 담당하는 스킬로 넘긴다.

## 실행 절차

1. 저장소 루트에서 `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`를 한
   번 실행해 `REPO_ROOT`와 `FEATURE_DIR`을 구한다. 사용자가 `specs/<feature>` 또는 정확한
   대상 파일을 명시했다면 저장소의 `specs/` 아래에 있고 파일명이
   `tacit-knowledge.md`인지 검증한 뒤 사용한다. 기능 디렉터리가 없으면 새 기능을 만들지
   말고 중단한다.
2. 대상 파일, Constitution, 관련 기능 산출물, 현재 코드·테스트와 사용 가능한 세션·Git
   근거를 읽는다. 최소 두 근거가 서로 독립적인지와 현재 상태에서 다시 확인 가능한지를
   평가한다.
3. 한 문장으로 해석을 작성한 뒤 다음을 분리한다.
   - 관찰된 반복 사실
   - 사실에서 도출한 해석
   - 적용 범위와 제외 범위
   - 반례, 불확실성 또는 시간이 지나면 달라질 수 있는 조건
   - 명시 문서로 승격하기 위한 검증 조건
4. 기존 기록에서 같은 해석과 범위를 검색한다. 같은 근거의 중복이면 파일을 수정하지 않고
   기존 항목을 보고한다. 새 근거, 범위 변경, 반증 또는 상태 변화가 있으면 기존 ID를
   참조하는 새 항목을 작성한다.
5. 오늘 날짜의 기존 ID를 확인하고 `TK-YYYYMMDD-NNN` 형식으로 다음 ID를 부여한다. 같은
   날짜에는 `NNN`을 001부터 증가시키며 기존 ID를 재사용하지 않는다.
6. 대상 파일이 없으면 아래 최소 머리말을 먼저 만들고 첫 항목을 작성한다. 파일이 있으면
   끝의 개행을 보장한 뒤 새 항목만 추가한다.

```markdown
# <feature> 암묵지 기록

**대상 기능**: `<feature>`

**기록 원칙**: 복수 근거에서 해석한 지식을 상태와 범위와 함께 append-only로 보존한다.
```

7. 각 항목은 다음 형식을 사용한다.

```markdown
## TK-YYYYMMDD-NNN: <암묵지 제목>

**기록일**: YYYY-MM-DD
**상태**: 후보 | 검증됨 | 폐기됨
**확신도**: 중간 | 높음
**적용 범위**: <기능, 패키지, 단계 또는 기간>
**관련 항목**: <요구사항, 작업 ID, 문제 ID 또는 없음>

### 해석

<문서에 직접 적혀 있지 않았던 판단 기준을 한 문장으로 기술>

### 근거

- `<파일:줄, 커밋, 명령 결과 또는 세션 식별자>`: <관찰한 사실>
- `<독립적인 두 번째 근거>`: <관찰한 사실>

### 적용과 제외

- 적용: <이 해석을 사용할 조건>
- 제외: <이 해석으로 판단하면 안 되는 조건>

### 반례와 불확실성

<반례, 미확인 범위 또는 오래될 수 있는 사실>

### 검증 또는 승격 조건

<사용자 확인, 반복 검증 또는 명시 문서 반영에 필요한 조건>

### 연결

<선행·후속 tacit knowledge ID, trouble-shooting ID 또는 없음>
```

8. 독립 근거가 둘 이상인지, 사실과 해석이 분리됐는지, 상태·확신도가 근거에 비해 과장되지
   않았는지, 상위 문서와 충돌하지 않는지, 민감 값이 제거됐는지, 기존 기록이 byte 단위로
   보존됐는지 확인한다. `git diff --check`와 대상 파일 diff를 검사한다.
9. 사용자에게 대상 경로, 새 ID, 상태, 확신도, 핵심 근거, 적용 범위와 미검증 조건을
   보고한다. 기록 조건을 충족하지 않았거나 중복이면 파일을 바꾸지 않은 이유를 보고한다.

## 완료 조건

- [ ] 독립적인 근거를 둘 이상 확인했다.
- [ ] 대상이 활성 기능의 정확한 `tacit-knowledge.md`인지 확인했다.
- [ ] 기존 기록을 보존하고 새 항목만 추가했다.
- [ ] 사실, 해석, 적용 범위, 반례와 검증 조건을 분리했다.
- [ ] 암묵지를 상위 규칙이나 확정 사실로 과장하지 않았다.
- [ ] 민감 값을 남기지 않고 변경 경로와 결과를 한국어로 보고했다.
