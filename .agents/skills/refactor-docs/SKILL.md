# 문서 리팩토링

마크다운 문서 여러 개를 읽고, (1) 한 문서 안의 중복을 병합하고 (2) 여러 문서에 걸쳐 반복되는
내용을 하나의 공통 문서로 뽑아내 링크로 연결한다. 목표는 세 가지다.

- **컨텍스트 절약**: 같은 내용을 여러 곳에서 반복해서 읽지 않도록 한다.
- **직관적 구조**: 어떤 문서를 봐야 할지, 어디서 상세 내용을 찾을지 헤매지 않게 한다.
- **재사용 가능한 공통 형태**: 다른 스킬·에이전트가 그 공통 문서 하나만 링크로 참조하면 되게
  만든다.

이 스킬은 **사용자가 지정한 문서/폴더 집합에만** 적용한다. 대상이 명확하지 않으면 먼저
확인한다("어떤 문서들을 대상으로 할까요?"). 대상 밖 파일은 절대 수정하지 않는다.

## 왜 이 순서로 하는가

문서 중복은 코드 중복과 달리 "완전히 같은 문장"과 "같은 주제를 다르게 설명한 것"이 섞여
있다. 전자는 기계적으로 병합해도 안전하지만, 후자를 무리하게 하나로 합치면 각 문서가 가진
맥락(대상 독자, 예외 상황, 그 문서만의 제약)이 사라져 오히려 정보 손실이 된다. 그래서 판단은
항상 "완전히 같은 뼈대 + 문서별로 다른 세부사항"으로 나눠서 하고, 뼈대만 공통 문서로 보내고
세부사항은 원래 자리에 남긴다. 코드에서 "비슷한 코드 세 줄이 섣부른 추상화보다 낫다"는 원칙과
같은 이유다.

## 절차

### 1. 인벤토리 작성

대상 문서를 전부 읽는다(전체를 다 붙여넣지 않아도 되면 목차·제목·섹션 헤더 수준으로 훑어도
좋다). 각 문서에 대해 다음을 짧게 기록한다: 경로, 목적(누가 언제 읽는 문서인가), 다른 문서가
이 문서를 링크하고 있는지(`grep -rn "문서파일명"`으로 backlink 확인).

이 시점에서 이미 다른 문서가 이 대상들을 가리키는 색인/진입점 문서(예: 이 저장소의
`AGENTS.md`, `docs/conventions/README.md` 같은 우선순위·목차 문서)가 있는지 확인해 둔다.
나중에 이 색인도 갱신 대상이 될 수 있다.

### 2. 중복 탐지

두 종류를 구분한다.

- **문서 내부 중복**: 같은 문서 안에서 같은 설명이나 같은 예시가 반복됨. 흔히 문서가
  여러 번 수정되면서 생긴다.
- **문서 간 중복·유사**: 서로 다른 문서에 같은 규칙, 같은 절차, 같은 배경 설명이 거의 그대로
  또는 표현만 바뀌어 반복됨. 특히 여러 하위 문서가 같은 상위 규칙을 각자 다시 설명할 때
  생긴다(예: 패키지별 규칙 문서마다 같은 "의존성 방향" 설명을 반복).

완전 일치가 아니어도 된다. 문단을 나란히 놓고 "이 두 문단이 같은 사실을 주장하는가"를
기준으로 판단한다.

### 3. 문서 내부 중복 병합

같은 내용을 다루는 섹션을 하나로 합치고 나머지를 지운다. 문서 안에서 그 내용을 다른
섹션이 참조해야 하면 마크다운 앵커 링크(`[제목](#섹션-앵커)`)로 연결한다. 새 섹션을
만들 때 원래 있던 두 표현 중 더 정확하고 최신인 쪽을 기준으로 삼는다(둘 다 부정확하면
직접 다시 쓴다). 삭제 전에 각 표현이 진짜 같은 내용인지, 미묘하게 다른 예외가 섞여
있지는 않은지 반드시 재확인한다 — 다른 조건을 가진 두 규칙을 하나로 합치면 정보가
사라진다.

### 4. 문서 간 반복 내용을 공통 문서로 추출

1. **공통 뼈대와 문서별 차이를 분리한다.** 여러 문서가 공유하는 부분만 뽑아낸다. 문서마다
   다른 세부사항(예: 이 패키지에만 있는 예외)은 원래 문서에 남긴다.
2. **공통 문서의 위치를 정한다.** 기존 문서 구조에 이미 공용 문서 폴더나 컨벤션이 있으면
   그것을 따른다(이 저장소라면 `docs/conventions/`, `docs/package-rules/`처럼 역할별
   폴더가 이미 있다 — 새 폴더를 만들기보다 이런 기존 자리부터 확인한다). 없으면 대상
   문서들의 가장 가까운 공통 상위 폴더에 새 파일을 만들고, 이름은 내용을 그대로 드러내는
   명사구로 짓는다.
3. **공통 문서는 자기 완결적으로 쓴다.** 스킬이나 에이전트가 그 문서 하나만 읽고 바로 쓸 수
   있어야 한다. 제목, 필요하면 목차, 예시를 포함한다. "위 문서 참고"처럼 다른 문서를
   전제하는 표현을 넣지 않는다.
4. **원래 자리에는 요약 한두 줄 + 링크만 남긴다.** 전체 내용을 복사해 두지 않는다 — 그러면
   중복이 다시 생긴다. 예:

   ```markdown
   ## 의존성 방향

   Domain/Data/Core는 서로 및 App/Feature/UI에 의존하지 않는다. 세부 규칙과 금지 목록은
   [아키텍처 문서 7.1](../architecture.md#71-의존성-방향)을 따른다.
   ```

5. **역방향 참조가 필요하면 공통 문서에도 "이 문서를 참조하는 곳" 같은 안내를 남기지 않는다**
   (공통 문서가 자신을 참조하는 모든 곳을 알 필요는 없다 — 결합도만 높아진다). 대신 진입점
   색인 문서(1단계에서 찾은 것)에 새 공통 문서로 가는 링크를 추가한다.

### 5. 링크 무결성 확인

- 모든 상대경로 링크가 실제로 그 파일/앵커를 가리키는지 확인한다(`ls`나 앵커 텍스트 대조로
  검증 — 눈대중으로 넘어가지 않는다).
  - 이 저장소는 GitHub Flavored Markdown 앵커 규칙(제목을 소문자로 바꾸고 공백을 `-`로
    치환)을 쓰므로 한글 제목이어도 이 규칙 그대로 앵커를 만든다.
- 순환 참조(A→B→A로 서로를 링크만 하고 실제 내용은 없는 상태)가 생기지 않았는지 확인한다.
- 원본 문서의 섹션 제목을 지우거나 옮겼다면, 그 제목을 링크하던 다른 문서도 같이 갱신한다
  (`grep -rn`으로 옛 제목·파일명을 검색).

### 6. 적용과 보고

git으로 추적되는 문서라면 직접 수정한다(승인 대기 없이 진행) — 되돌리기 쉬운 작업이다.
단, 다음은 지킨다.

- **대상으로 지정되지 않은 파일은 건드리지 않는다.** 새로 만드는 공통 문서 하나만 예외다.
- 이 저장소처럼 특정 스킬만 수정할 수 있는 경로 소유권 규칙이 있는 프로젝트에서는 그 규칙을
  먼저 확인한다(이 저장소는 `AGENTS.md`의 "Spec-Kit 작업 범위" 표 — 예를 들어
  `specs/<feature>/**`나 `docs/spec-kit/<feature>/**`의 append-only 파일은 소유
  스킬을 거치지 않고 구조를 바꾸지 않는다).
- 커밋은 사용자가 명시적으로 요청하기 전까지 하지 않는다.

작업이 끝나면 다음을 요약해 보고한다.

- 병합한 문서 내부 중복(어느 문서, 어느 섹션).
- 새로 만든 공통 문서 경로와, 그것을 링크하게 된 원본 문서 목록.
- 갱신한 색인/진입점 문서.
- 의도적으로 병합하지 않은 유사 내용과 그 이유(세부 차이가 있어서 등) — 판단 근거를
  남겨야 다음에 같은 문서를 다시 검토하는 사람이 왜 그대로 뒀는지 알 수 있다.
- 확인했지만 justify하지 못해 그대로 둔 애매한 케이스(있다면).

## 하지 말아야 할 것

- 유사하다는 이유만으로 서로 다른 제약을 가진 규칙을 하나로 뭉개기. 세부 차이가 실수로
  사라지면 코드 리뷰나 후속 작업에서 잘못된 규칙을 적용하게 된다.
- 공통 문서를 만들면서 원본에 원문을 그대로 남겨두기(링크만 남기지 않으면 중복이 그대로
  남는다 — 이 스킬의 목적 자체가 무효화된다).
- 대상으로 지정되지 않은 문서의 구조를 "더 좋아 보인다"는 이유로 바꾸기.
- 한 번도 다른 곳에서 참조되지 않는, 정말 그 문서에만 있는 내용까지 "일관성"을 이유로
  공통 문서로 옮기기 — 딱 한 곳에서만 쓰이는 내용은 그 자리가 맞는 자리다.
