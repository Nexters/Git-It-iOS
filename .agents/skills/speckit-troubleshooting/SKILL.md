# Spec Kit 문제 해결 기록

## 목적

Spec Kit 세션에서 실제로 발생한 문제를 재현 가능한 증거와 함께 보존한다. 현재 상태와
추론을 구분하고, 해결되지 않은 문제를 해결된 것처럼 기록하지 않는다.

## 사용자 입력

```text
$ARGUMENTS
```

입력이 있으면 문제의 증상, 실행 단계, 관련 명령과 사용자가 지정한 기능 경로를 우선
반영한다. 입력에 없는 사실을 추측해 채우지 않는다.

## 산출물 언어

자연어 기록과 사용자 보고는 한국어로 작성한다. 코드 식별자, 명령어, 파일 경로, 환경
변수, 라이브러리·API 고유 명칭과 오류 식별자는 원문을 유지한다. 비밀, credential,
token과 개인정보는 원문을 기록하지 않고 `<redacted>`로 바꾼다.

## 허용 수정 경로

이 스킬은 `GIT_IT_DOCS_ROOT` 아래 활성 기능의
`spec-kit/<feature>/trouble-shooting.md`만 생성하거나 파일 끝에 새 항목을 추가할 수 있다.
현재 활성 기능이 `001-apple-social-login`이고 문서 루트가 `docs`이면 대상은 정확히
`docs/spec-kit/001-apple-social-login/trouble-shooting.md`다.

- 기존 제목, 항목, 표, 순서와 문장을 수정하거나 삭제하지 않는다.
- 기존 내용의 교정이 필요하면 원래 항목을 참조하는 새 후속 항목을 추가한다.
- 명세, 계획, 작업 목록, 체크리스트, 소스, 테스트와 설정을 수정하지 않는다.
- 다른 파일의 수정이 필요하면 해당 책임을 가진 스킬 또는 별도 사용자 지시로 넘긴다.

## 기록 조건

다음 중 하나가 실제로 관찰된 경우에만 기록한다.

- 명령, 빌드, 테스트, 훅 또는 자동화가 실패하거나 예상과 다른 결과를 냈다.
- 문서·코드·실행 환경 사이의 불일치로 진행이 중단되거나 재작업이 발생했다.
- 잘못된 가정, 책임 경계 해석 또는 완료 판단을 근거로 교정했다.
- 환경 제약, 권한, 캐시 또는 외부 상태가 제품 코드 실패와 혼동될 수 있었다.
- rollback, 복구, 우회가 필요했거나 문제를 해결하지 못한 채 중단했다.

발생하지 않은 위험, 일반적인 주의사항, 근거 없는 가능성은 기록하지 않는다. 여러 세션의
근거를 일반화한 규칙이나 의사결정 기준은 `$speckit-tacit-knowledge`의 책임이다.

## 실행 절차

1. `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`로 `REPO_ROOT`와
   `FEATURE_DIR`을 구하고, 활성 `specs/<feature>` 디렉터리인지 확인한다.
   `tools/repository-paths/bin/repository-paths.sh GIT_IT_DOCS_ROOT`의 판독 결과가
   저장소 안의 실제 디렉터리인지 검증한 뒤
   `<docs-root>/spec-kit/<feature>/trouble-shooting.md`를 대상으로 삼는다.
   사용자가 기능이나 파일을 지정했다면 이 결과와 일치해야 하며, 기능 디렉터리가
   없으면 중단한다.
2. 대상 파일과 문제와 직접 관련된 현재 산출물, Git diff·이력, 명령 출력 또는 테스트
   결과를 읽는다. 관찰한 사실, 해석, 아직 확인하지 못한 내용을 분리한다.
3. 문제 상태를 `미해결`, `완화`, `해결`, `환경 제약` 중 하나로 정한다. `해결`은 원인을
   겨냥한 조치 뒤 관련 검증이 성공했다는 증거가 있을 때만 사용한다.
4. 기존 기록에서 같은 증상·원인·검증 근거를 검색한다. 완전히 같은 사건이면 파일을
   수정하지 않고 기존 항목을 보고한다. 새 증거, 재발 또는 상태 변화가 있으면 기존 항목을
   참조하는 새 항목을 작성한다.
5. 오늘 날짜의 기존 ID를 확인하고 `TS-YYYYMMDD-NNN` 형식으로 다음 ID를 부여한다. 같은
   날짜에는 `NNN`을 001부터 증가시키며 기존 ID를 재사용하지 않는다.
6. 대상 파일이 없으면 아래 최소 머리말을 먼저 만들고 첫 항목을 작성한다. 파일이 있으면
   끝의 개행을 보장한 뒤 새 항목만 추가한다.

```markdown
# <feature> 문제 해결 기록

**대상 기능**: `<feature>`

**기록 원칙**: 실제 발생한 문제와 검증 근거를 append-only로 보존한다.
```

7. 각 항목은 다음 형식을 사용한다. 해당 정보가 아직 확인되지 않았으면 생략하지 말고
   `확인 중` 또는 `미실행`으로 명시한다.

```markdown
## TS-YYYYMMDD-NNN: <문제 제목>

**기록일**: YYYY-MM-DD
**상태**: 미해결 | 완화 | 해결 | 환경 제약
**발생 단계**: <Spec Kit 스킬 또는 작업 단계>
**관련 항목**: <요구사항, 작업 ID, 파일, 커밋 또는 없음>

### 증상

<관찰된 결과와 재현 조건>

### 영향

<중단되거나 잘못 판단될 수 있는 범위>

### 근거

- `<명령, 파일:줄, 커밋 또는 세션 식별자>`: <관찰한 사실>

### 원인

<확정 원인 또는 확인 중인 가설을 명확히 구분>

### 조치

<실제로 수행한 조치, 미수행이면 미실행>

### 검증

- `<검증 명령 또는 확인 방법>`: <성공, 실패 또는 미실행과 핵심 결과>

### 재발 방지

<다음 세션에서 확인할 판별 기준 또는 절차>

### 연결

<선행·후속 문제 ID, tacit knowledge ID 또는 없음>
```

8. 사실과 추론이 섞이지 않았는지, 상태가 검증 결과와 일치하는지, 민감 값이 제거됐는지,
   기존 기록이 byte 단위로 보존됐는지 확인한다. `git diff --check`와 대상 파일 diff를
   검사한다.
9. 사용자에게 대상 경로, 새 ID, 상태, 사용한 핵심 근거와 미검증 범위를 보고한다. 기록할
   조건을 충족하지 않았거나 중복이면 파일을 바꾸지 않은 이유를 보고한다.

## 완료 조건

- [ ] 실제로 관찰된 문제인지 확인했다.
- [ ] 대상이 활성 기능의 정확한 `docs/spec-kit/<feature>/trouble-shooting.md`인지 확인했다.
- [ ] 기존 기록을 보존하고 새 항목만 추가했다.
- [ ] 증거, 원인, 조치, 검증과 상태가 서로 모순되지 않는다.
- [ ] 민감 값과 확인되지 않은 성공 주장을 남기지 않았다.
- [ ] 변경 경로와 결과를 한국어로 보고했다.
