# 006-domain-usecase-requirements 문제 해결 기록

**대상 기능**: `006-domain-usecase-requirements`

**기록 원칙**: 실제 발생한 문제와 검증 근거를 append-only로 보존한다.

## TS-20260819-001: AskUserQuestion 호출 시 questions 파라미터를 문자열로 이중 인코딩해 InputValidationError 발생

**기록일**: 2026-08-19
**상태**: 해결
**발생 단계**: `/speckit-clarify` 2차 세션 (재등록 소유권/삭제 후 재등록 질문 준비 중)
**관련 항목**: 없음

### 증상

`AskUserQuestion` 도구를 `{"raw": "{\"questions\": [...]}"}` 형태로 호출했다 — 즉 `questions` 배열을 최상위 파라미터로 직접 전달하지 않고, 전체 JSON을 문자열로 감싸 `raw`라는 존재하지 않는 파라미터에 넣었다. 호출은 `InputValidationError: AskUserQuestion was called with input that could not be parsed as JSON`으로 즉시 실패했고, 도구가 반환한 원문 앞부분도 이스케이프된 유니코드(`\uXXXX`)가 그대로 남은 깨진 문자열이었다.

### 영향

이 호출 자체는 부작용 없이 실패했으므로(질문이 사용자에게 노출되지 않음) 사용자에게 잘못된 질문이 전달되지는 않았다. 다만 재시도 없이 방치했다면 해당 턴에서 명확화 질문을 하나도 진행하지 못하고 세션이 중단됐을 것이다.

### 근거

- 세션 내 도구 호출 기록: 첫 번째 `AskUserQuestion` 호출이 `raw` 필드에 JSON 문자열을 담아 전송됨 → `InputValidationError` 응답.
- 같은 세션의 두 번째 호출: `questions` 배열을 최상위 파라미터로 직접 전달 → 정상 응답(사용자 답변 수신).

### 원인

`AskUserQuestion`의 파라미터 스키마는 `questions`(및 선택적으로 `answers`, `metadata` 등)를 최상위 필드로 요구하는데, 직전에 다른 도구에서 긴 텍스트를 다루며 사용하던 "raw 문자열로 감싸기" 패턴을 그대로 적용해 전체 JSON을 문자열 값으로 이중 인코딩한 것이 직접 원인이다. 도구 스키마 자체의 문제는 아니며, 호출 측(에이전트)의 파라미터 구성 실수다.

### 조치

동일 질문 내용을 `questions` 배열을 최상위 파라미터로 직접 전달하는 정상 형식으로 즉시 재호출했다. 한글 텍스트는 별도 이스케이프 없이 UTF-8 문자열 그대로 전달했다(이전에 성공했던 첫 세션의 호출 패턴과 동일).

### 검증

- 재호출: 성공 — 사용자 답변("사용자별 별도 projectId (권장)", "기존 프로젝트 복원")을 정상적으로 수신함.
- 이후 같은 세션에서 동일한 정상 형식으로 `AskUserQuestion`을 1회 더 호출: 성공 — 사용자 답변("레벨별로 독립 생성 (권장)")을 정상적으로 수신함.

### 재발 방지

`AskUserQuestion`(및 유사하게 최상위 배열/객체 파라미터를 받는 도구)을 호출할 때, 파라미터를 문자열로 사전 인코딩해 감싸지 않고 도구 스키마가 요구하는 최상위 필드(`questions` 등)에 배열/객체를 직접 채워 넣는지 호출 직전에 확인한다. 특히 긴 한글 텍스트가 포함될 때 "문자열로 감싸면 안전하다"는 습관적 판단을 적용하지 않는다.

### 연결

없음

## TS-20260819-002: TS-20260819-001과 동일한 AskUserQuestion 이중 인코딩 실수가 다음 `/speckit-clarify` 세션(별도 커맨드 호출)에서 재발

**기록일**: 2026-08-19
**상태**: 해결
**발생 단계**: `/speckit-clarify` 3차 세션 (동일 사용자의 저장소당 다중 quizLevel 질문 준비 중)
**관련 항목**: TS-20260819-001

### 증상

TS-20260819-001과 완전히 동일한 형태로 재발했다. `AskUserQuestion`을 `{"raw": "{\"questions\": [...]}"}`처럼 `questions` 배열을 문자열로 이중 인코딩해 호출했고, 동일한 `InputValidationError: ... could not be parsed as JSON`으로 즉시 실패했다. 이번에는 `/speckit-clarify`를 사용자가 새로 커맨드로 재호출한, TS-20260819-001과는 별개의 대화 턴/세션이었다.

### 영향

TS-20260819-001과 동일하게 호출 자체가 부작용 없이 실패했으므로 사용자에게 잘못된 질문이 노출되지는 않았다. 다만 동일 실수가 반복됐다는 것은, 직전에 기록한 재발 방지 지침이 새 커맨드 호출 세션에서는 자동으로 참조되지 않는다는 실제 제약을 드러낸다.

### 근거

- 세션 내 도구 호출 기록: 이번 `/speckit-clarify` 3차 세션의 첫 `AskUserQuestion` 호출이 다시 `raw` 필드에 JSON 문자열을 담아 전송됨 → `InputValidationError` 응답(TS-20260819-001과 동일한 오류 메시지 패턴).
- 같은 세션의 두 번째 호출: `questions` 배열을 최상위 파라미터로 직접 전달 → 정상 응답(사용자 답변 "저장소당 프로젝트 1개로 제한" 수신).

### 원인

TS-20260819-001과 동일 — `questions`를 최상위 필드로 직접 채우지 않고 문자열로 사전 인코딩해 감싼 파라미터 구성 실수. 추가로 확인된 사실: 이 실수를 방지하기 위해 TS-20260819-001에 남긴 "재발 방지" 지침은 같은 세션 내에서는 유효했지만(3차 세션 자체는 이전 트러블슈팅 기록을 열람하지 않고 시작함), 새 커맨드 호출로 시작된 이번 세션의 초기 호출에는 반영되지 않았다 — 즉 트러블슈팅 기록이 다음 세션 시작 시 자동으로 로드·적용되지는 않는다는 환경 제약이 실제로 관찰됨.

### 조치

TS-20260819-001과 동일하게, `questions` 배열을 최상위 파라미터로 직접 전달하는 정상 형식으로 즉시 재호출했다.

### 검증

- 재호출: 성공 — 사용자 답변("저장소당 프로젝트 1개로 제한")을 정상적으로 수신함.

### 재발 방지

TS-20260819-001의 재발 방지 지침(파라미터를 문자열로 사전 인코딩하지 말 것)은 여전히 유효하나, 이 지침이 세션 간에 자동 적용되지 않는다는 점을 감안해야 한다. `AskUserQuestion`을 호출하기 전에는 매번(이전 세션에서 이미 겪은 문제인지와 무관하게) 파라미터가 도구 스키마의 최상위 필드(`questions`)에 배열로 직접 채워졌는지 호출 직전에 확인한다.

### 연결

TS-20260819-001 (선행 사건, 동일 원인)
