## TK-20260814-001: 핵심 명세와 부가 관심사의 분리

**기록일**: 2026-08-14
**상태**: 검증됨
**확신도**: 높음
**적용 범위**: `003-http-client`와 이후 범용 기술 API의 Spec Kit 명세 범위 결정
**관련 항목**: `spec.md` 범위, `tasks.md` 패키지 순서와 승인 게이트

### 해석

범용 기술 API의 기본 명세를 작성할 때 핵심 요청·응답 계약을 성립시키는 데 필수적이지 않은 보안,
관찰, 운영 정책 등의 부가 관심사는 즉시 기능 요구사항으로 편입하지 않고 제안서에서 후속 이슈
후보로 분리해 검토하며, 현재 명세는 합의된 기본 책임과 검증 가능한 핵심 동작에 집중한다.

### 근거

- `2026-08-14 현재 세션의 사용자 확인`: HTTP 전송 객체의 보안과 같은 부가 요소는 제안서를 통해
  추가 이슈로 정리하고 기본 명세에 집중하는 것을 기본 판단으로 확인했다.
- `specs/003-http-client/spec.md:167-186,315-322`: 현재 명세는 단발성 HTTP 요청·응답과 실패·취소를
  포함 범위로 한정하고, 인증·재시도 정책·기록·추가 전송 보안 정책을 범위 밖 책임으로 분리한다.
- `specs/003-http-client/tasks.md:293-298`: 현재 패키지 밖 책임이 필요해지면 구현을 중단하고 작업
  소유권을 다시 조정하며, Composition Adapter는 별도 명세가 다루도록 정한다.
- `이전 Data/Core Authentication README 세션 기록`: 테스트로 보장된 공개 동작만 문서화하고
  계획됐거나 검증되지 않은 통합은 범위 밖으로 명시하는 판단이 독립적으로 확인됐다.

### 적용과 제외

- 적용: 부가 관심사가 기본 기술 계약의 성립 조건이 아니고, 독립된 요구사항·수용 기준·소유 경계로
  분리할 수 있을 때 먼저 제안서에 기록하고 후속 이슈 생성 여부를 검토한다.
- 제외: 법적·규제상 필수 조건, 개인정보 보호의 필수 통제, 기본 계약 자체의 안전성·정확성 또는
  Constitution 준수에 필요한 사항은 부가 요소라는 이유로 미루지 않는다. 현재 기능에 포함하기로
  사용자가 명시적으로 결정한 요구사항도 이 판단으로 제외하지 않는다.

### 반례와 불확실성

어떤 관심사가 핵심인지 부가적인지는 기능과 위험 수준에 따라 달라진다. 특히 보안이라는 분류만으로
항상 후속 이슈가 되는 것은 아니며, 전송 기밀성이나 입력 검증처럼 기본 계약의 전제에 직접 영향을
주는 사항은 현재 명세 안에서 다뤄야 할 수 있다. 제안서의 저장 위치와 이슈 전환 절차는 아직 이
기능 문서에서 확정되지 않았다.

### 검증 또는 승격 조건

다른 범용 기술 API 명세에서도 같은 분리 판단이 반복되고, 제안서의 위치·검토·이슈 전환 절차가
합의되면 해당 책임을 가진 Constitution 또는 Spec Kit 운영 문서에 일반 규칙으로 승격할 수 있다.
