# Git It iOS 네이밍 컨벤션

**상태**: 정본

**작성일**: 2026-08-13

**최종 수정일**: 2026-08-31 (문서 간 중복 제거와 소유 문서 정리)

## 목적

이 문서는 [Constitution 원칙 10](../../.specify/memory/constitution.md#10-책임과-문맥에-따른-네이밍)의 상세 적용 기준입니다. 프로젝트가 소유하는 공개 API와 패키지·선언 경계를 넘는 값의 이름을 검토할 때 사용합니다. 상위 문서와의 우선순위는 [컨벤션 공통 규칙](./README.md#상위-문서와-충돌-해소)을 따릅니다.

이 문서의 예시는 판단 기준을 설명하기 위한 것이며, 특정 기능에서 사용한 이름을 다른 기능의 필수 접두어·접미어 또는 전역 어휘로 승격하지 않습니다.

## 1. 적용 범위

다음과 같이 프로젝트가 이름을 소유하는 선언과 값에 적용합니다.

- 패키지 밖으로 공개되는 타입, 프로토콜, 연산과 프로퍼티
- Domain·Data·Infrastructure 등 독립 경계가 정의하는 계약과 모델
- Adapter, initializer와 delegate를 통해 패키지 경계를 넘는 값
- 저장되거나 비동기 작업 이후 다시 해석되는 값
- 테스트 대역과 실행 환경별 구현이 함께 준수하는 프로젝트 소유 인터페이스

한 선언 안에서만 사용되고 문맥이 사라지지 않는 지역 변수와 매개변수에도 같은 책임 기준을 적용하되, 이미 타입이나 메서드가 제공하는 문맥을 이름에 반복할 필요는 없습니다. 외부 계약이 고정한 이름에는 [외부 고정 명칭 기준](#7-외부-고정-명칭과-공급자-중립-경계)을 우선 적용합니다.

## 2. 핵심 원칙

### 2.1 실제 책임을 먼저 설명합니다

이름을 정하기 전에 선언의 책임을 한 문장으로 설명합니다. 후보 이름의 각 단어는 그 책임, 구분해야 할 경계 또는 값의 수명을 설명해야 합니다. 선언이 맡지 않는 저장 방식, 공급자 내부 개념, 실행 환경이나 미래 책임을 이름에 넣지 않습니다.

예를 들어 어떤 계약의 책임이 "로그인 세션을 시작하고 복원하며 종료한다"라면 로그인 세션 문맥은 책임을 구분하는 근거가 됩니다. 반대로 실제 authorization 상태를 다루지 않는 저장 계약에 `Authorization`을 붙이는 것은 저장 값의 내부 형태를 계약 책임으로 오인하게 할 수 있습니다.

### 2.2 필요한 최소 문맥을 남깁니다

짧은 이름 자체가 목표는 아닙니다. 선언이 사용처에서 독립적으로 읽힐 때 다른 개념과 구분되는 최소 문맥을 남기는 것이 목표입니다.

- 문맥을 제거해 책임이 모호해지면 수식어를 유지합니다.
- 타입, 소유 메서드 또는 둘러싼 선언이 이미 같은 문맥을 명확히 제공하면 중복 수식어를 생략할 수 있습니다.
- 패키지나 target 이름만 봐야 이해되는 공개 이름은 필요한 문맥을 충분히 포함하지 않은 것으로 봅니다.

### 2.3 표면적 통일보다 독립적인 해석을 우선합니다

한 기능의 모든 타입에 같은 접두어를 붙이거나 같은 길이로 줄이는 방식은 이름의 품질을 보장하지 않습니다. 각 선언은 자신의 책임과 사용 문맥을 기준으로 검토합니다. 같은 개념도 저장·전달되는 값과 짧게 유지되는 지역 값에서 필요한 문맥이 다를 수 있습니다.

## 3. 선언 종류별 기준

### 3.1 공개 타입

- 타입이 소유하는 핵심 개념과 역할을 함께 식별할 수 있어야 합니다.
- 패키지 밖에서 타입 이름만 보아도 다른 동명의 개념과 구분할 수 있어야 합니다.
- 현재 소유하지 않는 역할을 암시하는 `Manager`, `Service`, `Provider` 같은 포괄 명사는 구체 책임 없이 사용하지 않습니다.
- 구현 기술이나 실행 환경은 타입의 계약 자체가 그것을 소유할 때만 포함합니다.

`LoginSession`과 일반 `Session`이 함께 존재할 수 있는 문맥에서 전자는 필요한 구분을 제공합니다. 반면 충돌 가능성이 없다는 이유만으로 모든 인증 타입에 동일한 축약 접두어를 붙이는 것은 허용 근거가 되지 않습니다.

### 3.2 프로토콜과 계약

- 프로토콜 이름은 구현체의 기술이 아니라 호출자에게 제공하는 능력과 책임을 표현합니다.
- `Repository`, `Storage`, `Remote`, `Provider` 같은 역할어는 실제 연산 집합과 수명 경계가 해당 역할을 충족할 때만 사용합니다.
- 하나의 프로토콜 이름이 서로 다른 책임을 감추면 계약을 먼저 분리할지 검토합니다. 이름으로 설계 문제를 덮지 않습니다.
- Domain 계약은 비즈니스 언어, Data 계약은 데이터 처리에 필요한 기술 능력, Infrastructure API는 범용 기술 능력으로 표현합니다.

### 3.3 연산

- 동사와 목적어는 실제 효과와 반환 의미를 드러내야 합니다.
- `get`, `handle`, `process`, `execute`처럼 대상과 효과를 감추는 일반 동사는 더 구체적인 동사로 대체할 수 있는지 검토합니다.
- 조회, 관찰, 저장, 삭제와 취소처럼 동작과 수명에 차이가 있으면 이름에서도 구분합니다.
- 타입이나 프로토콜이 대상을 명확히 제공하면 연산명에 같은 대상을 반복하지 않을 수 있습니다.
- 비동기, 실패 가능성이나 구현 방식은 Swift 시그니처와 계약으로 충분히 표현되는 경우 이름에 중복하지 않습니다.

### 3.4 모델과 DTO

- Domain 모델은 비즈니스 의미와 상태를 표현하며 서버 schema, 플랫폼 타입이나 저장 기술을 이름에 노출하지 않습니다.
- Data 모델은 데이터 처리 책임과 수명을 표현합니다. 저장 모델은 저장 이후에도 무엇을 보존하는지 식별할 수 있어야 합니다.
- 외부 요청·응답 형식을 표현하는 DTO는 경계 역할이 실제로 DTO일 때 `DTO`를 사용할 수 있습니다. Domain 모델에 표면적 통일을 위해 `DTO`를 붙이지 않습니다.
- `Request`, `Response`, `Stored`, `Cached` 같은 수식어는 방향 또는 수명이 모델의 의미를 실제로 구분할 때만 사용합니다.
- 하나의 모델 이름으로 외부 계약, 저장 모델과 Domain 모델을 동시에 표현하지 않습니다. Adapter에서 각 경계가 소유하는 모델로 변환합니다.

### 3.5 경계를 넘는 값

저장되거나 반환·전달되어 원래 선언 문맥을 잃는 값은 이름만으로 목적을 재구성할 수 있어야 합니다.

- 서로 다른 발급 주체의 식별자가 공존하면 구분에 필요한 발급 주체 또는 소유 경계를 드러냅니다.
- 현재 값과 갱신 값, 일회성 값과 장기 저장 값처럼 수명이 의미를 바꾸면 그 차이를 드러냅니다.
- `id`, `reference`, `value`, `token`, `state`처럼 단독으로는 의미가 넓은 이름은 경계를 넘을 때 무엇의 값인지 검토합니다.
- 메서드와 타입이 목적을 명확히 제공하는 짧은 지역 매개변수에서는 같은 수식어를 반복하지 않을 수 있습니다.
- 비밀 값은 이름뿐 아니라 타입, 노출 범위와 문자열 표현 정책으로도 보호합니다. 보안 책임을 이름만으로 충족했다고 판단하지 않습니다.

## 4. 패키지 문맥

이름은 [아키텍처의 패키지 책임](../architecture.md#2-패키지-책임)을 넘어서지 않아야 합니다.

| 패키지 | 이름이 사용하는 주된 문맥 | 이름에 노출하지 않는 문맥 |
| --- | --- | --- |
| App | 실행 진입점, 앱 전체 Navigation, Feature↔Composition 연결 | Domain 규칙, Data·Infrastructure 구현 기술 |
| Composition | Adapter, 조립, 구현 선택, 객체 수명 | 새로운 비즈니스 규칙, Data 처리 정책 |
| Feature | 사용자 기능, Presentation 상태·Action·화면 흐름 | DTO, 저장·네트워크 기술, production 구현체 |
| Domain | 비즈니스 모델·정책·Use Case·외부 기능 계약 | 공급자, 서버 schema, 저장·플랫폼 기술 |
| Data | 획득·저장·캐시·동기화, DTO, 필요한 기술 계약 | Domain 모델·Repository, Infrastructure 구체 타입 |
| Infrastructure | 범용 플랫폼·라이브러리 기술 능력 | Domain·Data 의미, 서비스 고유 schema |
| UI | 디자인 토큰과 범용 UI 구성요소 | 특정 Feature 상태·업무 흐름·데이터 접근 |

패키지 이름을 접두어처럼 붙여 경계를 표시하지 않습니다. 대신 선언 자체가 소유하는 책임을 표현합니다. 패키지 밖에서 충돌하거나 오해할 실제 근거가 있을 때만 구분 문맥을 추가합니다.

### Target과 소스 폴더

Tuist target 이름은 빌드 그래프에서 소속 패키지를 식별해야 하므로 필요한 패키지 문맥을
포함할 수 있습니다. 반면 `sources/Projects/<패키지>/` 아래의 source·test 폴더는 이미
패키지 문맥 안에 있으므로 target 이름의 패키지 접두어를 반복하지 않고 역할만 사용합니다.
예를 들어 `InfrastructureAuthentication`과 `InfrastructureAuthenticationTests` target의
source·test 폴더는 각각 `Authentication/`, `Tests/Authentication/`으로 둡니다.

이 이름 관계를 실제 폴더 경로와 Tuist 매니페스트에 적용하는 절차는
[디렉터리·파일 컨벤션 §3](./directory-file.md#3-소스-루트)과
[§7](./directory-file.md#7-tuist-매니페스트와의-일치)이 소유합니다.

## 5. 접두어와 접미어

접두어·접미어는 다음 질문에 모두 답할 수 있을 때 사용합니다.

1. 어떤 책임, 방향, 수명 또는 경계를 구분하는가?
2. 제거하면 어떤 실제 충돌이나 오해가 생기는가?
3. 선언의 모든 연산과 상태가 그 수식어의 의미를 충족하는가?

허용할 수 있는 예는 실제 wire 경계를 표현하는 `RequestDTO`·`ResponseDTO`, 저장 수명을 구분하는 `Stored...`, 책임을 충족하는 `...Repository`·`...Storage`입니다. 다만 같은 접미어라도 역할이 맞지 않으면 사용할 수 없습니다.

다음 목적의 일괄 적용은 허용하지 않습니다.

- 같은 feature 또는 target 소속임을 표시하기 위한 공통 접두어
- 이름 길이와 모양을 맞추기 위한 공통 접미어
- 현재 책임이 아닌 향후 가능성을 나타내기 위한 `Manager`, `Service`, `Handler`
- 패키지 이름을 반복하는 `Domain...`, `Data...`, `Infrastructure...` 접두어

## 6. 축약과 약어

- 축약형이 원래 용어보다 책임과 범위를 불명확하게 만들면 사용하지 않습니다.
- 동일 경계의 독자가 일반적으로 원형을 복원할 수 있고 오해 가능성이 낮은 표준 약어만 사용합니다.
- Apple 플랫폼과 Swift 생태계가 고정한 `URL`, `HTTP`, `ID` 같은 표기는 해당 의미를 그대로 사용할 때 유지할 수 있습니다.
- 표준 약어는 단어별로 첫 글자만 대문자로 쓰는 `Url`, `Id`, `Http` 형태를 사용하지 않습니다. 카멜케이스 규칙이 허용하는 위치라면 약어를 구성하는 글자를 전부 대문자로 유지해 `HTTP`, `URL`, `ID` 형태로 씁니다. 카멜케이스 규칙상 식별자의 첫 단어가 소문자로 시작해야 하고 그 첫 단어가 약어인 경우에만 해당 약어 전체를 소문자로 낮춰 `http`, `url`, `id` 형태로 씁니다. 여러 약어가 연달아 붙어 하나의 단어처럼 결합될 때도 각 약어 내부의 대소문자를 이 규칙대로 통일하며, 약어 하나마다 첫 글자만 대문자로 바꾸는 절충 표기는 사용하지 않습니다.
  - 첫 단어가 아닌 위치: `fetchHTTPURLID(...)`, `RegisterProjectRequestDTO.repositoryURL`
  - 식별자의 첫 단어인 위치: `urlString`, `idToken`, `httpMethod`
- `DTO`는 Data의 외부 전송 모델 역할을 구분할 때 사용할 수 있지만, 모든 모델에 붙이는 공통 접미어가 아닙니다.
- 기능 이름을 임의로 줄인 접두어는 같은 글자가 다른 개념을 뜻하거나 검색 가능성을 낮출 수 있으므로 사용 근거가 없다면 전체 용어를 사용합니다.

한 파일이나 target 안에서만 통하는 축약은 공개 API의 근거가 되지 않습니다. 새 약어가 필요하면 사용처, 원형, 충돌 가능성과 경계 밖 가독성을 리뷰에서 설명할 수 있어야 합니다.

## 7. 외부 고정 명칭과 공급자 중립 경계

외부 API, 서버 schema, 표준과 플랫폼이 고정한 고유 명칭은 원문 의미와 표기를 보존합니다.

- 외부 타입·프로토콜·필드·상태를 직접 표현하는 Adapter 또는 DTO에서는 계약명을 임의로 다른 개념으로 바꾸지 않습니다.
- Swift 표기 규칙에 맞춘 프로퍼티를 사용하더라도 serialization key와 변환을 명시해 외부 원문 필드와의 대응을 보존합니다.
- 플랫폼의 고유 타입명과 표준 약어를 프로젝트의 일반 네이밍 규칙으로 다시 쓰지 않습니다.
- 외부 계약 변경을 프로젝트 내부 rename으로 위장하지 않습니다. 계약·mapping·호환성 변경으로 별도 검증합니다.

프로젝트가 소유하는 공급자 중립 경계에는 특정 공급자, 저장 기술 또는 실행 환경의 용어를 노출하지 않습니다. 예를 들어 Domain의 인증 상태가 플랫폼 타입이나 특정 공급자의 credential 상태를 그대로 반환하면 안 됩니다. Data가 요구하는 저장 계약도 실제 책임이 값의 저장·조회·삭제라면 `Keychain` 같은 구현 기술을 계약 이름에 포함하지 않습니다. 특정 공급자나 기술 용어는 그 대상을 직접 감싸는 Infrastructure API 또는 외부 Adapter처럼 책임상 필요한 경계에만 둡니다.

공급자 중립은 가장 일반적인 단어로 이름을 흐리는 것과 다릅니다. 여러 공급자의 차이를 내부 계약에서 보존해야 한다면 프로젝트 소유의 중립적인 모델과 명시적인 변환으로 의미를 표현합니다.

## 8. rename과 설계·동작 변경 분리

rename은 기존 책임과 동작을 유지한 채 식별자와 그 참조를 바꾸는 변경입니다. 다음 중 하나라도 함께 바뀌면 순수 rename으로 보지 않습니다.

- 프로토콜의 연산 집합 또는 타입의 상태
- 저장 위치, 값의 수명과 소유자
- 비동기·오류·취소 동작
- 패키지 책임 또는 의존 방향
- 외부 API·schema와의 mapping 또는 호환성

순수 rename은 선언, 모든 참조, 테스트 이름과 관련 문서를 같은 범위에서 일관되게 갱신하고 기존 동작을 검증합니다. 설계·동작 변경도 필요하면 네이밍 변경과 별도의 명세·계획·작업으로 나누고 각각의 변경 이유, 영향과 검증 범위를 구분합니다. 이름을 먼저 바꿀지 설계를 먼저 바꿀지는 의존 관계에 따라 결정하되, 한 변경에서 두 결과를 구분할 수 없게 섞지 않습니다.

대규모 공개 API rename은 이름이 더 짧거나 통일돼 보인다는 이유만으로 수행하지 않습니다. 호출부, Adapter, 테스트, 문서, 외부 호환성과 진행 중인 명세에 미치는 영향을 먼저 확인하고 책임 불일치가 근거로 확인된 범위만 변경합니다.

## 9. 허용·비허용 예

아래 이름은 판단 기준을 보여 주는 예시이며 프로젝트 전체에 그대로 사용해야 하는 식별자 목록이 아닙니다.

| 상황 | 허용 예 | 비허용 예 | 이유 |
| --- | --- | --- | --- |
| 서로 다른 종류의 세션이 공존 | `LoginSessionRepository` | `SessionRepository` | `Login`이 실제 책임을 구분하는 최소 문맥입니다. |
| 로컬 인증 정보의 저장·조회·삭제 | 책임을 그대로 표현하는 `AuthenticationStorage` | 실제로 다루지 않는 상태를 붙인 `AuthenticationAuthorizationStorage` | 저장 값의 내부 용어를 계약 책임으로 오인시키지 않습니다. |
| 실제 authorization 상태 조회 | `authorizationStatus()` | `status()` | 상태 종류를 구분해야 하는 공개 계약에서는 목적어가 필요합니다. |
| 타입이 대상을 이미 제공하는 지역 인자 | `SessionStorage.save(_ session:)` | `SessionStorage.save(_ storedLoginSession:)` | 타입과 연산이 제공하는 문맥을 지역 이름에 반복하지 않습니다. |
| 저장 후 독립적으로 해석되는 식별자 | 발급 주체가 실제로 구분되는 `issuerIdentifier` | 여러 발급 주체가 공존하는 모델의 `id` | 저장 문맥이 사라져도 값의 목적을 식별할 수 있어야 합니다. |
| Data의 wire 응답 모델 | `ProfileResponseDTO` | Domain의 `ProfileDTO` | `DTO`는 실제 전송 경계에서만 역할을 설명합니다. |
| 공급자 중립 Domain 상태 | 프로젝트 소유 `AuthorizationStatus` | 플랫폼 고유 credential 상태 타입 | 외부 공급자 타입을 Domain 계약에 노출하지 않습니다. |
| Data가 요구하는 보안 저장 능력 | 책임 중심의 `CredentialStorage` | 구현 기술 중심의 `KeychainCredentialStorage` 프로토콜 | 구현 기술은 중립 계약이 아니라 Infrastructure 구현 경계에서 선택합니다. |
| 플랫폼 API를 직접 감싸는 Infrastructure 타입 | 플랫폼 고유 명칭을 보존한 Adapter 이름 | 고유 명칭을 임의의 프로젝트 용어로 치환 | 외부 계약과의 대응을 숨기지 않습니다. |
| 한 기능의 공개 타입 묶음 | 각 책임을 완전한 용어로 표현 | 모든 타입에 `Auth...` 같은 축약 접두어 적용 | 소속 표시만을 위한 일괄 축약은 책임을 설명하지 않습니다. |
| 표준 약어가 식별자 첫 단어가 아닌 위치 | `repositoryURL`, `projectID` | `repositoryUrl`, `projectId` | 카멜케이스가 대문자 표기를 허용하는 위치에서는 약어 전체를 대문자로 유지합니다. |
| 표준 약어가 식별자 첫 단어인 위치 | `urlString`, `idToken` | `URLString`, `IDToken` | 첫 단어는 소문자로 시작해야 하므로 약어 전체를 소문자로 낮춥니다. |

## 10. 검토 체크리스트

### 책임과 문맥

- [ ] 선언의 책임을 한 문장으로 설명할 수 있는가?
- [ ] 이름의 각 단어가 실제 책임, 경계 또는 수명을 설명하는가?
- [ ] 공개 이름을 패키지·파일 문맥 없이 읽어도 다른 개념과 구분되는가?
- [ ] 타입이나 메서드가 이미 제공하는 문맥을 불필요하게 반복하지 않는가?

### 역할별 이름

- [ ] 타입·프로토콜·연산·모델 이름이 각각 실제 역할과 효과를 표현하는가?
- [ ] 저장·캐시·전송·외부 응답처럼 방향과 수명을 나타내는 수식어가 실제로 필요한가?
- [ ] 경계를 넘는 `id`, `reference`, `value`, `token`, `state`의 대상과 소유자가 명확한가?
- [ ] 포괄적인 `Manager`, `Service`, `Provider`, `Handler`가 여러 책임을 숨기지 않는가?

### 접두어·접미어·축약

- [ ] 공통 접두어·접미어가 소속이나 표면적 통일이 아니라 실제 구분을 제공하는가?
- [ ] 약어를 경계 밖의 독자도 오해 없이 원형으로 복원할 수 있는가?
- [ ] 표준 약어가 `Url`, `Id`, `Http`처럼 단어별 첫 글자만 대문자인 절충 표기 없이, 위치에 따라 전부 대문자이거나 전부 소문자인가?
- [ ] 특정 기능에서 채택한 이름을 다른 기능에 자동 적용하지 않았는가?

### 외부 계약과 변경 범위

- [ ] 외부 API·schema·플랫폼의 고정 명칭과 mapping을 보존하는가?
- [ ] 공급자 중립 경계에 공급자·저장 기술·실행 환경 용어가 새지 않는가?
- [ ] rename이 동작, 상태 수명, 책임, 의존 방향 또는 외부 계약 변경과 분리돼 있는가?
- [ ] 공개 API 영향, 호출부, Adapter, 테스트와 문서의 갱신 범위를 확인했는가?
- [ ] 예외가 있다면 Constitution 원칙 3에 따라 이유, 영향과 미검증 범위를 기록했는가?
