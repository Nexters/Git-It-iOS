# 기능 명세: 레포지토리 생성 상태관리 Repository

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/repository-creation-state`

**브랜치 상태**: `생성`

**생성일**: 2026-09-06

**상태**: 초안

**입력**: 사용자 설명: "레포지토리 생성 상태관리 Repository 추가: 사용자가 레포지토리(GitHub repo) 등록을 요청하면 해당 요청이 처리 중(생성 중) 상태임을 추적하는 새로운 Domain Repository를 도입한다. FetchLearningProjects(목록 조회) UseCase는 조회 시 현재 생성 중인 레포지토리를 결과 목록에서 필터링해 제외한다. CreateLearningProject(생성) UseCase는 이미 동일 레포지토리에 대한 생성 요청이 진행 중이면 중복 생성 요청을 방지(에러 반환 또는 거부)한다. 기존 LearningProjectRepository(register/fetchProjects), BookmarkRepository 패턴과 Domain/Data/Composition 계층 분리 컨벤션을 따른다."

## 명확화

### 세션 2026-09-06

- 질문: 생성 완료/실패 신호 유실에 대한 안전장치가 필요한가? → 답변: 필요하다. 일정 시간 경과 시 "생성 중" 상태를 자동으로 해제하는 타임아웃을 도입한다. 정상적인 생성 완료 신호(FCM 수신과 300~500초 사이의 무작위 지연이 모두 끝난 시점)보다 충분히 긴 15분(900초)을 타임아웃으로 사용해, 정상 흐름에서는 타임아웃이 발동하지 않으면서도 신호 유실 시 상태가 영구히 남지 않도록 한다.
- 질문: 이미 생성이 완료된(진행 중이 아닌) 동일 레포지토리로 재등록을 시도하는 경우도 이 기능의 범위에 포함하는가? → 답변: 범위 밖이다. 이 기능은 "생성 중" 상태의 중복 요청 방지에만 집중하며, 완료된 레포지토리의 재등록 차단 여부는 기존 서버(`register` API) 정책에 위임한다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 동일 레포지토리 중복 생성 요청 차단 (우선순위: P1)

사용자가 이미 생성(퀴즈 생성)이 진행 중인 GitHub 레포지토리에 대해 다시 등록을 시도하면, 시스템은 새로운 서버 등록 요청을 보내지 않고 즉시 "이미 생성 중" 오류를 반환해 사용자가 중복 리소스를 만들지 않도록 한다.

**주요 행위자**: 최종 사용자(레포지토리 등록 화면 이용자), 개발자(CreateLearningProjectUseCase 호출부)

**우선순위 이유**: 중복 생성 요청은 동일 레포지토리에 대한 중복 프로젝트·중복 과금성 생성 작업을 유발할 수 있는 핵심 방지 대상이다.

**독립 테스트**: `CreateLearningProjectUseCase`에 동일 `githubRepoURL`로 두 번 연속 요청을 보내고, 첫 번째 요청이 아직 생성 중인 상태에서 두 번째 요청이 네트워크 호출 없이 즉시 거부되는지 확인하는 것으로 전체 가치를 검증할 수 있다.

**수용 시나리오**:

1. **전제** 어떤 레포지토리에 대한 생성 요청도 진행 중이지 않다, **실행** 사용자가 `githubRepoURL: A`로 생성을 요청한다, **결과** 시스템은 정상적으로 서버에 등록 요청을 보내고 해당 레포지토리를 "생성 중" 상태로 기록한다.
2. **전제** `githubRepoURL: A`에 대한 생성 요청이 이미 "생성 중" 상태다, **실행** 사용자가 동일한 `githubRepoURL: A`로 다시 생성을 요청한다, **결과** 시스템은 서버 등록 요청을 보내지 않고 중복 생성 오류를 반환한다.
3. **전제** `githubRepoURL: A`에 대한 생성 요청이 "생성 중" 상태다, **실행** 사용자가 다른 `githubRepoURL: B`로 생성을 요청한다, **결과** 시스템은 정상적으로 서버에 등록 요청을 보낸다.

---

### 시나리오 2 - 생성 중인 레포지토리를 프로젝트 목록에서 제외 (우선순위: P1)

사용자가 프로젝트 목록을 조회하면, 아직 생성(퀴즈 생성)이 완료되지 않은 레포지토리는 목록에 나타나지 않아 미완성 상태의 프로젝트를 혼동 없이 구분할 수 있다.

**주요 행위자**: 최종 사용자(프로젝트 목록 화면 이용자)

**우선순위 이유**: 생성 중인 프로젝트가 목록에 그대로 노출되면 사용자가 아직 사용할 수 없는 프로젝트를 정상 항목으로 오인해 탭할 수 있다.

**독립 테스트**: 하나의 레포지토리가 "생성 중" 상태로 기록된 상태에서 `FetchLearningProjectsUseCase`를 호출하고, 반환된 목록에 해당 프로젝트가 포함되지 않는지 확인하는 것으로 전체 가치를 검증할 수 있다.

**수용 시나리오**:

1. **전제** 서버가 반환하는 프로젝트 목록에 프로젝트 X가 포함되어 있고 X는 현재 "생성 중" 상태로 기록되어 있다, **실행** 사용자가 프로젝트 목록을 조회한다, **결과** 반환된 목록에서 프로젝트 X는 제외된다.
2. **전제** 어떤 프로젝트도 "생성 중" 상태로 기록되어 있지 않다, **실행** 사용자가 프로젝트 목록을 조회한다, **결과** 서버가 반환한 목록이 그대로 반환된다.

---

### 시나리오 3 - 생성 완료 또는 실패 시 상태 해제 (우선순위: P2)

레포지토리 생성(퀴즈 생성)이 성공적으로 끝나거나 실패로 종료되면, 해당 레포지토리의 "생성 중" 상태가 해제되어 이후 목록 조회에 다시 나타나거나 동일 레포지토리로 재생성을 요청할 수 있다.

**주요 행위자**: 최종 사용자, 개발자(생성 진행 상황을 관찰하는 기존 흐름)

**우선순위 이유**: 상태가 해제되지 않으면 생성이 끝난 후에도 목록에서 영구히 숨겨지거나 재시도가 영구히 차단되는 회귀를 유발한다.

**독립 테스트**: "생성 중"으로 기록된 프로젝트에 대해 생성 완료(성공) 또는 생성 실패 결과를 전달한 뒤, 목록 조회에 해당 프로젝트가 다시 나타나거나(성공 시 서버 목록 기준) 동일 레포지토리로 재생성 요청이 허용되는지(실패 시) 확인하는 것으로 검증할 수 있다.

**수용 시나리오**:

1. **전제** 프로젝트 Y가 "생성 중" 상태이고 생성이 성공적으로 완료된다, **실행** 생성 완료 결과가 시스템에 전달된다, **결과** 프로젝트 Y의 "생성 중" 상태가 해제되고, 이후 서버 목록에 Y가 포함되어 있다면 조회 결과에 정상적으로 나타난다.
2. **전제** 프로젝트 Y가 "생성 중" 상태이고 생성이 실패로 종료된다, **실행** 생성 실패 결과가 시스템에 전달된다, **결과** 프로젝트 Y의 "생성 중" 상태가 해제되고, 동일 `githubRepoURL`로 재생성을 요청할 수 있다.

---

### 예외·경계 사례

- 앱이 종료되었다가 다시 실행되었을 때, 이전 세션에서 "생성 중"이던 레포지토리의 상태는 유지되지 않는다(가정 참고). 재실행 후에는 서버의 실제 상태(예: 진행 중 생성 재조회)에 따라 사용자가 다시 판단한다.
- 동일 `githubRepoURL`이라도 대소문자, 앞뒤 공백, 끝 슬래시(trailing slash) 차이가 있으면 시스템은 이를 정규화해 동일 레포지토리로 판별해야 한다.
- 생성 요청이 서버 오류로 즉시 실패한 경우(등록 API 자체가 에러를 반환), 시스템은 해당 레포지토리를 "생성 중" 상태로 남기지 않고 즉시 해제해 재시도를 허용해야 한다.
- 생성 완료/실패 신호가 유실된 경우, 레포지토리가 "생성 중" 상태로 기록된 지 15분(900초)이 지나면 시스템은 해당 상태를 자동으로 해제해 목록 노출과 재생성 요청을 다시 허용해야 한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 특정 GitHub 레포지토리(`githubRepoURL` 기준, 정규화 후 비교)에 대한 생성 요청이 현재 "생성 중"인지 조회할 수 있어야 한다.
- **FR-002**: 시스템은 레포지토리 생성 요청을 시작할 때 해당 레포지토리를 "생성 중" 상태로 기록해야 한다.
- **FR-003**: `CreateLearningProject` UseCase는 이미 "생성 중" 상태인 `githubRepoURL`로 생성 요청이 들어오면 서버에 등록 요청을 보내지 않고 중복 생성 오류를 반환해야 한다.
- **FR-004**: `CreateLearningProject` UseCase는 서버 등록 요청이 실패하면 해당 레포지토리의 "생성 중" 상태를 즉시 해제해 재시도를 허용해야 한다.
- **FR-005**: 시스템은 레포지토리 생성(퀴즈 생성)이 성공 또는 실패로 종료되었다는 기존 완료 신호를 받으면 해당 레포지토리의 "생성 중" 상태를 해제해야 한다.
- **FR-005a**: 시스템은 완료/실패 신호 유실에 대비해, 레포지토리가 "생성 중" 상태로 기록된 시점부터 15분(900초)이 지나면 완료 신호 수신 여부와 무관하게 해당 상태를 자동으로 해제해야 한다. (근거: 정상 완료는 FCM 수신과 300~500초 무작위 지연이 모두 끝난 뒤 이뤄지므로, 15분은 정상 흐름보다 충분히 긴 안전 여유다.)
- **FR-006**: `FetchLearningProjects` UseCase는 서버로부터 받은 프로젝트 목록에서, 현재 "생성 중" 상태로 기록된 레포지토리에 대응하는 항목을 결과 목록에서 제외해야 한다.
- **FR-007**: "생성 중" 상태 저장소는 Domain 계층에 계약(Protocol)을 두고, 실제 구현(Adapter)은 Composition 계층에 위치해 기존 `LearningProjectRepository`/`BookmarkRepository`와 동일한 계층 분리를 따라야 한다.
- **FR-008**: "생성 중" 상태는 앱 프로세스가 살아있는 동안(메모리 내)에만 유지되며, 별도의 영속 저장소(디스크·서버)에 기록하지 않는다.

### 핵심 엔터티 *(기능에 데이터가 포함되면 작성)*

- **RepositoryCreationState(레포지토리 생성 상태)**: 생성 요청이 진행 중인 GitHub 레포지토리를 나타낸다. 정규화된 `githubRepoURL`을 식별자로 가지며, 서버 등록 응답으로 받은 `projectID`가 알려지면 함께 보관해 이후 생성 완료/실패 신호(프로젝트 ID 기준)와 매칭한다. 상태가 기록된 시각을 함께 보관해 15분(900초) 타임아웃 판정에 사용한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 동일 `githubRepoURL`에 대해 생성 요청이 진행 중인 동안 재요청 시, 100%의 경우 서버 등록 API 호출 없이 즉시 중복 오류가 반환된다.
- **SC-002**: "생성 중" 상태로 기록된 레포지토리는 100%의 경우 프로젝트 목록 조회 결과에서 제외된다.
- **SC-003**: 생성 완료 또는 실패 신호가 전달된 후에는, 100%의 경우 해당 레포지토리가 더 이상 "생성 중" 상태로 남지 않아 재생성 요청과 목록 노출이 정상적으로 재개된다. 신호가 전달되지 않더라도 기록 시점으로부터 15분(900초) 이내에 동일하게 상태가 해제된다.
- **SC-004**: 기존 `LearningProjectRepository`·`BookmarkRepository`의 공개 계약과 동작은 이 기능 추가 전후로 100% 동일하게 유지된다(회귀 없음).

## 가정

- "생성 중" 상태는 앱 세션(프로세스 생존 기간) 동안만 유지되면 충분하며, 앱 재시작 후에는 서버 데이터를 기준으로 사용자가 다시 판단한다. 여러 기기 간 동기화는 이 기능의 범위에 포함하지 않는다.
- 레포지토리 동일성 판별은 `githubRepoURL` 문자열의 정규화(트림, 소문자 변환, 끝 슬래시 제거) 비교로 충분하며, 별도의 GitHub API 조회(owner/repo 정규화 등)는 필요하지 않다.
- "생성 완료/실패" 신호는 기존에 존재하는 생성 결과 관찰 체계(퀴즈 생성 진행 상황을 프로젝트 ID 기준으로 알려주는 기존 도메인 개념)를 그대로 재사용할 수 있으며, 새로운 서버 API나 폴링 메커니즘을 추가로 도입할 필요는 없다.
- `FetchLearningProjects` 조회 시 필터링은 클라이언트 측에서만 수행되는 추가 필터이며, 서버가 이미 생성 중 항목을 목록에서 제외해 반환하는 경우와도 안전하게 공존한다(중복 필터링이 있어도 결과가 달라지지 않음).
- 이미 생성이 완료된 레포지토리와 동일한 `githubRepoURL`로 다시 등록을 요청하는 경우의 차단 여부는 이 기능의 범위 밖이며, 기존 서버(`register` API) 정책을 그대로 따른다.
- `FetchLearningProjects` 조회 시 "생성 중" 항목을 제외하는 필터링은 클라이언트 측에서만 적용되며, 서버가 응답하는 페이지네이션 총 개수(`hasNext` 등)를 필터링 결과에 맞춰 보정하지 않는다. 페이지당 표시 항목 수가 줄어드는 것은 이 기능이 허용하는 정상 동작이다.
