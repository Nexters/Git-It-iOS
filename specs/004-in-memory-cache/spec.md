# 기능 명세: InMemoryCache

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/in-memory-cache`

**생성일**: 2026-08-15

**상태**: 초안

**입력**: 사용자 설명: "infrastructure 패키지에 대한 구현이 목표입니다. 기능은 최대한 심플하게 구현하세요. InMemoryCache 구현"

## 사용자 시나리오와 테스트 *(필수)*

이 기능의 사용자는 Infrastructure 패키지의 범용 기술 API를 소비해 Composition의 Data↔Infrastructure Adapter를 구현하는 개발자입니다. 최종 앱 사용자는 이 기술 API를 직접 인지하지 않으며, 이 기능이 다른 기능(예: 데이터 캐시가 필요한 기능)의 응답 속도와 안정성을 뒷받침하는 방식으로 간접적인 혜택을 받습니다.

### 사용자 스토리 1 - 값을 저장하고 같은 키로 즉시 조회한다 (우선순위: P1)

개발자가 임의의 키에 값을 저장한 뒤, 같은 키로 다시 조회하면 방금 저장한 값을 그대로 돌려받습니다. 저장과 조회는 네트워크나 디스크 접근 없이 메모리 안에서만 이루어집니다.

**우선순위 이유**: 저장과 조회는 캐시가 성립하기 위한 최소 동작입니다. 이 스토리 없이는 캐시로서의 가치가 전혀 없습니다.

**독립 테스트**: 키-값 쌍을 저장한 직후 같은 키로 조회해 저장한 값과 완전히 일치하는지 확인하는 것으로 독립적으로 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** 캐시가 비어 있을 때, **실행** 개발자가 키 A에 값 V를 저장하면, **결과** 같은 키 A로 조회했을 때 값 V가 반환된다.
2. **전제** 키 A에 이미 값 V1이 저장되어 있을 때, **실행** 개발자가 같은 키 A에 값 V2를 다시 저장하면, **결과** 이후 키 A를 조회하면 V1이 아닌 V2가 반환된다.

---

### 사용자 스토리 2 - 저장한 값을 제거하거나 전체를 비운다 (우선순위: P2)

개발자가 더 이상 필요 없는 키의 값을 개별적으로 제거하거나, 캐시 전체를 한 번에 비웁니다. 제거 이후에는 해당 키를 조회해도 값이 나오지 않습니다.

**우선순위 이유**: 캐시가 오래되거나 무효화된 값을 계속 반환하면 이를 사용하는 다른 기능이 잘못된 데이터를 사용하게 됩니다. 값을 걷어낼 수 있어야 캐시를 실제 기능에 안전하게 연결할 수 있습니다.

**독립 테스트**: 값을 저장한 뒤 제거하거나 전체 비우기를 실행하고, 같은 키를 조회했을 때 값이 없음으로 확인되는 것으로 독립적으로 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** 키 A에 값이 저장되어 있을 때, **실행** 개발자가 키 A를 제거하면, **결과** 이후 키 A를 조회하면 값이 없음으로 확인된다.
2. **전제** 여러 키에 값이 저장되어 있을 때, **실행** 개발자가 캐시 전체를 비우면, **결과** 어떤 키를 조회해도 값이 없음으로 확인된다.
3. **전제** 캐시가 비어 있을 때, **실행** 개발자가 존재하지 않는 키를 제거하면, **결과** 오류 없이 아무 값도 제거되지 않은 상태로 완료된다.

---

### 사용자 스토리 3 - 여러 곳에서 동시에 접근해도 값이 깨지지 않는다 (우선순위: P3)

애플리케이션의 여러 실행 흐름이 동시에 같은 캐시에 값을 저장·조회·제거하더라도, 캐시는 손상되거나 값을 잃어버리지 않고 각 요청을 순서대로 처리한 것과 같은 결과를 보장합니다.

**우선순위 이유**: 실제 애플리케이션은 여러 비동기 작업이 동시에 실행되므로, 동시 접근에 안전하지 않은 캐시는 프로덕션에서 예측할 수 없는 오류를 일으킵니다. 다만 이 안전성은 앞의 두 스토리가 이미 동작한 뒤에야 의미가 있습니다.

**독립 테스트**: 같은 캐시 인스턴스에 여러 저장·조회·제거 요청을 동시에 실행한 뒤, 최종 상태가 각 요청을 어떤 순서로든 하나씩 처리했을 때 나올 수 있는 상태와 일치하는지 확인해 독립적으로 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** 캐시가 비어 있을 때, **실행** 서로 다른 키에 대한 저장 요청이 동시에 여러 건 발생하면, **결과** 모든 키가 각자의 값으로 정확히 저장되고 값이 섞이거나 유실되지 않는다.
2. **전제** 같은 키에 대한 저장 요청이 동시에 여러 건 발생할 때, **실행** 모든 요청이 완료되면, **결과** 그 키에는 요청들 중 하나의 값이 손상 없이 남아 있다.

---

### 예외·경계 사례

- 존재하지 않는 키를 조회하면 어떤 결과가 발생하는가? 오류 없이 값이 없음을 알려야 한다.
- 애플리케이션 프로세스가 종료되거나 재시작되면 캐시에 저장된 값은 어떻게 되는가? 메모리 전용이므로 모두 사라지며, 이는 의도된 동작이다.
- 같은 이름의 캐시가 여러 목적(예: 서로 다른 기능)으로 동시에 필요할 때, 한 캐시의 키가 다른 목적의 캐시와 충돌하지 않아야 한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: Infrastructure는 키와 값을 메모리에 저장하는 범용 기술 API를 제공해야 한다(`MUST`).
- **FR-002**: 저장된 값은 저장에 사용한 것과 같은 키로 조회할 수 있어야 한다(`MUST`).
- **FR-003**: 존재하지 않는 키를 조회하면 오류를 발생시키지 않고 값이 없음을 알려야 한다(`MUST`). 잘못된 조회가 예외나 크래시로 이어져서는 안 된다(`MUST NOT`).
- **FR-004**: 이미 값이 있는 키에 새 값을 저장하면 기존 값을 새 값으로 교체해야 한다(`MUST`).
- **FR-005**: 특정 키 하나의 값만 선택해 제거할 수 있어야 한다(`MUST`).
- **FR-006**: 저장된 모든 값을 한 번의 호출로 비울 수 있어야 한다(`MUST`).
- **FR-007**: 존재하지 않는 키를 제거하려는 시도는 오류 없이 완료되어야 한다(`MUST`).
- **FR-008**: 여러 저장·조회·제거 요청이 동시에 발생해도 저장된 값이 손상되거나 유실되지 않아야 한다(`MUST`).
- **FR-009**: 캐시는 메모리 범위에서만 값을 유지해야 하며, 디스크나 그 밖의 영속 저장소에 값을 기록해서는 안 된다(`MUST NOT`).
- **FR-010**: 캐시가 저장하는 값의 형태는 특정 Data 모델이나 DTO에 종속되지 않아야 한다(`MUST NOT`). Infrastructure는 Data가 소유한 모델을 소유하거나 정의해서는 안 된다(`MUST NOT`).
- **FR-011**: 캐시는 프로젝트 내부의 다른 패키지(Domain, Data 등)에 의존하지 않아야 한다(`MUST NOT`).
- **FR-012**: 캐시는 동일한 프로세스 안에서 서로 독립된 여러 개의 캐시 인스턴스를 만들 수 있어야 한다(`MUST`). 하나의 전역 인스턴스만 존재하도록 강제해서는 안 된다(`MUST NOT`).

### 핵심 엔터티

- **캐시 항목**: 하나의 키와 그 키에 대응하는 값의 쌍. 값은 캐시를 사용하는 쪽이 정하는 임의의 형태를 가질 수 있다.
- **캐시 저장소**: 캐시 항목들의 모음이며, 저장·조회·제거·전체 비우기 동작의 대상이 되는 단위. 프로세스 메모리 범위에서만 존재한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 값을 저장한 직후 같은 키로 조회하면 100%의 경우 방금 저장한 값과 완전히 일치하는 값이 반환된다.
- **SC-002**: 저장된 적 없는 키를 조회했을 때 오류나 예외 없이 값이 없음으로 식별되는 비율이 100%이다.
- **SC-003**: 값을 제거하거나 전체를 비운 직후 해당 키를 조회하면 100%의 경우 값이 없음으로 확인된다.
- **SC-004**: 서로 다른 키에 대한 동시 저장 요청 100건을 동시에 실행했을 때, 값이 섞이거나 유실되는 사례가 0건이다.
- **SC-005**: 이 기능의 동작 검증을 화면 실행, 네트워크 접근, 디스크 접근 없이 100% 수행할 수 있다.

## 가정

- PR #9(`feature/http-client`, Core → Infrastructure 명칭 변경 및 Infrastructure 패키지 구성)가 `develop`에 병합되어 Infrastructure 패키지가 이미 존재한다. 이 기능은 그 위에서 진행한다.
- "최대한 심플하게 구현"이라는 요청을 반영해, 만료(TTL), 용량 제한, 축출(eviction) 정책은 이번 범위에 포함하지 않는다고 가정한다. 저장된 값은 명시적으로 제거하거나 전체를 비우거나 프로세스가 종료될 때까지 유지된다.
- 캐시 키와 값의 구체적인 타입은 캐시를 사용하는 쪽(Composition의 Data↔Infrastructure Adapter)이 결정하며, Infrastructure는 특정 타입에 얽매이지 않는 범용 저장 메커니즘만 제공한다고 가정한다.
- 캐시는 이 프로세스(앱 실행 인스턴스) 안에서만 유효하며, 여러 기기·여러 프로세스 간 캐시 공유는 요구되지 않는다고 가정한다.

## 범위 밖

- 만료(TTL), 최대 용량, LRU 등 축출 정책.
- 디스크, UserDefaults, 데이터베이스 등 영속 저장소와의 연동.
- Data가 정의한 캐시 관련 계약의 구현이나 Composition의 Data↔Infrastructure Adapter 작성.
- 여러 프로세스·여러 기기 간 캐시 공유 또는 동기화.
- 캐시 적중률 등 모니터링·로깅·지표 수집.
