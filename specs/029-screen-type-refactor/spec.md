# 기능 명세: Screen 화면 골격 프레임워크

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/screen-type-refactor`

**브랜치 상태**: `재사용`

**생성일**: 2026-09-08

**상태**: 초안

**입력**: 사용자 설명: "UI Screen 을 프레임워크로 정의해 사용하고자 합니다. Screen 은 Header / Body / Footer 로 이뤄지며, Sticky, Overlay 등 의 스타일을 갖도록합니다"

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - Header·Body·Footer 슬롯과 배치 스타일로 화면 골격을 조립한다 (우선순위: P1)

Feature 개발자가 화면 루트를 하나의 Screen 골격으로 선언하고, Header·Body·Footer 슬롯에
화면 콘텐츠를 담은 뒤 Header와 Footer 각각에 Sticky 또는 Overlay 배치 스타일을 지정한다.
현재 화면 루트는 스크롤하지 않는 `ScreenContainer`, 본문이 헤더·푸터 뒤로 스크롤하는
`OverlayContainer`, 그리고 어느 컨테이너도 쓰지 않고 `VStack`으로 직접 조립한 화면 세
가지로 나뉜다. 개발자는 "어느 컨테이너를 고를지"가 아니라 "각 영역을 어떻게 배치할지"만
결정하면 되어야 한다.

**주요 행위자**: Feature 개발자(화면 작성자)

**우선순위 이유**: 골격이 하나로 통일되지 않으면 화면마다 배경·안전 영역·헤더 여백을
다시 구현하게 되고, 이 기능의 목적인 "프레임워크로 정의한 Screen"이 성립하지 않는다.

**독립 테스트**: UI 패키지 안에서 Header·Body·Footer 슬롯의 생성, 생략, 스타일 조합
(Sticky·Overlay × 헤더·푸터 유무 × 스크롤·고정 본문)을 계약 테스트와 프리뷰로 검증할 수
있으며, Feature 화면을 이전하지 않아도 새 화면 작성에 바로 쓸 수 있다.

**수용 시나리오**:

1. **전제** 개발자가 스크롤 목록과 하단 액션이 있는 새 화면을 만든다, **실행** Screen 골격의
   Header에 컨트롤 바와 제목, Body에 목록, Footer에 하단 액션을 담고 Header와 Footer를 모두
   Overlay로 지정한다, **결과** 본문이 헤더·푸터 뒤로 스크롤되고, 스크롤 맨 위와 맨 아래에서
   본문의 첫 콘텐츠와 마지막 콘텐츠가 헤더·푸터에 가려지지 않는다.
2. **전제** 위와 같은 화면, **실행** Header를 Sticky로 지정한다, **결과** 헤더가 상단에 고정된
   채 본문은 헤더 아래 영역에서만 스크롤되며, 어떤 스크롤 위치에서도 헤더가 본문을 덮지
   않는다.
3. **전제** 세로 중앙 정렬처럼 스크롤이 필요 없는 화면, **실행** Body를 고정(비스크롤) 본문으로
   지정한다, **결과** 본문이 헤더와 푸터 사이의 남은 전체 영역을 차지하고 `Spacer` 기반
   정렬이 접히지 않고 동작한다.
4. **전제** Header 또는 Footer가 필요 없는 화면, **실행** 해당 슬롯을 생략한다, **결과** 생략한
   영역을 위한 여백, 가림 방지 보정, 스크림이 나타나지 않는다.
5. **전제** Feature 화면이 Header에 `ScreenControlBar`와 `ScreenHeaderTitle`을 조합한다,
   **실행** 슬롯에 콘텐츠만 전달한다, **결과** 화면 좌우 여백과 영역의 상하 여백은 골격이
   적용하며, 화면은 헤더 행 높이나 헤더 하단 여백 같은 값을 자체 상수로 정의하지 않는다.

### 시나리오 2 - 기존 화면을 Screen 골격으로 이전해도 사용자 화면이 유지된다 (우선순위: P1)

모든 기존 Feature 화면을 Screen 골격으로 이전하되, 최종 사용자가 보는 레이아웃·색·스크림·
스크롤 범위·키보드 동작은 이전 전과 동일하게 유지된다.

**주요 행위자**: 최종 사용자, Feature 개발자

**우선순위 이유**: 이전이 시각 회귀를 만들면 골격 통일의 이득보다 손실이 크고, 회귀 여부를
화면별로 확인할 수 없으면 이전을 병합할 수 없다.

**독립 테스트**: 화면별로 이전 전후 프리뷰 또는 Simulator 화면을 비교하고, 전체 공유 scheme
빌드와 테스트 통과로 검증한다. 화면 단위로 이전과 검증을 나눌 수 있다.

**수용 시나리오**:

1. **전제** `OverlayContainer`를 쓰는 화면(예: 문제 풀이 화면), **실행** Screen 골격의 Overlay
   스타일 헤더·푸터로 이전한다, **결과** 헤더 스크림, 푸터 위치, 본문 스크롤 범위와 가림 방지
   보정이 이전과 동일하다.
2. **전제** `ScreenContainer`를 쓰는 화면(예: 학습 완료 화면), **실행** 고정 본문으로 이전한다,
   **결과** 배경 색, 색 구성표, 중앙 정렬 결과가 이전과 동일하다.
3. **전제** 컨테이너 없이 직접 조립한 화면(예: 레포지토리 링크 입력 화면), **실행** Sticky
   헤더·푸터와 고정 본문으로 이전한다, **결과** 키보드가 표시될 때 하단 버튼의 위치와 동작이
   이전과 동일하다.
4. **전제** 상태에 따라 헤더 구성이 바뀌는 화면(예: 프로젝트 목록의 삭제 모드), **실행**
   이전한다, **결과** 상태 전환 시 헤더 컨트롤과 제목 변경이 동일하게 동작한다.
5. **전제** 탭 안에서 표시되는 화면(홈·프로젝트·저장·마이), **실행** 이전한다, **결과** 탭 바와
   하단 안전 영역 처리가 이전과 동일하다.

### 시나리오 3 - 골격을 단일화하고 컨벤션 정본을 갱신한다 (우선순위: P2)

모든 화면 이전이 끝나면 옛 컨테이너를 제거하고, View 컨벤션과 컴포넌트 배치 표가 Screen
골격을 화면 루트의 유일한 정본으로 기술한다. 리뷰어는 화면 루트 규칙 위반을 기계적으로 찾을
수 있다.

**주요 행위자**: UI 패키지 유지보수자, 코드 리뷰어

**우선순위 이유**: 옛 컨테이너가 남아 있으면 화면 루트 규칙이 둘로 남고 새 화면이 다시 옛
골격을 쓰는 회귀가 생긴다.

**독립 테스트**: production 소스에서 옛 컨테이너 참조가 0건인지 검색으로 확인하고, 컨벤션
문서와 컴포넌트 인덱스가 Screen 골격을 기술하는지 검토한다.

**수용 시나리오**:

1. **전제** 모든 화면 이전이 완료됐다, **실행** `ScreenContainer`와 `OverlayContainer`를 UI
   패키지에서 제거한다, **결과** production 소스와 테스트에서 두 타입 참조가 0건이고 빌드가
   성공한다.
2. **전제** View 컨벤션 §4.1이 두 컨테이너 선택 규칙과 화면 골격 표를 기술한다, **실행**
   문서를 갱신한다, **결과** View 컨벤션 화면 골격 표, UIComponent 컨벤션 §3.4 배치 표,
   Figma 컴포넌트 인덱스가 Screen 골격과 배치 스타일을 정본으로 기술한다.
3. **전제** 리뷰어가 새 화면 PR을 검토한다, **실행** 화면 루트를 확인한다, **결과** 화면 루트가
   Screen 골격 하나인지와 헤더·푸터 여백 상수를 화면이 정의하지 않았는지를 검색으로 확인할
   수 있다.

### 예외·경계 사례

- 본문 높이가 화면보다 짧을 때 스크롤 본문은 상단 정렬을 유지하고 크기에 따른 바운스 동작이
  이전과 동일하다.
- Header나 Footer 콘텐츠의 높이가 상태에 따라 바뀔 때(예: 저장 화면의 필터 섹션 표시) Overlay
  본문의 가림 방지 보정은 실제 높이를 따라간다.
- 큰 동적 글꼴에서 헤더·푸터 높이가 커져도 Sticky·Overlay 두 스타일 모두 본문이 가려지지
  않는다.
- 키보드가 표시될 때 헤더·푸터는 현재 동작대로 키보드 안전 영역을 무시하고 위치를 유지한다.
  키보드 위로 올려야 하는 요소가 있는 화면은 Body 안에서 그 동작을 처리한다.
- 화면이 당겨서 새로고침, 스크롤 인디케이터 숨김처럼 스크롤 modifier를 Body에 적용해야 하는
  경우 골격이 이를 막지 않는다.
- 골격 밖에 `.overlay`로 쌓는 액션 메뉴·모달은 색 구성표를 잃지 않는다. 색 구성표는 루트
  골격이 소유하며 화면이 다시 지정하지 않는다.
- 본문과 함께 스크롤되는 배경 장식을 쓰는 화면이 있으면 이전 후에도 같은 위치에서 같은 방식으로
  스크롤된다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: UI 패키지는 Header, Body, Footer 세 슬롯을 갖는 단일 화면 골격 컴포넌트(이하
  Screen 골격)를 제공해야 한다. Body는 필수이고 Header와 Footer는 생략할 수 있다.
- **FR-002**: Header와 Footer는 각각 독립적으로 배치 스타일을 선택할 수 있어야 하며, 배치
  스타일 어휘는 최소 Sticky와 Overlay를 포함해야 한다.
- **FR-003**: Sticky 스타일의 영역은 화면 가장자리에 고정되고, Body 표시 영역은 고정 영역을
  제외한 나머지로 한정되어 어떤 스크롤 위치에서도 Body 콘텐츠가 그 영역에 가려지지 않아야
  한다.
- **FR-004**: Overlay 스타일의 영역은 Body 위에 떠 있고 Body는 그 뒤로 스크롤되며, 스크롤
  양 끝에서 첫·마지막 콘텐츠가 가려지지 않도록 영역의 실제 높이만큼 보정해야 한다. 이 영역은
  스크롤 콘텐츠 위에서 판독성을 유지하는 배경 처리(현재 헤더·푸터 스크림 토큰)를 포함해야 한다.
- **FR-005**: Body는 스크롤 본문과 고정(비스크롤) 본문 두 방식을 지원해야 하며, 두 방식 모두
  Sticky·Overlay 스타일의 Header·Footer와 조합할 수 있어야 한다.
- **FR-006**: Screen 골격은 화면 배경 색 토큰, 색 구성표, 안전 영역 처리를 소유하고,
  Header·Footer 영역의 표준 좌우 여백과 상하 여백을 적용해야 한다. Feature 화면은 슬롯
  콘텐츠만 제공하며 헤더·푸터 영역의 높이와 여백 값을 자체 상수로 정의하지 않아야 한다.
- **FR-007**: 슬롯은 임의의 View를 받아야 하며, 형태별로 미리 조립한 헤더·푸터 변형(뒤로가기
  전용, 제목 전용 등)을 골격의 공개 API로 추가하지 않아야 한다. 화면은 `ScreenControlBar`,
  `ScreenHeaderTitle`, `BottomActionBar` 같은 기존 컴포넌트를 슬롯 안에서 자유롭게 조합한다.
- **FR-008**: Screen 골격의 공개 API는 UI 패키지 규칙에 따라 TCA, Feature, Domain 타입에
  의존하지 않고 표시 값, `Binding`, 콜백과 `@ViewBuilder` 콘텐츠만 받아야 한다.
- **FR-009**: 라우터가 그리는 전체 화면 View를 포함한 모든 Feature 화면 루트는 Screen 골격
  하나를 사용하도록 이전해야 하며, 이전 완료 후 `ScreenContainer`와 `OverlayContainer`를 UI
  패키지에서 제거해야 한다.
- **FR-010**: 이전은 사용자에게 보이는 레이아웃, 색, 스크림, 스크롤 범위, 키보드 동작을 바꾸지
  않아야 한다. 이전 중 발견한 화면별 레이아웃 불일치는 이 기능에서 고치지 않고 별도 변경으로
  분리한다.
- **FR-011**: 골격 계약(슬롯 생성, 슬롯 생략, 스타일 조합, 본문 방식)은 UI 패키지 테스트로
  검증하고, 스타일 조합을 한 곳에 나열한 프리뷰를 제공해야 한다.
- **FR-012**: View 컨벤션의 화면 골격 표와 §4.1 규칙, UIComponent 컨벤션 §3.4 배치 표, Figma
  컴포넌트 인덱스를 Screen 골격과 배치 스타일 기준으로 갱신해야 한다.

### 핵심 엔터티 *(기능에 데이터가 포함되면 작성)*

- **Screen 골격**: 화면 루트. 배경 색 토큰, 색 구성표, 안전 영역과 세 슬롯의 배치를 소유한다.
  슬롯 콘텐츠의 의미는 소유하지 않는다.
- **Header·Footer 영역**: 슬롯 콘텐츠, 배치 스타일, 표준 여백으로 구성된다. 생략 가능하며
  생략 시 어떤 공간도 차지하지 않는다.
- **배치 스타일**: Header·Footer 영역이 Body와 맺는 관계. Sticky(고정, 본문과 겹치지 않음)와
  Overlay(본문 위에 떠 있음, 본문이 뒤로 스크롤)를 포함한다.
- **Body 본문 방식**: 스크롤 본문 또는 고정 본문. 스크롤 본문은 배치 스타일에 따라 가림 방지
  보정을 받는다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: Feature 패키지의 화면 루트 100%가 Screen 골격을 사용하고, `ScreenContainer`,
  `OverlayContainer`, 컨테이너 없이 직접 조립한 화면 루트가 0건이다.
- **SC-002**: Feature 화면에서 헤더·푸터 영역의 높이와 여백을 정의하는 상수(예: 컨트롤 행 높이,
  헤더 하단 여백)가 0건이다.
- **SC-003**: 이전 대상 화면 전부에 대해 이전 전후 프리뷰 또는 Simulator 화면 비교에서 레이아웃
  차이가 0건이다.
- **SC-004**: 전체 공유 scheme 빌드, build-for-testing, test-without-building이 모두 통과하고
  기존 UI 계약 테스트가 100% 통과한다.
- **SC-005**: View 컨벤션, UIComponent 컨벤션, Figma 컴포넌트 인덱스에서 `ScreenContainer`와
  `OverlayContainer` 언급이 0건이고, 화면 루트 규칙이 Screen 골격 하나로 기술된다.

## 가정

- 배치 스타일은 화면 단위가 아니라 Header와 Footer 각각에 지정한다. 헤더 Sticky와 푸터
  Overlay 같은 조합을 허용한다.
- 배치 스타일 어휘는 Sticky와 Overlay로 시작한다. 본문과 함께 스크롤되는 헤더는 Body 콘텐츠로
  표현할 수 있으므로 별도 스타일을 두지 않는다. 추가 스타일은 이전 중 기존 화면이 필요로 할
  때만 이 명세를 갱신해 추가한다.
- 이 기능은 새 골격 도입뿐 아니라 기존 화면 전체 이전과 옛 컨테이너 제거를 포함한다. 두 골격을
  병존시키면 화면 루트 규칙이 둘로 남아 "프레임워크로 정의한 Screen"이라는 목적을 달성하지
  못한다.
- 이전은 시각 결과를 바꾸지 않는 순수 구조 변경이다. 이전 대상에는 Share Extension의 화면과
  라우터가 직접 그리는 전체 화면 View를 포함한다.
- 색 구성표는 현재와 같이 다크로 고정하며 Screen 골격이 소유한다.
- Overlay 스타일의 스크림은 기존 `overlayHeaderScrim`, `overlayFooterScrim` 그라디언트 토큰을
  그대로 사용한다.
- 탭 구조(`TabShell`), 흐름 스택(`FlowNavigationStack`), 시트·모달 오버레이 컴포넌트는 이
  기능의 범위 밖이며 변경하지 않는다.
- Screen 골격 컴포넌트, 슬롯과 배치 스타일의 실제 공개 이름은 계획 단계에서 네이밍 컨벤션에
  따라 결정한다.
