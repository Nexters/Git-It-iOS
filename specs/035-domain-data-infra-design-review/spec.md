**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/domain-data-infra-design-review`

**브랜치 상태**: `생성`

**상태**: 초안

**입력**: 사용자 설명: "Domain, Data, Infra 패키지 설계 점검 및 문서와 네이밍 교정"

## 배경

명세 013(Data↔Infrastructure 변환을 Data 내부로 이동), 031(계층 축소), 032(Composition 책임
반환), 033(UseCase 통합), 034(패키지 의존성 강제)를 거치며 Domain·Data·Infrastructure의 실제
구조가 여러 번 바뀌었습니다. 그 과정에서 규칙 문서와 코드가 어긋난 흔적이 확인됩니다.
명세 작성 시점에 관찰한 예시는 다음과 같으며, 점검 범위를 이 목록으로 한정하지 않습니다.

- [Infrastructure 패키지 규칙](../../docs/package-rules/infrastructure.md)은 "Composition의
  Adapter가 해당 API를 Data의 기술 계약과 연결"한다고 설명하지만, D-ARCH-003 이후 그 변환은
  Data 내부 구현이 담당합니다.
- `sources/Projects/Domain/Authentication/README.md`는 코드에 존재하지 않는
  `AuthenticationOutcome`을 공개 모델로 설명합니다.
- Data의 `DataAuthenticationError`, `DataMemberError`, `DataLearningProjectError`,
  `DataExternalRepositoryError`는 [네이밍 컨벤션](../../docs/conventions/naming.md) 4장이
  금지하는 패키지 이름 접두어 형태입니다.
- Data에는 `APIResponseDTO`, `FieldErrorDTO`, `EmptyResponseData`, `ServerAPIError`가 여러
  target에 같은 이름으로 반복되고, Infrastructure와 같은 이름의 `HTTPMethod`가 Data에도
  있습니다.
- Infrastructure `Authentication` target이 Keychain과 난수 생성처럼 인증에 한정되지 않는
  기술 기능을 함께 담아, "모든 내부 target은 하나의 범용 기술 기능"이라는 규칙과의 관계가
  문서로 설명되지 않습니다.

## 명확화

### 세션 2026-09-17

- 질문: Domain·Data 사이 "관심사 중복 객체"를 무엇으로 판정하는가? → 답변: 다음 세 경우 중
  하나라도 해당하면 점검 대상으로 삼는다. (1) 두 객체가 책임과 연산 단위로 완전히 1:1
  대응하는 경우, (2) Domain 쪽에 비즈니스 로직이 없고 Data 구현을 그대로 감싸는 경우,
  (3) 이름과 필드가 완전히 같은 경우.
- 질문: 발견한 관심사 중복 쌍을 이 기능에서 어디까지 해소하는가? → 답변: 탐지와 기록만
  수행한다. 모든 관심사 중복 쌍은 "후속 설계 변경"으로 분류하고 제거 방향과 영향 범위를
  남기며, 실제 제거는 별도 명세에서 다룬다.
- 질문: rename 범위에 target(모듈)과 target 소스 루트 폴더 이름을 포함하는가? → 답변:
  포함한다. target·소스 폴더 rename도 이 기능에서 수행하고 manifest, import, 패키지 의존성
  검사 설정, scheme을 같은 변경에서 갱신한다. target 분리·병합은 여전히 후속 설계 변경이다.
- 질문: Data target 사이와 Data↔Infrastructure 사이에 반복되는 타입(`APIResponseDTO`,
  `HTTPMethod` 등)과 기술 노출을 어떤 기준으로 판정하고 어디까지 해소하는가? → 답변: 패키지
  관심사 원칙을 점검 기준으로 삼는다. Data는 HTTP 같은 기술·라이브러리·프레임워크에 종속된
  형태로 정의하지 않고 실행하는 역할만 다루며, 기술은 Infrastructure가 모두 담당하고 Data는
  이를 외부에 노출하지 않는다. Domain은 비즈니스 로직의 관심사를 기준으로 Data나 특정 API에
  의존하지 않고 사용자·서비스 관점의 역할만 정의한다. 이 원칙을 규칙 문서에 반영하고, 위반 중
  이름만 바꾸면 되는 항목은 이 기능에서 rename으로 해소하며, 기술 타입 이동·제거, 공개 API에서
  Infrastructure 타입 숨기기, Data target 사이 반복 타입 정리는 "후속 설계 변경"으로 기록한다.
- 질문: 외부 고정 명칭 보존 예외와 FR-017이 충돌할 때 Data 공개 이름을 어떻게 판정하는가?
  → 답변: Data 공개 타입·프로토콜 이름의 전송·저장 기술 용어(HTTP, Keychain, UserDefaults,
  URLSession)는 FR-017 위반이다. 외부 서비스·공급자 이름(GitHub, Apple)은 그 서비스가 Data의
  역할 대상일 때만 허용한다. 외부 고정 명칭 보존은 직렬화 key·서버 필드·플랫폼 API 값에만
  적용한다.
- 질문: Domain 계약 이름의 접미어와 연산 이름을 FR-017로 어떻게 판정하는가? → 답변:
  `Repository`는 외부 기능 계약의 역할 어휘로 허용한다. `Store`, `Registry`, `Gateway`,
  `Parser`처럼 저장 매체·형식·접근 방식을 드러내는 접미어와 `load`/`save`처럼 저장소 연산을
  그대로 드러내는 연산 이름은 FR-017 위반으로 판정하고, 이름만 바꾸면 되는 경우 rename한다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 세 패키지의 설계 점검 결과를 한곳에서 확인한다 (우선순위: P1)

개발자(또는 코드 작업을 맡는 AI 에이전트)가 Domain·Data·Infrastructure를 수정하기 전에, 각
패키지가 현재 아키텍처·패키지 규칙·네이밍·추상화·디렉터리 컨벤션과 어디서 어긋나는지
근거와 함께 기록된 점검 결과를 읽고 판단할 수 있습니다.

**주요 행위자**: 개발자, AI 코딩 에이전트

**우선순위 이유**: 문서 교정과 rename은 모두 이 점검 결과를 입력으로 삼습니다. 점검 없이
교정하면 누락과 과잉 수정을 구분할 수 없습니다.

**독립 테스트**: 점검 결과만 산출하고 코드·문서를 전혀 바꾸지 않아도, 발견 항목마다 위반한
규칙 위치와 코드 위치를 따라가 사실 여부를 확인할 수 있습니다.

**수용 시나리오**:

1. **전제** 점검 결과가 작성됨, **실행** 임의의 발견 항목을 고름, **결과** 항목에 적힌 규칙
   문서 위치와 코드(또는 문서) 위치를 열어 불일치를 재현할 수 있다.
2. **전제** 점검 결과가 작성됨, **실행** 발견 항목의 처리 구분을 확인, **결과** 각 항목이
   "문서 교정", "rename", "후속 설계 변경", "위반 아님(근거 포함)" 중 정확히 하나로 분류되어
   있다.
3. **전제** 배경에 적은 예시 불일치, **실행** 점검 결과에서 검색, **결과** 모든 예시가
   발견 항목 또는 "위반 아님" 판정으로 포함되어 있다.

### 시나리오 2 - 규칙 문서가 현재 구조를 정확히 설명한다 (우선순위: P2)

개발자가 아키텍처 문서, Domain·Data·Infrastructure 패키지 규칙, 세 패키지 안의 README를
읽으면 현재 코드의 책임 경계·의존 방향·변환 위치와 모순되지 않는 설명을 얻습니다.

**주요 행위자**: 개발자, AI 코딩 에이전트

**우선순위 이유**: 에이전트와 개발자는 규칙 문서를 근거로 코드를 작성하므로, 낡은 설명은
이미 제거한 구조를 다시 만들어 내는 원인이 됩니다.

**독립 테스트**: 코드 rename 없이 문서만 교정해도, 점검 결과에서 "문서 교정"으로 분류한
항목이 모두 해소되었는지 문서와 코드를 대조해 확인할 수 있습니다.

**수용 시나리오**:

1. **전제** Infrastructure 패키지 규칙, **실행** Data↔Infrastructure 연결 주체에 대한 설명을
   읽음, **결과** D-ARCH-003과 같이 Data 내부 구현이 변환을 담당한다고 설명한다.
2. **전제** 세 패키지 안의 README, **실행** 설명된 공개 타입과 동작을 코드와 대조, **결과**
   존재하지 않는 타입이나 제거된 동작을 설명하지 않는다.
3. **전제** 문서 교정 완료, **실행** 규칙 문서끼리 대조, **결과** 같은 사안에 대해 서로
   다른 결론을 내리는 문서가 없다.
4. **전제** 문서 교정 완료, **실행** Data·Domain의 책임과 예시를 읽음, **결과** Data는 기술을
   노출하지 않는 실행 역할로, Domain은 Data·특정 API와 무관한 사용자·서비스 관점의 역할로
   설명되며 기술 이름을 가진 Data 공개 구현 예시가 없다.

### 시나리오 3 - 공개 이름이 네이밍 컨벤션을 따른다 (우선순위: P3)

개발자가 세 패키지의 공개 타입·프로토콜·연산·target 이름을 읽으면 패키지 접두어나 근거 없는
접미어 없이 실제 책임을 알 수 있고, 같은 이름이 다른 개념을 가리키지 않습니다.

**주요 행위자**: 개발자, AI 코딩 에이전트

**우선순위 이유**: rename은 호출부·Composition Adapter·테스트까지 영향이 퍼지므로 점검과
문서 교정으로 기준을 확정한 뒤 수행해야 합니다.

**독립 테스트**: rename만 적용한 상태에서 전체 빌드와 기존 테스트가 동작 변경 없이 통과하고,
점검 결과에서 "rename"으로 분류한 항목이 모두 해소되었는지 확인할 수 있습니다.

**수용 시나리오**:

1. **전제** "rename"으로 분류된 항목, **실행** rename 적용, **결과** 해당 이름을 참조하던
   Composition·Feature·App·테스트·문서가 모두 새 이름을 사용하고 옛 이름이 남지 않는다.
2. **전제** rename 적용 전후, **실행** 전체 빌드와 기존 테스트 실행, **결과** 동일하게
   통과하며 테스트 기대값 변경은 이름 치환에 한정된다.
3. **전제** 외부 API·서버 schema·플랫폼이 고정한 명칭, **실행** rename 대상 검토, **결과**
   외부 고정 명칭과 그 mapping은 바뀌지 않는다.

### 예외·경계 사례

- 규칙 문서와 코드가 어긋나지만 코드 쪽 설계가 더 타당한 경우, 코드를 문서에 맞추지 않고
  문서를 교정 대상으로 분류하며 그 판단 근거를 남긴다. 판단이 아키텍처 결정 변경에 해당하면
  아키텍처 문서의 결정 기록을 함께 갱신한다. 단, FR-017의 패키지 관심사 원칙에 어긋나는 코드는
  문서를 코드에 맞추지 않고 코드 쪽 위반으로 분류한다.
- Data 공개 initializer나 공개 프로퍼티가 `HTTPClient`처럼 Infrastructure 타입을 받거나
  노출하는 경우, 이름 변경으로 해소되지 않으므로 "후속 설계 변경"으로 기록한다.
- 외부 고정 명칭 보존은 직렬화 key, 서버 필드, 플랫폼 API가 정한 값에만 적용한다. Data 공개
  타입·프로토콜 이름은 프로젝트가 소유하므로 FR-017을 따르며, 전송·저장 기술 용어(HTTP,
  Keychain, UserDefaults, URLSession)를 포함하면 위반으로 판정한다. 외부 서비스·공급자
  이름(GitHub, Apple)은 그 서비스가 해당 선언의 역할 대상일 때만 허용하고, 그렇지 않으면
  위반으로 판정한다.
- Data target 사이에 같은 이름으로 반복되는 타입과 Data·Infrastructure에 함께 존재하는 기술
  타입(`HTTPMethod` 등)은 발견 항목으로 기록하고 "후속 설계 변경"으로 분류한다.
- rename이 저장소 key, Keychain 항목, 직렬화 key, 서버 요청 필드처럼 저장·전송 값에 영향을
  주는 경우, 그 값은 바꾸지 않거나 해당 항목을 rename 대상에서 제외하고 사유를 기록한다.
- target rename 후 `tuist generate`로 만들어지는 workspace·scheme에 옛 target 이름이 남는 경우,
  생성물이 아니라 manifest와 설정의 누락으로 보고 같은 변경 안에서 해소한다.
- Composition·Feature·App에서 발견한 위반은 이 기능의 교정 대상이 아니며, 세 패키지의
  rename에 따른 참조 갱신만 수행한다.
- 관심사 중복 쌍의 한쪽 객체가 네이밍 위반에도 해당하는 경우, 후속 설계 변경에서 제거될
  객체의 rename은 수행하지 않고 중복 항목에 네이밍 위반 사실을 함께 기록한다.
- Domain 객체가 Data 구현을 감싸면서 오류 변환이나 값 검증처럼 비즈니스 판단이 아닌 변환만
  수행하는 경우, FR-014의 판정 조건 (2)에 해당하는지 여부와 그 근거를 발견 항목에 남긴다.
- 점검 중 동작 결함(버그)을 발견하면 교정하지 않고 후속 항목으로 기록한다.
- 이미 진행 중이거나 머지된 명세(031~034)가 결정한 사항과 충돌하는 발견은 기존 결정을
  뒤집지 않고 충돌 사실과 근거만 기록한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 점검은 Domain·Data·Infrastructure의 모든 프로덕션 target, 테스트 target, 각
  패키지 안의 README를 대상으로 해야 한다.
- **FR-002**: 점검은 최소한 다음 기준 문서와의 불일치를 확인해야 한다: Constitution,
  아키텍처 문서, Domain·Data·Infrastructure 패키지 규칙, 네이밍 컨벤션, 추상화 컨벤션과 구조
  기준선, 디렉터리·파일 컨벤션, 파일 어휘, 테스트 컨벤션.
- **FR-003**: 각 발견 항목은 위반한 규칙의 문서 위치, 대상 코드 또는 문서 위치, 불일치 설명,
  처리 구분("문서 교정", "rename", "후속 설계 변경", "위반 아님") 하나를 가져야 한다.
- **FR-004**: "위반 아님"으로 판정한 항목은 규칙을 적용하지 않는 근거(예외 조항, 외부 고정
  명칭 등)를 명시해야 한다.
- **FR-005**: "문서 교정"으로 분류한 모든 항목은 이 기능에서 해소되어야 하며, 교정 후 문서는
  현재 코드 구조와 확정된 아키텍처 결정을 설명해야 한다.
- **FR-006**: 문서 교정은 기존 문서의 소유 범위를 지켜야 한다. 한 규칙의 정본은 한 문서에만
  두고 다른 문서는 그 정본을 참조한다.
- **FR-007**: "rename"으로 분류한 모든 항목은 이 기능에서 해소되어야 하며, 동작·상태 수명·
  책임·의존 방향·외부 계약 변경을 동반해서는 안 된다.
- **FR-008**: rename은 세 패키지 밖의 참조(Composition Adapter, Feature, App, 테스트, 문서)를
  같은 변경 안에서 모두 갱신해야 하며, 옛 이름을 참조하는 코드나 문서가 남아서는 안 된다.
- **FR-009**: rename은 파일 이름·폴더 위치를 디렉터리·파일 컨벤션에 맞게 함께 정리해야 한다.
- **FR-009a**: rename 대상에는 타입·프로토콜·연산·파일·하위 폴더뿐 아니라 세 패키지의
  target(모듈) 이름과 target 소스 루트 폴더 이름이 포함된다. target rename은 Tuist manifest의
  target·의존성 선언, 모든 `import` 구문, 패키지 의존성 검사 도구의 target·소스 루트 설정,
  scheme 이름, 해당 target을 가리키는 문서를 같은 변경 안에서 갱신해야 한다.
- **FR-009b**: target rename은 target의 소스 구성과 target 간 의존 관계를 바꾸지 않는다.
  target 분리·병합이 필요한 이름 불일치는 "후속 설계 변경"으로 분류한다.
- **FR-010**: 저장·전송되는 값(저장소 key, 직렬화 key, 서버 필드, Keychain 식별자)은 rename
  과정에서 바뀌어서는 안 된다.
- **FR-011**: "후속 설계 변경"으로 분류한 항목은 코드에 적용하지 않고, 영향 범위와 권장 방향을
  점검 결과에 남겨야 한다.
- **FR-012**: 프로덕션 프로토콜의 추가·제거가 발생하면 추상화 구조 기준선을 함께 갱신해야
  한다. rename만 발생하면 기준선의 이름만 갱신한다.
- **FR-013**: 이 기능은 프로젝트 내부 패키지 의존성 방향과 외부 패키지 의존성을 변경해서는
  안 된다.
- **FR-014**: 점검은 Domain과 Data 사이의 관심사 중복 객체를 찾아야 한다. 다음 중 하나라도
  해당하는 Domain·Data 객체 쌍을 모두 발견 항목으로 기록한다: (1) 책임과 연산이 완전히 1:1로
  대응한다, (2) Domain 쪽에 비즈니스 로직이 없고 Data 구현을 그대로 감싼다, (3) 이름과 필드가
  완전히 같다. 모델·계약·오류·UseCase 구현 등 선언 종류와 관계없이 적용한다.
- **FR-015**: 관심사 중복 발견 항목은 해당하는 판정 조건 번호, 대응하는 Domain·Data 선언
  위치, 두 객체 사이에서 연결하는 Composition Adapter 위치(있으면)를 함께 기록해야 한다.
- **FR-016**: 관심사 중복 발견 항목은 모두 "후속 설계 변경"으로 분류해야 하며, 어느 쪽 객체를
  남기고 제거할지에 대한 권장 방향과 제거 시 영향받는 Composition·Feature·App·테스트 범위를
  기록해야 한다. 이 기능에서는 관심사 중복 쌍의 객체·계약·Adapter를 제거하거나 병합하지 않는다.
- **FR-017**: 점검은 다음 패키지 관심사 원칙을 기준으로 적용해야 한다.
  - Data의 공개 선언(타입·프로토콜·연산·initializer·프로퍼티 이름과 시그니처)은 HTTP,
    Keychain, UserDefaults, URLSession 같은 기술이나 라이브러리·프레임워크에 종속된 형태로
    정의하지 않고 실행하는 역할만 표현한다.
  - 기술은 Infrastructure가 모두 담당하며, Data는 내부 구현에서 Infrastructure를 사용하더라도
    그 기술을 Data 밖으로 노출하지 않는다.
  - Domain의 공개 선언은 비즈니스 로직의 관심사를 기준으로 정의하며, Data의 형태나 특정 API에
    의존하지 않고 사용자·서비스 관점의 역할을 표현한다.
- **FR-018**: FR-017의 원칙은 아키텍처 문서(패키지 책임, 3.3 Data↔Infrastructure 설명과 예시,
  결정 기록), Domain·Data·Infrastructure 패키지 규칙, 네이밍 컨벤션의 패키지 문맥 표에 모순 없이
  반영되어야 하며, 원칙의 정본은 한 문서에만 두고 나머지는 참조한다.
- **FR-019**: FR-017 위반은 다음처럼 분류해야 한다. 이름만 바꾸면 원칙을 충족하는 항목은
  "rename"으로 이 기능에서 해소한다. 기술 타입의 Infrastructure 이동·제거, 공개 API에서
  Infrastructure 타입 숨기기, Data target 사이 반복 타입 정리처럼 선언의 구성이나 시그니처를
  바꿔야 하는 항목은 "후속 설계 변경"으로 분류하고 권장 방향과 영향 범위를 기록한다.
- **FR-020**: Domain 공개 계약과 연산 이름은 다음 기준으로 FR-017을 판정한다. `Repository`
  접미어는 Domain이 요구하는 외부 기능 계약의 역할 어휘로 허용한다. `Store`, `Registry`,
  `Gateway`, `Parser`처럼 저장 매체·형식·접근 방식을 드러내는 접미어와 `load`/`save`처럼
  저장소 연산을 그대로 드러내는 연산 이름은 위반으로 판정한다. 위반은 FR-019의 분류 기준을
  따르며, 연산 이름 변경이 계약 시그니처(인자·반환 타입)를 바꾸지 않으면 rename으로 본다.

### 핵심 엔터티

- **점검 기준**: 규칙을 소유한 문서와 그 안의 조항. 발견 항목이 인용하는 근거다.
- **발견 항목**: 하나의 불일치. 기준 위치, 대상 위치, 설명, 처리 구분을 갖는다.
- **처리 구분**: 문서 교정, rename, 후속 설계 변경, 위반 아님 중 하나. 이 기능에서 해소할지를
  결정한다.
- **관심사 중복 쌍**: FR-014의 판정 조건 중 하나 이상에 해당하는 Domain 객체와 Data 객체의
  짝. 발견 항목의 한 종류이며 판정 조건 번호를 갖는다.

- **SC-003**: 기능 완료 후 세 패키지의 프로덕션 코드와 README에서 옛 이름 또는 존재하지 않는

- **SC-010**: 교정 후 아키텍처 문서와 Domain·Data·Infrastructure 패키지 규칙에서 FR-017 원칙과

## 가정

- "설계 점검"은 현재 설계를 기준 문서와 FR-017의 패키지 관심사 원칙에 대조해 불일치를 찾는
  것을 뜻한다. FR-017 원칙의 문서 반영 외에 새 아키텍처를 제안하거나 패키지 책임을 재정의하는
  것은 포함하지 않는다.
- "교정"은 문서 수정과 동작을 보존하는 rename(파일·폴더 이동 포함)으로 한정한다. 타입 통합,
  target 분리·병합, 프로토콜 추가·제거처럼 구조를 바꾸는 변경은 점검 결과에 후속 항목으로만
  남기고 별도 명세에서 다룬다.
- 기준 문서끼리 충돌하면 AGENTS.md의 우선순위(Constitution → 아키텍처·컨벤션·패키지 규칙)를
  따르고, 하위 문서를 교정 대상으로 분류한다.
- Constitution 자체의 수정이 필요한 발견은 이 기능에서 교정하지 않고 `speckit-constitution`
  후속 항목으로 기록한다.
- `specs/` 아래 과거 명세 산출물은 당시 결정의 기록이므로 rename에 맞춰 수정하지 않는다.
- 네이밍 컨벤션의 외부 고정 명칭 기준은 직렬화 key·서버 필드·플랫폼 API 값에 적용한다.
  Infrastructure 공개 이름의 기술·플랫폼 명칭(Apple, Firebase, Keychain, HTTP 등)은 Infrastructure
  패키지 규칙에 따라 보존하고, Data 공개 이름은 FR-017과 예외·경계 사례의 판정 기준을 따른다.
- 빌드·테스트 실행은 프로젝트의 공개 빌드 러너를 사용하며, 실행 주체는 구현 단계에서 정한다.
