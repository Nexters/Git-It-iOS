# 기능 명세: 공유 확장에서 진행 중인 생성이 있으면 새 생성 요청 차단

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/share-generation-guard`

**브랜치 상태**: `생성`

**생성일**: 2026-09-28

**상태**: 초안

**입력**: 사용자 설명: "공유 확장(Share Extension)으로 프로젝트 생성을 요청할 때, 앱과 동일하게 진행 중인 프로젝트 생성이 있으면 새 생성 요청을 막는다. 현재 공유 확장은 같은 저장소 중복만 막고, 다른 저장소의 생성이 진행 중이어도 등록을 허용해 진행 중 기록이 두 개가 된다(앱 홈은 진행 중 생성이 있으면 불러오기를 잠그는 023 정책). 생성 상태 확인은 기존 ProjectGenerationUseCase의 상태(ProjectGenerationState)를 그대로 사용하되, 이를 래핑해 단순화한 형태의 UseCase를 ShareExtension Feature에서 정의해 사용한다."

## 배경

앱은 학습 세트 생성이 진행 중인 동안 홈의 불러오기를 "문제 생성 중"으로 잠가 새 생성 요청을 막는다
(023 시나리오 2). 이 정책은
생성 결과가 어느 요청의 것인지 섞이는 문제와 중복 요청을 막기 위한 것이다.

공유 확장(027)은 이 정책을 따르지 않는다. 공유 확장의 등록은 같은 저장소의 진행 중 기록만 중복으로
거절하므로, 저장소 A의 생성이 진행 중일 때 다른 앱에서 저장소 B를 공유하면 B의 등록이 성공하고 진행 중
기록이 두 개가 된다. 027 FR-015("요청이 진행 중인 동안 추가 등록 실행 차단")는 공유 확장 화면 안의
중복 실행만 다루며 앱 전체의 생성 진행 상태를 보지 않는다.

앱과 공유 확장은 생성 기록을 같은 공유 저장소에 기록하므로, 공유 확장도 앱과 같은 생성 상태를 읽어 판정할
수 있다.

## 명확화

### 세션 2026-09-28

- 질문: 공유 확장은 언제 생성 진행 여부를 판정하는가? → 답변: 저장소 조회 전과 등록 요청 직전에 모두 판정한다.
- 질문: 생성 기록을 읽지 못해 생성 진행 여부를 확인할 수 없으면 어떻게 하는가? → 답변: 별도의 실패 안내와 재시도 동작을 보여 주고 등록을 막는다.
- 질문: 결과를 받지 못해 보관 기한까지 남은 진행 중 기록이 있으면 공유를 어떻게 처리하는가? → 답변: 앱과 같이 막고, 생성 중 안내 문구에 앱을 열면 최신 상태가 반영된다는 복구 안내를 넣는다(앱 실행은 하지 않음). 생성 상태 확인과 생성 요청은 본 앱과 공유 확장이 같은 UseCase와 같은 로직을 사용해 일관성을 유지한다.

### 세션 2026-09-29

- 질문: 공유 확장 Feature의 단순화된 경계를 별도 타입(판정 결과 enum과 판정 struct)으로 둘 것인가? → 답변: 두 타입을 두지 않는다. 공유 확장 Feature는 현재 생성 상태를 한 번 읽는 클로저 하나만 주입받고, 그 결과를 Domain의 "생성 중" 판정 규칙으로 해석한다. 흐름 루트에 새 파일을 두지 않아 Feature 흐름 배치 컨벤션과 충돌하지 않게 한다.
- 질문: 공유 확장의 하위 등록 Feature는 생성 상태 조회 외의 동작도 UseCase 전체로 받는가? → 답변: 받지 않는다. 하위 등록 Feature는 저장소 조회·생성 요청·현재 생성 상태 조회 클로저 3개만 받고 `ExternalRepositoryUseCase`·`ProjectGenerationUseCase` 전체를 받지 않는다(Domain 패키지 규칙의 말단 Feature 규칙). 루트 공유 확장 Feature의 공개 initializer는 유지한다.
- 질문: 공유 확장 흐름의 기존 배치가 Feature 흐름 배치 컨벤션과 어긋나는 문제를 이번 기능에서 정리하는가? → 답변: 정리한다. 기능 구현 전에 동작 변경 없는 이동 단위로 흐름 루트의 화면·Feature·진단 사례와 흐름 1뎁스의 서브뷰·화면 프리뷰를 화면 폴더(`Feature/ShareRegistration/ShareRegistration/`)로, 테스트를 같은 축(`Feature/Tests/ShareRegistration/ShareRegistration/`)으로 옮긴다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 생성이 진행 중이면 공유로 새 생성을 시작할 수 없다 (우선순위: P1)

회원 사용자가 저장소 A의 학습 세트 생성을 요청해 두고, 끝나기 전에 Safari나 GitHub 앱에서 다른 저장소를
Git-It으로 공유한다. 공유 확장은 저장소를 조회하거나 등록하지 않고 "이미 문제를 생성 중"이라는 안내와 닫기
동작만 보여 준다. 진행 중인 생성은 하나로 유지된다.

**주요 행위자**: 회원 사용자

**우선순위 이유**: 이 기능의 존재 이유다. 이 경로가 열려 있으면 앱에서 막는 동시 생성이 공유 경로로 그대로
발생한다.

**독립 테스트**: 생성 기록 저장소에 진행 중 기록 하나를 둔 상태에서 공유 확장 흐름에 저장소 URL을 전달하고,
생성 중 안내 상태로 전환되며 저장소 조회와 등록 요청이 한 번도 일어나지 않는지 자동 테스트로 확인한다.

**수용 시나리오**:

1. **전제** 다른 저장소의 진행 중 생성 기록이 있다, **실행** 사용자가 저장소 URL을 공유해 공유 확장이 실행된다, **결과** 저장소 조회와 등록 요청 없이 생성 중 안내 상태가 표시되고 닫기 동작이 제공된다.
2. **전제** 공유한 저장소와 같은 저장소의 진행 중 생성 기록이 있다, **실행** 공유 확장이 실행된다, **결과** 등록 실패 문구가 아니라 1과 같은 생성 중 안내 상태가 표시된다.
3. **전제** 진행 중 생성 기록이 없다(기록이 없거나 모두 완료·실패했거나 보관 기한이 지났다), **실행** 공유 확장이 실행된다, **결과** 기존과 같이 저장소 조회 후 등록 가능 상태가 표시된다.
4. **전제** 공유 확장이 등록 가능 상태를 표시하는 동안 앱에서 다른 저장소의 생성이 시작되었다, **실행** 사용자가 등록을 실행한다, **결과** 등록 요청 없이 생성 중 안내 상태로 전환된다.
5. **전제** 생성 중 안내 상태가 표시되어 있다, **실행** 사용자가 닫기를 선택한다, **결과** 공유 확장이 종료되어 호스트 앱으로 돌아가고, 공유된 URL은 보관되거나 이후 자동으로 등록되지 않는다.
6. **전제** 생성 기록을 읽지 못해 생성 진행 여부를 확인할 수 없다, **실행** 공유 확장이 판정한다, **결과** 저장소 조회와 등록 요청 없이 확인 실패 안내와 재시도·닫기 동작이 표시된다.
7. **전제** 확인 실패 안내가 표시되어 있고 생성 기록을 다시 읽을 수 있게 되었다, **실행** 사용자가 재시도를 선택한다, **결과** 생성 진행 판정부터 다시 수행해 결과에 따라 생성 중 안내 또는 저장소 조회로 진행한다.

---

### 시나리오 2 - 공유 확장이 앱과 같은 기준으로 생성 진행 여부를 판정한다 (우선순위: P2)

개발자는 공유 확장의 생성 진행 판정이 앱 홈 잠금과 같은 생성 상태와 같은 기준을 쓰는지 자동 테스트로 확인할
수 있다. 공유 확장 기능은 생성 요청 전체 기능이 아니라 현재 생성 상태를 한 번 읽는 단순한 경계만 받으므로,
테스트는 그 경계의 대역만으로 공유 확장 흐름을 검증한다.

**주요 행위자**: 개발자

**우선순위 이유**: 두 경로의 판정 기준이 어긋나면 한쪽에서는 막히고 다른 쪽에서는 열리는 불일치가 다시
생긴다. 판정 경계가 단순해야 공유 확장 테스트가 생성 관찰 전체에 의존하지 않는다.

**독립 테스트**: 같은 생성 상태(진행 중 기록 있음, 완료만 있음, 실패만 있음, 기록 없음)를 앱 홈 잠금 판정과
공유 확장 판정에 각각 입력해 결론이 모두 같은지, 공유 확장 기능 테스트가 단순화된 경계의 대역만으로
구성되는지 확인한다.

**수용 시나리오**:

1. **전제** 진행 중 단계의 생성 요청이 하나 이상 있는 생성 상태다, **실행** 공유 확장 판정을 수행한다, **결과** 생성 중으로 판정되고 앱 홈도 같은 상태에서 잠긴다.
2. **전제** 생성 요청이 모두 완료 또는 실패 단계이거나 요청이 없는 생성 상태다, **실행** 공유 확장 판정을 수행한다, **결과** 생성 중이 아니라고 판정되고 앱 홈도 같은 상태에서 잠기지 않는다.
3. **전제** 공유 확장 기능 테스트를 작성한다, **실행** 현재 생성 상태 조회 대역을 주입한다, **결과** 생성 요청 기능 전체의 관찰 동작 없이 조회 결과(생성 상태 또는 읽기 실패)만으로 흐름을 검증할 수 있다.

### 예외·경계 사례

- 공유 확장의 판정 순서는 URL 로컬 판정 → 로그인 필요·앱 실행 필요 판정 → 생성 진행 판정 → 저장소 조회다. URL 오류, 로그인 필요, 앱 실행 필요 상태는 기존대로 먼저 표시되고, 이때는 생성 진행 판정을 하지 않는다.
- 저장소 조회 실패로 실패 상태가 된 뒤 조회를 재시도할 때도 조회 전에 생성 진행 판정을 다시 한다.
- 프로젝트 식별자가 아직 연결되지 않은 진행 중 기록(등록 응답 전)도 진행 중으로 본다.
- 결과가 도착해 완료·실패로 바뀐 기록은 막지 않는다. 앱 홈과 같이 진행 중 단계만 기준으로 삼는다.
- 요청 후 보관 기한(1시간)이 지난 진행 중 기록은 진행 중으로 보지 않는다. 앱과 같은 생성 상태 규칙을 따른다.
- 생성은 끝났지만 결과를 받지 못해 진행 중 기록이 보관 기한(1시간)까지 남아 있으면 공유 확장도 앱 홈과 같이 생성 중으로 판정한다. 공유 확장은 알림 센터의 결과 알림을 생성 기록에 반영하지 않으며, 생성 중 안내 문구로 앱을 열어 최신 상태를 반영하도록 안내한다. 앱은 활성화될 때 기존 동기화로 이 기록을 정리한다.
- 생성 중 안내 상태를 표시한 뒤 공유 확장이 열려 있는 동안 진행 중 생성이 끝나도 안내 상태를 자동으로 바꾸지 않는다. 사용자는 닫고 다시 공유한다.
- 생성 중 안내 상태에는 재시도 동작을 두지 않는다. 확인 실패 안내 상태에만 재시도 동작을 둔다.
- 등록 직전 판정에서 확인에 실패해도 등록 요청을 보내지 않고 확인 실패 안내 상태로 전환한다. 이때 재시도는 생성 진행 판정부터 다시 수행한다.
- 공유 확장의 등록 요청 중에는 기존 027 FR-015에 따라 추가 실행이 막힌다. 이 기능은 그 규칙을 바꾸지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 공유 확장에서 로그인 상태가 확인된 뒤 저장소를 조회하기 전에, 진행 중인 생성이 있는지 판정해야 한다. 판정 기준은 앱 홈의 불러오기 잠금과 같아야 하며, 보관 기한 안의 진행 중 단계 생성 요청이 저장소와 무관하게 하나라도 있으면 생성 중으로 본다.
- **FR-002**: 시스템은 생성 중으로 판정하면 저장소 조회와 등록 요청을 보내지 않고 생성 중 안내 상태로 전환해야 한다. 이 상태는 닫기 동작을 제공하고 재시도 동작을 제공하지 않아야 한다.
- **FR-003**: 시스템은 사용자가 등록을 실행하면 등록 요청 직전에 생성 진행 여부를 다시 판정하고, 생성 중이면 등록 요청 없이 생성 중 안내 상태로 전환해야 한다.
- **FR-003a**: 시스템은 생성 기록을 읽지 못해 생성 진행 여부를 확인할 수 없으면 저장소 조회와 등록 요청을 보내지 않고 확인 실패 안내 상태로 전환해야 한다. 이 상태는 재시도와 닫기 동작을 제공하며, 재시도는 생성 진행 판정부터 다시 수행해야 한다. 확인 실패를 생성 중이 아닌 것으로 간주해 등록을 허용하지 않아야 한다.
- **FR-004**: 시스템은 생성 중 안내 상태로 끝난 공유의 URL을 보관하거나 이후 자동으로 등록하지 않아야 한다.
- **FR-005**: 시스템은 생성 중이 아니라고 판정하면 기존 공유 확장 흐름(027)을 바꾸지 않아야 한다.
- **FR-006**: 시스템은 생성 중 안내 문구를 본 앱의 "문제 생성 중" 표기와 같은 의미로 제공하고, 본 앱을 열면 최신 생성 상태가 반영된다는 복구 안내를 함께 제공해야 한다. 이 안내는 본 앱을 실행하거나 본 앱 화면으로 이동시키지 않아야 한다(027 FR-025). 또한 확인 실패 안내 문구는 생성 상태를 확인하지 못했음을 알리는 의미로 제공해야 한다. 두 문구는 기존 공유 확장 문구와 같이 현지화 문자열 경로로 관리해야 한다.
- **FR-007**: 시스템은 생성 중으로 판정하거나 생성 진행 여부 확인에 실패해 공유 등록을 막은 사실을 구분해 기존 공유 확장 로컬 진단 로그 방식으로 남겨야 하며, 토큰·개인정보는 기록하지 않아야 한다.
- **FR-008**: 공유 확장 기능은 생성 진행 여부를 기존 생성 요청 기능이 제공하는 생성 상태(`ProjectGenerationState`)를 그대로 사용해 판정해야 한다. 이 판정을 위해 새 Domain 상태 모델을 추가하지 않아야 한다.
- **FR-009**: 공유 확장 기능은 생성 진행 판정에 생성 요청 UseCase 전체가 아니라 현재 생성 상태를 한 번 읽는 단순화된 경계(클로저)만 사용해야 하며, 판정에 필요한 생성 상태는 그 경계를 통해서만 받아야 한다. 이 경계는 FR-011의 같은 생성 요청 UseCase가 제공하는 생성 상태를 그대로 전달할 뿐이며, 공유 확장 기능은 그 상태를 Domain의 "생성 중" 판정 규칙으로만 해석하고 별도의 판정 로직이나 판정 전용 타입을 두지 않아야 한다(명확화 2026-09-29). 공유 확장의 하위 등록 Feature는 저장소 조회·생성 요청·현재 생성 상태 조회 클로저 3개만 받아야 하며, 저장소 조회 UseCase와 생성 요청 UseCase 전체를 받지 않아야 한다. 루트 공유 확장 Feature의 공개 initializer는 바꾸지 않아야 한다(명확화 2026-09-29).
- **FR-010**: 이 변경은 본 앱의 홈 잠금 결과(023), 생성 기록 저장 규칙, 서버 API를 바꾸지 않아야 한다.
- **FR-011**: 본 앱과 공유 확장은 생성 상태 확인과 생성 요청에 같은 생성 요청 UseCase(`ProjectGenerationUseCase`)를 사용해야 하며, 보관 기한·중복·결과 반영 규칙을 경로마다 따로 구현하지 않아야 한다. "생성 중" 판정 규칙(진행 중 단계 요청이 하나라도 있으면 생성 중)은 한 곳에서 정의되어 앱 홈 잠금과 공유 확장 판정이 같은 규칙을 사용해야 한다.
- **FR-012**: 공유 확장 흐름의 소스와 테스트는 이 기능의 동작 변경 전에 동작 변경 없는 이동으로 Feature 흐름 배치 컨벤션을 따르는 화면 폴더(`Feature/ShareRegistration/ShareRegistration/`)와 같은 축의 테스트 폴더(`Feature/Tests/ShareRegistration/ShareRegistration/`)로 정리되어야 한다. 이동은 기존 자동 테스트 결과를 바꾸지 않아야 한다(명확화 2026-09-29).

### 핵심 엔터티

- **생성 상태**: 기존 생성 요청 기능이 제공하는 생성 요청 목록과 각 요청의 단계(진행 중·완료·실패). 앱 홈 잠금과 공유 확장 판정이 공유하는 입력이다.
- **생성 진행 여부**: 공유 확장이 현재 생성 상태 조회 결과로 도출하는 판정 결과이며 별도 타입으로 두지 않는다. 생성 중, 생성 중 아님, 확인 실패 중 하나다. 생성 상태에 진행 중 단계 요청이 하나라도 있으면 생성 중이고, 생성 기록을 읽지 못하면 확인 실패다.
- **생성 중 안내 상태**: 공유 확장 화면 상태 중 하나. 생성이 진행 중이라 등록할 수 없음을 알리고 닫기만 제공한다.
- **확인 실패 안내 상태**: 공유 확장 화면 상태 중 하나. 생성 진행 여부를 확인하지 못해 등록할 수 없음을 알리고 재시도와 닫기를 제공한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 진행 중 생성 기록이 있는 상태로 공유 확장 흐름을 실행하는 자동 테스트 사례의 100%에서 저장소 조회와 등록 요청이 0회이고 생성 중 안내 상태가 표시된다.
- **SC-002**: 진행 중 생성 기록이 없는 상태(기록 없음, 완료만, 실패만, 보관 기한 경과)의 자동 테스트 사례 100%에서 공유 확장 흐름의 결과가 변경 전과 같다.
- **SC-003**: 등록 가능 상태 표시 후 진행 중 생성이 생긴 뒤 등록을 실행하는 자동 테스트 사례의 100%에서 등록 요청이 0회이고 생성 중 안내 상태로 전환된다.
- **SC-003a**: 생성 기록 읽기가 실패하는 자동 테스트 사례의 100%에서 저장소 조회와 등록 요청이 0회이고 확인 실패 안내 상태가 표시되며, 재시도 후 읽기가 성공하면 생성 진행 판정 결과에 따라 진행한다.
- **SC-004**: 같은 생성 상태를 입력한 자동 테스트 사례의 100%에서 공유 확장의 생성 진행 판정과 앱 홈 잠금 판정의 결론이 같다. "생성 중" 판정 규칙의 정의는 코드베이스에 한 곳뿐이다.
- **SC-005**: 기존 공유 확장, 생성 요청, 앱 루트 관련 자동 테스트가 변경 후에도 모두 통과한다.
- **SC-006**: 실기기에서 저장소 A의 생성이 진행 중일 때 저장소 B를 공유한 검증 사례에서 생성 중 안내가 표시되고, 앱으로 돌아왔을 때 진행 중 생성 기록이 A 하나뿐이다.

## 가정

- 공유 확장과 본 앱은 같은 공유 생성 기록 저장소를 사용하며, 공유 확장이 읽는 생성 상태는 앱이 홈 잠금에 쓰는 생성 상태와 같은 규칙(보관 기한 경과 기록 제외 등)으로 만들어진다.
- 생성 기록 읽기 실패는 기록이 없는 경우와 구분할 수 있어야 한다. 기존 생성 상태(`ProjectGenerationState`)가 이 구분을 제공하는지, 제공하지 않으면 공유 확장 경계가 어디서 구분을 받는지는 계획 단계에서 확인한다(명확화 2026-09-28).
- 공유 확장은 생성 상태 변화를 계속 관찰하지 않고 판정 시점마다 한 번 읽는다. 공유 확장은 짧게 머무는 화면이며 관찰을 유지할 필요가 없다.
- 생성 중 안내 화면은 기존 공유 확장의 안내 화면 구성(제목·설명·닫기)을 재사용한다. 전용 Figma 노드가 있으면 구현 시 그 노드를 따른다.
- 본 앱 안의 등록 진입(홈 불러오기)은 생성 중이면 이미 막혀 있으며(023) 이 기능의 범위가 아니다.
- 서버의 등록 API와 생성 규칙은 바꾸지 않는다.
- 공유 확장 흐름의 배치 정리(FR-012)는 파일 위치만 바꾸며, 타입 이름·공개 API·동작과 Tuist manifest는 바꾸지 않는다. 다른 흐름이 함께 쓰는 선언의 배치 문제는 이 기능의 범위가 아니다.
