### 6차 검증 (2026-09-02) — `/speckit-analyze` 잔여 지적 정리

잔여 지적 6건(M3 · M1 · I1 · I2 · D1 · G2·G3)을 반영했다. 체크박스 16개 전부 통과를 유지한다.

- **사실 오류 정정(M3)**: "토큰 — 이름 불일치" 문단이 근거 없는 주장을 담고 있었다. 저장소
  조사 결과 `GradientToken.all`은 5개로 규격 `GRADIENTS` 5행과 **이미 일치**하고,
  `topToBottomStart`·`topToBottomEnd`는 `private` `UnitPointRatio` 방향 상수이지 토큰이 아니며,
  규격에 있다고 적혀 있던 `topStart`·`bottomEnd`는 **네 규격 문서 어디에도 없다**
  (`reference-swift/GradientToken.swift`가 같은 두 방향 상수를 그 이름으로 두지만 그쪽도
  `private`이고 값이 같아 공개 계약이 아니다). 문단과
  FR-008, 경계 사례 항목을 실제 상태로 바꿨다. 남은 실제 과제는 `all`에 없고 사용처 0건인
  `gradient4`의 제거뿐이며, 삭제이므로 승인 대상으로 명시했다.
- **판정 불가 해소(M1)**: SC-004의 "레이아웃 변수 11종"이 무엇을 검사해야 통과인지 정하지
  못했다. Responsive Layout Spec의 `METRICS`는 11행(`headerHeight` 포함)인데 계약은 §07이
  확정한 `tabBarBottomInset`·`sheetMaximumHeight`를 더해 다루고 `headerHeight`는 헤더 종류가
  소유한다. 13종으로 명시하고 소유 주체를 나눠 적었다.
- **명세와 계획의 충돌 해소(I1)**: SC-013이 "pre-commit에서 실행된다"였으나 조사(R-05)와 작업
  목록은 "등록만, 활성화 안 함"으로 좁혀 두 산출물이 문자 그대로 충돌했다. 실제 판정 기준으로
  문구를 확정했다. 활성화는 협업 영향이 있는 별도 결정이라 범위 밖임을 명시했다.
- **문구 정합(I2)**: SC-012의 "기존 테스트가 100% 통과"가 `TextField` 높이 56→52처럼 규격
  반영으로 기대값을 갱신하는 작업과 충돌했다. 갱신한 테스트를 포함한 전체 통과로 바꿨다.
- **중복 제거(D1)**: FR-021이 FR-033의 개별 사례를 중복 규정해 접근성 라벨 조항을 FR-033
  참조로 정리했다. 요구 내용은 동일하다.
- **검증 수단 확보(G2·G3)**: FR-018(세로 고정)과 FR-037(Dynamic Type 미지원 유지)에 판정
  수단이 없었다. FR-042의 정적 검사 대상에 "종횡비·웹 콘텐츠 밖의 세로 채움"과 "Dynamic Type
  연동 API 사용"을 추가했다.

**요구사항 ID 무결**: FR-001~FR-043 43개, SC-001~SC-015 15개로 이번 정정에서 번호를 추가하거나
제거하지 않았다.

**후속 정합성 필요**: `/speckit-plan`이 data-model.md의 `GradientToken` 행(현재 8은 `private`
상수 2개를 센 값)과 파생값 개수, contracts의 GradientToken 절과 정적 검사 규칙 2종을,
`/speckit-tasks`가 T009·T023·T059·T062·T084를 맞춰야 한다.


### 5차 검증 (2026-09-02) — `/speckit-analyze` 지적 반영

`/speckit-analyze`가 찾은 인벤토리 오류 1건을 정정했다. 체크박스 16개 전부 통과를 유지한다.

- **정정 내용**: "규격 인덱스에 없는 기존 컴포넌트 11종"이 실제로는 15종이었다. Design System
  Spec의 `COMPONENT_INDEX` 33행(UI 소관 30항목)을 `sources/Projects/UI/Component`의 실제 파일과
  대조해 `ScreenContainer` · `StyledText` · `EmptyState` · `PolicyAgreementRow` 4종이 규격
  인덱스에도, 기존 11종 목록에도 없음을 확인했다.
- **영향**: SC-008이 "15종 전부"를 요구하므로 이 4종도 판정과 근거 기록 대상이 된다. 이전
  문구대로면 4종이 판정 없이 통과했다.
- **함께 확인한 사실**: 같은 대조에서 인덱스와 코드의 **역할 폴더 불일치는 0건**이고 결손은
  `Chip` · `BookmarkButton` · `ChoiceResultRow` 3건뿐이었다. SC-007은 신설 3종이 지정 폴더에
  들어가면 충족된다.
- **수정한 위치**: spec.md의 6곳(차이 목록 제목·목록·명확화 기록·시나리오 4 설명·수용 시나리오
  3·FR-029·SC-008). 토큰 카테고리 11종과 레이아웃 변수 11종은 다른 개념이라 그대로 두었다.
- **검증 항목 재확인**: "요구사항이 검증 가능하고 모호하지 않다"는 판정 대상이 명시적으로
  열거되어 이전보다 강화되었다. 나머지 15개 항목은 이 델타의 영향을 받지 않는다.

**후속 정합성 필요**: [tasks.md](../tasks.md)의 T064 판정 대상 표가 11개 파일 집합이라 4종을
추가해야 한다. 이 스킬은 `spec.md`와 이 체크리스트만 수정할 수 있으므로 `/speckit-tasks`가
처리한다.

**기존 형식 결함(미수정)**: "판단이 필요했던 항목과 선택한 기본값" 표의 마지막 두 행이 단락
뒤로 떨어져 표 밖에 렌더된다. 이번 델타와 무관한 기존 상태라 보존했다.

계획 수립 뒤 명세를 다시 스캔해 명확화 3건을 반영했다. 체크박스 16개 전부 통과를 유지한다.

- **해소된 모호성**: (1) UIUX Guide의 타이포 적용 규칙이 요구사항에 사실상 빠져 있어 작업

  없던 문제.
- **범위 축소**: 타이포 적용과 폰트 설정은 현행을 유지한다. `TextStyleToken` 13종 값도 이
  기능에서 바꾸지 않는다. "알려진 차이" 섹션을 신설해 확인된 규격 위반 2건을 기록만 했다.
- **변경된 요구사항**: FR-029(판정 시점·주체·삭제 확인) · FR-037(회귀 방지 기준임을 명시) ·

- **새 섹션**: `## 알려진 차이 (이 기능에서 해소하지 않음)` — 성공 기준에서 제외되는 항목을
  명시적으로 분리해, 규격 준수 판정 시 예외임을 남겼다.

**계획 산출물과의 정합성**: 이 스킬은 `spec.md`와 이 체크리스트만 수정할 수 있다. 타이포
범위 축소로 [data-model.md](../data-model.md)의 `TextStyleToken` 행("값 대조")과
[contracts/design-token-catalog.md](../contracts/design-token-catalog.md)의 관련 서술이
현재 명세보다 넓다. 계획 산출물 갱신이 필요하다.

### 2차 검증 (2026-09-02) — Responsive Layout Spec 반영 후

원본 문서 묶음에 첨부되지 않은 문서 3종이 더 있음을 확인하고, 그중 UI 패키지 범위에
해당하는 `Responsive Layout Spec`을 명세에 반영한 뒤 재검증했다. 전 항목 통과.

- **추가된 요구사항**: 반응형 레이아웃 FR-010~FR-018 (레이아웃 변수 11종, 계산식, 골격
  계층 크기 규칙, 크기 결정 방식 4종), 컴포넌트 FR-023(`TextField` 재작도).
- **추가된 성공 기준**: SC-004(기기 9종 범위 검증) · SC-005(정본 고정값 사용처 0곳) ·
  SC-006(고정 폭 사용처 축소).
- **시나리오 재정렬**: 골격은 20개 화면 전부가 공유하고 기기 양 끝(SE·Air)에서 어긋남이
  가장 크므로 반응형을 P2로 두고, 개별 화면에 영향이 국한되는 컴포넌트 신설을 P3으로 내렸다.
- **제외 범위 명시**: `Screen Layouts`와 `Screen Layouts v2`는 화면별 좌표·구성이라 Feature
  범위로 판단해 이 기능에 포함하지 않았다.
- **문서 보관 위치 변경**: 규격 문서와 참조 구현이 `.gitignore` 대상인 `private/`에 있어
  다른 개발자와 CI가 볼 수 없었으므로 `specs/024-ui-design-spec-alignment/design-specs/`와
  `reference-swift/`로 옮겼다. 파일명은 저장소 문서 관례에 맞춰 kebab-case로 바꿨다.
  Swift 포맷·린트 훅은 `sources/Projects`로 범위가 한정되어 있어 참조 구현 41개 파일은
  검사 대상이 아니다.

### 1차 검증 (2026-09-02)

전 항목 통과. 확인한 근거는 다음과 같다.

- **결과 중심 확인**: 토큰 요구사항(FR-001~FR-009)은 "어떤 값이 존재해야 하는가"를
  기술하며 Swift 타입 구조나 파일 배치를 지정하지 않는다. FR-003의 "레이어 2개를 표현할 수
  있는 구조"는 설계 선택이 아니라 `sheetElevation`이 2레이어라는 규격 사실에서 오는 제약이다.
- **고정 제약 명시**: 토큰과 컴포넌트 이름은 규격 문서가 확정한 명칭이므로 원문을 유지했다.
  Constitution 원칙 10과 충돌하지 않는다.
- **측정 가능성**: 모든 성공 기준이 개수·비율·통과 여부로 판정 가능하다. 토큰 개수 6·6·2,
  규격 밖 컴포넌트 11종, 역할 폴더 6종 각 1개 이상으로 수치가 확정되어 있다. (번호는 이후
  검증에서 재부여되었으므로 항목 내용으로 적는다.)
- **검증 가능성**: 각 FR이 코드 검사 또는 테스트로 판정 가능하다. FR-019·FR-020은 판정 결과와
  근거 기록의 존재로 확인한다.
- **범위 한정**: Feature 패키지 화면 재구성, Figma 파일 리네이밍, 화면 흐름 변경을 명시적으로
  제외했다.

### 판단이 필요했던 항목과 선택한 기본값

명세 작성 중 여러 해석이 가능했던 세 항목은 [NEEDS CLARIFICATION]으로 남기지 않고 아래
기본값을 선택해 "가정"에 기록했다. 계획 단계에서 뒤집을 수 있다.

| 항목 | 선택한 기본값 | 근거 |
| --- | --- | --- |
| Feature 패키지 화면 재구성 포함 여부 | 제외 | 사용자 요청이 "UI 패키지 리팩토링"으로 대상을 지정했다 |
| 추가 문서 3종 반영 범위 | `Responsive Layout Spec`만 반영 | 사용자 확인. 나머지 2종은 화면별 레이아웃이라 Feature 범위 |
| 규격 문서 보관 위치 | 기능 디렉터리로 이동 | 사용자 지시. `private/`는 gitignore 대상이라 공유되지 않는다 |
| 규격 인덱스에 없는 컴포넌트 15종 | 기본은 유지, 삭제는 사용처 없음 확인 시에만 | 사용 중인 컴포넌트를 지우면 화면이 깨진다 |
| `private/swift/` 참조 구현 사용법 | 값·계약 근거로만 사용하고 저장소 컨벤션으로 재작성 | 참조 구현이 `+` 대신 `-` 파일명을 쓰는 등 이 저장소 규칙과 다르다 |

3차 검증에서 위 표의 첫 항목("Feature 패키지 화면 재구성 포함 여부 = 제외")은 유지하되
경계를 좁혔다. 호출부의 컴파일 복구는 포함이고, 화면 구조를 규격의 Screen·Sub View 체계로
옮기는 작업은 여전히 제외다.

나머지 세 항목은 `/speckit-clarify`에서 사용자 확인으로 확정되어 더 이상 기본값이 아니다.

## 7차 검증 (2026-09-02, 잔여 산출물 정합)

6차 정정 뒤 남은 파생 산출물의 사실 불일치를 정리했다. 체크박스 16개 전부 통과를 유지한다.

## 8차 검증 (2026-09-02, 재분석 편집안 반영)

재분석에서 확인한 실행 불가·자기 모순 항목을 명세에 반영했다. 체크박스 16개 전부 통과를
