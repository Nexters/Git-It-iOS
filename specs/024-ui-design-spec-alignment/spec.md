**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/ui-design-spec-alignment`

**브랜치 상태**: `생성`

**생성일**: 2026-09-02

**상태**: 초안

**입력**: 사용자 설명: "파일들을 통해 UI 패키지 리팩토링 — 첨부 문서: Screen Hierarchy Spec.dc.html, UIUX Guide.dc.html, Design System Spec.dc.html"

## 배경

네 규격 문서가 Figma 정본 실측을 근거로 UI 계층의 정본(canonical) 값과 계약을 확정했습니다.
문서는 이 기능 디렉터리의 [`design-specs/`](./design-specs)에 함께 보관합니다.

| 문서 | 확정한 것 |
| --- | --- |
| [Design System Spec](./design-specs/design-system-spec.dc.html) | 토큰 11개 카테고리의 이름·값, 컴포넌트 인덱스 33행, Figma→Swift 리네이밍 표, 결함 F-01~F-17 |
| [UIUX Guide](./design-specs/uiux-guide.dc.html) | 레이아웃 리듬 7항, Figma auto-layout→SwiftUI 매핑 20항, 타이포 13종과 적용 규칙 6항, 상태 매트릭스 10행, 접근성 7항, 기기 9종 대응, 햅틱 4지점 |
| [Screen Hierarchy Spec](./design-specs/screen-hierarchy-spec.dc.html) | Screen·Sub View·Component 3계층 판정 기준, 상태 소유 규칙 6항, List/Stack/HScroll 반복 구조 분류 16행, 확정 사항 9항 |
| [Responsive Layout Spec](./design-specs/responsive-layout-spec.dc.html) | 기기 폭 375–440 대응 원칙 4항, 런타임 레이아웃 변수 11종과 계산식, 크기 규칙 4종, 골격 계층 8종의 크기·정렬, 정본 근거 없던 3건의 확정값 |

참조 구현은 [`reference-swift/`](./reference-swift)에 있습니다. 토큰 12개 파일, 적용 확장
7개, 컴포넌트 21개로 규격 값과 공개 계약의 근거이며 그대로 이식할 대상은 아닙니다.

네 규격 문서가 실측한 원본은 Figma 파일 `넥터 Git-it (MCP)`입니다. 규격 문서와 코드가
어긋나거나 문서에 없는 값을 확인해야 할 때 최종 근거로 사용합니다. 파일 위치와 취급은
아래 "의존성"에 있습니다.

현재 `sources/Projects/UI`는 이 규격보다 앞서 만들어졌고, 대조 결과 토큰 3종이 빈 배열로
선언만 되어 있는 등 확인 가능한 차이가 있습니다. 이 명세는 그 차이를 해소해 UI 패키지가
규격 문서를 정본으로 삼도록 정렬하는 것을 목표로 합니다.

### 확인된 현재 상태와 규격의 차이

아래는 `sources/Projects/UI`와 규격 문서를 대조해 실제로 확인한 차이입니다.

**토큰 — 선언만 있고 값이 비어 있음**

| 토큰 | 현재 | 규격 요구 |
| --- | --- | --- |
| `BorderToken.all` | `[]` (빈 배열) | 6종 — default·focus·highlight·error·tabBar·loadingTrack |
| `OpacityToken.all` | `[]` (빈 배열) | 6종 — disabled·subtleSurface·tabSurface·track·border·scrim |
| `EffectToken.all` | `[]` (빈 배열) | 2종 — sheetElevation(2레이어)·cardElevation |

**토큰 — 항목 누락 (16종)**

| 토큰 | 누락 항목 |
| --- | --- |
| `ColorToken` | `black25` · `black35` · `black45` · `blue300Alpha10` · `blue300Alpha24` (5) |
| `SemanticColorToken` | `tabBarSurface` · `tabBarBorder` · `selectedSurface` · `grabber` · `disabledText` (5) |
| `LayoutToken` | `cardHorizontalPadding`(18) · `cardTopPadding`(14) · `iconSpacing`(6) · `tightSpacing`(4) (4) |
| `CornerRadiusToken` | `pill`(999) (1) |
| `ControlSizeToken` | `minimumTouch`(44) (1) |

**토큰 — 규격 밖 항목**

`GradientToken.all`은 규격 목록 5종(`gradient1`·`gradient2`·`gradient3`·`topEdgeScrim`·
`bottomEdgeScrim`)과 이미 일치합니다. 다만 `gradient4`가 public으로 정의되어 있으면서 `all`에
포함되지 않고 `sources/Projects` 전체 사용처도 0건입니다. `topToBottomStart`·`topToBottomEnd`는
`private` 방향 상수(`UnitPointRatio`)이지 토큰이 아니므로 규격 대조 대상이 아닙니다.

**반응형 — 런타임 레이아웃 변수가 없음**

`LayoutMetrics`에 해당하는 타입이 `sources/Projects` 전체에 존재하지 않습니다. 규격은 화면
폭·높이·safe area 셋만 기기에서 읽고 나머지 8종을 계산식으로 유도하도록 정의합니다.

| 변수 | 계산식 | 범위 | 현재 |
| --- | --- | --- | --- |
| `screenWidth` | 기기 | 375 – 440 | 없음 |
| `screenHeight` | 기기 | 667 – 956 | 없음 |
| `safeAreaTop` | 기기 | 20 – 68 | 없음 |
| `safeAreaBottom` | 기기 | 0 – 34 | 없음 |
| `contentWidth` | `screenWidth − margin × 2` | 335 – 400 | 없음 |
| `gridColumn2` | `(contentWidth − gutter) / 2` | 161.5 – 194 | 없음 (정본 154 사용 금지) |
| `gridColumn3` | `(contentWidth − gutter × 2) / 3` | 103.67 – 125.33 | 없음 |
| `headerHeight` | `ScreenHeader.Style` | 50 · 64 · 98 · 120 | 없음 |
| `topScrimHeight` | `safeAreaTop + headerHeight` | 70 – 188 | 없음 (정본 103 사용 금지) |
| `bottomScrimHeight` | `safeAreaBottom + (탭바 ? 93 : 0)` | 0 – 127 | 없음 |
| `contentBudget` | `screenHeight − safeAreaTop − safeAreaBottom − headerHeight − tabBarClearance(92)` | 435 – 718 | 없음 |

UI 패키지에서 safe area를 읽는 컴포넌트는 `SheetSurface` 하나뿐이고, `ScreenEdgeScrim`은
읽지 않습니다. 스크림 높이가 헤더 타입과 safe area에 따라 70에서 188까지 달라져야 하는데
현재는 그 입력이 없습니다.

**반응형 — 고정 폭 사용**

`Component/` 아래에 `.frame(width:` 호출이 56곳 있습니다. 규격 원칙 P4는 고정 폭을 종횡비가
의미를 갖는 요소(이미지 썸네일·로딩 애니메이션·가로 스크롤 카드)로 한정하고, 버튼·행·카드·
텍스트는 모두 콘텐츠 폭을 채우도록 요구합니다.

**컴포넌트 — 규격이 요구하나 코드에 없음 (4종)**

`Controls/Chip` · `Controls/PressOverlayStyle` · `Controls/BookmarkButton` ·
`CollectionItems/ChoiceResultRow`

**컴포넌트 — 규격이 Sub View로 분류 (2종)**

`Component/Displays/QuestionPrompt`와 `Component/Controls/EssayAnswerInput`은 Screen Hierarchy
Spec의 Sub View 카탈로그에 각각 `QuestionPrompt`, `AnswerEditor`로 실려 있습니다. Sub View는
자기 영역의 상태를 소유하므로 "아무 상태도 소유하지 않는" Component 계층의 정의와 충돌합니다.

**컴포넌트 — 규격 인덱스에 없는 기존 컴포넌트 (15종)**

`SelectionCardStyle` · `AccountActionRow` · `LabeledTextField` · `SelectableSettingRow` ·
`LaunchLogo` · `OnboardingMockup` · `RubricView` · `SplashView` · `WebContentView` ·
`WebSheet` · `TabShellPreviewItem` · `ScreenContainer` · `StyledText` · `EmptyState` ·
`PolicyAgreementRow`

뒤의 4종은 Design System Spec의 컴포넌트 인덱스 33행에 행이 없고 화면 구성 설명이나 파일
목록에만 등장합니다. `ScreenContainer`는 FR-027이 화면 좌우 여백 소유자로 지정한 필수
컴포넌트이고, `EmptyState`는 UIUX Guide 상태 매트릭스에는 행이 있으나 인덱스에는 없습니다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 디자인 토큰 정본 완성 (우선순위: P1)

Feature 패키지를 구현하는 개발자가 화면을 만들 때 필요한 값을 토큰에서 전부 찾을 수 있고,
찾지 못해 숫자를 직접 적어 넣을 이유가 없어집니다. 현재는 테두리·불투명도·그림자 토큰이 빈
배열이라 이 세 종류의 값을 쓰려면 반드시 하드코딩해야 합니다.

**주요 행위자**: UI 패키지를 사용하는 Feature 개발자

**우선순위 이유**: 컴포넌트 구현과 화면 구현이 모두 토큰 위에 놓입니다. 토큰이 비어 있으면
그 위의 모든 작업이 하드코딩으로 시작하므로, 이것을 먼저 해소하지 않으면 나머지 시나리오가
규격 위반을 새로 만들어 냅니다.

**독립 테스트**: `DesignTokenSet.current.validate()`가 빈 배열을 반환하고, 규격 문서의 토큰
이름 목록과 코드의 토큰 이름 집합이 일치하는지 검사하는 테스트만으로 화면 렌더링 없이
전체를 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** `BorderToken.all`이 빈 배열인 상태에서, **실행** 규격의 선 6종을 정의하면,
   **결과** `BorderToken.all`이 6개를 반환하고 각 항목의 굵기와 색 토큰 참조가 규격 표와
   일치한다.
2. **전제** `OpacityToken.all`과 `EffectToken.all`이 빈 배열인 상태에서, **실행** 규격의
   불투명도 6종과 그림자 2종을 정의하면, **결과** 각각 6개와 2개를 반환하고 `sheetElevation`은
   레이어 2개를 갖는다.
3. **전제** 누락 토큰 16종이 없는 상태에서, **실행** 규격 값으로 추가하면, **결과** 규격
   문서에 나열된 모든 토큰 이름이 코드에 존재한다.
4. **전제** 토큰을 모두 채운 상태에서, **실행** `DesignTokenSet.current.validate()`를 호출하면,
   **결과** 이름 중복·값 범위·참조 무결성 위반이 없어 빈 배열을 반환한다.

### 시나리오 2 - 반응형 레이아웃 변수와 골격 계층 정렬 (우선순위: P2)

화면 골격이 기기에서 읽은 값으로 계산되어, 지원 기기 9종 어디에서도 스크림·탭바·시트가
어긋나지 않습니다. 현재는 런타임 레이아웃 변수가 없어 스크림 높이와 그리드 열 폭이 정본
캔버스(360 × 800) 수치에 묶여 있고, 그 수치는 실기기 어느 것과도 일치하지 않습니다.

**주요 행위자**: 최종 사용자(모든 지원 기기)와 UI 패키지를 사용하는 Feature 개발자

**우선순위 이유**: 골격은 20개 화면 전부가 공유합니다. 스크림 높이나 탭바 인셋이 틀리면 한
화면이 아니라 모든 화면이, 그리고 SE(safe area 20/0)와 Air(68/34) 같은 양 끝 기기에서 특히
크게 어긋납니다. 토큰 다음으로 파급이 큽니다.

**독립 테스트**: 레이아웃 변수를 값 계산 함수로 두고 지원 기기 9종의 입력을 넣어 규격의
min–max 범위와 대조하면 화면 렌더링 없이 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** 런타임 레이아웃 변수가 없는 상태에서, **실행** 화면 폭·높이·safe area 셋을
   입력으로 받아 나머지 8종을 유도하는 계산을 도입하면, **결과** 지원 기기 9종 전부에서 각
   변수가 규격의 min–max 범위 안에 들어간다.
2. **전제** 상단 스크림 높이가 고정값인 상태에서, **실행** `safeAreaTop + headerHeight`로
   계산하면, **결과** plain 헤더의 SE에서 70, largeTitle 헤더의 Air에서 188이 되고 헤더 타입이
   바뀌면 높이가 따라간다.
3. **전제** 2열 그리드가 정본 값 154를 쓰는 상태에서, **실행** `(contentWidth − gutter) / 2`로
   바꾸면, **결과** 폭 375에서 161.5, 폭 440에서 194가 되어 콘텐츠 폭을 남김없이 나눈다.
4. **전제** 시트가 비율 detent를 쓰는 곳이 있으면, **실행** 규격을 적용하면, **결과** 시트
   높이는 콘텐츠를 따르고 상한은 `screenHeight − safeAreaTop − 16`이며, 콘텐츠가 상한을
   넘으면 시트 안에서 스크롤한다.
5. **전제** 탭바 하단 여백이 고정값인 상태에서, **실행** 규격을 적용하면, **결과** 하단
   여백이 `max(safeAreaBottom, 24)`가 되어 홈 인디케이터가 없는 SE에서도 24가 유지된다.
6. **전제** 종횡비와 무관한 요소가 고정 폭을 갖는 상태에서, **실행** 크기 규칙 4종을
   적용하면, **결과** 버튼·행·카드·텍스트는 콘텐츠 폭을 채우고, 고정 폭은 종횡비가 의미를
   갖는 요소와 규격이 직접 확정한 `TabShell` 298에만 남는다.

### 시나리오 3 - 규격 컴포넌트 신설과 상태 계약 정렬 (우선순위: P3)

규격이 요구하는 컴포넌트 4종이 UI 패키지에 생기고, 기존 컴포넌트의 상태별 표현이 UIUX
Guide의 상태 매트릭스와 일치합니다. 현재는 필터 칩과 채점 결과 행이 없어 저장 문제 화면과
서술형 채점 화면을 규격대로 만들 수 없습니다.

**주요 행위자**: UI 패키지를 사용하는 Feature 개발자

**우선순위 이유**: 없는 컴포넌트는 해당 화면 구현을 막고, 상태 표현이 어긋난 컴포넌트는
화면마다 서로 다른 눌림·비활성 표현을 낳습니다. 다만 영향 범위가 골격보다 좁습니다.

**독립 테스트**: 신설 컴포넌트 4종 각각의 공개 생성 경로와 상태별 표현을 검사하는 계약
테스트로 검증할 수 있고, 기존 컴포넌트는 상태 매트릭스 10행을 표로 옮긴 테스트로 검증합니다.

**수용 시나리오**:

1. **전제** `Chip`이 없는 상태에서, **실행** 규격대로 추가하면, **결과** 선택 여부를 값으로
   받아 비선택은 `raisedBackground` 배경에 `blue100` 라벨, 선택은 `brandAccent` 배경에
   `grey700` 라벨로 그리고 반경은 `CornerRadiusToken.small`(8)을 쓴다.
2. **전제** `PressOverlayStyle`이 없어 컴포넌트마다 눌림 표현이 제각각인 상태에서, **실행**
   공용 누름 표현을 추가하면, **결과** `Component/` 프로덕션 코드의 모든 SwiftUI `Button`
   사용처가 눌림 시 `white30` 오버레이 하나만 사용한다.
3. **전제** `ChoiceResultRow`가 없는 상태에서, **실행** 추가하면, **결과** 정답·오답 축과
   접힘·펼침 축을 값으로 받고, 접힘과 펼침의 높이가 규격 값을 따르며, 스스로 펼침 상태를
   보관하지 않는다.
4. **전제** `BookmarkButton`이 없는 상태에서, **실행** 추가하면, **결과** 저장 여부를 값으로
   받고 동작 이름의 접근성 라벨을 필수 입력으로 요구한다.
5. **전제** `TextField` 높이가 규격과 다른 상태에서, **실행** 규격을 적용하면, **결과** 높이
   52, 반경 8, 내부 좌우 16, 상태별 테두리가 규격 표와 일치한다.

### 시나리오 4 - 계층 소유 규칙 정합 (우선순위: P4)

UI 패키지의 컴포넌트가 Screen Hierarchy Spec의 Component 계층 정의를 지킵니다. 곧 상태를
소유하지 않고, 화면 여백을 붙이지 않고, 햅틱을 울리지 않고, 데이터를 조회하지 않습니다.
규격 인덱스에 없는 기존 컴포넌트 15종은 유지·이동·삭제 중 하나로 판정하고 근거를 남깁니다.

**주요 행위자**: UI 패키지를 사용하는 Feature 개발자

**우선순위 이유**: 소유 규칙이 무너지면 같은 컴포넌트가 시트 안에서 여백이 두 번 붙거나,
펼침 같은 판정이 아닌 동작에 햅틱이 울립니다. 다만 앞의 시나리오와 달리 화면 구현을 막지는
않으므로 그다음입니다.

**독립 테스트**: 컴포넌트 공개 계약을 훑어 상태 보관·화면 여백·햅틱·데이터 조회가 있는지
검사하고, 규격 인덱스와 코드 컴포넌트 목록의 차집합이 판정 기록을 갖는지 확인합니다.

**수용 시나리오**:

1. **전제** 컴포넌트가 자체 상태를 보관하는 곳이 있으면, **실행** 계약을 점검하면, **결과**
   해당 상태가 상위(Sub View 또는 Screen)로 올라가고 컴포넌트는 값으로만 받는다.
2. **전제** 컴포넌트가 `LayoutToken.margin`을 직접 붙이는 곳이 있으면, **실행** 점검하면,
   **결과** 화면 좌우 여백은 `ScreenContainer`가 한 번만 붙인다.
3. **전제** 규격 인덱스에 없는 컴포넌트 15종이 있는 상태에서, **실행** 각각의 사용처를 조사해
   판정하면, **결과** 유지·이동·삭제 결정과 근거가 PR 본문에 기록되고, 유지 대상은 역할 폴더
   판정 순서를 따라 배치된다. 삭제로 판정한 항목은 확인을 받기 전까지 지우지 않는다.
4. **전제** `QuestionPrompt`와 `EssayAnswerInput`이 Component 계층에 있는 상태에서, **실행**
   Feature 패키지로 옮기면, **결과** UI 패키지의 Component 계층에 상태를 소유하는 타입이
   남지 않고, 두 타입이 쓰던 무상태 표현 조각은 UI에 컴포넌트로 남아 재사용 가능하다.

### 시나리오 5 - 접근성 계약 준수 (우선순위: P5)

UIUX Guide의 접근성 7항을 컴포넌트 공개 계약으로 강제합니다. 아이콘만 있는 버튼이 접근성
라벨 없이 만들어질 수 없고, 정답·오답이 색으로만 전달되지 않습니다.

**주요 행위자**: 보조 기술 사용자(최종 사용자)

**우선순위 이유**: 규격 준수 항목이지만 앞의 시나리오가 끝나야 대상 컴포넌트가 확정됩니다.
화면 동작을 막지는 않으므로 마지막입니다.

**독립 테스트**: 조작 컴포넌트의 터치 영역이 44pt 이상인지, 아이콘 전용 버튼이 접근성
라벨을 필수 인자로 받는지, 선택 상태를 갖는 컴포넌트가 선택 특성을 노출하는지 검사합니다.

**수용 시나리오**:

1. **전제** 표면이 44pt보다 작은 조작 요소가 있으면, **실행** 점검하면, **결과** 표면 크기는
   규격 값을 유지한 채 히트 영역만 44 × 44 이상으로 넓어진다.
2. **전제** 아이콘만 있는 버튼이 접근성 라벨 없이 생성 가능하면, **실행** 계약을 바꾸면,
   **결과** 동작 이름의 접근성 라벨이 필수 입력이 되어 생략할 수 없다.
3. **전제** 정답·오답을 배경색으로만 알리면, **실행** 계약을 보완하면, **결과** 접근성
   라벨에 정답·오답이 함께 전달된다.
4. **전제** 카드가 여러 텍스트를 따로 읽히게 두면, **실행** 묶으면, **결과** 하나의 접근성
   요소로 읽힌다.

### 예외·경계 사례

- 규격 인덱스에 없는 컴포넌트가 현재 화면에서 실제로 쓰이고 있으면 어떻게 하는가? — 사용처가
  있으면 삭제하지 않고 유지 판정하며, 규격 밖인 이유(예: Figma 정본 범위 밖의 웹뷰)를 기록한다.
- 규격 값과 현재 화면 구현이 다르면 어느 쪽을 따르는가? — 규격 문서가 정본이므로 항상 규격을
  따른다. 그 결과 화면이 달라지는 것은 회귀가 아니라 의도된 변경으로 취급하고, 어떤 화면의
  어떤 값이 무엇에서 무엇으로 바뀌었는지를 PR 본문에 남긴다. 예외는 "알려진 차이"에 적은
  타이포·폰트 항목이며, 이들은 현행을 유지하므로 변경 목록에 오르지 않는다.
- 규격 문서끼리 값이 다르면? — Responsive Layout Spec이 정본 근거가 없어 확정한 3건
  (탭바 알약 폭 298 고정 · `TextField` 높이 52 · 시트 최대 높이)은 그 확정값을 따른다.
  나머지 충돌은 해당 값을 소유한 문서를 따른다.
- `all`에 없고 사용처도 없는 public 토큰(`gradient4`)은? — 제거하되 되돌리기 어려우므로
  실행 전에 확인을 받는다. `private` 방향 상수(`topToBottomStart`·`topToBottomEnd`)는 토큰이
  아니라 구현 세부이므로 규격 대조 대상이 아니고 이름을 바꾸지 않는다.
- 그림자처럼 레이어가 여러 개인 값은 어떻게 표현하는가? — 단일 값이 아니라 레이어 배열을 갖는
  구조로 정의해 `sheetElevation`의 2레이어를 손실 없이 담는다.
- 지원 범위 밖의 화면 크기(폭 375 미만 또는 440 초과)에서는? — 지원하지 않는다. 계산식은
  그대로 동작하되 규격이 보장하는 범위는 375–440이다.
- 최소 폭·최소 높이 기기(375 × 667, safe area 20/0)에서 콘텐츠가 넘치면? — 세로 예산이 가장
  좁은 435(largeTitle)에서 잘리지 않는 것을 기준으로 삼고, 넘치면 스크롤한다. 세로 간격을
  줄여 맞추지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

**토큰**

- **FR-001**: UI 패키지는 `BorderToken`에 규격의 선 6종(default·focus·highlight·error·tabBar·
  loadingTrack)을 굵기와 색 토큰 참조로 정의해야 한다.
- **FR-002**: UI 패키지는 `OpacityToken`에 규격의 불투명도 6종(disabled 30% · subtleSurface 5% ·
  tabSurface 10% · track 15% · border 24% · scrim 70%)을 정의해야 한다.
- **FR-003**: UI 패키지는 `EffectToken`에 규격의 그림자 2종을 정의하고, `sheetElevation`이
  레이어 2개를 표현할 수 있는 구조를 가져야 한다.
- **FR-004**: UI 패키지는 누락된 원시 색 5종(`black25`·`black35`·`black45`·`blue300Alpha10`·
  `blue300Alpha24`)을 `ColorToken`에 추가해야 한다.
- **FR-005**: UI 패키지는 누락된 역할 색 5종(`tabBarSurface`·`tabBarBorder`·`selectedSurface`·
  `grabber`·`disabledText`)을 `SemanticColorToken`에 추가하고 각각 규격이 지정한 원시 색을
  참조해야 한다.
- **FR-006**: UI 패키지는 반복 실측값 4종(`cardHorizontalPadding` 18 · `cardTopPadding` 14 ·
  `iconSpacing` 6 · `tightSpacing` 4)을 `LayoutToken`에 추가해야 한다.
- **FR-007**: UI 패키지는 `CornerRadiusToken.pill`(999)과 `ControlSizeToken.minimumTouch`(44)를
  추가해야 한다.
- **FR-008**: `GradientToken.all`은 규격 목록 5종과 일치해야 한다. `all`에 포함되지 않고
  사용처가 0건인 `gradient4`는 제거 대상이며, 되돌리기 어려우므로 실행 전에 확인을 받아야
  한다. `private` 방향 상수는 토큰이 아니므로 이 요구사항의 대상이 아니다.
- **FR-009**: `DesignTokenSet.current.validate()`는 이름 중복·값 범위·참조 무결성을 검사해
  위반이 없을 때 빈 배열을 반환해야 한다.

**반응형 레이아웃**

- **FR-010**: UI 패키지는 화면 폭·화면 높이·safe area 상하 네 값만 입력으로 받아 나머지
  레이아웃 변수를 계산식으로 유도하는 수단을 제공해야 한다.
- **FR-011**: 콘텐츠 폭은 `screenWidth − LayoutToken.margin × 2`로 계산해야 하며, 지원 기기
  범위에서 335–400이어야 한다.
- **FR-012**: 2열·3열 그리드의 열 폭은 `(contentWidth − gutter × (열수 − 1)) / 열수`로 계산해야
  하며, 정본 캔버스 값(2열 154)을 사용하지 않아야 한다.
- **FR-013**: 상단 스크림 높이는 `safeAreaTop + headerHeight`로, 하단 스크림 높이는
  `safeAreaBottom + (탭바가 있으면 93, 없으면 0)`으로 계산해야 하며, 정본 고정값(103 · 127 · 34)을
  사용하지 않아야 한다.
- **FR-014**: 헤더 높이는 헤더 종류에 따라 plain 50 · inlineTitle 64 · inlineUser 98 ·
  largeTitle 120이어야 한다.
- **FR-015**: 시트는 비율 기반 높이를 사용하지 않고 콘텐츠 높이를 따라야 하며, 상한은
  `screenHeight − safeAreaTop − 16`이고 상한을 넘으면 시트 내부에서 스크롤해야 한다.
- **FR-016**: 하단 탭바는 폭 298을 기본값으로 가로 중앙 정렬하고 폭을 인자로 바꿀 수 있어야
  하며, 하단 여백은 `max(safeAreaBottom, 24)`여야 한다.
- **FR-017**: 컴포넌트의 폭 결정 방식은 채움·그리드·내용맞춤·고정 네 가지 중 하나로 명시해야
  한다. 고정 폭은 종횡비가 의미를 갖는 요소에 사용하되, Responsive Layout Spec §07이
  명시적으로 확정한 `TabShell` 기본 폭 298은 규격 소유 예외로 허용한다.
- **FR-018**: 세로 간격과 컴포넌트 높이는 화면 높이와 무관하게 규격 값을 유지해야 하며, 남는
  높이를 채우려고 늘리지 않아야 한다.

**컴포넌트**

- **FR-019**: UI 패키지는 `Controls/Chip`을 제공해야 하며, 선택 여부를 값으로 받고 스스로
  선택을 보관하지 않아야 한다.
- **FR-020**: UI 패키지는 `Controls/PressOverlayStyle`을 제공해 `Component/` 프로덕션 코드에서
  SwiftUI `Button`으로 구현한 모든 조작 컴포넌트의 눌림 표현을 `white30` 오버레이 하나로
  통일해야 한다.
- **FR-021**: UI 패키지는 `Controls/BookmarkButton`을 제공해야 하며, 저장 여부를 값으로 받고
  스스로 보관하지 않아야 한다. 접근성 라벨 요구는 FR-033을 따른다.
- **FR-022**: UI 패키지는 `CollectionItems/ChoiceResultRow`를 제공해야 하며, 정답·오답 축과
  접힘·펼침 축을 값으로 받아야 한다.
- **FR-023**: `Controls/TextField`는 높이 52 · 반경 8 · 내부 좌우 16으로 재작도하고 기본·활성·
  입력됨·오류 네 상태의 테두리를 규격대로 표현해야 한다.
- **FR-024**: UI 패키지의 컴포넌트는 UIUX Guide 상태 매트릭스 10행이 지정한 상태별 배경·라벨·
  테두리 표현을 따라야 한다.
- **FR-025**: 규격 컴포넌트 인덱스가 지정한 역할 폴더와 코드의 배치가 일치해야 한다.

**계층과 소유**

- **FR-026**: UI 패키지의 컴포넌트는 표시 상태를 스스로 보관하지 않고 값과 콜백으로만 받아야
  한다.
- **FR-027**: UI 패키지의 컴포넌트는 화면 좌우 여백(`LayoutToken.margin`)을 스스로 붙이지
  않아야 하며, 화면 여백은 `ScreenContainer`가 소유해야 한다.
- **FR-028**: UI 패키지의 컴포넌트는 햅틱을 발생시키지 않아야 한다.
- **FR-029**: 규격 인덱스에 없는 기존 컴포넌트 15종은 구현 중 사용처를 조사해 각각 유지·이동·
  삭제로 판정하고 근거를 PR 본문에 기록해야 한다. 삭제는 되돌리기 어려우므로 삭제로 판정한
  항목은 실행 전에 확인을 받아야 한다.
- **FR-030**: 규격이 Sub View로 분류한 `QuestionPrompt`와 `EssayAnswerInput`은 UI 패키지에서
  제거하고 Feature 패키지로 옮겨야 하며, 옮긴 뒤 Component 계층에 상태를 소유하는 타입이
  남지 않아야 한다.
- **FR-031**: 이동한 두 타입이 사용하던 무상태 표현 조각은 UI 패키지에 컴포넌트로 남아
  재사용 가능해야 한다.

**접근성**

- **FR-032**: 조작 가능한 모든 컴포넌트는 표면 크기와 무관하게 44 × 44 이상의 터치 영역을
  확보해야 한다.
- **FR-033**: 아이콘만 있는 버튼은 아이콘 이름이 아니라 동작 이름의 접근성 라벨을 필수
  입력으로 받아야 한다.
- **FR-034**: 선택 상태를 갖는 컴포넌트는 색·테두리 외에 선택 특성을 접근성으로 노출해야 한다.
- **FR-035**: 정답·오답을 표시하는 컴포넌트는 색과 함께 접근성 라벨로도 판정을 전달해야 한다.
- **FR-036**: 여러 텍스트를 담는 카드 컴포넌트는 하나의 접근성 요소로 읽히도록 묶어야 한다.
- **FR-037**: 텍스트는 고정 pt 크기를 사용하고 사용자 글자 크기 설정에 따라 레이아웃이 변하지
  않아야 한다. 현행 구현이 이미 이를 만족하므로 이 항목은 변경이 아니라 회귀 방지 기준이다 —
  다른 요구사항을 적용하면서 Dynamic Type 대응을 새로 넣지 않는다는 뜻이다.

**검증**

- **FR-038**: 역할 폴더 6종(Scaffolds·Overlays·Controls·CollectionItems·Indicators·Displays)은
  각각 최소 하나의 테스트를 가져야 한다.
- **FR-039**: 규격에 값이 있는 수치는 컴포넌트 구현에 직접 적지 않고 토큰 또는 레이아웃 변수를
  통해 참조해야 한다.
- **FR-040**: UI 공개 API 변경으로 컴파일이 깨진 Feature 패키지 호출부는 같은 변경 단위에서
  복구해야 하며, 그 복구는 호출 형태 변경에 한정하고 화면 동작·흐름·상태 전이를 바꾸지
  않아야 한다.
- **FR-041**: 규격 적용으로 화면 표시가 달라지는 항목은 화면·값·변경 전후를 담은 표로 PR
  본문에 기록해야 한다. 이를 위해 저장소에 새 문서 파일을 만들지 않는다.
- **FR-042**: 규격 위반을 나타내는 금지 패턴은 저장소 정적 검사로 자동 판정할 수 있어야 하며,
  대상은 규격 예외 밖의 고정 폭, 정본 캔버스 수치를 레이아웃 차원으로 사용한 코드, 토큰으로
  대체 가능한 하드코딩 수치, 컴포넌트의 표시 상태 보관·화면 여백·햅틱,
  종횡비·웹 콘텐츠 밖의 세로 채움,
  Dynamic Type 연동 API 사용이다.
- **FR-043**: 토큰 값, 레이아웃 변수 계산식, 컴포넌트 공개 계약은 화면 렌더링 없이 단위
  테스트로 검증할 수 있어야 한다.

### 핵심 엔터티

- **토큰 카테고리**: 이름과 값을 갖는 디자인 값의 묶음. 11종이며 `DesignTokenSet`이 취합해
  일괄 검증한다. 원시 값(색·크기)과 역할 값(화면에서의 쓰임)으로 나뉘고, 역할 값은 원시 값을
  참조한다. 기기와 무관한 고정 값만 담는다.
- **레이아웃 변수**: 기기에서 읽은 화면 폭·높이·safe area로부터 계산되는 값 13종(입력 4 ·
  파생 8 · 헤더 종류가 소유하는 `headerHeight` 1). 토큰과 달리
  런타임에 결정되며, 구현은 계산식을 쓰고 검수는 min–max 범위를 본다.
- **컴포넌트**: 값과 콜백만 받아 그리는 재사용 표현 단위. 상태·네비게이션·데이터 조회·햅틱·
  화면 여백을 소유하지 않는다. 역할 폴더 하나에 속하고, 폭 결정 방식 네 가지 중 하나를 갖는다.
- **역할 폴더**: 컴포넌트가 화면에서 맡는 역할에 따른 분류 6종. 공개 계약으로 판정하며 판정
  순서가 곧 우선순위다.
- **계층**: Screen·Sub View·Component 3단계. 무엇을 소유하는가로 나뉘며, 이 명세의 대상은
  Component 계층과 그 계층이 지켜야 할 경계다.

## 알려진 차이 (이 기능에서 해소하지 않음)

타이포 적용과 폰트 설정을 현행 유지하기로 했으므로, 아래 규격 위반은 확인만 하고 이 기능에서
고치지 않는다. 별도 기능으로 다룰 후보다.

| 항목 | 규격 | 현재 | 영향 |
| --- | --- | --- | --- |
| 숫자 폰트 | "숫자는 항상 라틴" — 진행률 %, 문제 번호, 세트 번호는 Plus Jakarta Sans | `TextStyleResolver`가 `0x41–0x5A`·`0x61–0x7A`만 라틴으로 보내 숫자 `0x30–0x39`는 Noto Sans KR로 렌더 | 한글 폰트의 숫자는 자폭이 달라 정렬이 흔들린다 |
| 번들 폰트 굵기 | Regular·Medium·Bold 3종만 번들 | `Resources/Fonts/`에 Light·SemiBold·Italic과 VariableFont 파일이 함께 있음. Tuist manifest는 3종만 glob하므로 번들에는 포함되지 않음 | 저장소에 사용하지 않는 자산이 남는다 |

이 두 항목은 성공 기준에 포함하지 않는다. 규격 준수 판정 시 예외로 취급한다.

## 가정

- 네 규격 문서가 UI 계층의 정본이며, 현재 코드와 다를 때는 예외 없이 문서를 따른다. 현재
  화면 모습을 보존하는 것은 이 기능의 목표가 아니다.
- 사용자가 요청한 대상은 UI 패키지이므로, 규격이 Sub View로 분류한 타입은 이 명세에서 처리
  방침을 확정하되 Feature 패키지의 화면 재구성까지 확장하지 않는다.
- 규격 인덱스에 없는 기존 컴포넌트는 현재 화면에서 사용 중일 수 있으므로 기본값은 삭제가
  아니라 유지이며, 삭제는 사용처가 없음을 확인하고 사용자 확인을 받은 경우로 한정한다.
  판정 시점은 구현 중이며 명세에 결과를 미리 고정하지 않는다.
- `reference-swift/`의 참조 구현은 규격 값과 공개 계약의 근거로 사용하며, 파일 하나에 타입
  하나와 `{상위타입}+{중첩타입}.swift` 분할 등 이 저장소의 디렉터리·파일 컨벤션에 맞춰
  다시 작성한다. 참조 구현을 그대로 복사해 넣지 않는다. 참조 구현이 파일명에 `+` 대신 `-`를
  쓰는 것은 원본 저장 환경의 제약이며 이 저장소 규칙이 아니다.
- Figma 정본 캔버스 360 × 800은 어느 지원 기기와도 일치하지 않으므로 크기 기준으로 쓰지 않고,
  정본에서는 구성 순서·간격·컴포넌트 높이·색만 가져온다.
- 단일 다크 테마를 유지하며 라이트 테마 대응은 만들지 않는다.
- 타이포 적용과 폰트 설정은 현행 구현이 기준이다. 규격과 어긋나는 지점은 "알려진 차이"에
  기록하되 이 기능의 성공 기준에 넣지 않는다.
- Dynamic Type을 지원하지 않고 고정 pt를 사용한다는 규격의 결정을 유지한다.
- 지원 기기 범위는 375 × 667(iPhone SE 3)부터 440 × 956(iPhone 17 Pro Max)까지이며 주력
  기기는 402 × 874(iPhone 17 Pro)다. 이 범위 밖은 지원하지 않는다.
- 이 브랜치는 `origin/develop`보다 60커밋 앞선 `feature/registration-home-ux-fixes`의 HEAD에서
  분기했다. 대조 근거인 UI 패키지 상태가 그 HEAD의 상태이기 때문이다.

## 의존성

- 규격 문서 4종과 참조 구현은 이 기능 디렉터리에 함께 보관한다. 원본은 저장소 밖에 있었고
  `private/`는 `.gitignore` 대상이라 다른 개발자와 CI가 볼 수 없었으므로 옮겼다.
  - [`design-specs/`](./design-specs) — 규격 문서 4종
  - [`reference-swift/`](./reference-swift) — 참조 구현 41개 파일
- **Figma 정본 원본**: `private/넥터 Git-it (MCP).fig` (약 17MB). 네 규격 문서가 실측한
  출처이며 최종 근거다. `.gitignore`의 `private/**` 규칙이 제외하므로 **저장소에 커밋하지
  않는다**. 따라서 이 파일은 로컬에만 존재하고 다른 개발자와 CI는 접근할 수 없다.
  - 값이 필요하면 규격 문서(`design-specs/`)를 먼저 본다. 문서에 없거나 문서끼리 충돌해
    원본 확인이 필요하면, 확인한 값과 노드 근거를 문서나 산출물에 옮겨 적어 원본 없이도
    검증할 수 있게 한다.
  - 파일 크기가 커 Git으로 관리하기에 적합하지 않고, 규격 문서가 이미 실측 결과를 담고
