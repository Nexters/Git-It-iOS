## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 화면 목록과 디자인 상수 계약 확정 (우선순위: P1)

UI 개발자가 Figma `최종 UXUI` 섹션의 모든 프레임을 화면 단위로 열거하고, 각 화면의 여백·간격·색 적용을 하나의 검증 가능한 계약 문서로 확정한다. 각 항목은 Figma에서 직접 확인한 값인지, 저장소 기준선인지 근거 수준으로 구분한다.

**주요 행위자**: UI 개발자와 디자이너

**우선순위 이유**: 화면 목록과 상수값이 확정되지 않으면 "모든 화면"의 완료 판정도, "Figma와 동일한 값"의 일치 판정도 불가능하다. 이 시나리오만 완료해도 남은 구현 범위와 공수를 확정할 수 있다.

**독립 테스트**: 계약 문서만으로 화면 하나를 지목했을 때 그 화면의 여백·간격·색 값과 근거 수준, 현재 구현 상태를 다른 문서를 열지 않고 확인할 수 있는지 검토한다.

**수용 시나리오**:

1. **전제** Figma `최종 UXUI` 섹션에 화면 프레임이 존재할 때, **실행** 계약 문서를 확인하면, **결과** 모든 프레임이 고유 화면 식별자, 대응 구현 위치와 구현 상태를 가진 항목으로 등재되어 있다.
2. **전제** 한 화면에 여러 상태 변형(빈 상태, 로딩, 선택됨 등)이 있을 때, **실행** 계약 문서를 확인하면, **결과** 각 변형이 서로 구분되는 항목으로 기록되고 어떤 변형이 미대응인지 식별할 수 있다.
3. **전제** Figma 속성값을 직접 조회하지 못한 항목이 있을 때, **실행** 계약 문서를 확인하면, **결과** 해당 항목은 확정값이 아닌 보류 상태와 사유가 기록되고 현재 구현값이 Figma 확정값으로 서술되지 않는다.
4. **전제** Figma에는 있으나 현재 토큰 집합에 없는 여백·간격·색 값이 있을 때, **실행** 계약 문서를 확인하면, **결과** 신규 토큰으로 추가해야 할 값이 이름·값과 함께 별도로 열거된다.

### 시나리오 2 - 참조 화면 하나로 구현 방식이 실증된다 (우선순위: P2)

UI 개발자가 화면 하나를 끝까지 구현해, 이 기능이 마련한 토큰·공용 컴포넌트·Use Case 주입 구조·자동 검증이 실제 화면에서 함께 동작하는 것을 확인한다. 앱 사용자는 이 화면을 실행 중에 볼 수 있고, 화면 안의 조작에 따라 상태가 실제로 바뀐다. 이 화면은 후속 기능이 나머지 화면을 구현할 때 따르는 본보기가 된다.

**주요 행위자**: UI 개발자와 앱 사용자

**우선순위 이유**: 기반만 만들고 실제 화면으로 확인하지 않으면, 검증 수단과 주입 구조가 화면에서 통하는지 모르는 채 후속 기능 다섯 개로 넘어가 같은 재작업이 다섯 번 반복될 수 있다.

**독립 테스트**: 참조 화면 하나만 구현한 상태에서 그 화면의 레이아웃·색·상호작용 검증을 실행해, 나머지 화면이 하나도 구현되지 않았어도 통과·실패를 판정할 수 있는지 확인한다.

**수용 시나리오**:

1. **전제** 참조 화면이 구현되었을 때, **실행** 앱에서 그 화면으로 이동하면, **결과** 디자인에 정의된 구성 요소가 모두 표시되고 자리표시자나 미구현 표시가 남아 있지 않다.
2. **전제** 참조 화면에 빈 상태·로딩 상태가 정의되어 있을 때, **실행** 해당 조건을 만들면, **결과** 디자인에 정의된 상태 화면이 표시된다.
3. **전제** 디자인이 참조 화면의 어떤 요소에 선택·입력·토글 같은 조작을 정의할 때, **실행** 사용자가 그 조작을 하면, **결과** 디자인에 정의된 상태로 화면이 바뀐다.
4. **전제** 참조 화면의 상태 동작이 Use Case를 필요로 할 때, **실행** 주입하는 구현을 Mock에서 다른 구현으로 교체하면, **결과** 화면 코드를 수정하지 않고 동작한다.
5. **전제** 참조 화면의 Feature에 Mock Use Case를 주입했을 때, **실행** 조작에 해당하는 Action을 전달하면, **결과** 기대한 상태 전이가 일어나고 Mock 호출 여부를 확인할 수 있다.
6. **전제** 참조 화면이 헤더·카드·버튼 같은 시각 요소를 사용할 때, **실행** 구현을 확인하면, **결과** 화면 안에 새로 정의하지 않고 공용 컴포넌트를 재사용한다.
7. **전제** 나머지 화면이 하나도 구현되지 않았을 때, **실행** 참조 화면의 검증을 실행하면, **결과** 미구현 화면의 영향을 받지 않고 통과·실패를 판정할 수 있다.

### 시나리오 3 - 여백·간격이 Figma 값과 일치한다 (우선순위: P3)

UI 개발자가 참조 화면과 공용 컴포넌트의 화면 여백, 요소 사이 간격, 구성 요소 내부 여백을 Figma에 정의된 수치 그대로 적용하고, 값이 어긋나면 자동 검증으로 검출한다. 이 검증 수단은 후속 기능이 나머지 화면에 그대로 적용할 수 있어야 한다.

**주요 행위자**: UI 개발자와 디자이너

**우선순위 이유**: 사용자가 명시한 핵심 제약이다. 눈대중으로 맞춘 값은 화면이 늘어날수록 누적 편차를 만들고, 자동 검출이 없으면 이후 변경에서 다시 어긋난다. 검증 수단이 이 기능에서 확립되어야 후속 기능 다섯 개가 같은 기준으로 판정된다.

**독립 테스트**: 참조 화면에서 여백값 하나를 의도적으로 다르게 만들고 검증을 실행해 화면 이름·항목·기대값·실제값을 포함한 실패가 나오는지, 원복 후 통과하는지 확인한다.

**수용 시나리오**:

1. **전제** 계약 문서가 화면의 여백·간격 목표값을 정의할 때, **실행** 레이아웃 검증을 실행하면, **결과** 목표값과 허용 오차 안에서 렌더링된 항목이 통과한다.
2. **전제** 어떤 요소의 여백이 목표값과 다를 때, **실행** 같은 검증을 실행하면, **결과** 화면 이름, 항목, 기대값과 실제값을 포함해 실패한다.
3. **전제** Figma에서 확정한 여백값이 현재 토큰 집합에 없을 때, **실행** 구현을 확인하면, **결과** 화면 코드에 수치를 직접 적지 않고 해당 값의 토큰이 추가되어 사용된다.
4. **전제** 기기 폭이나 시스템 글자 크기가 기준 디자인 프레임과 다를 때, **실행** 화면을 표시하면, **결과** 고정 여백은 유지되고 콘텐츠가 잘리거나 겹치지 않는다.

### 시나리오 4 - 색이 Figma 값과 일치한다 (우선순위: P4)

UI 개발자가 색 토큰 집합을 Figma 색 변수와 정합시키고, 참조 화면과 공용 컴포넌트의 색을 화면 코드에 직접 적지 않고 디자인 문서와 같은 이름의 토큰으로 적용한다.

**주요 행위자**: UI 개발자와 앱 사용자

**우선순위 이유**: 사용자가 명시한 두 번째 핵심 제약이다. 색을 화면마다 직접 적으면 디자인 값이 바뀔 때 화면 수만큼 수정 비용이 발생하고, 같은 역할의 요소가 화면마다 달라진다. 토큰 정합을 이 기능에서 끝내야 후속 기능이 색을 다시 논의하지 않는다.

**독립 테스트**: 참조 화면과 공용 컴포넌트 코드에서 색상 리터럴 사용 여부를 검사하고, 토큰 정의의 색 값 하나를 바꾸었을 때 화면 코드 수정 없이 반영되는지 확인한다.

**수용 시나리오**:

1. **전제** 디자인이 어떤 요소에 이름 있는 색을 지정할 때, **실행** 화면을 표시하면, **결과** 그 요소에 디자인과 동일한 색 값이 적용된다.
2. **전제** 화면 구현 코드를 검사할 때, **실행** 색상 리터럴을 탐색하면, **결과** 화면 코드에 색상 리터럴이 존재하지 않는다.
3. **전제** Figma 색 변수와 저장소 색 토큰을 대조할 때, **실행** 정합 결과를 확인하면, **결과** 이름·값이 어긋나거나 한쪽에만 있는 항목이 빠짐없이 열거되고 해소되어 있다.
4. **전제** 색이 불투명도와 함께 지정된 경우, **실행** 화면을 표시하면, **결과** 색 값과 불투명도가 함께 디자인과 동일하게 적용된다.

### 시나리오 5 - 후속 기능 다섯 개가 독립적으로 시작될 수 있다 (우선순위: P5)

기능 계획자가 화면 65개를 흐름 그룹으로 나눈 분할 정의를 보고, 각 그룹을 별도 기능으로 착수한다. 각 그룹은 포함 화면, 진입 조건, 이 기능이 제공한 기반 중 무엇에 의존하는지가 명시되어 있어 서로를 기다리지 않고 진행할 수 있다.

**주요 행위자**: 기능 계획자와 UI 개발자

**우선순위 이유**: 분할 정의가 없으면 후속 기능들이 같은 화면을 중복 구현하거나 빠뜨리고, 그룹 사이 경계에서 공용 컴포넌트 소유권 충돌이 생긴다.

**독립 테스트**: 분할 정의만 보고 임의의 그룹 하나를 골랐을 때, 그 그룹의 구현 대상 화면과 선행 조건을 다른 문서 없이 확정할 수 있는지 검토한다.

**수용 시나리오**:

1. **전제** 화면 목록에 65개 프레임이 등재되어 있을 때, **실행** 분할 정의를 확인하면, **결과** 모든 프레임이 정확히 하나의 그룹에 배정되거나 제외 사유와 함께 구분된다.
2. **전제** 어떤 그룹을 착수하려 할 때, **실행** 분할 정의를 확인하면, **결과** 그 그룹의 선행 조건과 이 기능이 제공한 기반 항목을 식별할 수 있다.
3. **전제** 두 그룹이 같은 공용 컴포넌트를 필요로 할 때, **실행** 분할 정의를 확인하면, **결과** 그 컴포넌트의 소유 기능이 하나로 정해져 있다.

### 예외·경계 사례

- Figma 프레임에 있으나 앱의 진입 흐름에서 도달할 수 없는 화면(디자인 검토용 프레임, 중복 프레임)은 화면 목록에서 제외 사유와 함께 구분한다.
- 같은 화면이 여러 프레임으로 그려진 상태 변형인 경우, 별개 화면이 아니라 한 화면의 상태 변형으로 집계해 화면 수를 부풀리지 않는다.
- 시스템 글자 크기를 최대로 키워도 고정 여백이 텍스트 잘림을 유발해서는 안 된다.
- 기기 폭이 디자인 기준 프레임과 다르면 화면 전체 폭이 아니라 여백과 고정 표면만 비교한다.
- `TabView`, 안전 영역, 시스템 키보드처럼 플랫폼이 소유하는 적응형 값은 디자인 프레임의 픽셀 높이로 고정하지 않는다.
- 애니메이션 자산은 Lottie 형식이다. 재생 수단이 도입되기 전까지 해당 화면은 정적 대체 표현으로 구현하고 미대응 상태를 계약 문서에 남기되, 정적 대체 상태에서도 그 화면의 레이아웃·색 검증은 통과해야 한다.
- Use Case에 Mock만 있고 실제 구현이 없는 상태에서도 화면 단위 검증이 실행 가능해야 한다. 실제 구현이 없다는 이유로 화면을 미완료로 남기지 않는다.
- 후속 기능이 공용 컴포넌트나 토큰을 함께 바꿀 수 있다. 이때 참조 화면을 포함해 앞서 완료 판정된 화면의 검증이 깨지면 해당 화면도 다시 검증해야 한다.
- 참조 화면이 이 기능에서 확정하지 못한 값(예: 조회하지 못한 Figma 속성, Lottie 재생)에 의존하면, 그 부분은 미대응으로 기록하고 참조 화면 자체는 나머지 항목으로 완료 판정한다.
- 참조 화면이 속한 그룹의 후속 기능은 이미 구현된 참조 화면을 다시 만들지 않고 이어받는다.
- Figma 프로토타입으로 확인된 화면 간 전환 5개는 확정 근거로 사용하고, 나머지 전환은 후속 기능이 확정하기 전까지 추정으로만 표기한다.
- 참조 화면이 Use Case를 전혀 필요로 하지 않는 화면이면 주입 구조를 실증하지 못한다. 이 경우 Use Case를 사용하는 화면으로 참조 화면을 바꾸거나, 주입 구조 실증을 별도 화면으로 보완해야 한다.
- 공유 테스트 지원 대상이 신설되어도 이 기능은 참조 화면이 필요로 하는 Mock만 채운다. 나머지 Use Case의 Mock이 비어 있다는 이유로 이 기능을 미완료로 판정하지 않는다.
- Figma에서 값을 직접 조회하지 못한 항목은 현재 구현값을 그대로 목표값으로 승격하지 않는다. 순환 검증이 되기 때문이다.
- 기존 검증이 실패했을 때 원인이 컴포넌트 교정이면 기준선을 Figma 근거로 갱신하고, 원인이 구현 결함이면 구현을 고친다. 두 경우를 구분하지 않고 기준선을 실패값에 맞추어서는 안 된다.
- 기존 `UIComponent` 구현이 Figma와 다르면 화면에서 우회 조정하지 않고 컴포넌트 자체를 교정한다.

## 요구사항 *(필수)*

### 기능 요구사항

**적용 범위**: 계약·목록·토큰·검증 수단에 관한 요구사항(FR-001·002·006·007·008·011·018·029)은 화면 65개 전체를 대상으로 한다. 화면 구현과 Use Case에 관한 요구사항(FR-003·004·005·009·010·012·013·014·015·016·022~025)은 이 기능에서 **참조 화면 1개**와 그 화면이 필요로 하는 Use Case에만 적용하며, 나머지 화면에는 후속 기능이 같은 요구사항을 적용한다. 분할과 공유 자산에 관한 요구사항(FR-017·019·020·021·026·027·028)은 이 기능 고유의 산출물이다.

**Use Case 책임 경계**: Protocol은 `Domain`, 앱 실행용 임시 구현과 주입 조립은 `Composition`, Protocol을 주입받는 상태 관리와 화면은 `Feature`, Mock은 공유 테스트 지원 대상이 소유한다.

- **FR-001**: 시스템은 Figma `최종 UXUI` 섹션의 모든 화면 프레임을 고유 화면 식별자, 대응 구현 위치, 구현 상태를 가진 목록으로 제공해야 한다.
- **FR-002**: 화면 목록의 각 항목은 그 화면이 가지는 상태 변형(빈 상태, 로딩, 오류, 선택 여부 등)을 구분해 기록해야 한다.
- **FR-003**: 구현 대상 화면의 화면 여백, 요소 사이 간격, 구성 요소 내부 여백은 Figma에 정의된 수치와 동일해야 하며, 임의로 반올림하거나 근사한 값을 사용해서는 안 된다.
- **FR-004**: 구현 대상 화면 요소의 색은 Figma가 정의한 색 값 및 불투명도와 동일해야 한다.
- **FR-005**: 화면 구현은 색 값과 여백 수치를 코드에 직접 적지 않고, 디자인 문서와 같은 이름의 토큰을 통해 적용해야 한다.
- **FR-006**: Figma에 존재하지만 현재 토큰 집합에 없는 여백·간격·색 값은 화면 구현 전에 토큰으로 추가되어야 한다.
- **FR-007**: 각 계약 항목은 Figma에서 직접 확인한 값과 확인하지 못한 값을 구분하는 근거 수준을 가져야 하며, 확인하지 못한 값을 Figma 확정값으로 기록해서는 안 된다.
- **FR-008**: 자동 검증은 화면의 고정 여백·간격과 색 적용이 계약과 다를 때 화면 이름, 항목, 기대값과 실제값을 포함해 실패해야 한다.
- **FR-009**: 사용자는 앱 실행 중 참조 화면에 도달할 수 있어야 한다. 나머지 화면의 화면별 진입 경로는 이 기능에서 확정하지 않으며, 각 후속 기능이 담당 그룹의 전환을 디자이너와 확정한다.
- **FR-010**: 화면은 같은 역할의 시각 요소를 화면마다 새로 정의하지 않고 공용 컴포넌트를 재사용해야 한다.
- **FR-011**: 기존 공용 컴포넌트가 Figma와 다르면 컴포넌트를 Figma 기준으로 교정해야 한다. 교정으로 기존 검증 기준선이 바뀌면 그 기준선을 Figma 확정값으로 갱신하고, 갱신한 항목·이전값·새 값·Figma 근거를 목록으로 기록해야 한다.
- **FR-012**: 상호작용 요소는 최소 44pt × 44pt 터치 영역과 화면 목적을 식별할 수 있는 VoiceOver 라벨을 유지해야 한다.
- **FR-013**: 시스템 글자 크기를 확대해도 화면의 텍스트가 잘리거나 겹치지 않아야 한다.
- **FR-014**: 참조 화면은 디자인에 정의된 화면 내 상호작용(선택, 입력, 토글, 펼침·접힘 등)에 따라 실제로 상태가 바뀌어야 한다. 표시되는 데이터는 표본 데이터를 사용하며, 서버 연동은 이 기능의 범위가 아니다.
- **FR-015**: 화면이 의존하는 Use Case는 `Domain` 패키지가 소유하는 Protocol로 정의해야 한다. Protocol은 비즈니스 의미로만 표현하고 저장·네트워크·플랫폼 기술 용어를 노출해서는 안 된다.
- **FR-016**: 화면의 상태 동작은 Use Case Protocol을 생성자 주입으로 전달받는 화면 단위 상태 관리 단위(TCA Feature)가 소유해야 한다. Feature는 Protocol에만 의존하고 구현을 직접 생성해서는 안 되며, 구현이 교체되어도 화면 코드는 바뀌지 않아야 한다.
- **FR-017**: 나머지 화면의 구현은 흐름 그룹별 후속 기능으로 분리해야 한다. 각 후속 기능은 Constitution 원칙 7의 패키지 순서를 자체적으로 지키며, 그 안에서 화면 단위로 검수한다.
- **FR-018**: 색은 Figma 파일의 색 변수 컬렉션에서, 텍스트 스타일은 Figma 텍스트 스타일에서, 여백·간격은 각 화면 프레임의 auto-layout 속성(패딩, 항목 간격)에서 확정해야 한다. Figma 파일에 여백·간격 변수가 정의되어 있지 않으므로, 여백·간격은 화면·구성 요소 단위 실측값을 계약에 기록하고 반복 사용되는 값만 토큰으로 승격한다.
- **FR-019**: 시스템은 화면 65개를 후속 기능 단위의 흐름 그룹으로 배정한 분할 정의를 제공해야 한다. 각 그룹은 포함 화면, 시작 화면, 다른 그룹과의 연결 지점, 선행 조건, 의존하는 기반 항목을 명시해야 하며, 어떤 프레임도 두 그룹에 중복 배정되거나 누락되어서는 안 된다.
- **FR-020**: 여러 그룹이 공유하는 공용 컴포넌트와 토큰은 소유 기능을 하나로 지정해야 하며, 후속 기능은 이 기능이 제공한 검증 수단·토큰·컴포넌트를 새로 만들지 않고 재사용할 수 있어야 한다.
- **FR-021**: 참조 화면은 화면 목록에 등재된 화면 중 하나여야 하며, 어떤 화면을 선택했고 왜 선택했는지 기록되어야 한다.
- **FR-022**: Feature의 상태 흐름은 Use Case Protocol의 Mock 객체를 주입해 독립적으로 검증할 수 있어야 한다. 검증은 조작에 따른 상태 전이와 Mock 호출 여부를 확인해야 하며, 실제 구현이나 실행 환경에 의존해서는 안 된다.
- **FR-023**: 이 기능은 Use Case Protocol, 테스트용 Mock, 그리고 앱 실행용 임시 구현까지만 제공한다. 실제 Use Case 구현은 이후 작업자가 담당하며, 그 구현이 없는 상태에서도 참조 화면과 그 검증이 독립적으로 동작해야 한다.
- **FR-024**: 앱 실행 경로에 주입할 Use Case 구현은 `Composition`이 제공해야 하며, 표본 데이터를 반환하는 임시 구현이어도 된다. 실제 구현으로 교체할 때 바꾸는 위치는 조립 지점 한 곳이어야 하고 화면·Feature 코드는 바뀌지 않아야 한다.
- **FR-025**: Mock 객체는 테스트 대상에서만 사용해야 하며 앱 실행 경로와 배포 산출물에 포함되어서는 안 된다.
- **FR-026**: Use Case Protocol의 Mock은 여러 기능의 테스트가 재사용할 수 있는 단일 공유 테스트 지원 대상이 소유해야 한다. 같은 Protocol의 Mock을 여러 대상에 중복 정의해서는 안 된다.
- **FR-027**: 공유 테스트 지원 대상은 이 기능에서 신설하고, 후속 기능이 새 Use Case Protocol을 추가할 때 그 Mock을 같은 대상에 추가하는 방식으로 확장할 수 있어야 한다.
- **FR-028**: 분할 정의는 화면 간 전환의 근거 수준을 구분해야 한다. Figma 프로토타입으로 확인한 전환과 주석·배치로 추정한 전환을 섞어 기록해서는 안 되며, 추정 전환을 확정 전환으로 기록해서는 안 된다.
- **FR-029**: 검증 기준선의 갱신은 Figma 근거가 있을 때만 허용해야 한다. 구현을 편하게 하려고 기준선을 현재 구현값에 맞추는 갱신은 허용되지 않는다.

### 핵심 엔터티

- **화면(Screen)**: Figma `최종 UXUI` 섹션의 프레임 하나에 대응하는 표시 단위. 고유 식별자, 디자인 근거(프레임 이름과 노드 식별자), 상태 변형 목록, 소속 그룹, 구현 상태를 가진다.
- **상태 변형(Screen state)**: 한 화면이 가지는 표시 조건별 변형. 조건, 표시 내용, 대응 여부를 가진다.
- **레이아웃 상수(Layout constant)**: 화면 또는 구성 요소에 적용하는 여백·간격 값. 이름, 값, 적용 대상, 근거 수준, 허용 오차를 가진다.
- **색 적용(Color application)**: 화면 요소에 적용하는 색. 요소, 색 이름, 색 값, 불투명도, 근거 수준을 가진다.
- **화면 전환(Screen transition)**: 출발 화면, 도착 화면, 전환을 일으키는 조작, 근거 수준(Figma 프로토타입 확인 / 추정)을 가진다.
- **후속 기능 그룹(Screen group)**: 후속 기능 하나가 담당하는 화면 묶음. 그룹 이름, 포함 화면 목록, 시작 화면, 다른 그룹과의 연결 지점, 선행 조건, 의존하는 기반 항목, 소유하는 공용 컴포넌트를 가진다.
- **Use Case 계약(Use case contract)**: 화면이 상태 동작을 위해 의존하는 추상 연산. 이름, 입력, 출력, 실패 조건, 대응하는 Mock과 임시 구현의 존재 여부를 가진다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: Figma `최종 UXUI` 섹션의 화면 프레임 100%가 화면 목록에 등재되고, 각 항목이 구현 상태와 근거 수준을 가진다.
- **SC-002**: 참조 화면이 앱 실행 중 도달 가능하고, 후속 기능 그룹 100%가 시작 화면과 다른 그룹과의 연결 지점을 갖는다.
- **SC-003**: 계약에 확정값이 기록된 참조 화면·공용 컴포넌트의 여백·간격 항목 100%가 목표값 ±0.5pt 안에서 렌더링된다.
- **SC-004**: 참조 화면과 공용 컴포넌트 코드에 등장하는 색상 리터럴과 여백 수치 리터럴이 0건이다.
- **SC-005**: 여백값 또는 색 하나를 의도적으로 어긋나게 하면 자동 검증이 해당 항목을 지목해 실패한다(검출력 확인).

## 가정

- Figma `최종 UXUI` 섹션이 화면 목록의 유일한 원천이며, 같은 파일의 `사용한 컴포넌트`·`사용한 아이콘` 페이지는 부품 원천으로만 사용한다.
- `최종 UXUI`는 Figma 페이지가 아니라 `📌 서비스 설계` 페이지 안의 SECTION(`720:8655`)이다. 화면 목록은 부록에 열거했다.
- 부록의 화면 프레임 중 이름이 같은 여러 프레임은 대부분 한 화면의 상태 변형이거나 같은 화면의 중복 배치다. 어떤 프레임이 별개 화면이고 어떤 프레임이 상태 변형인지는 계획 단계에서 프레임 내용을 대조해 확정한다.
- `Examples/Notifications`(402×874)는 앱 화면이 아니라 iOS 잠금 화면 알림 표현 예시이므로 구현 대상 화면에서 제외하고, 알림 문구 사양의 근거로만 사용한다.
- Figma 프로토타입은 화면 전환의 원천이 아니다. 섹션 전체에서 이동 액션 198개 중 193개가 컴포넌트 variant 전환이고 화면 간 전환은 5개뿐이다(부록 참조). 화면별 진입 경로는 각 후속 기능이 디자이너와 확정한다.
- 색은 Figma 색 변수 25개(`Blue/*`, `Purple/*`, `Grey/*` 등)로 정의되어 있고 저장소 `ColorToken`과 이름 체계가 대응한다. 반면 여백·간격 변수는 존재하지 않으므로(FLOAT 변수 0개) 여백값의 원천은 프레임별 auto-layout 실측이다.
- `002-design-token-system`이 정의한 토큰 적용 방식(이름 기반 토큰, 화면 코드 하드코딩 금지)을 그대로 따르며, 새 값은 같은 방식으로 토큰에 추가한다.
- `005-figma-layout-audit`이 확정한 컴포넌트 레이아웃 계약과 근거 수준 구분(직접 확인값 / 저장소 기준선)을 이어받는다. 그중 근거 수준 `C`(현재 구현에만 존재하는 기준선) 항목은 Figma 확정값이 확보되면 갱신 대상이며, 갱신은 이 기능의 정상 산출물이지 회귀가 아니다.
- 앱은 디자인이 정의한 단일 색 구성표만 제공하며, 이 기능에서 별도의 라이트 테마 대응은 다루지 않는다.
- 화면 조립은 `Feature` 패키지가, 재사용 시각 요소는 `UI` 패키지가 소유한다. 현재 `Feature` 패키지에는 화면 구현이 없어 이 기능이 첫 화면들을 추가한다.
- 디자인 자산은 2026-08-19에 `sources/Projects/UI/UIComponent/Resources/animation & logo/`로 이동되어 읽을 수 있다. 내용은 부록에 기록했다.
- 애니메이션 자산 6종은 모두 Lottie(bodymovin) 형식이며 외부 이미지를 포함하지 않는 순수 벡터다. 재생 수단(외부 의존성 도입 여부)은 이 명세에서 결정하지 않고 계획 단계로 넘긴다.
- 상호작용 상태는 화면 단위 TCA Feature가 소유하고 Use Case는 생성자 주입으로 전달받는다. Use Case 계약은 `Domain` 패키지가 소유한다(아키텍처 문서 기준).
- Mock Use Case는 공유 테스트 지원 대상이 소유하고 앱 실행 경로에 포함되지 않는다. 앱 실행 경로에는 `Composition`의 임시 구현이 표본 데이터를 공급한다.
- 공유 테스트 지원 대상을 어느 패키지에 두는지는 계획 단계에서 확정한다. Domain 패키지 규칙의 target 정책(모든 내부 target은 도메인 모델·규칙·Use Case 또는 외부 기능 계약을 소유해야 한다)과 충돌하지 않는 위치여야 하며, 충돌하면 규칙 개정 없이 다른 패키지를 선택한다.
- 임시 구현은 표본 데이터를 반환할 뿐 비즈니스 규칙을 갖지 않는다. 규칙이 필요해지면 Domain 또는 실제 구현의 책임이며 임시 구현에 넣지 않는다.
- 이 기능은 계약·기반과 참조 화면 1개까지를 담당한다. 나머지 화면은 흐름 그룹별 후속 기능이 구현하며, 그룹 후보는 부록의 분류(온보딩·인증, 스플래시·학습 세트 생성, 메인 탭, 프로젝트 상세·등록, 문제 풀이) 다섯 개다. 최종 그룹 경계는 FR-019의 분할 정의에서 확정한다.
- 참조 화면은 공용 컴포넌트를 여러 종류 사용하고 상호작용과 상태 변형을 모두 가진 화면에서 고르는 것이 기반 실증에 유리하다. 구체적인 선택은 계획 단계에서 확정하고 근거를 기록한다(FR-021).
- 후속 기능들은 이 기능이 확정한 화면 목록·상수 계약·토큰·검증 수단을 원천으로 사용하며, 같은 항목을 다시 정의하지 않는다.
