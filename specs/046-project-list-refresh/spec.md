# 기능 명세: 프로젝트 목록 자동 갱신과 생성 상태 고착 해결

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/project-list-refresh`

**브랜치 상태**: `생성` (2026-09-27 `/speckit-specify` 병합 시 `재사용`)

**생성일**: 2026-09-26

**상태**: 초안

**입력**: 사용자 설명: "앱이 foreground 로 올라오는 경우 프로젝트 리스트를 업데이트하도록하고, foreground에 있는 경우, APNs 알림을 수신하는 경우 프로젝트 리스트를 업데이트하도록 합니다."

**병합 입력** (2026-09-27): 사용자 설명: "045(생성 결과 누락 시 생성 중 상태 고착 수정)를 046에 흡수한다. '지금 불러오기' 버튼 잠금(G1~G4) 해결 요구사항을 포함하고, 045 FR-007(기록 정리 시 목록 재조회)은 046의 목록 자동 갱신 계기로 대체해 폐기한다. 045 기기 검증 항목을 이관한다. 체리픽으로 구현된 부분은 이미 구현됨으로 표기한다. 최소 대기(준비 대기 시간)는 필터 제거 커밋에 따라 제외한다."

## 배경

생성 중인 프로젝트를 목록에서 빼던 필터가 제거되면서, 생성이 끝났을 때 목록을 다시 받아오던 동작도 함께 사라졌다.
이제 목록은 서버가 돌려준 프로젝트를 그대로 보여 주므로, 서버 쪽 변화(새 프로젝트 생성 완료, 학습 세트 준비 등)를
앱이 언제 다시 받아올지가 목록의 최신성을 결정한다. 이 기능은 그 시점을 두 가지로 정한다.

1. 앱이 포그라운드로 올라올 때
2. 앱이 포그라운드에 있는 동안 생성 결과 원격 알림(APNs)을 받았을 때

### 흡수한 045: 생성 중 상태 고착

Home의 "지금 불러오기" 버튼 잠금은 앱과 공유 확장이 함께 쓰는 **생성 기록 저장소**(App Group 공유 저장소)의
진행 중 기록으로 결정된다. 045 이전에는 진행 중 기록을 완료·실패로 바꾸는 경로가 백그라운드 원격 알림
콜백 하나뿐이어서, 이 경로를 놓치면 사용자가 알림을 보았는데도 버튼이 잠긴 채 남았다. 앱을 삭제 후
재설치하면 공유 저장소가 함께 지워져 정상화되는 현상이 이 원인과 일치했다.

| 식별자 | 결함 | 근거 수준 | 상태 |
|---|---|---|---|
| G1 | 알림 표시·탭, 종료 상태에서 알림으로 실행하는 경로에서 생성 결과를 반영하지 않는다 | 코드로 확정. 포그라운드 alert+content-available 푸시에서 표시 콜백만 호출됨을 시뮬레이터에서 관찰 | 구현됨(`756696d`) |
| G2 | 결과 관찰을 시작하기 전에 도착한 생성 결과를 버린다 | 코드로 확정 | 구현됨(`0a76670`, `573a30b`) |
| G3 | 실행 중에는 진행 중 기록의 보관 기한이 지나도 상태가 풀리지 않고, 앱 활성화 시 저장소를 다시 읽지 않는다 | 코드로 확정 | 구현됨(`573a30b`, `78d065c`) |
| G4 | 공유 확장이 남긴 생성 기록이 실행 중인 앱에 반영되지 않는다 | 코드로 확정 | 구현됨(`78d065c`) |

시뮬레이터의 `simctl push`는 content-available 알림을 앱에 전달하지 못해(`background_fetch` 실행 거부)
백그라운드 원격 알림 콜백의 실제 호출 여부는 판단하지 못했다. 이 부분은 실기기 검증 항목(시나리오 7)으로 남긴다.

045가 전제로 삼았던 "생성 중 프로젝트를 목록에서 제외"와 "요청 후 5분 준비 대기 시간"은 `0d6e197`에서
제거되었다. 따라서 045의 목록 제외·준비 대기 관련 요구사항은 이 명세에 옮기지 않고, 기록 정리 시 목록을
다시 부르던 045 FR-007은 이 명세의 목록 자동 갱신 계기(FR-001, FR-002)로 대체한다.

### 세션 2026-09-28

- 질문: 여러 페이지를 불러온 상태에서 자동 갱신이 일어나면 목록을 어떻게 바꾸는가? → 답변: 수동 새로고침과 같이 첫 페이지 응답만 남기고 목록 전체를 교체한다. 이미 불러온 뒤쪽 페이지는 버리며, 이로 인해 스크롤 위치가 바뀌는 것을 허용한다.
- 질문: 목록 자동 갱신에 진단 로그 요구사항을 추가하는가? → 답변: 추가하지 않는다. 실기기에서 목록 요청 횟수는 네트워크 계측으로 확인한다.
- 질문: 생성 결과 알림 시점에 서버 목록 API에 새 프로젝트가 반영되어 있는가? → 답변: 반영되어 있다고 가정한다. 앱은 지연·재시도를 두지 않고, 시나리오 7에서 실기기로 확인하며 어긋나면 서버 협의 항목으로 분리한다.
- 질문: 같은 생성 결과가 여러 수신 경로나 여러 번 도착하면 목록 요청을 몇 번 시작하는가? → 답변: 한 번만 시작한다. 같은 결과는 프로젝트 식별자(`projectId`)와 상태(`status`)가 같고 앞선 도착으로부터 생성 기록 보관 기한(1시간) 안인 결과다. 상태가 다른 결과는 다른 알림으로 본다.
- 질문: 메인 화면 흐름에 그 위에 표시된 등록 흐름도 포함하는가? → 답변: 포함한다. 가려진 목록이 바뀌어도 보이는 화면은 바뀌지 않는다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 앱으로 돌아오면 최신 목록을 본다 (우선순위: P1)

회원 사용자가 다른 앱을 쓰다가, 또는 홈 화면에서 Git It으로 돌아오면 프로젝트 목록이 서버의 최신 상태로 바뀐다.
생성을 요청해 두고 앱을 떠났다가 돌아온 사용자는 직접 새로고침하지 않아도 생성이 끝난 프로젝트를 목록에서 본다.

**주요 행위자**: 회원 사용자

**우선순위 이유**: 원격 알림을 받지 못하는 경우(알림 권한 없음, 백그라운드 수신 실패)에도 목록을 최신으로 되돌리는 가장 넓은 복구 경로다.

**독립 테스트**: 서버 목록이 바뀐 상태에서 앱을 백그라운드로 보냈다가 다시 열면, 사용자가 아무 조작을 하지 않아도 목록이 서버 목록과 같아지는지 확인한다.

**수용 시나리오**:

1. **전제** 회원이 메인 화면(홈 또는 프로젝트 목록 탭)을 보고 있고 앱이 백그라운드에 있는 동안 서버에 새 프로젝트가 생겼다, **실행** 앱을 포그라운드로 올린다, **결과** 목록에 새 프로젝트가 나타난다.
2. **전제** 회원이 프로젝트 상세나 풀이 화면을 띄운 채 앱을 백그라운드로 보냈다, **실행** 앱을 포그라운드로 올린다, **결과** 앞에 떠 있는 화면은 그대로 유지되고, 그 아래의 프로젝트 목록은 서버 목록으로 갱신된다.
3. **전제** 사용자가 게스트이거나 로그인 전(온보딩) 화면에 있다, **실행** 앱을 포그라운드로 올린다, **결과** 프로젝트 목록 요청을 보내지 않는다.
4. **전제** 회원이 메인 화면을 보고 있다, **실행** 제어 센터나 알림 센터를 내렸다가 닫거나 시스템 알럿을 닫아 앱이 백그라운드를 거치지 않고 다시 활성화된다, **결과** 프로젝트 목록 요청을 보내지 않는다.

### 시나리오 2 - 앱을 보고 있을 때 생성 결과 알림이 오면 목록이 바뀐다 (우선순위: P1)

회원 사용자가 앱을 보고 있는 동안 생성 결과 원격 알림이 도착하면 프로젝트 목록이 서버의 최신 상태로 바뀐다.
생성 완료 알림을 받은 사용자는 알림을 누르거나 화면을 새로고침하지 않아도 생성이 끝난 프로젝트를 목록에서 본다.

**주요 행위자**: 회원 사용자, 원격 알림을 보내는 서버

**우선순위 이유**: 사용자가 보고한 핵심 증상("알림이 도착했는데 목록이 갱신되지 않음")을 직접 해결한다.

**독립 테스트**: 앱을 포그라운드에 둔 채 서버 목록을 바꾸고 생성 결과 원격 알림을 보내면, 사용자 조작 없이 목록이 서버 목록과 같아지는지 확인한다.

**수용 시나리오**:

1. **전제** 회원이 메인 화면을 보고 있고 서버에서 프로젝트 생성이 끝났다, **실행** 생성 완료 원격 알림이 도착한다, **결과** 알림 배너가 표시되는 것과 별개로 목록에 새 프로젝트가 나타난다.
2. **전제** 회원이 앱을 보고 있고 알림 권한이 꺼져 있어 배너가 표시되지 않는다, **실행** 백그라운드 수신이 가능한 생성 결과 원격 알림이 도착한다, **결과** 목록이 갱신된다.
3. **전제** 앱이 백그라운드에 있다, **실행** 생성 결과 원격 알림이 도착한다, **결과** 이 시점에는 목록을 요청하지 않고, 이후 포그라운드로 올라올 때 시나리오 1에 따라 갱신된다.
4. **전제** 사용자가 게스트이거나 로그인 전이다, **실행** 포그라운드에서 생성 결과 원격 알림이 도착한다, **결과** 프로젝트 목록 요청을 보내지 않는다.
5. **전제** 회원이 메인 화면을 보고 있다, **실행** 생성 결과가 아닌 원격 알림이나 프로젝트 식별자·상태를 파싱할 수 없는 원격 알림이 도착한다, **결과** 프로젝트 목록 요청을 보내지 않는다.

---

### 시나리오 3 - 알림을 눌러 앱을 열면 생성 결과가 반영된다 (우선순위: P1, 구현됨)

사용자가 프로젝트 생성을 요청한 뒤 앱을 종료하거나 백그라운드로 보낸다. 생성 완료 알림이 도착해
사용자가 그 알림을 눌러 앱을 열면, 앱이 백그라운드에서 결과를 받지 못했더라도 알림에 담긴 생성
결과로 기록을 갱신하고 "지금 불러오기" 버튼을 정상 상태로 되돌린다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 보고된 증상(알림은 왔는데 버튼이 잠긴 채)의 가장 유력한 경로이며, 알림을 본 뒤 앱으로 들어오는 가장 흔한 동선이다.

**독립 테스트**: 진행 중 기록이 있는 상태에서 백그라운드 결과 수신 없이 생성 결과 알림 탭만 전달했을 때 기록이 완료·실패로 바뀌고 Home 상태가 갱신되는지 확인한다.

**수용 시나리오**:

1. **전제** 프로젝트 A의 진행 중 기록이 있고 앱이 결과를 받지 못한 채 종료되어 있다, **실행** 사용자가 A의 생성 완료 알림을 눌러 앱을 연다, **결과** A의 기록이 완료로 바뀌고 버튼이 활성화되며, 포그라운드 진입(시나리오 1)에 따라 A가 목록에 나타난다.
2. **전제** 앱이 백그라운드에 있고 A의 진행 중 기록이 있다, **실행** A의 생성 실패 알림을 눌러 앱으로 돌아온다, **결과** A의 기록이 실패로 바뀌고 버튼이 활성화된다.
3. **전제** A의 결과가 이미 백그라운드 수신으로 반영되었다, **실행** 같은 결과 알림을 다시 누른다, **결과** 기록과 화면 상태가 바뀌지 않고 알림이 중복 예약되지 않는다.

---

### 시나리오 4 - 관찰 시작 전에 도착한 결과도 반영된다 (우선순위: P1, 구현됨)

앱이 원격 알림으로 새로 실행되거나 실행 직후처럼 생성 결과 관찰을 아직 시작하지 않은 시점에 결과가
도착해도, 그 결과를 잃지 않고 관찰이 시작되는 즉시 반영한다.

**주요 행위자**: 최종 사용자, 연동 시스템(원격 알림)

**우선순위 이유**: 결과 전달 경로가 여러 개가 되는 만큼 전달 시점과 무관하게 보존되어야 시나리오 3이 유효하다.

**독립 테스트**: 결과를 먼저 전달한 뒤 관찰을 시작하고, 방출된 상태에 그 결과가 반영되는지 자동 테스트로 확인한다.

**수용 시나리오**:

1. **전제** A의 진행 중 기록이 있고 결과 관찰이 시작되지 않았다, **실행** A의 완료 결과가 도착한 뒤 관찰이 시작된다, **결과** 관찰이 방출하는 상태에서 A가 완료로 반영된다.
2. **전제** 관찰 시작 전에 같은 프로젝트의 결과가 두 번 도착했다, **실행** 관찰이 시작된다, **결과** 결과가 한 번만 반영된다.

---

### 시나리오 5 - 결과를 끝내 받지 못해도 실행 중 고착되지 않는다 (우선순위: P2, 구현됨)

결과 알림이 어느 경로로도 도착하지 않으면, 진행 중 기록이 보관 기한을 넘기는 시점에 앱을 다시 실행하지
않아도 기록이 정리되어 버튼이 풀린다. 앱이 다시 활성화될 때도 저장소의 최신 기록을 읽고 기한이 지난 기록을 정리한다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 서버가 알림을 보내지 않거나 사용자가 알림 권한을 끈 경우처럼 앱이 막을 수 없는 누락에 대한 최종 안전장치다.

**독립 테스트**: 결과 없이 시각을 보관 기한 이후로 진행시킨 뒤 관찰 상태가 진행 중 기록 없이 다시 방출되는지 자동 테스트로 확인한다.

**수용 시나리오**:

1. **전제** A의 진행 중 기록이 있고 앱이 포그라운드로 실행 중이다, **실행** 결과 없이 보관 기한이 지난다, **결과** 재실행이나 화면 전환 없이 A가 진행 중 상태에서 빠지고 버튼이 활성화된다.
2. **전제** 앱이 백그라운드에 있는 동안 A의 보관 기한이 지났다, **실행** 앱으로 돌아온다, **결과** 활성화 시점에 기록이 정리되어 버튼이 갱신되고, 시나리오 1에 따라 목록도 갱신된다.

---

### 시나리오 6 - 공유 확장에서 등록한 생성이 앱에 반영된다 (우선순위: P2, 구현됨)

사용자가 앱을 백그라운드에 둔 채 공유 확장으로 저장소를 등록하고 앱으로 돌아오면, 앱이 그 생성 기록을 반영해 버튼을 잠근다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 확장으로 등록한 생성이 앱에 보이지 않아 중복 등록 진입이 열리는 불일치다.

**독립 테스트**: 앱 프로세스 밖에서 공유 저장소에 진행 중 기록을 쓴 뒤 앱 활성화 이벤트를 전달했을 때 관찰 상태에 그 기록이 반영되는지 확인한다.

**수용 시나리오**:

1. **전제** 앱이 백그라운드로 실행 중이다, **실행** 공유 확장으로 B를 등록한 뒤 앱으로 돌아온다, **결과** 버튼이 생성 중 상태로 바뀐다.
2. **전제** 공유 확장으로 등록한 B의 결과가 앱이 백그라운드일 때 반영되지 않았다, **실행** B의 결과 알림을 눌러 앱을 연다, **결과** 시나리오 3과 같이 B의 결과가 반영된다.

---

### 시나리오 7 - 실기기에서 결과 수신과 목록 갱신 경로를 검증한다 (우선순위: P3)

개발자가 실기기에서 서버가 보내는 실제 생성 결과 알림을 앱 상태별로 받아, 어떤 경로로 결과가 반영되고
목록이 갱신되는지와 서버 알림 payload가 전제 조건을 충족하는지 기록한다.

**주요 행위자**: 개발자

**우선순위 이유**: 시뮬레이터로 판단하지 못한 백그라운드 수신 동작과 서버 payload 계약을 확인해야 시나리오 1~6의 효과와 남은 위험을 판단할 수 있다.

**독립 테스트**: [실기기 검증 기록](./device-verification.md)에 상태별 관찰 결과가 모두 채워졌는지 확인한다.

**수용 시나리오**:

1. **전제** 실기기에 개발 빌드가 설치되어 있다, **실행** 포그라운드·백그라운드·사용자 강제 종료 후 알림 탭의 세 상태에서 생성 결과 알림을 받는다, **결과** 상태별로 결과 수신 경로 호출 여부, 기록 갱신 여부, 버튼·목록 상태가 기록된다.
2. **전제** 서버 생성 결과 알림을 한 건 이상 수신했다, **실행** payload를 확인한다, **결과** content-available 포함 여부, 프로젝트 식별자·상태 키와 값 형식, 등록 응답의 프로젝트 식별자와의 일치 여부가 기록된다.
3. **전제** 앱이 포그라운드에 있다, **실행** 생성 완료 원격 알림을 받아 목록이 자동 갱신된다, **결과** 그 갱신 응답에 알림의 프로젝트가 포함되었는지가 기록된다.

---

### 예외·경계 사례

- 하나의 생성 결과 원격 알림이 여러 수신 경로(표시 직전 콜백과 백그라운드 수신 콜백)로 들어오거나 같은 결과가 다시 도착해도 목록 요청은 한 번만 시작된다. 같은 결과는 `projectId`와 `status`가 같고 앞선 도착으로부터 보관 기한(1시간) 안인 결과다. 같은 프로젝트라도 상태가 다른 결과는 새 계기다.
- 포그라운드 진입과 생성 결과 원격 알림 수신이 거의 동시에 일어나면, 나중 계기가 진행 중인 요청을 취소하고 새로 요청한다. 동시에 진행되는 목록 요청은 언제나 하나다.
- 짧은 시간에 생성 결과 원격 알림이 여러 개 연달아 오면, 알림마다 진행 중인 요청을 취소하고 새로 요청한다. 목록에는 마지막 알림 이후 시작한 요청의 응답만 반영된다.
- 취소된 요청은 실패로 취급하지 않는다. 오류 표시나 마지막 성공 목록 유지(FR-006) 판단에 쓰지 않는다.
- 자동 갱신 계기가 진행 중인 수동 새로고침과 겹쳐도 같은 규칙(취소 후 새로 요청)을 따른다.
- 목록 갱신이 실패하면 마지막으로 성공한 목록을 그대로 보여 주고, 이 자동 갱신 때문에 별도 오류 화면이나 경고를 띄우지 않는다.
- 사용자가 여러 페이지를 불러온 상태에서 자동 갱신이 일어나면 기존 수동 새로고침과 같이 첫 페이지 응답만 남기고 목록 전체를 교체한다. 이미 불러온 뒤쪽 페이지는 버리고 다음 페이지는 다시 이어 받는다. 사용자가 목록 중간을 스크롤하던 중이어도 이로 인한 스크롤 위치 변화는 허용한다.
- 사용자가 프로젝트 삭제 모드에 있는 동안 갱신이 일어나도 기존 수동 새로고침과 같은 규칙을 따른다.
- 알림 탭으로 앱이 백그라운드에서 포그라운드로 올라오는 경우는 포그라운드 진입(시나리오 1)으로 처리된다. 종료 상태에서 알림 탭으로 새로 실행되는 경우는 백그라운드→활성 전환이 아니므로, 목록은 앱 시작 시 최초 로드로 받는다.
- 백그라운드를 거치지 않은 비활성→활성 전환(제어 센터, 알림 센터, 시스템 권한 알럿, Apple 로그인 시트, 앱 전환기를 열었다 닫음)은 목록 갱신 계기가 아니다.
- 알림 payload에 프로젝트 식별자나 상태가 없거나 알 수 없는 상태 값이면 생성 기록을 바꾸지 않고 목록 갱신 계기(FR-002)로도 쓰지 않는다.
- 결과 알림의 프로젝트가 생성 기록에 없으면(이미 정리됨, 다른 계정, 재설치 후) 기록과 버튼 상태를 바꾸지 않는다. 포그라운드 중이면 목록 갱신 계기(FR-002)로는 쓴다.
- 같은 결과가 백그라운드 수신·알림 표시·알림 탭으로 여러 번 전달되면 한 번만 반영되고 결과 알림도 한 번만 예약된다.
- 결과가 등록 응답의 프로젝트 식별자 연결보다 먼저 도착해도 결과를 잃지 않는다.
- 이미 완료·실패로 확정된 기록에 반대 상태의 결과가 뒤늦게 도착하면 먼저 확정된 상태를 유지한다.
- 로그아웃 뒤에 도착하거나 보존된 결과는 새 로그인 세션의 기록에 반영하지 않는다.
- 보존 중인 결과가 무한히 쌓이지 않도록 보존 수와 기간에 상한을 둔다.
- 완료 알림이 예약된 뒤 울리기 전에 로그아웃하거나 프로젝트를 삭제하면 알림이 울리지 않는다.
- 알림 권한이 꺼진 동안 결과가 도착했다가 사용자가 권한을 켠 뒤 앱이 활성화되면, 결과 도착 후 5분이 지난 결과에 대해서는 로컬 알림을 발송하지 않는다.
- 유효 시간 판정은 로컬 알림을 예약하는 시점에 한 번 한다. 판정을 통과한 알림은 결과 반영 즉시 울린다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 회원 사용자가 메인 화면 흐름(홈, 프로젝트 목록, 그 위에 뜬 상세·풀이·등록 흐름 포함)에 있을 때 앱이 백그라운드에서 활성 상태로 돌아오면 프로젝트 목록을 서버에서 다시 받아와야 한다. 백그라운드를 거치지 않은 비활성→활성 전환으로는 목록을 요청하지 않아야 한다.
- **FR-002**: 시스템은 회원 사용자가 메인 화면 흐름에 있고 앱이 포그라운드인 동안 생성 결과 원격 알림을 받으면, 알림의 표시 여부와 수신 경로(백그라운드 수신·알림 표시)와 관계없이 프로젝트 목록을 서버에서 다시 받아와야 한다. 생성 결과 원격 알림은 payload에서 프로젝트 식별자와 완료·실패 상태를 파싱하는 데 성공한 알림이며, 그 프로젝트의 생성 기록이 있는지와 무관하다. 그 밖의 원격 알림과 파싱에 실패한 알림으로는 목록을 요청하지 않아야 한다.
- **FR-003**: 시스템은 앱이 포그라운드가 아닐 때 받은 생성 결과 원격 알림으로는 목록을 요청하지 않아야 한다. 이 경우 목록은 다음 포그라운드 진입 때 갱신된다.
- **FR-004**: 시스템은 게스트 사용자이거나 로그인 전 화면에 있을 때는 FR-001, FR-002의 목록 요청을 보내지 않아야 한다.
- **FR-005**: 시스템은 하나의 계기(포그라운드 진입 한 번 또는 생성 결과 원격 알림 하나)로 목록 요청을 두 번 이상 시작하지 않아야 한다. 새 계기가 올 때 목록 첫 페이지 요청이 진행 중이면 그 요청을 취소하고 새로 요청해야 하며, 취소된 요청의 응답은 목록에 반영하지 않아야 한다. 동시에 진행되는 목록 첫 페이지 요청은 하나를 넘지 않아야 한다.
- **FR-006**: 자동 갱신이 실패하면 시스템은 마지막으로 성공한 목록을 유지해야 하며, 자동 갱신 실패만으로 오류 화면이나 경고를 표시하지 않아야 한다.
- **FR-007**: 자동 갱신은 사용자가 보고 있는 화면 전환, 앞에 떠 있는 상세·풀이·등록 흐름, 알림 배너 표시 방식에 영향을 주지 않아야 한다. 목록 내용이 첫 페이지로 교체되면서 생기는 목록 스크롤 위치 변화는 예외로 허용한다.
- **FR-008**: 자동 갱신은 홈의 프로젝트 목록과 프로젝트 목록 탭에 같은 결과를 반영해야 한다.

#### 생성 상태 고착 해결 (045에서 이관, 괄호는 045 원 식별자)

- **FR-009** (045 FR-001, 구현됨): 시스템은 사용자가 생성 결과 원격 알림을 눌러 앱을 열거나 앱으로 돌아올 때, 또는 앱이 포그라운드에서 그 알림을 표시하기 직전에, 알림에 담긴 생성 결과를 백그라운드 수신과 같은 방식으로 생성 기록에 반영해야 한다.
- **FR-010** (045 FR-002, 구현됨): 시스템은 앱이 종료된 상태에서 생성 결과 알림으로 실행될 때도 FR-009와 같은 결과를 보장해야 한다.
- **FR-011** (045 FR-003, 구현됨): 시스템은 생성 결과 관찰을 시작하기 전에 도착한 결과를 보존했다가 관찰이 시작되면 반영해야 한다.
- **FR-012** (045 FR-004, 구현됨): 시스템은 같은 프로젝트의 같은 결과가 여러 경로나 여러 번으로 도착해도 기록 전이와 결과 알림 예약을 한 번만 수행해야 한다.
- **FR-013** (045 FR-005, 구현됨): 시스템은 회원 상태에서 앱이 활성화될 때마다 공유 생성 기록 저장소의 최신 상태를 다시 읽어, 앱 밖에서 추가·변경된 기록과 보관 기한이 지난 기록의 정리를 버튼 상태에 반영해야 한다.
- **FR-014** (045 FR-006, 구현됨): 시스템은 앱이 실행 중일 때 진행 중 기록이 보관 기한에 도달하면 재실행이나 활성화 없이 그 시점에 기록을 정리하고 변경된 상태를 방출해야 한다.
- **FR-015** (045 FR-008, 구현됨): 시스템은 식별자·상태가 없거나 형식이 맞지 않는 알림 payload, 생성 기록에 없는 프로젝트의 결과로 기록을 바꾸지 않아야 한다.
- **FR-016** (045 FR-009, 구현됨): 시스템은 로그아웃 시 보존 중인 결과를 모두 폐기해야 한다.
- **FR-017** (045 FR-010, 구현됨): 시스템은 보존 중인 결과의 개수와 보존 기간에 상한을 두어야 하며, 보존 기간은 생성 기록 보관 기한을 넘지 않아야 한다.
- **FR-018** (045 FR-011, 구현됨): 시스템은 생성 결과 원격 알림의 수신, 파싱 성공·실패, 기록 반영 여부를 전달 경로(백그라운드 수신·알림 표시·알림 탭)와 함께 진단 로그로 남겨 실기기에서 경로별 동작을 확인할 수 있게 해야 한다.
- **FR-019** (045 FR-012): 개발자는 실기기에서 포그라운드·백그라운드·사용자 강제 종료 후 알림 탭의 세 상태별 결과 수신 경로, 기록 갱신 여부와 버튼·목록 상태, 서버 payload의 content-available 포함 여부와 키·값 형식, 생성 완료 알림 직후 갱신한 목록에 그 프로젝트가 포함되는지를 [실기기 검증 기록](./device-verification.md)으로 남겨야 한다.
- **FR-020** (045 FR-013): 이 변경은 서버의 알림 payload와 API를 바꾸지 않아야 하며, 생성 상태나 프로젝트 목록을 주기적으로 조회하는 폴링을 추가하지 않아야 한다(019 FR-022 유지).
- **FR-021** (045 FR-014, 구현됨): 시스템은 리마인드 대상을 알림 권한 여부와 무관하게 유지하되, 생성 결과가 반영되는 시점에 알림 권한이 있고 그 결과의 도착 시각으로부터 5분(유효 시간) 안인 경우에만 로컬 알림을 발송해야 한다. 결과 도착 시각은 백그라운드 수신이면 수신 시각, 알림 표시·탭·알림으로 인한 실행이면 원격 알림이 전달된 시각으로 한다. 유효 시간을 넘긴 대상은 발송하지 않고 폐기해야 하며, 권한이 나중에 허용되더라도 폐기된 대상이나 유효 시간을 넘긴 결과로 알림을 발송하지 않아야 한다.
- **FR-022** (045 FR-015, 구현됨): 시스템은 로그아웃하면 예약된 생성 결과 로컬 알림을 모두 취소하고, 프로젝트를 삭제하거나 해당 프로젝트의 생성 기록이 정리(보관 기한 만료 포함)되면 그 프로젝트의 예약된 로컬 알림을 울리기 전에 취소해야 한다. 프로젝트를 삭제하면 그 프로젝트의 생성 기록도 해제해야 한다.

#### 폐기한 045 요구사항

- 045 FR-007(생성 기록 정리로 목록 제외 대상에서 빠진 프로젝트가 있으면 목록 재조회): 목록 제외 필터가 `0d6e197`에서 제거되어 전제가 사라졌다. 목록 최신화는 FR-001, FR-002의 계기가 대신한다.

### 핵심 엔터티

- **프로젝트 목록**: 사용자가 가진 학습 프로젝트 요약의 목록. 서버가 기준이며 앱은 첫 페이지부터 다시 받아 최신화한다.
- **갱신 계기**: 목록을 다시 받게 만드는 사건. 이 기능에서는 포그라운드 진입과 포그라운드 중 생성 결과 원격 알림 수신 두 가지다.
- **생성 기록**: 저장소 URL, 프로젝트 식별자(등록 후 연결), 요청 시각, 상태(진행 중·완료·실패), 종료 시각을 가진다. 앱과 공유 확장이 함께 쓰는 공유 저장소에 영속되며, Home "지금 불러오기" 버튼 잠금의 유일한 근거다.
- **생성 결과**: 프로젝트 식별자, 완료·실패 상태, 도착 시각으로 구성된다. 백그라운드 원격 알림 수신, 알림 표시, 알림 탭, 알림으로 인한 앱 실행 중 어느 경로로든 전달될 수 있다.
- **보존 중인 결과**: 관찰 시작 전이나 프로젝트 식별자 연결 전에 도착해 아직 기록에 반영하지 못한 생성 결과다. 개수·기간 상한과 로그아웃 시 폐기 규칙을 가진다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 회원이 앱을 백그라운드에서 포그라운드로 올린 뒤, 네트워크가 정상일 때 2초 안에 목록이 서버 목록과 같아진다. 백그라운드를 거치지 않은 비활성→활성 전환에서는 목록 요청이 0회다.
- **SC-002**: 회원이 앱을 보고 있는 동안 생성 결과 원격 알림이 도착하면, 네트워크가 정상일 때 2초 안에 목록이 서버 목록과 같아진다. 사용자의 추가 조작은 0회다.
- **SC-003**: 게스트·로그인 전 상태에서 포그라운드 진입과 생성 결과 원격 알림 수신이 일어나도, 그리고 회원 상태에서 생성 결과가 아니거나 파싱할 수 없는 원격 알림이 도착해도 프로젝트 목록 요청은 0회다.
- **SC-004**: 앱이 백그라운드에 있는 동안 생성 결과 원격 알림이 도착해도 그 시점의 프로젝트 목록 요청은 0회다.
- **SC-005**: 생성 결과 원격 알림 하나(여러 수신 경로로 전달되거나 같은 결과가 다시 도착한 경우 포함) 또는 포그라운드 진입 한 번당 시작하는 목록 요청은 최대 1회다. 계기가 연달아 일어나는 자동 테스트 사례의 100%에서 동시에 진행되는 목록 요청은 1개 이하이고, 목록에는 마지막 계기 이후 시작한 요청의 응답만 반영된다.
- **SC-006**: 기존 수동 새로고침, 페이지 이어 받기, 삭제 후 목록 갱신 동작의 자동 테스트가 변경 전후 모두 통과한다.
- **SC-007** (045 SC-001): 진행 중 기록이 있고 백그라운드 결과 수신이 없었던 상태에서 생성 결과 알림을 눌러 앱을 연 모든 검증 사례(종료 상태·백그라운드 상태 각 1건 이상)에서, 앱 화면이 표시된 뒤 2초 이내에 기록이 결과 상태로 바뀌고 버튼이 활성화된다.
- **SC-008** (045 SC-002, 충족): 결과가 관찰 시작보다 먼저 도착하는 자동 테스트 사례의 100%에서 결과가 한 번만 반영된다.
- **SC-009** (045 SC-003, 충족): 결과 없이 보관 기한이 지나는 자동 테스트 사례의 100%에서, 재실행·활성화 이벤트 없이 기한 시점에 진행 중 기록이 빠진 상태가 방출된다.
- **SC-010** (045 SC-004, 충족): 앱 밖에서 공유 저장소에 기록을 추가한 뒤 활성화 이벤트를 전달하는 자동 테스트 사례의 100%에서, 활성화 후 방출되는 상태에 그 기록이 반영된다.
- **SC-011** (045 SC-005, 충족): 같은 결과를 두 경로로 전달하는 자동 테스트 사례의 100%에서 결과 알림 예약이 1회만 일어난다.
- **SC-012** (045 SC-006): 기존 ProjectGeneration, Project, 생성 기록 저장소, 푸시 결과 소스 관련 테스트가 변경 후에도 모두 통과한다.
- **SC-013** (045 SC-007): 실기기 검증 기록에 세 가지 앱 상태의 관찰 결과, 서버 payload 확인 결과, 생성 완료 알림 직후 갱신한 목록에 그 프로젝트가 포함되는지가 빈칸 없이 채워진다.
- **SC-014** (045 SC-008, 충족): 결과 도착 후 5분이 지난 뒤 권한을 켜고 앱을 활성화하는 자동 테스트 사례의 100%에서 로컬 알림 예약이 0회이고, 5분 안에 권한이 있는 사례의 100%에서 1회다.
- **SC-015** (045 SC-009, 충족): 예약 후 울리기 전에 로그아웃·프로젝트 삭제·기록 정리가 일어나는 자동 테스트 사례의 100%에서 해당 예약이 취소된다.

## 가정

- "APNs 알림 수신"은 생성 결과 원격 알림으로 한정한다(명확화 2026-09-27). 판정은 생성 기록 반영에 쓰는 것과 같은 payload 파싱 결과를 따르며, 목록 갱신 계기로 쓰더라도 관찰 시작 전에 보존된 결과가 생성 기록 반영(FR-011)에서 빠지지 않아야 한다.
- 알림 권한이 꺼져 있으면 표시 콜백이 호출되지 않으므로, 이 경우 포그라운드 중 수신은 백그라운드 수신이 가능한 생성 결과 알림(`content-available`)일 때만 감지된다. 서버 payload 형식은 이 기능에서 바꾸지 않는다.
- 목록 자동 갱신(FR-001~FR-008)은 프로젝트 목록만 다시 받는다. "지금 불러오기" 버튼 잠금은 생성 기록으로 결정되며 FR-009~FR-022가 다룬다. 앱 활성화 시 목록 갱신과 생성 상태 동기화는 같은 계기에서 일어나지만 서로의 결과를 기다리지 않는다.
- 회원이 메인 화면 흐름에 있을 때 앱 활성화로 목록을 다시 받는 동작은 이미 일부 존재한다. 현재 동작은 백그라운드를 거치지 않은 비활성→활성 전환에서도 목록을 다시 받으므로, 이 기능은 계기를 백그라운드→활성 전환으로 좁혀 요구사항으로 확정하고, 포그라운드 중 생성 결과 원격 알림 수신 계기를 새로 추가한다.
- 목록을 다시 받는 방법과 실패 처리는 기존 수동 새로고침 규칙을 그대로 따른다.
- 목록 자동 갱신(FR-001~FR-008)에는 별도 진단 로그를 두지 않는다. 실기기 검증에서 목록 요청 횟수와 취소 여부는 Xcode Instruments의 네트워크 계측이나 HTTP 프록시 같은 네트워크 계측으로 확인한다. 생성 결과 수신 경로의 진단 로그(FR-018)는 그대로 유지한다.
- 서버 API와 원격 알림 발송 방식은 바꾸지 않는다.
- 서버는 생성 결과 원격 알림을 보내는 시점에 그 프로젝트를 목록 API 응답에 이미 반영했다고 가정한다(명확화 2026-09-28). 앱은 알림 뒤 지연 요청이나 재시도를 두지 않는다. 이 가정은 시나리오 7에서 검증하며, 어긋나면 서버 협의 항목으로 분리한다. 그 전까지는 다음 포그라운드 진입이나 수동 새로고침이 복구 경로다.
- 서버의 생성 결과 원격 알림은 사용자에게 보이는 알림 내용과 함께 프로젝트 식별자(`projectId`)와 상태(`status`: `completed`/`failed`)를 payload에 담는다. 이 가정은 시나리오 7에서 검증하며, 어긋나면 서버 협의 항목으로 분리한다.
- 알림 탭 경로는 사용자가 알림 권한을 허용해 알림이 표시된 경우에만 동작한다. 알림 권한이 없는 사용자는 백그라운드 수신, 앱 활성화 동기화, 보관 기한 정리(시나리오 5)에 의존한다.
- 진행 중 기록의 보관 기한(요청 후 1시간)은 기존 정책을 유지한다. 준비 대기 시간은 `0d6e197`에서 제거되어 적용하지 않는다.
- 공유 확장은 대부분 다른 앱 위에서 실행되므로 앱은 그동안 백그라운드에 있다. 따라서 앱 활성화 시 재동기화(FR-013)로 충분하다고 보고, 프로세스 간 실시간 변경 알림은 요구하지 않는다.
- 사용자가 강제 종료한 앱이 백그라운드 원격 알림으로 깨어나지 않는 것은 iOS 정책이며 앱이 바꿀 수 없다.
- 알림 옵션 시트의 수락·거절 선택은 리마인드 발송 판정에 쓰지 않는다(현재 동작 유지). 선택 반영은 후속 과제로 남긴다.
- 서버 생성 상태 조회 API는 현재 없다. 알림이 누락될 때 보관 기한 전에 복구하는 서버 조회 방식은 대안으로만 기록하며, 채택하려면 019 FR-022 결정을 다시 논의해야 한다.
