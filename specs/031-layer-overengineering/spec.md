**브랜치 상태**: `생성`

**상태**: 초안

**입력**: 사용자 설명: "docs/review/layer-overengineering-requirements.md 의 요구사항을 기능 명세로 정의한다. 값을 더하지 않는 계층과 간접 참조를 제거해 구조적 복잡성을 줄인다. 전제: Domain↔Data 경계 구조는 현행 유지, Feature는 단일 target 유지. 근거와 FR-1~FR-5, 수용 기준은 해당 문서를 따른다."

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 프로토콜을 두는 근거를 규칙으로 고정한다 (우선순위: P1)

이 저장소를 고치는 개발자가 새 타입을 만들 때, 프로토콜을 둘지 말지를 관례가 아니라 기록된 두 가지 근거로 판단한다. 근거가 없으면 구체 타입 하나만 만든다.

**주요 행위자**: 이 저장소에서 기능을 추가·수정하는 개발자와 PR 리뷰어

**우선순위 이유**: 기준이 먼저 서지 않으면 시나리오 2·3으로 줄인 계층이 다음 기능에서 같은 형태로 다시 생긴다. 이 시나리오만 적용해도 이후 PR에서 불필요한 프로토콜 추가를 막을 수 있다.

**독립 테스트**: 공통 컨벤션 문서에서 기준 절을 찾아 읽고, 현재 남아 있는 프로덕션 프로토콜을 그 기준으로 하나씩 분류할 수 있는지 확인한다. 분류되지 않는 프로토콜이 있으면 기준이 불완전한 것이다.

**수용 시나리오**:

1. **전제** 개발자가 새 타입에 프로토콜을 둘지 고민한다, **실행** 공통 컨벤션의 프로토콜 생성 기준 절을 읽는다, **결과** 패키지 경계를 넘는 계약인지, 프로덕션에 구현 교체 지점이 실재하는지 두 질문으로 판단이 끝난다.
2. **전제** 어떤 타입에 테스트 더블이 필요하다, **실행** 기준을 적용한다, **결과** 그 타입에 프로토콜을 두는 대신, 그 타입이 의존하는 경계 계약에 더블을 주입하는 방법이 안내된다.
3. **전제** 리뷰어가 프로토콜을 추가한 PR을 본다, **실행** 기준의 두 근거 중 어느 것에 해당하는지 확인한다, **결과** 어느 쪽에도 해당하지 않으면 근거 부족으로 지적할 수 있다.

---

### 시나리오 2 - 단일 구현 Data 계약을 걷어낸다 (우선순위: P2)

Data 패키지 안에서만 쓰이고 구현이 하나뿐인 Remote·Store 계약을 없애, Composition 조립이 구체 타입을 직접 받게 한다. 계약이 보장하던 검증 항목은 하나도 잃지 않는다.

**주요 행위자**: Data·Composition을 수정하는 개발자

**우선순위 이유**: 파일 수와 주입 배관이 가장 많이 줄어드는 구간이다. 서버 응답 필드가 하나 늘 때 손대야 하는 지점이 줄어든다.

**독립 테스트**: 대상 계약 파일이 사라졌는지 확인하고, 제거 전후 Data 테스트의 검증 항목 수를 비교한다. 줄어들지 않았고 Data·Composition 테스트가 통과하면 이 시나리오만으로 검증된다.

**수용 시나리오**:

1. **전제** `AuthenticationRemote` 계약과 그 계약 테스트가 있다, **실행** 계약을 제거하고 Composition 어댑터가 `HTTPAuthenticationRemote`를 직접 받게 한다, **결과** 계약 테스트가 보장하던 항목이 구현 테스트에 남아 있고 Data·Composition 테스트가 통과한다.
2. **전제** 어댑터 테스트가 계약 더블을 주입하고 있다, **실행** 계약을 제거한다, **결과** 어댑터 테스트가 `HTTPTransport` 스텁으로 구성되며 같은 동작을 검증한다.
3. **전제** 프로덕션 구현이 하나도 없는 계약이 있다, **실행** 기준을 적용한다, **결과** 그 계약과 그것만을 위해 존재하는 테스트 더블이 함께 제거된다.

---

### 시나리오 3 - 의미가 같은 오류 case 중복을 없앤다 (우선순위: P3)

Data 오류와 Domain 오류가 의미 차이 없이 1:1로 대응하는 구간을 정리해, Composition 어댑터가 반복하는 재매핑 분기를 줄인다.

**주요 행위자**: Composition 어댑터를 읽고 수정하는 개발자

**우선순위 이유**: 범위가 좁고 어댑터 코드가 즉시 줄어든다. 다만 시나리오 2보다 감소 폭이 작아 뒤에 둔다.

**독립 테스트**: 정리 전후 어댑터의 오류 재매핑 분기 수를 세어 비교하고, 오류 전파 테스트가 같은 Domain 오류를 계속 관측하는지 확인한다.

**수용 시나리오**:

1. **전제** Data 오류와 Domain 오류에 이름과 의미가 같은 case가 있다, **실행** 중복을 정리한다, **결과** 어댑터의 재매핑 분기 수가 줄고 같은 입력에 같은 Domain 오류가 나온다.
2. **전제** Domain이 Data 오류를 노출하면 안 된다, **실행** 정리 결과를 확인한다, **결과** Domain 공개 API에 Data 오류 타입이 나타나지 않는다.

---

### 예외·경계 사례

- 계약을 제거했는데 그 계약 테스트가 보장하던 항목을 옮길 구현 테스트가 없으면 어떻게 하는가? — 구현 테스트를 먼저 추가한 뒤 계약 테스트를 제거한다. 옮길 곳이 없다고 판단하면 제거 근거를 대조표에 남긴다.
- 하나의 테스트 더블이 여러 계약을 동시에 채택하고 있으면 어떻게 하는가? — 그 더블이 채택한 계약이 모두 제거될 때 더블도 함께 제거하고, 남는 계약이 있으면 더블을 그 계약으로 좁힌다.
- 아직 다른 명세가 소유 중인 계약은 어떻게 하는가? — 이 명세에서 건드리지 않고, 소유 명세가 끝난 뒤 별도로 판단한다.
- Data 오류 case를 통합했는데 서버 응답 코드가 그 구분에 의존하고 있으면 어떻게 하는가? — 구분이 실제로 쓰이므로 의미 차이가 있다고 보고 통합하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 공통 컨벤션 문서는 프로젝트가 소유한 타입에 프로토콜을 두는 근거를 두 가지로 한정해 기록해야 한다 — (1) 패키지 경계를 넘는 계약이다, (2) 경계를 넘지 않더라도 구현을 교체하는 지점이 프로덕션에 실재한다.
- **FR-002**: 공통 컨벤션 문서는 테스트 더블 제공만을 근거로 프로토콜을 두지 않는다는 규칙과, 그 대신 의존하는 경계 계약에 더블을 주입한다는 대안을 함께 기록해야 한다.
- **FR-003**: Data 패키지의 Remote·Store 계약 중 프로덕션 구현이 하나 이하이고 패키지 경계를 넘지 않는 것을 제거해야 한다. 대상은 `AuthenticationRemote`, `ExternalRepositoryRemote`, `AnswerRemote`, `BookmarkRemote`, `LearningSetRemote`, `ProjectRemote`, `MemberRemote`, `QuizGenerationRemote`, `PolicyConsentStore`이다.
- **FR-004**: Composition 어댑터는 FR-003으로 제거된 계약 자리에 Data 구체 타입을 직접 받아야 한다.
- **FR-005**: FR-003으로 제거되는 계약 테스트가 보장하던 항목은 대응하는 구현 테스트로 이관해야 하며, 이관처 또는 제거 근거를 계약 하나마다 대조표에 기록해야 한다. Data 테스트의 총 검증 항목 수가 줄어서는 안 된다.
- **FR-006**: FR-003으로 제거된 계약만을 위해 존재하던 테스트 더블을 함께 제거해야 한다. 남는 계약이 있는 더블은 그 계약 범위로 좁힌다.
- **FR-007**: 어댑터 테스트는 제거된 계약의 더블 대신 `HTTPTransport` 스텁으로 구성해야 한다.
- **FR-008**: Data 오류와 Domain 오류에서 이름과 의미가 모두 같아 재매핑이 항등에 가까운 case를 식별하고, 의미 차이가 없는 구간의 Data 오류를 통합하거나 제거해 어댑터의 재매핑 분기를 줄여야 한다.
- **FR-009**: Domain 오류 타입은 유지해야 하며, Domain 공개 API가 Data 오류 타입을 노출해서는 안 된다.
- **FR-010**: 이 명세 적용 후의 프로덕션 Swift 파일 수와 프로덕션 프로토콜 수를 기록하고, 남은 프로덕션 프로토콜 각각이 FR-001의 두 근거 중 어느 것에 해당하는지 대응시켜야 한다.
- **FR-011**: `GenerationStateStore`와 `QuizGenerationOutcomeSource`는 이 명세에서 제거하지 않는다. 앞선 명세가 소유한 계약이며 이 명세의 판단 대상이 아니다.
- **FR-012**: 위임 전용 UseCase 계층은 이 명세에서 다루지 않는다. UseCase 통합을 다루는 별도 명세가 소유한다.

### 핵심 엔터티

- **프로토콜 생성 기준**: 프로젝트가 소유한 타입에 프로토콜을 둘 근거 두 가지와, 테스트 더블만을 근거로 삼지 않는다는 배제 규칙. 공통 컨벤션 문서가 소유한다.
- **보장 항목 대조표**: 제거한 계약 테스트가 보장하던 항목과 그것을 이어받은 구현 테스트의 1:1 대응. 이어받을 곳이 없으면 제거 근거를 담는다.
- **구조 기준선**: 적용 시점의 프로덕션 Swift 파일 수, 프로덕션 프로토콜 수와 각 프로토콜의 존치 근거.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 공통 컨벤션에서 프로토콜 생성 기준을 찾아 읽는 데 문서 한 곳만 확인하면 되고, 그 기준으로 남은 프로덕션 프로토콜 전부를 두 근거 중 하나에 분류할 수 있다.
- **SC-002**: Data 패키지의 프로덕션 Contracts 파일에서 FR-003의 대상 9개가 사라진다.
- **SC-003**: Data 테스트의 총 검증 항목 수가 적용 전보다 줄지 않는다.
- **SC-004**: Composition 어댑터가 주입받는 Data 타입에 FR-003 대상 계약이 남아 있지 않고, 해당 어댑터 테스트가 `HTTPTransport` 스텁으로 구성된다.
- **SC-005**: Composition 어댑터의 오류 재매핑 분기 수가 적용 전보다 줄어든다.
- **SC-006**: 제거한 계약 테스트 하나마다 이관처 또는 제거 근거가 대조표에 기록되어 있다.
- **SC-007**: 프로덕션 Swift 파일 수와 프로덕션 프로토콜 수가 적용 전후 값으로 기록되어 있고, 둘 다 적용 전보다 줄어든다.
- **SC-008**: Domain·Data·Composition·Feature·App의 기존 테스트가 적용 전후 동일하게 통과한다.

## 가정

- 적용 시점의 기준선은 프로덕션 Swift 파일 497개, 프로덕션 프로토콜 56개, Data 프로덕션 Contracts 파일 11개다. 근거 문서가 기록한 513개·58개는 그 이후 진행된 명세들로 이미 줄어든 값이다.
- `QuizGenerationRemote`는 프로덕션 구현이 없고 테스트 더블과 계약 테스트만 참조한다. FR-003의 "구현이 하나 이하" 조건에 해당해 대상에 포함한다.
- Domain↔Data 경계 구조(Domain 계약 ← Composition Adapter → Data API)는 유지한다. 이 명세는 그 경계 안쪽의 중복만 다룬다.
- Feature는 단일 target을 유지한다.
- Infrastructure의 `HTTPClient`·`HTTPTransport` 계약은 패키지 경계를 넘으므로 FR-001의 첫 근거를 충족한다. 제거 대상이 아니다.
- 서버 API 응답 스키마와 HTTP 상태·오류 코드 매핑 규칙은 바꾸지 않는다.
- Data 테스트의 "검증 항목 수"는 `#expect`와 `#require` 호출 수로 센다.
