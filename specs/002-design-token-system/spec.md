## 명확화

### Session 2026-08-12

- Q: 행간 백분율을 실제 표시 행 높이로 바꾸는 규칙은 무엇인가? → A: 토큰은 백분율만 보유하고, 실제 행 높이 계산은 적용 시점(토큰 적용 수단)에 위임한다.
- Q: 그라데이션 방향을 값에 어떻게 표현하는가? → A: 방향은 두 점(시작점·끝점)의 좌표비율(0~1)로 정의한다. 각 토큰의 기본 좌표는 참고 디자인 미리보기와 같은 시각적 방향(`Gradient 1`~`Gradient 3` 모두 위→아래)이 되도록 정한다.
- Q: 시스템 글자 크기 설정이 바뀌면 텍스트 스타일의 크기·행간은 어떻게 되는가? → A: 시스템 글자 크기 설정과 무관하게 항상 디자인 문서의 고정 크기·행간을 유지한다.
- Q: 한글과 영문이 한 문장에 섞인 경우 어느 글꼴 패밀리를 적용하는가? → A: 문자 단위로 스크립트를 판별해 한글과 기본 문자(숫자·공백·기호를 포함한 영문 알파벳 외 문자)에는 `Noto Sans`, 영문 알파벳에는 `Plus Jakarta Sans`를 적용한다(2026-08-13 정정).

## 사용자 시나리오 및 테스트 *(필수)*

이 기능의 사용자는 화면을 구현하는 기능 개발자, 디자인 시스템을 유지보수하는 담당자, 그리고 그 결과로 일관된 화면을 보게 되는 앱 최종 사용자입니다.

### 사용자 스토리 1 - 화면 구현자가 토큰만으로 스타일을 적용한다 (우선순위: P1)

기능 개발자가 새 화면을 만들 때 색상 값이나 글꼴 크기를 직접 적어 넣지 않고, 디자인 문서에 적힌 이름과 같은 이름의 토큰(`Blue500`, `Headline 1`, `Margin` 등)을 골라 화면 요소에 적용합니다. 적용 방법은 요소 하나에 한 줄로 스타일을 붙이는 방식이며, 텍스트 스타일 하나를 적용하면 글꼴, 굵기, 크기, 행간, 자간이 함께 적용됩니다.

**이 우선순위인 이유**: 토큰이 실제 화면에 적용되지 못하면 나머지 가치가 성립하지 않습니다. 이 스토리만 구현해도 화면 구현에서 하드코딩을 제거하고 디자인 일관성을 확보하는 최소 가치가 나옵니다.

**독립 테스트**: 디자인 참고 문서의 화면 예시 하나를 토큰만 사용해 구성하고, 화면 어디에도 색상 값·글꼴 이름·수치가 직접 등장하지 않는지 확인하는 것으로 완결 검증할 수 있습니다.

**수용 시나리오**:

1. **Given** 디자인 문서에 `Subtitle 2`로 표기된 텍스트 요소가 있을 때, **When** 개발자가 같은 이름의 텍스트 스타일 토큰을 적용하면, **Then** 글꼴·굵기·크기·행간·자간이 디자인 문서의 값과 동일하게 반영된다.
2. **Given** 디자인 문서에 `Blue500` 배경으로 표기된 요소가 있을 때, **When** 개발자가 같은 이름의 색상 토큰을 배경에 적용하면, **Then** 화면에 `#2F3853`이 표시된다.
3. **Given** 디자인 문서에 `Gradient 2` 배경으로 표기된 요소가 있을 때, **When** 개발자가 같은 이름의 그라데이션 토큰을 적용하면, **Then** 정의된 두 정지점과 방향으로 선형 그라데이션이 표시된다.
4. **Given** 화면 좌우 여백 규칙이 있을 때, **When** 개발자가 레이아웃 토큰을 적용하면, **Then** 화면 여백 20, 요소 사이 간격 12가 적용된다.
5. **Given** `가A1!`처럼 한글·영문 알파벳·기본 문자가 섞인 문자열이 있을 때, **When** 텍스트 스타일 토큰을 적용하면, **Then** `가`·`1`·`!`에는 `Noto Sans`, `A`에는 `Plus Jakarta Sans`가 적용된다.

### 사용자 스토리 2 - 디자인 값이 바뀌어도 화면 코드를 고치지 않는다 (우선순위: P2)

디자인 담당자가 팔레트의 색을 조정하거나, 텍스트 스타일의 크기를 바꾸거나, 토큰을 추가·삭제합니다. 유지보수 담당자는 토큰 정의 한 곳만 갱신하고, 이미 그 토큰을 사용하는 화면들은 수정 없이 새 값으로 표시됩니다.

**이 우선순위인 이유**: 사용자가 "데이터는 변경될 수 있습니다"라고 명시한 핵심 제약입니다. 값 변경 비용이 화면 수에 비례하면 토큰 도입의 이점이 사라집니다.

**독립 테스트**: 색상 토큰 하나와 텍스트 스타일 토큰 하나의 값을 바꾼 뒤, 화면 구현 코드를 한 줄도 수정하지 않고 변경이 반영되는지 확인해 검증할 수 있습니다.

**수용 시나리오**:

1. **Given** 여러 화면이 `Blue300`을 사용하고 있을 때, **When** `Blue300`의 값이 다른 색으로 바뀌면, **Then** 해당 화면들은 수정 없이 새 색으로 표시된다.
2. **Given** 디자인에 새 색상 단계가 추가될 때, **When** 토큰 정의에 항목을 추가하면, **Then** 기존 토큰을 사용하는 화면은 영향을 받지 않고 새 토큰을 즉시 사용할 수 있다.
3. **Given** 사용 중인 토큰이 디자인에서 삭제될 때, **When** 토큰 정의에서 항목을 제거하면, **Then** 해당 토큰을 참조하던 위치가 빌드 시점에 오류로 드러난다.
4. **Given** 텍스트 스타일의 크기와 행간이 조정될 때, **When** 정의만 갱신하면, **Then** 그 스타일을 쓰는 모든 텍스트의 행간이 함께 갱신된다.

---

### 사용자 스토리 3 - 토큰 정의를 화면 없이 검증한다 (우선순위: P3)

유지보수 담당자가 디자인 문서와 토큰 정의가 일치하는지, 누락·중복·오타가 없는지를 화면을 띄우지 않고 확인합니다. 토큰 값 자체는 UI 프레임워크와 무관한 순수 데이터이므로 화면 렌더링이나 시뮬레이터 없이 점검할 수 있습니다.

**이 우선순위인 이유**: 값 변경이 잦은 만큼 회귀 확인이 빨라야 하며, 프레임워크 비의존이라는 요구가 실제로 지켜지는지를 증명하는 수단입니다.

**독립 테스트**: 토큰 정의만 대상으로 하는 검증을 화면 구성 없이 실행해, 디자인 문서에 정의된 항목 수와 값이 모두 일치하는지 확인해 검증할 수 있습니다.

**수용 시나리오**:

1. **Given** 디자인 문서에 정의된 토큰 목록이 있을 때, **When** 토큰 정의를 점검하면, **Then** 누락된 토큰과 문서에 없는 토큰이 각각 드러난다.
2. **Given** 토큰 값이 잘못 입력되었을 때, **When** 화면을 실행하지 않고 검증을 수행하면, **Then** 어떤 토큰의 어떤 값이 어긋났는지 식별된다.

---

### 예외 상황

- 한 문장에 한글·영문 알파벳·기본 문자가 섞인 경우, 문자 단위 판별로 인해 한 텍스트 스타일 안에서 두 글꼴이 함께 렌더링되는 것을 어떻게 검증하는가?
- 행간이 백분율(예: 148%)로 정의되어 실제 값이 소수점으로 계산될 때, 적용 수단의 단일 변환 규칙이 어떤 기준 값과 반올림 방식을 쓰는지 검증 가능한가?
- 불투명도 토큰(`white 15`, `white 30`, `white 70`, `Black 70`)이 배경 위에 겹쳐질 때 최종 표시 색을 어떻게 정의하는가?
- 서로 다른 이름의 토큰이 같은 색상 값을 갖는 경우(`Grey100`과 흰색 계열) 이름과 값 중 무엇을 기준으로 취급하는가?
- 사용자가 시스템 글자 크기를 크게 설정한 경우, 텍스트 스타일의 크기와 행간이 디자인 문서의 고정 값으로 유지되어 시스템 접근성 확대 기능과 별개로 동작하는 것을 어떻게 안내하는가?
- 그라데이션이 적용될 요소의 가로세로 비율이 디자인과 다를 때, 좌표비율로 정의된 시작점·끝점이 요소 크기에 비례해 재계산되어 정지점 위치가 유지되는가?
- 디자인 문서에 없는 값이 화면 구현에 필요해진 경우 어떤 경로로 처리하는가?

## 요구사항 *(필수)*

### 기능 요구사항

**토큰 모델**

- **FR-001**: 토큰 값 모델은 UI 프레임워크나 플랫폼 화면 기술에 의존하지 않는 순수 데이터로 정의해야 한다(`MUST`). 화면 구성 요소 없이 값의 존재와 내용을 확인할 수 있어야 한다.
- **FR-002**: 각 토큰의 이름은 디자인 참고 문서의 표기와 1:1로 대응해야 한다(`MUST`). 디자이너가 문서에서 부르는 이름으로 개발자가 토큰을 찾을 수 있어야 한다.
- **FR-003**: 토큰은 원시 값 그룹(색상, 그라데이션, 타이포그래피, 레이아웃)으로 분류되어야 하며, 그룹은 디자인 문서의 분류를 따라야 한다(`MUST`).
- **FR-004**: 존재하지 않는 토큰을 참조하는 시도는 화면 실행 이전에 드러나야 한다(`MUST`). 잘못된 이름이 조용히 기본값으로 대체되어서는 안 된다(`MUST NOT`).

- **FR-006**: 불투명도가 포함된 색상 토큰 `white 15`(`#FFFFFF` 15%), `white 30`(`#FFFFFF` 30%), `white 70`(`#FFFFFF` 70%), `Black 70`(`#000000` 70%)을 제공해야 한다(`MUST`). 불투명도는 토큰 값의 일부로 표현되어야 하며 사용처에서 별도로 지정하지 않아도 되어야 한다(`MUST`).
- **FR-007**: 상태 색상 토큰 `Error`(`#FF3721`), `Caution`(`#ECBD23`), `Success`(`#249900`)를 제공해야 한다(`MUST`).
- **FR-008**: 선형 그라데이션 토큰 `Gradient 1`(`#3B3749` → `#56718A`), `Gradient 2`(`#141414` → `#A5C4F0`), `Gradient 3`(`#82ACE5` → `#D5E7FE`)를 제공해야 한다(`MUST`). 각 토큰은 정지점 위치(0%, 100%)를 값에 포함해야 한다(`MUST`).
- **FR-008a**: 그라데이션 방향은 시작점과 끝점의 좌표비율(가로 0~1, 세로 0~1)로 정의해야 한다(`MUST`). 세 토큰의 기본 좌표는 참고 디자인 미리보기와 같은 시각적 방향(위 `(0.5, 0)` → 아래 `(0.5, 1)`)을 갖는다(`MUST`). 좌표비율은 요소의 실제 가로세로 크기와 무관하게 상대 위치를 유지해야 한다(`MUST`).

- **FR-010**: 글꼴 패밀리 토큰으로 한글 및 기본 문자용 `Noto Sans`와 영문 알파벳용 `Plus Jakarta Sans`를 제공해야 한다(`MUST`). 한 문자열 안에 문자가 섞인 경우 문자 단위로 판별해 한글과 기본 문자(숫자·공백·기호를 포함한 영문 알파벳 외 문자)에는 `Noto Sans`, 영문 알파벳에는 `Plus Jakarta Sans`를 적용해야 한다(`MUST`).
- **FR-011**: 텍스트 스타일 토큰은 행간을 백분율 값으로만 보유해야 한다(`MUST`). 백분율을 실제 표시 행 높이로 변환하는 계산은 토큰 적용 수단이 수행하며, 변환 규칙(기준 값과 반올림 방식)은 적용 수단 한 곳에만 존재해야 한다(`MUST`). 화면 구현이 행 높이를 개별적으로 계산하거나 스타일마다 다른 방식으로 변환해서는 안 된다(`MUST NOT`).
- **FR-012**: 지정한 글꼴을 사용할 수 없는 경우 텍스트가 사라지지 않도록 대체 글꼴로 표시하되, 크기·굵기·행간 값은 유지해야 한다(`MUST`).

**레이아웃 토큰**

- **FR-013**: 레이아웃 토큰으로 화면 좌우 여백 `Margin`(20)과 요소 사이 간격 `Gutter`(12)를 제공해야 한다(`MUST`).

**적용 방식**

- **FR-014**: 화면 요소에 토큰을 적용하는 수단을 제공해야 하며(`MUST`), 최소한 다음을 지원해야 한다: 텍스트 스타일 적용, 전경색 적용, 배경색 적용, 그라데이션 배경 적용, 레이아웃 여백 적용.
- **FR-015**: 텍스트 스타일 적용은 한 번의 적용으로 글꼴·굵기·크기·행간·자간이 모두 반영되어야 한다(`MUST`). 개별 속성을 사용처에서 나누어 지정하도록 요구해서는 안 된다(`MUST NOT`).
- **FR-016**: 화면 구현에서 색상 값, 글꼴 이름, 글자 크기, 여백 수치를 직접 기재하지 않고 토큰만으로 스타일을 완성할 수 있어야 한다(`MUST`).
- **FR-017**: 토큰 적용 수단은 토큰 값 모델을 사용하는 쪽에 위치해야 하며, 토큰 값 모델이 적용 수단에 의존해서는 안 된다(`MUST NOT`).

**변경 대응**

- **FR-018**: 토큰의 값이 변경되면 그 토큰을 사용하는 모든 화면에 사용처 수정 없이 반영되어야 한다(`MUST`).
- **FR-019**: 토큰이 추가되면 기존 사용처는 영향을 받지 않아야 하며(`MUST`), 토큰이 제거되면 해당 토큰을 참조하던 위치가 빌드 시점에 드러나야 한다(`MUST`).
- **FR-020**: 토큰 값 전체를 하나의 교체 가능한 집합으로 다룰 수 있어야 하며(`MUST`), 집합을 교체해도 사용처의 토큰 참조 방식은 동일하게 유지되어야 한다(`MUST`). 활성 집합은 항상 하나이며, 실행 중에 사용처가 집합을 선택하도록 해서는 안 된다(`MUST NOT`).
- **FR-021**: 텍스트 스타일 토큰의 크기와 행간은 시스템 글자 크기 설정과 무관하게 디자인 문서의 고정 값을 유지해야 한다(`MUST`). 사용자의 접근성 글자 크기 설정에 비례해 확대·축소해서는 안 된다(`MUST NOT`).
- **FR-022**: 토큰 집합은 참고 디자인에 정의된 단일 팔레트 하나만 제공해야 한다(`MUST`). 다크 모드 등 외관 설정에 따라 같은 토큰 이름이 다른 값을 갖도록 해서는 안 된다(`MUST NOT`).
- **FR-023**: 토큰은 디자인 문서에 표기된 원시 값 토큰만 제공해야 한다(`MUST`). 역할 기반 시맨틱 토큰 계층(예: 본문 텍스트 색, 화면 배경 색, 구분선 색)을 정의해서는 안 되며(`MUST NOT`), 사용처는 원시 토큰 이름으로 직접 참조한다.

### 핵심 엔터티

- **색상 토큰**: 이름과 색상 값(선택적 불투명도 포함)을 갖는 단일 색. 그룹(Blue, Purple, Grey, Opacity, State)에 속한다.
- **그라데이션 토큰**: 이름, 종류(선형), 시작점·끝점의 좌표비율(0~1)로 표현된 방향, 그리고 위치와 색으로 구성된 정지점 목록을 갖는다. 정지점의 색은 색상 값으로 표현된다.
- **텍스트 스타일 토큰**: 이름, 글꼴 패밀리, 굵기, 크기, 행간(백분율), 자간, 문단 간격, 문단 들여쓰기를 갖는다.
- **글꼴 패밀리 토큰**: 이름과 사용 문자 범위(한글·기본 문자/영문 알파벳)를 갖는다. 텍스트 스타일 토큰이 참조한다.
- **레이아웃 토큰**: 이름과 수치를 갖는 간격 값(`Margin`, `Gutter`).
- **토큰 집합**: 위 토큰들의 전체 묶음. 값 변경과 교체의 단위이며, 사용처는 개별 토큰 이름으로만 이 집합을 참조한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 참고 디자인 문서에 정의된 토큰 24개 색상(Blue 5, Purple 5, Grey 7, 불투명도 4, 상태 3), 그라데이션 3개, 텍스트 스타일 10개, 레이아웃 값 2개가 빠짐없이 제공되어 누락률 0%이다.
- **SC-002**: 토큰 값 하나를 변경할 때 수정해야 하는 위치는 정의 1곳이며, 그 토큰을 사용하는 화면 구현의 수정 줄 수는 0이다.
- **SC-003**: 참고 디자인의 화면 예시를 구현했을 때, 화면 구현에 직접 기재된 색상 값·글꼴 이름·글자 크기·여백 수치가 0건이다.
- **SC-004**: 토큰 정의의 정확성 검증을 화면 렌더링이나 기기·시뮬레이터 실행 없이 100% 수행할 수 있다.
- **SC-005**: 구현된 텍스트 스타일과 색상을 디자인 문서와 대조했을 때, 크기·행간의 오차가 1 이내이고 색상 값은 완전히 일치하며, 문자 분류별 글꼴 패밀리 불일치 건수는 0건이다.
- **SC-006**: 디자인 문서에서 토큰 이름을 확인한 개발자가 다른 문서를 참고하지 않고 해당 토큰을 찾아 적용할 수 있으며, 이름 대응 실패 건수가 0이다.
- **SC-007**: 토큰이 제거되거나 이름이 바뀐 경우, 영향을 받는 사용처가 실행 전 단계에서 100% 식별된다.
- **SC-008**: 제공되는 토큰 이름과 화면이 참조하는 토큰 이름 중 참고 디자인 문서에 존재하지 않는 이름(역할 이름 등)이 0건이며, 하나의 토큰 이름이 상황에 따라 서로 다른 값을 갖는 경우가 0건이다.

## 가정

- 참고 디자인 문서는 `docs/design-system-ref`의 이미지 4종(`Design system`, `Variable collection`, `Color Styles`, `Text Styles`)이며, 이 문서의 값이 현재 기준입니다. 이미지에서 잘려 표시된 그라데이션 정지점 값은 동봉된 벡터 파일의 정의에서 확인했습니다.
- "데이터는 변경될 수 있습니다"는 토큰 값·구성이 이후에 바뀔 수 있다는 의미로 해석했습니다. 값을 원격에서 내려받아 실행 중에 교체하는 동작은 요구되지 않은 것으로 보고 범위에서 제외했습니다. 변경은 정의를 갱신해 다시 배포하는 방식으로 반영됩니다.
- 토큰 값은 사용처가 아니라 단일 정의 지점이 소유하며, 사용처는 이름으로만 참조합니다.
- 색상은 참고 문서 표기대로 sRGB 16진수 값을 기준으로 합니다.
- 텍스트 스타일의 크기 단위는 참고 문서의 pt 표기를 따르며, 화면 표시 단위로 그대로 사용합니다.
- 글꼴 `Noto Sans`와 `Plus Jakarta Sans`는 제품에 포함되어 사용 가능한 상태로 준비된다고 가정합니다. 준비 자체는 이 기능의 범위 밖이며, 사용할 수 없을 때의 동작만 FR-012에서 정의합니다.
- 팔레트는 참고 디자인의 단일 구성만 사용하기로 결정했습니다(FR-022). 다크 팔레트 값이 참고 문서에 없고, 값 변경 요구는 정의 갱신만으로 충족되기 때문입니다. 이후 복수 테마가 필요해지면 FR-020의 집합 교체 구조를 확장하는 별도 변경으로 처리합니다.
- 토큰 이름 체계는 원시 값 이름만 사용하기로 결정했습니다(FR-023). 참고 문서에 역할 정의가 없어 매핑을 새로 만들면 FR-002의 1:1 이름 대응이 깨지고, 디자이너와 개발자가 서로 다른 이름을 쓰게 되기 때문입니다.
- `Grey100`은 참고 문서 표기에 따라 `#FFFFFF`이며, 불투명도 그룹의 흰색 토큰과는 이름과 용도가 구분되는 별개의 토큰으로 취급합니다.
- 레이아웃 가이드의 `Margin: 20`, `Gutter: 12`는 각각 화면 좌우 여백과 요소 사이 간격을 의미하는 것으로 해석했습니다.
- 이 기능은 여러 기능 화면이 공유하는 시각 언어를 제공하며, 아키텍처 문서의 UI 경계 책임에 해당합니다.

## 범위 밖

- 버튼, 입력창 등 재사용 UI 구성요소의 설계와 구현(토큰을 소비하는 별도 작업).
- 아이콘, 일러스트, 이미지 자산 체계.
- 그림자, 모서리 반경, 애니메이션 등 참고 디자인 문서에 정의되지 않은 토큰 범주.
- 디자인 도구에서 토큰 정의를 자동으로 내보내거나 동기화하는 도구 구축.
- 값을 원격에서 내려받아 실행 중에 교체하는 동작.
- 다크 모드 등 복수 테마 지원과 외관 설정에 따른 토큰 값 전환.
- 시스템 글자 크기(접근성 확대) 설정에 따른 텍스트 스타일의 비례 확대.
- 역할 기반 시맨틱 토큰 계층과 역할↔원시 토큰 매핑 정의.
- 기존 화면의 일괄 마이그레이션.
