# 기능 명세: HTTP 통신 기술 API

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/http-client`

**생성일**: 2026-08-14

**상태**: 초안

**입력**: 사용자 설명: "Core 패키지에 HTTPClient  구현"

## 명확화

### 세션 2026-08-14

- 질문: 성공이 아닌 상태 코드일 때 응답 본문을 어떤 방식으로 전달하는가? → 답변: 성공 상태 코드
  (200~299)에서만 호출자가 지정한 형식으로 변환하고, 그 밖의 상태 코드에서는 변환하지 않은 원형
  본문을 상태 코드·헤더와 함께 전달한다.
- 질문: 서버가 다른 위치로 이동을 지시하는 응답을 보내면 어떻게 처리하는가? → 답변: 이동을
  자동으로 따라가지 않고, 이동 지시 상태 코드와 원형 본문을 그대로 응답 결과로 전달한다.
- 질문: 성공 상태 코드인데 응답 본문이 비어 있으면 어떻게 처리하는가? → 답변: 시스템이 빈 본문을
  특별 취급하지 않고 호출자가 지정한 변환 규칙에 그대로 넘겨 성공 여부를 그 규칙이 결정한다.
  다만 본문 내용이 빈 컬렉션을 나타내는 경우는 본문 없음이나 실패가 아니라 정상 값으로 전달한다.
- 질문: 취소와 응답 시간 초과가 동시에 성립하면 어느 원인을 전달하는가? → 답변: 취소를 우선해
  항상 취소로 구분되는 결과를 전달한다.
- 질문: 기본 응답 대기 한도를 얼마로 정하는가? → 답변: 60초를 기본값으로 하되, 이후 값 변경에
  대응할 수 있도록 한 곳에서 바꿀 수 있는 구성값으로 다룬다.
- 질문: 쿼리 파라미터를 어떤 방식으로 표현하는가? → 답변: 경로 문자열에 섞지 않고 이름-값 모음을
  요청의 별도 항목으로 받으며, 전송 규칙에 맞는 부호화는 이 기능이 수행한다.
- 질문: 쿼리 파라미터의 중복 이름과 빈 값을 어떻게 처리하는가? → 답변: 같은 이름을 여러 번
  허용하고 지정 순서를 보존하며, 값이 비어 있어도 파라미터를 제거하지 않고 그대로 전송한다.
- 질문: 요청 방식의 허용 범위를 어떻게 정하는가? → 답변: GET, POST, PUT, PATCH, DELETE, HEAD로
  이뤄진 닫힌 집합만 허용하고, 그 밖의 요청 방식은 지정할 수 없게 한다.
- 질문: 헤더 이름의 대소문자를 어떻게 취급하는가? → 답변: 헤더 병합과 조회 모두 대소문자를
  구분하지 않으며, 헤더 이름을 하나의 표기로 정규화해 전달한다. 서버가 보낸 원래 표기는 보존하지
  않는다.
- 질문: 통신 진단과 기록은 누가 책임지는가? → 답변: 이 기능은 자체 기록도 관찰 수단도 제공하지
  않으며, 전달받은 요청·응답·실패 원인을 바탕으로 호출자가 직접 기록한다.

## 사용자 시나리오와 테스트 *(필수)*

이 기능의 사용자는 원격 서버와 데이터를 주고받는 경계를 구현하는 개발자입니다. 구체적으로는
Data 계약과 Core 기술 API를 연결하는 Adapter 구현자가 직접 사용자이며, 그 결과로 서버 통신
결과와 실패 안내를 보게 되는 앱 최종 사용자가 간접 사용자입니다.

### 사용자 스토리 1 - 경계 구현자가 원격 요청을 보내고 응답을 받는다 (우선순위: P1)

Adapter 구현자가 서버의 특정 자원에 대해 요청 방식, 경로, 헤더와 본문을 정해 요청을 보내고,
서버가 돌려준 상태 코드·헤더·본문을 받아 자신의 경계 모델로 변환합니다. 성공 응답의 본문은
구현자가 지정한 형식으로 변환되어 오므로 바이트를 직접 다루지 않고, 성공이 아닌 응답에서는
상태 코드와 원형 본문을 받아 구현자가 직접 해석합니다. 서버 주소와 공통 헤더는 미리 구성하고,
요청마다 달라지는 값만 그때그때 지정합니다.

**우선순위 이유**: 요청을 보내고 응답을 받는 능력이 없으면 이 기능의 나머지 가치가 성립하지
않습니다. 이 스토리만 구현해도 서버 연동 경계를 실제로 만들 수 있는 최소 가치가 나옵니다.

**독립 테스트**: 임의의 요청 하나를 구성해 보내고, 지정한 요청 방식·경로·헤더·본문이 그대로
전달되며 응답의 상태 코드·헤더와 본문이 손실 없이 돌아오는지 확인해 완결 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** 기본 주소와 공통 헤더를 구성한 상태, **실행** 상대 경로와 조회 요청 방식으로 요청을
   보내면, **결과** 기본 주소와 상대 경로가 결합된 대상으로 요청이 전달되고 공통 헤더가 함께
   전송된다.
2. **전제** 공통 헤더에 이미 존재하는 헤더 이름을 대소문자만 다르게 요청별 헤더로도 지정한 상태,
   **실행** 요청을 보내면, **결과** 둘이 같은 헤더로 취급되어 요청별 값 하나만 전송된다.
3. **전제** 공백과 비ASCII 문자가 섞인 쿼리 파라미터 값을 지정한 상태, **실행** 요청을 보내면,
   **결과** 호출자가 부호화를 직접 하지 않았는데도 값의 의미가 손상되지 않은 대상으로 전송된다.
4. **전제** 같은 이름의 쿼리 파라미터를 값만 달리해 두 번 지정하고 값이 빈 파라미터도 포함한
   상태, **실행** 요청을 보내면, **결과** 두 값이 지정 순서대로 모두 전송되고 빈 값 파라미터도
   제거되지 않는다.
5. **전제** 호출자가 자신의 값으로 본문을 지정한 생성 요청, **실행** 요청을 보내면, **결과** 그
   값이 호출자가 지정한 형식으로 변환되어 전송된다.
6. **전제** 호출자가 응답 본문의 형식을 지정한 상태, **실행** 서버가 성공 상태 코드로 응답하면,
   **결과** 응답 본문이 그 형식의 값으로 변환되어 상태 코드·헤더와 함께 전달된다.
7. **전제** 서버가 성공이 아닌 상태 코드로 응답한 상태, **실행** 응답을 받으면, **결과** 본문
   변환을 시도하지 않고 상태 코드·헤더와 변환하지 않은 원형 본문이 응답 결과로 전달되며 실패로
   단정하지 않는다.
8. **전제** 성공이 아닌 상태 코드의 응답 본문이 호출자가 지정한 성공 형식과 다른 상태, **실행**
   응답을 받으면, **결과** 변환 실패가 아니라 정상 응답으로 전달되어 호출자가 상태 코드를 확인할
   수 있다.
9. **전제** 빈 본문을 허용하는 변환 규칙을 지정한 요청, **실행** 서버가 성공 상태 코드로 본문 없이
   응답하면, **결과** 시스템이 빈 본문을 따로 판단하지 않고 그 규칙에 넘겨 정상 응답으로 전달된다.
10. **전제** 목록 형식의 응답을 기대하는 요청, **실행** 서버가 성공 상태 코드로 원소가 없는 목록을
    응답하면, **결과** 본문 없음이나 실패가 아니라 원소가 없는 값으로 변환되어 정상 전달된다.
11. **전제** 서버가 다른 위치로 이동을 지시하는 상태, **실행** 요청을 보내면, **결과** 이동 대상으로
    추가 요청이 전송되지 않고 이동 지시 상태 코드와 원형 본문이 그대로 전달된다.

### 사용자 스토리 2 - 통신 실패의 원인을 구분해 처리한다 (우선순위: P2)

Adapter 구현자가 통신이 실패했을 때 그 원인을 구분합니다. 요청 대상을 만들 수 없는 경우, 요청
본문을 변환하지 못한 경우, 네트워크가 끊겨 요청이 서버에 닿지 못한 경우, 응답이 제한 시간 안에
오지 않은 경우, 사용자가 화면을 벗어나 요청이 취소된 경우, 성공 응답의 본문을 기대한 형식으로
변환하지 못한 경우를 각각 다르게 처리해 상위 경계에 서로 다른 의미로 전달할 수 있어야 합니다.
재시도할지 여부는 이 기능이 아니라 원인을 받은 호출자가 결정합니다.

**우선순위 이유**: 실패 원인을 구분하지 못하면 상위 경계가 "재시도해도 되는 실패"와 "상태를
정리해야 하는 실패"를 구별할 수 없습니다. 이는 로그인 상태 유지·재시도 같은 이미 확정된 제품
요구사항을 충족하지 못하게 만듭니다.

**독립 테스트**: 각 실패 상황을 하나씩 재현하고, 결과로 전달되는 실패 원인이 서로 구분되며
호출자가 원인별로 다른 분기를 작성할 수 있는지 확인해 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** 네트워크에 연결할 수 없는 상태, **실행** 요청을 보내면, **결과** 연결 실패로 구분되는
   결과가 전달된다.
2. **전제** 응답 대기 한도를 짧게 지정한 상태, **실행** 서버 응답이 그보다 늦으면, **결과** 시간
   초과로 구분되는 결과가 전달되고 대기가 종료된다.
3. **전제** 요청이 진행 중인 상태, **실행** 호출자가 요청을 취소하면, **결과** 통신이 중단되고
   취소로 구분되는 결과가 전달된다.
4. **전제** 응답 대기 한도가 끝나는 시점과 취소가 겹친 상태, **실행** 결과를 받으면, **결과**
   시간 초과가 아니라 취소로 구분되는 결과가 전달된다.
5. **전제** 서버가 성공 상태 코드로 응답했으나 본문이 호출자가 지정한 형식과 다른 상태, **실행**
   응답을 받으면, **결과** 응답 본문 변환 실패로 구분되는 결과가 전달된다.
6. **전제** 요청 본문을 지정한 형식으로 변환할 수 없는 상태, **실행** 요청을 시도하면, **결과**
   요청 본문 변환 실패로 구분되는 결과가 전달되고 서버로는 아무것도 전송되지 않는다.
7. **전제** 일시적인 연결 실패가 발생한 상태, **실행** 결과를 받으면, **결과** 같은 요청이 자동으로
   다시 전송되지 않고 호출자가 재시도 여부를 결정할 수 있다.
8. **전제** 어떤 실패가 발생한 상태, **실행** 호출자가 실패 내용을 기록하면, **결과** 인증 토큰과
   자격 증명 값이 기록된 내용에 포함되지 않는다.

### 사용자 스토리 3 - 실제 서버 없이 통신 경계를 검증한다 (우선순위: P3)

경계 구현자와 테스트 작성자가 실제 원격 서버가 없거나 엔드포인트가 확정되지 않은 상태에서도
요청 구성과 응답 처리 흐름 전체를 자동 테스트로 검증합니다. 정해진 응답을 돌려주거나 특정
실패를 일으키는 통신 수단으로 갈아끼워 상위 경계의 동작을 확인합니다.

**우선순위 이유**: 서버 엔드포인트 확정 전에도 개발과 검증을 진행해야 한다는 제약이 이미
존재하며, 실제 네트워크에 의존하는 테스트는 재현성과 실행 속도를 해칩니다.

**독립 테스트**: 실제 네트워크 연결이 없는 환경에서 요청·응답·실패·취소 시나리오를 모두 자동
테스트로 실행해 통과하는지 확인해 검증할 수 있습니다.

**수용 시나리오**:

1. **전제** 미리 정한 응답을 돌려주는 통신 수단으로 구성한 상태, **실행** 요청을 보내면, **결과**
   네트워크 접근 없이 그 응답이 호출자에게 전달된다.
2. **전제** 특정 실패를 일으키도록 구성한 통신 수단, **실행** 요청을 보내면, **결과** 해당 실패
   원인이 그대로 전달되어 호출자의 분기를 검증할 수 있다.
3. **전제** 테스트용 통신 수단으로 구성한 상태, **실행** 요청을 보내면, **결과** 실제로 전달된 요청
   방식·대상·쿼리 파라미터·헤더와 변환된 본문을 검사해 요청 구성이 의도와 같은지 확인할 수 있다.
4. **전제** 성공이 아닌 상태 코드를 돌려주도록 구성한 통신 수단, **실행** 요청을 보내면, **결과**
   호출자가 그 상태 코드와 원형 본문을 검사해 오류 응답 처리 분기를 검증할 수 있다.

### 예외·경계 사례

- 기본 주소와 상대 경로를 결합했을 때 유효한 대상이 만들어지지 않으면 어떻게 되는가?
- 같은 이름의 헤더가 공통 구성과 요청별 구성에 모두 있으면 어느 값이 전송되는가?
- 응답 본문이 매우 크거나 응답이 끊겨 일부만 도착하면 어떻게 처리되는가?
- 여러 요청을 동시에 보낸 상태에서 그중 하나만 취소하면 나머지 요청은 어떻게 되는가?
- 요청 대상이 안전하지 않은 평문 통신을 요구하면 어떻게 되는가?

## 요구사항 *(필수)*

### 범위

**포함**

- 요청-응답 방식의 단발성 원격 통신을 보내고 받는 프로젝트 소유의 범용 기술 능력
- 요청 구성(대상, 요청 방식, 쿼리 파라미터, 헤더, 본문)과 응답 전달(상태 코드, 헤더, 본문)
- 쿼리 파라미터의 전송 규칙에 맞는 부호화
- 요청 본문 변환과, 성공 상태 코드 응답에 한정된 응답 본문 변환
- 통신 실패 원인의 구분과 프로젝트 소유 오류로의 변환
- 요청별·기본 응답 대기 한도와 요청 취소
- 실제 통신 수단을 대체해 자동 테스트를 수행할 수 있는 구성

**제외**

- 특정 서비스의 엔드포인트, 요청·응답 형식과 그 의미 해석
- 성공이 아닌 상태 코드로 받은 오류 본문의 해석
- 이동 지시에 따른 자동 재요청과 이동 대상 해석
- 특정 서비스의 필드 표기 규칙 소유
- 일시적 실패에 대한 자동 재시도와 재시도 정책 결정
- 인증 흐름, 토큰 저장·갱신·폐기 판단
- 실제 서버 연동을 위한 경계 변환 구현과 그 배치
- 지속 연결, 스트리밍 수신, 업로드·다운로드 진행률 보고
- 응답 캐시 정책, 오프라인 요청 보관과 나중 재전송
- 요청·응답의 자체 기록과 외부 관찰 수단 제공

### 기능 요구사항

- **FR-001**: 시스템은 호출자가 지정한 대상, 요청 방식, 쿼리 파라미터, 요청 헤더와 요청 본문으로
  원격 요청을 보낼 수 있어야 한다.
- **FR-002**: 시스템은 수신한 응답의 상태 코드와 응답 헤더를 손실 없이 전달해야 한다. 응답 본문은
  성공 상태 코드(200~299)일 때만 호출자가 지정한 형식의 값으로 변환해 전달하고, 그 밖의 상태
  코드에서는 변환하지 않은 원형 본문을 상태 코드·헤더와 함께 전달해야 한다.
- **FR-003**: 시스템은 상태 코드를 성공 범위(200~299)에 속하는지 판정하는 용도로만 사용해야 하며,
  그 판정 결과는 응답 본문의 변환 여부를 정하는 데에만 쓴다. 시스템은 상태 코드의 서비스적
  의미(인증 만료, 권한 없음, 자원 없음 등)를 판단해서는 안 되며, 응답을 정상적으로 수신했다면
  상태 코드와 무관하게 실패가 아닌 응답 결과로 전달해야 한다.
- **FR-004**: 시스템은 통신 실패를 프로젝트가 소유한 오류로 전달해야 하며, 최소한 다음 여섯
  가지를 서로 구분할 수 있어야 한다: 요청 구성 불가, 요청 본문 변환 실패, 연결 실패, 응답 시간
  초과, 요청 취소, 응답 본문 변환 실패(성공 상태 코드 응답에 한함).
- **FR-005**: 시스템은 외부 통신 기술의 구체 타입과 오류를 이 기능의 경계 밖으로 노출해서는
  안 된다.
- **FR-006**: 시스템은 특정 서버 주소, 엔드포인트 경로 또는 특정 서비스의 데이터 형식을 내부에
  고정해서는 안 되며, 호출자가 구성으로 제공해야 한다.
- **FR-007**: 시스템은 생성 시점에 기본 주소, 공통 헤더와 기본 응답 대기 한도를 구성할 수
  있어야 하고, 요청별로 지정한 값이 공통 값을 대신하도록 해야 한다. 기본 응답 대기 한도를
  구성하지 않으면 60초를 사용해야 한다.
- **FR-008**: 시스템은 응답 대기 한도를 초과하면 대기를 종료하고 시간 초과로 구분되는 결과를
  전달해야 한다.
- **FR-009**: 시스템은 진행 중인 요청이 취소되면 통신을 중단하고 취소로 구분되는 결과를
  전달해야 하며, 취소한 요청 외의 다른 요청에 영향을 주어서는 안 된다. 취소와 응답 대기 한도
  초과가 동시에 성립하면 취소를 우선해 취소로 구분되는 결과를 전달해야 한다.
- **FR-010**: 시스템은 여러 요청을 동시에 수행할 수 있어야 하며, 동시 사용 시 요청과 응답이
  서로 섞이거나 공유 상태가 오염되어서는 안 된다.
- **FR-011**: 시스템은 실제 원격 서버 없이 요청 구성, 본문 변환, 응답 전달, 실패 구분과 취소를
  검증할 수 있도록 실제 통신 수단을 대체 가능한 형태로 제공해야 한다.
- **FR-012**: 시스템은 인증 토큰, 자격 증명과 개인정보가 오류 설명과 값의 문자열 표현에 드러나지
  않도록 해야 하며, 호출자가 그 값을 그대로 기록하더라도 비밀 값이 노출되지 않아야 한다.
- **FR-013**: 시스템은 본문이 없는 요청과 본문이 없는 응답을 표현할 수 있어야 한다. 성공 상태
  코드 응답의 본문이 비어 있어도 시스템이 이를 특별 취급하거나 그 자체로 실패로 판단해서는
  안 되며, 호출자가 지정한 변환 규칙에 그대로 전달해 성공 여부를 그 규칙이 결정하도록 해야 한다.
- **FR-014**: 시스템은 요청 본문을 항상, 응답 본문을 FR-002가 정한 조건에서 호출자가 지정한
  형식의 값으로 변환해야 하며, 변환 대상 형식과 필드 표기 대응 규칙은 호출자가 지정해야 한다.
  시스템은 특정 서비스의 본문 형식이나 필드 표기 규칙을 내부에 고정해서는 안 된다.
- **FR-015**: 시스템은 실패한 요청을 자동으로 다시 보내서는 안 되며, 실패 원인을 그대로 전달해
  재시도 여부와 방식을 호출자가 결정하도록 해야 한다. 한 번의 요청 호출은 최대 한 번만 서버로
  전송되어야 한다.
- **FR-016**: 시스템은 서버가 지시한 이동(3xx)을 자동으로 따라가서는 안 되며, 이동 지시 응답도
  성공이 아닌 상태 코드와 동일하게 상태 코드·헤더와 변환하지 않은 원형 본문으로 전달해야 한다.
  이동 대상으로의 재요청 여부는 호출자가 새로운 요청으로 결정한다.
- **FR-017**: 시스템은 응답 본문의 내용이 빈 컬렉션(원소가 없는 목록 등)을 나타내는 경우를 본문
  없음이나 실패로 해석해서는 안 되며, 변환된 빈 값을 정상 응답으로 전달해야 한다.
- **FR-018**: 시스템은 기본 응답 대기 한도를 한 곳에 정의된 기본 구성값으로 다뤄야 하며, 그 값을
  바꿀 때 이 기능의 다른 정의나 호출자를 함께 수정하지 않아도 되어야 한다.
- **FR-019**: 시스템은 쿼리 파라미터를 이름과 값의 모음으로 받아야 하며, 호출자가 경로 문자열에
  직접 넣거나 부호화를 직접 수행하지 않아도 되도록 전송 규칙에 맞게 부호화해 대상에 결합해야
  한다. 공백, 비ASCII 문자와 예약 문자가 값에 포함되어도 의미가 손상되지 않아야 한다.
- **FR-020**: 시스템은 같은 이름의 쿼리 파라미터를 여러 번 지정할 수 있게 해야 하고 호출자가
  지정한 순서를 보존해 전송해야 하며, 값이 비어 있다는 이유로 파라미터를 제거해서는 안 된다.
- **FR-021**: 시스템은 요청 방식을 GET, POST, PUT, PATCH, DELETE, HEAD로 이뤄진 닫힌 집합으로
  제공해야 하며, 호출자가 그 밖의 값을 요청 방식으로 지정할 수 없어야 한다.
- **FR-022**: 시스템은 헤더 이름을 대소문자 구분 없이 다뤄야 한다. 공통 헤더와 요청별 헤더를
  합칠 때 표기만 다른 같은 이름을 하나의 헤더로 취급해야 하고, 호출자가 응답 헤더를 어떤 표기로
  조회해도 같은 값을 찾을 수 있어야 하며, 헤더 이름은 하나의 표기로 정규화해 전달해야 한다.
- **FR-023**: 시스템은 요청과 응답을 자체적으로 기록하거나 호출자가 끼워 넣는 관찰 수단을
  제공해서는 안 되며, 기록에 필요한 정보는 전달하는 요청·응답·실패 원인만으로 충분해야 한다.

### 핵심 엔터티

- **원격 요청**: 하나의 통신 시도가 무엇을 어디에 요구하는지 표현한다. 대상, 요청 방식, 쿼리
  파라미터 모음, 헤더 모음, 호출자의 값으로 표현된 본문과 이 요청에만 적용할 응답 대기 한도를
  가진다. 요청 방식은 GET, POST, PUT, PATCH, DELETE, HEAD로 이뤄진 닫힌 집합의 한 값이다.
  쿼리 파라미터 모음은 순서를 가진 이름-값 목록이며 같은 이름이 여러 번 나타날 수 있다.
  이름과 값은 부호화되지 않은 상태로 표현하며 부호화는 전송 시점에 이뤄진다.
- **원격 응답**: 서버가 돌려준 결과를 표현한다. 상태 코드, 헤더 모음과 본문을 가진다. 헤더 이름은
  정규화된 표기로 담기며 대소문자 구분 없이 조회된다. 본문은 성공
  상태 코드일 때 호출자가 지정한 형식으로 변환된 값이고 그 밖의 상태 코드에서는 변환하지 않은
  원형 값이다. 서비스적 의미는 포함하지 않는다.
- **본문 변환 규칙**: 호출자의 값과 전송 형식 사이를 오가는 방법을 표현한다. 대상 형식, 필드 표기
  대응과 빈 본문 허용 여부를 포함하며 호출자가 소유한다.
- **통신 실패 원인**: 응답을 받지 못했거나 사용할 수 없는 이유를 서로 구분되는 유한한 값으로
  표현한다. 호출자가 원인별로 다른 처리와 재시도 여부를 선택하는 근거가 된다.
- **통신 구성**: 여러 요청에 공통으로 적용되는 기본값을 표현한다. 기본 주소, 공통 헤더와 기본
  응답 대기 한도를 가진다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 새로운 원격 요청 하나를 연결할 때 이 기능의 정의를 한 줄도 수정하지 않고 구성과
  호출만으로 완료할 수 있다.
- **SC-002**: 명세가 정의한 6가지 실패 원인이 각각 서로 다른 결과로 전달되며, 호출자가 원인별
  분기를 100% 작성할 수 있다.
- **SC-003**: 요청 구성, 본문 변환, 응답 전달, 실패 구분과 취소를 다루는 자동 테스트가 실제
  네트워크 연결 없이 100% 실행되고 통과한다.
- **SC-004**: 이 기능이 경계 밖으로 전달하는 값과 오류에 외부 통신 기술의 고유 타입이 하나도
  포함되지 않는다.
- **SC-005**: 통신 대상 서버의 주소, 엔드포인트 또는 응답 형식이 바뀌어도 이 기능의 정의를
  수정하지 않는다.
- **SC-006**: 서로 다른 요청 10개를 동시에 보내고 그중 1개를 취소했을 때, 나머지 9개가 모두
  각자의 올바른 결과를 받는다.
- **SC-007**: 실패 결과를 기록한 내용에서 인증 토큰과 자격 증명 값이 0건 노출된다.
- **SC-008**: 실패와 이동 지시를 포함한 모든 요청 호출에서 같은 요청이 서버로 2회 이상
  전송되거나 호출자가 지시하지 않은 추가 요청이 전송되는 사례가 0건이다.
- **SC-009**: 성공이 아닌 상태 코드로 받은 응답이 변환 실패로 전달되는 사례가 0건이며, 호출자는
  해당 응답의 상태 코드와 원형 본문을 100% 확인할 수 있다.
- **SC-010**: 원소가 없는 목록을 담은 성공 응답이 실패나 본문 없음으로 전달되는 사례가 0건이다.
- **SC-011**: 취소와 응답 대기 한도 초과가 겹치는 상황을 반복 실행해도 100% 취소로 전달된다.
- **SC-012**: 대기 한도를 따로 지정하지 않은 요청은 응답이 오지 않을 때 60초 이내에 대기가
  종료된다.
- **SC-013**: 기본 응답 대기 한도 값을 바꾸는 데 수정해야 하는 지점이 1곳이며, 호출자 코드는
  수정하지 않는다.
- **SC-014**: 공백, 비ASCII 문자와 예약 문자를 포함한 쿼리 값이 호출자의 추가 처리 없이 100%
  의미 손상 없이 전달되며, 호출자가 부호화를 직접 수행하는 지점이 0곳이다.
- **SC-015**: 같은 이름으로 지정한 쿼리 파라미터가 지정 순서 그대로 100% 전송되고, 빈 값이라는
  이유로 누락되는 파라미터가 0건이다.
- **SC-016**: 헤더 이름의 표기가 달라 조회에 실패하거나 같은 헤더가 중복 전송되는 사례가 0건이다.

## 가정

- 이 명세는 범용 기술 능력만 정의하며, 실제 서비스 엔드포인트 연결과 경계 변환 구현은 별도
  명세와 작업에서 다룬다.
- 상태 코드가 뜻하는 서비스적 의미(예: 인증 만료, 권한 없음)의 판단은 이 기능이 아니라 상위
  경계의 호출자가 수행한다.
- 성공 범위(200~299) 판정은 HTTP 표준이 정한 구분이며 특정 서비스의 규약이 아니므로 이 기능이
  수행해도 서비스 의미 판단에 해당하지 않는다.
- 본문 변환의 대상 형식과 필드 표기 규칙은 호출자가 지정하며, 이 기능은 어떤 서비스의 형식도
  내부에 두지 않는다. 성공이 아닌 상태 코드의 오류 본문 해석도 호출자가 수행한다.
- 이동 지시를 받은 뒤 이동 대상으로 다시 요청할지는 호출자가 새로운 요청으로 결정한다. 이
  기능은 이동 대상 주소를 해석하거나 보관하지 않는다.
- 빈 본문을 정상으로 볼지 실패로 볼지는 호출자가 지정한 변환 규칙이 결정하므로, 같은 상태 코드와
  빈 본문이라도 호출마다 결과가 다를 수 있다. 이는 의도된 동작이다.
- 일시적 통신 실패에 대한 재시도 정책은 상위 경계가 소유한다. 이 기능은 재시도 판단에 필요한
  실패 원인만 제공한다.
- 요청마다 달라지는 인증 헤더는 호출자가 요청별 헤더로 전달한다. 이 기능은 인증 흐름과 토큰의
  존재를 알지 못한다.
- 기본 응답 대기 한도 60초는 확정된 시작값이 아니라 조정될 수 있는 값으로 본다. 실제 서버 응답
  특성이 파악되면 기본 구성값만 바꿔 대응하며, 개별 요청은 요청별 값으로 먼저 조정한다.
- 통신 대상은 보안 전송을 사용하는 것을 전제로 하며, 인증서 고정과 같은 추가 검증 정책은 이번
  범위에 포함하지 않는다.
- 통신 내용의 기록과 진단은 상위 경계가 책임진다. 이 기능은 기록에 필요한 정보를 결과로 전달할
  뿐 무엇을 남길지 결정하지 않는다.
- 자동 테스트는 실제 네트워크에 의존하지 않으며, 대체 가능한 통신 수단으로 수행한다.
