### 확인된 데이터 유실

Data 패키지의 DTO는 필요한 값을 모두 보유하지만, Domain 모델이 그중 일부를 버린다. 아래는 DTO와
Domain 모델을 직접 대조해 확인한 유실이다.

| 값 | Data DTO | Domain 모델 | 상태 |
| --- | --- | --- | --- |
| 세트 설명 | `LearningSetResponseDTO.description` | `LearningSet`에 필드 없음 | 유실 |
| 출처 줄 번호·심볼·설명 | `SourceResponseDTO.startLine`, `.symbol`, `.summary` (배열 `sources`의 각 항목) | `QuestionSource`는 `filePath`, `referenceURL`만 보유하고 `Question.source`는 단수 | 유실 |
| 기존 답변의 선택 index·정답 여부 | `MyAnswerResponseDTO.selectedIndex`, `.correct` | `Question.myAnswer`는 `String?` 하나 | 유실 |

따라서 이번 범위의 데이터 정합 작업은 Data 패키지가 아니라 Domain 모델과 Composition 매핑에서
수행한다.

북마크 여부는 유실이 아니라 애초에 세트 조회 계약에 없다. `QuestionResponseDTO`와 `Question` 모두
북마크 필드를 갖지 않으며, 유일한 출처는 `FetchBookmarkedQuestions(projectID:)`가 반환하는
`BookmarkedQuestionCollection`이다.

### 서술형 채점에 대한 서버 계약

`EssayAnswerResult`는 `explanation`과 `rubric`만 가지며 정오 판정을 포함하지 않는다. 반면
`ChoiceAnswerResult`는 `correct`, `answerIndex`, `explanation`을 가진다. 즉 서버는 서술형을 채점하지
않는다. 완료 화면의 정답 카운터 규칙(FR-037, FR-038)은 이 계약에서 도출한 것이다.

### 시나리오 1 - 객관식 문제를 풀고 결과를 확인한다 (우선순위: P1)

학습자가 객관식 문제에서 선택지 하나를 고르고 제출해, 정답 여부와 정답 선택지, AI 해설을 확인한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 세트 문제의 기본 형식이며, 이 흐름 하나만 완성해도 학습자가 즉시 채점과 해설을
받는 제품의 핵심 가치를 경험할 수 있다.

**독립 테스트**: 객관식 문제 fixture 하나로 미선택 → 선택 → 제출 중 → 결과 상태를 TestStore와
Preview에서 독립 검증한다.

**수용 시나리오**:

1. **전제** 객관식 문제가 편집 상태, **실행** 화면을 확인하면, **결과** 문제 번호, 질문, 선택지 목록, 출처 진입 컨트롤, 북마크, 하단 `확인` CTA가 표시된다. (`s03`)
2. **전제** 선택지가 여러 개 표시된 상태, **실행** 하나를 누르면, **결과** 그 선택지만 선택 상태가 되고 이전 선택은 해제된다. (`s05`)
3. **전제** 선택지가 화면 높이를 넘는 상태, **실행** 스크롤하면, **결과** 문제 본문·선택지·출처는 세로로 스크롤되고 하단 북마크·CTA 영역은 safe area 위에 고정된 채 남는다. (`s06`, `s07`)
4. **전제** 선택지가 하나 선택된 상태, **실행** 제출 입력을 연속으로 두 번 하면, **결과** 제출은 한 번만 일어나고 두 번째 입력은 무시된다.
5. **전제** 제출이 진행 중인 상태, **실행** 결과가 도착하면, **결과** 정답일 때 정답 선택지의 결과 역할, AI 해설, 출처, `다음` CTA가 표시된다. (`s08`)
6. **전제** 제출이 진행 중인 상태, **실행** 오답 결과가 도착하면, **결과** 사용자가 고른 오답 역할과 실제 정답 역할이 서로 구별되는 의미 상태로 동시에 표시된다. (`s09`)
7. **전제** 아직 아무 선택지도 고르지 않은 상태, **실행** 제출 입력을 하면, **결과** 제출이 일어나지 않고 화면 상태가 변하지 않는다.
8. **전제** 제출이 실패한 상태, **실행** 화면을 확인하면, **결과** 선택 상태가 유지되고 다시 제출할 수 있는 입력 경로가 남아 있다.

### 시나리오 2 - 서술형 답안을 작성하고 AI 답안과 비교한다 (우선순위: P1)

학습자가 자유 서술 문제에 답안을 작성해 제출하고, 자신의 답안과 AI 답안을 나란히 확인한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 세트에는 객관식과 서술형이 함께 들어오므로, 서술형이 동작하지 않으면 세트를
끝까지 풀 수 없다.

**독립 테스트**: 서술형 fixture로 빈 상태 → 입력 → 상한 도달 → 제출 → 결과 상태를 독립 검증한다.

**수용 시나리오**:

1. **전제** 서술형 문제가 편집 상태, **실행** 화면을 확인하면, **결과** 문제 번호, 질문, 입력 영역, placeholder, 글자 수 표시, 북마크, 하단 CTA가 표시된다. (`s10`)
2. **전제** 빈 입력 상태, **실행** 답안을 입력하면, **결과** 입력값이 draft로 보존되고 `현재 글자 수 / 400`이 갱신된다. (`s11`)
3. **전제** 답안이 400자에 도달한 상태, **실행** 계속 입력하면, **결과** 400자를 넘는 값이 저장되지 않고 글자 수 표시가 400에 머문다.
4. **전제** 공백만 입력된 상태, **실행** 제출 입력을 하면, **결과** 제출이 일어나지 않는다.
5. **전제** 답안이 입력된 상태, **실행** 제출해 결과가 도착하면, **결과** 편집기가 읽기 전용 결과 표현으로 바뀌고 `나의 답안`과 `AI의 답안`이 별도 카드로 표시된다. (`s12`)
6. **전제** 결과가 표시된 상태, **실행** `나의 답안`을 확인하면, **결과** 제출 당시 사용자 텍스트가 그대로 보존되어 표시된다.

### 시나리오 3 - 선택한 학습 세트를 시작한다 (우선순위: P1)

학습자가 세트 시작 화면에서 세트의 라벨·제목·설명을 확인하고 풀이를 시작한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 개별 문제 풀이에 진입하는 경로이며, 이 화면이 없으면 문제 화면에 도달할 수 없다.

**독립 테스트**: 세트 fixture 하나로 진입 이벤트 → 조회 로딩 → 세트 시작 화면 → 첫 미응답 문제 화면까지 독립 검증한다. 앞쪽 문제에 기존 답변이 있는 fixture로 시작 지점 판정도 함께 검증한다.

**수용 시나리오**:

1. **전제** 프로젝트 상세에 세트가 표시된 상태, **실행** 세트의 진입 컨트롤을 누르면, **결과** 선택한 세트의 식별 정보가 학습 흐름 시작 의도로 전달된다. (`s01`)
2. **전제** 세트 시작 화면이 열린 상태, **실행** 조회가 끝난 화면을 확인하면, **결과** 세트 라벨, 제목, 설명, 뒤로가기, 하단 `시작하기` CTA가 표시된다. (`s02`)
3. **전제** 세트 시작 화면, **실행** `시작하기`를 누르면, **결과** 그 세트의 첫 미응답 문제를 편집 상태로 표시하는 문제 화면으로 전환된다.
4. **전제** 화면 전환이 일어난 상태, **실행** Router 상태를 확인하면, **결과** 이전·이후 활성 화면과 전환 원인 Action이 이동 이벤트로 기록되어 있다.
5. **전제** 앞쪽 문제에 이미 제출한 답변이 있는 세트, **실행** `시작하기`를 누르면, **결과** 답변이 있는 문제는 표시하지 않고 첫 미응답 문제가 표시된다.
6. **전제** 모든 문제에 답변이 있는 세트, **실행** `시작하기`를 누르면, **결과** 첫 문제가 편집 상태로 표시되고 프로젝트·세트의 진행 표시는 그대로 유지된다.
7. **전제** 세트 상세 조회가 진행 중이거나 실패한 상태, **실행** `시작하기`를 누르면, **결과** 풀이가 시작되지 않고 로딩 또는 실패 표현과 재시도 경로가 유지된다.
8. **전제** 문제 화면, **실행** 뒤로가기를 누르면, **결과** 활성 화면이 세트 시작 화면으로 되돌아가고 이동 이벤트가 기록된다.
9. **전제** 뒤로가기로 세트 시작 화면에 돌아온 상태, **실행** `시작하기`를 다시 누르면, **결과** 직전까지 진행하던 문제와 그 입력·결과가 그대로 이어서 표시된다.
10. **전제** 세트 시작 화면, **실행** 뒤로가기를 누르면, **결과** 되돌아갈 이전 화면이 없으므로 흐름을 벗어나 프로젝트 상세로 돌아간다.

### 시나리오 4 - 다음 문제로 진행해 세트를 완료한다 (우선순위: P1)

학습자가 결과를 확인한 뒤 다음 문제로 이동하고, 마지막 문제 뒤에 학습 완료 화면에서 성과를 본다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 개별 문제 풀이를 하나의 학습 단위로 묶어 시작과 끝을 만든다. 완료 화면이 없으면
학습자가 세트를 끝냈다는 사실을 알 수 없다.

**독립 테스트**: 문제 2개 이상 fixture로 `결과 → 다음 문제 → 마지막 결과 → 완료`를 독립 검증한다.

**수용 시나리오**:

1. **전제** 현재 문제가 결과 상태이고 다음 문제가 있는 상태, **실행** 다음 진행 입력을 하면, **결과** 다음 문제의 편집 상태가 표시되고 이전 문제의 선택·결과 표시는 남지 않는다.
2. **전제** 문제 사이를 이동한 상태, **실행** Router 이동 이벤트를 확인하면, **결과** 활성 화면이 바뀌지 않았으므로 이동 이벤트가 추가되지 않았다.
3. **전제** 마지막 문제가 결과 상태, **실행** 완료 진행 입력을 하면, **결과** Router의 활성 화면이 완료 화면으로 바뀐다.
4. **전제** 완료 화면, **실행** 화면을 확인하면, **결과** 닫기, 완료 제목, 완료 일러스트, 객관식 정답 수와 객관식 문제 수, 완료 메시지, 하단 CTA가 표시된다. (`s13`)
5. **전제** 객관식 문제가 하나도 없는 세트를 마친 상태, **실행** 완료 화면을 확인하면, **결과** 카운터 없이 완료 메시지만 표시된다.
6. **전제** 앞쪽 객관식을 이미 정답으로 답변해 건너뛴 세트를 마친 상태, **실행** 완료 화면을 확인하면, **결과** 분모는 세트 전체 객관식 수이고 분자에는 건너뛴 정답도 포함되어 있다.

### 시나리오 5 - 문제의 출처를 확인한다 (우선순위: P1)

학습자가 문제를 풀거나 결과를 보면서 그 문제가 어떤 코드에서 나왔는지 Sheet로 확인한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 오픈소스 코드를 학습한다는 제품 정체성을 문제와 실제 코드로 연결한다. 풀이
흐름과 독립적으로 열리고 닫히므로 분리해 검증할 수 있다.

**독립 테스트**: 문제 fixture에서 출처를 열고 닫은 뒤 선택·입력·결과 상태가 보존되는지 검증한다.

**수용 시나리오**:

1. **전제** 출처가 있는 문제 화면, **실행** 출처 컨트롤을 누르면, **결과** 현재 화면 위에 dim과 Bottom Sheet가 표시된다. (`s04`)
2. **전제** 출처 Sheet가 열린 상태, **실행** 내용을 확인하면, **결과** 문제 번호에 대응하는 제목과 함께, 그 문제의 출처 배열 전체가 각각의 설명·URL 행·외부 링크 아이콘을 갖춘 목록으로 표시되고, 하단에 `닫기` CTA가 표시된다.
3. **전제** 출처 Sheet가 열린 상태, **실행** `닫기`를 누르면, **결과** Sheet만 사라지고 선택·입력·결과 상태가 그대로 유지된다.
4. **전제** 출처 Sheet를 열고 닫은 상태, **실행** Router 이동 이벤트를 확인하면, **결과** 이동 이벤트가 추가되지 않았다.
5. **전제** 출처 Sheet의 URL 행, **실행** 선택하면, **결과** 외부 URL 열기 의도가 발생한다.
6. **전제** 출처 목록이 비어 있는 문제, **실행** 화면을 확인하면, **결과** 출처를 여는 컨트롤이 노출되지 않는다.

### 시나리오 6 - 프로젝트 상세에서 세트를 선택해 진입한다 (우선순위: P2)

학습자가 프로젝트 상세에서 저장소 정보와 진행 상태를 확인하고 세트를 선택해 풀이를 시작한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 풀이 흐름으로 들어가는 유일한 진입 경로다. 현재 Screen이 없어 앱에서 흐름에
도달할 수 없다. 다만 풀이 흐름 자체(P1)는 이 화면 없이도 독립 검증할 수 있다.

**독립 테스트**: 프로젝트 상세에 진입해 세트 목록과 진행 상태가 표시되고, 세트를 선택하면 그 세트의
시작 화면으로 이동하는지 검증한다.

**수용 시나리오**:

1. **전제** 프로젝트를 선택한 상태, **실행** 상세 화면에 진입하면, **결과** 저장소 정보와 전체 진행률, 세트 목록이 표시된다. (`s01`)
2. **전제** 세트 목록이 표시된 상태, **실행** 각 항목을 확인하면, **결과** 세트 라벨·제목과 함께 그 세트의 실제 문제 수와 완료 수를 반영한 진행 상태가 표시된다.
3. **전제** 세트 목록이 표시된 상태, **실행** 세트 하나를 선택하면, **결과** 그 세트의 시작 화면으로 이동한다.
4. **전제** 학습 완료 화면, **실행** 닫기 또는 하단 CTA를 누르면, **결과** 그 세트가 속한 프로젝트 상세 화면으로 돌아간다.
5. **전제** 프로젝트 상세 화면, **실행** 우상단 메뉴를 누르면, **결과** `저장한 문제`, `GitHub에서 보기`, `삭제하기` 항목이 펼쳐진다. (`s01`)
6. **전제** 메뉴가 펼쳐진 상태, **실행** `저장한 문제`를 선택하면, **결과** 그 프로젝트의 저장한 문제 목록 화면으로 이동한다.
7. **전제** 메뉴가 펼쳐진 상태, **실행** `삭제하기`를 선택하면, **결과** 확인 단계가 표시되고 확인 전에는 삭제가 실행되지 않으며 취소할 수 있다.
8. **전제** 삭제를 확인한 상태, **실행** 삭제가 성공하면, **결과** 프로젝트 상세가 닫힌다.
9. **전제** 메뉴가 펼쳐진 상태, **실행** `GitHub에서 보기`를 선택하면, **결과** 그 프로젝트의 저장소 URL을 외부에서 여는 의도가 발생한다.
10. **전제** 미완료 세트가 있는 프로젝트 상세, **실행** 저장소 영역의 시작 컨트롤을 누르면, **결과** 첫 미완료 세트의 세트 시작 화면으로 이동한다.

### 시나리오 7 - 문제를 북마크한다 (우선순위: P2)

학습자가 문제 편집·결과 화면에서 현재 문제의 저장 상태를 바꾼다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 풀이 흐름은 P1 시나리오로 완결되며, 북마크는 이후 복습 경험을 위한 부가 기능이다.

**독립 테스트**: 북마크되지 않은 문제 fixture에서 토글 → Effect 결과 → 표시 반영을 검증한다.

**수용 시나리오**:

1. **전제** 문제 화면, **실행** 하단 액션 영역을 확인하면, **결과** 북마크 컨트롤이 노출된다.
2. **전제** 북마크되지 않은 문제, **실행** 북마크를 누르면, **결과** 명시적인 View Action이 Effect를 거쳐 처리되고 Binding 변경만으로 mutation이 시작되지 않는다.
3. **전제** 북마크 mutation이 진행 중인 상태, **실행** 같은 문제에서 다시 누르면, **결과** 중복 요청이 발생하지 않는다.
4. **전제** 북마크 mutation이 완료된 상태, **실행** 결과를 확인하면, **결과** 현재 문제 ID와 일치하는 결과만 표시에 반영된다.
5. **전제** 진입 시 북마크 목록 조회가 실패한 상태, **실행** 문제 화면을 확인하면, **결과** 풀이는 그대로 진행되고 모든 문제가 미북마크로 표시되며 북마크 토글은 여전히 동작한다.

---

### 시나리오 8 - 저장한 문제를 다시 푼다 (우선순위: P2)

학습자가 프로젝트 상세의 메뉴에서 저장한 문제 목록을 열고, 그중 하나를 골라 단일 문제로 다시 푼다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 북마크(시나리오 7)로 저장한 문제를 실제로 다시 풀 수 있게 해 복습 경로를 닫는다.
세트 풀이(P1)와 독립적으로 열리고 닫히므로 분리해 검증할 수 있다.

**독립 테스트**: 저장한 문제 fixture로 목록 표시 → `문제 풀기` → 제출 → 결과 → 목록 복귀를 독립 검증한다.

**수용 시나리오**:

1. **전제** 프로젝트 상세 메뉴가 펼쳐진 상태, **실행** `저장한 문제`를 선택하면, **결과** 그 프로젝트의 저장한 문제만 담긴 목록이 표시된다.
2. **전제** 저장한 문제 목록, **실행** 한 항목의 `문제 풀기`를 누르면, **결과** 세트 시작 화면 없이 그 문제의 문제 화면이 편집 상태로 열린다.
3. **전제** 기존 답변이 있는 저장한 문제, **실행** 문제 화면을 확인하면, **결과** 이전 답안과 결과가 복원되지 않고 편집 상태로 표시된다.
4. **전제** 단일 문제에서 답안을 제출해 결과가 표시된 상태, **실행** 하단 컨트롤을 누르면, **결과** 저장한 문제 목록으로 돌아가며 다음 문제로 이어지지 않는다.
5. **전제** 저장한 문제가 없는 프로젝트, **실행** 목록을 열면, **결과** 빈 상태 표현이 표시된다.
6. **전제** 목록 조회에 실패한 상태, **실행** 화면을 확인하면, **결과** 실패 표현과 다시 시도할 수 있는 입력 경로가 표시된다.

### 예외·경계 사례

- 선택지 수가 4개가 아닌 객관식 문제도 서버가 준 개수 그대로 렌더링해야 한다. `A`~`D`는 화면 fixture일 뿐 고정 개수의 근거가 아니다.
- 긴 질문, 긴 선택지, 긴 AI 해설이 있어도 본문을 모두 읽을 수 있어야 하고 하단 고정 액션이 콘텐츠의 터치 영역을 가리지 않아야 한다.
- 서술형 입력 중 키보드가 올라와도 하단 CTA와 글자 수 표시가 가려지지 않아야 한다.
- 출처 Sheet를 열고 닫아도 문제 draft·선택·결과가 사라지지 않아야 한다.
- 답안 제출이 진행 중일 때는 중복 제출과, 진행 중인 mutation의 결과를 잃게 만드는 화면 이탈을 차단해야 한다.
- Effect가 실패하면 실패 의미를 상태에 보존하고 재시도할 수 있는 입력 경로를 제공해야 한다. 실패 전용 화면 디자인은 자료가 없으므로 기존 공통 오류 표현을 재사용한다.
- 세트 조회에 실패하면 세트 시작 화면이 실패 상태를 표시하고 다시 시도할 수 있어야 한다.
- 북마크 목록 조회만 실패하면 풀이 흐름을 막지 않고 초기 표시만 미북마크로 둔다.
- 문제가 하나도 없는 세트로 진입하면 문제 화면을 열지 않고 문제가 없음을 알려야 한다.
- 모든 문제에 답변이 있는 세트는 건너뛸 대상이 없으므로 첫 문제부터 다시 풀이한다. 이때 진행 표시가 줄어들거나 초기화되어 보여서는 안 된다.
- 문제·세트 데이터가 바뀌어도 화면의 샘플 문자열이나 옵션 위치를 기준으로 분기해서는 안 된다.

## 요구사항 *(필수)*

### 기능 요구사항 - 진입과 세트 시작

- **FR-001**: 시스템은 프로젝트 상세의 학습 세트 선택 이벤트에서 선택한 세트 식별 정보를 포함한 학습 시작 의도를 만들어야 한다.
- **FR-002**: 시스템은 학습 흐름 진입 시 세트 시작 화면을 최초 활성 화면으로 표시해야 한다.
- **FR-002a**: 시스템은 흐름 진입 시 세트 상세와 북마크 목록을 각각 1회 조회해야 하며, 이후 문제 이동마다 다시 조회해서는 안 된다.
- **FR-002b**: 세트 시작 화면의 로딩·실패·내용 상태는 세트 상세 조회 결과로만 결정해야 하고, 로딩·실패 상태에서는 `시작하기`로 풀이를 시작할 수 없어야 한다.
- **FR-002c**: 세트 상세 조회 실패 상태에서는 다시 시도할 수 있는 입력 경로를 제공해야 한다.
- **FR-003**: 세트 시작 화면은 세트 라벨, 제목, 설명을 상태에서 전달된 동적 값으로 렌더링해야 한다. 라벨은 진입 시 전달된 값을, 제목과 설명은 세트 상세 응답 값을 사용한다. 흐름 진입 의도에는 라벨만 담고 제목·설명을 전달해서는 안 되며, 세트 상세 조회가 끝나기 전에는 제목과 설명을 표시하지 않는다.
- **FR-004**: 흐름에 처음 진입한 뒤의 `시작하기` 입력은 그 세트의 첫 미응답 문제를 준비하고 문제 화면으로 전환해야 한다. 이미 답변이 있는 문제는 표시하지 않고 건너뛴다. 뒤로가기로 세트 시작 화면에 돌아온 뒤의 재입력은 FR-035d를 따른다.
- **FR-004a**: 시작 지점은 서버가 준 기존 답변 유무로 판정해야 하며, 클라이언트가 별도 진행 상태를 저장해 판정해서는 안 된다.
- **FR-004b**: 미응답 문제가 하나도 없는 세트는 첫 문제부터 다시 풀이를 시작해야 한다. 이 경우 건너뛰는 문제가 없으므로 모든 문제가 편집 상태로 순서대로 표시된다.
- **FR-004c**: 재풀이는 프로젝트와 세트의 진행 표시를 낮추지 않아야 한다. 클라이언트가 진행 값을 임의로 되돌리거나 초기화해서는 안 된다.

### 기능 요구사항 - 문제 화면 공통

- **FR-005**: 문제 화면은 문제 순번, 질문, 문제 유형별 답안 영역, 출처, 북마크, 하단 액션을 공통 골격으로 제공해야 한다.
- **FR-006**: 문제 번호·질문·선택지·답안·해설·출처는 상태에서 전달된 값을 표시해야 하며, 화면 자료의 예시 문구를 하드코딩해서는 안 된다.
- **FR-007**: 문제 화면 본문은 콘텐츠가 viewport를 넘으면 세로로 스크롤되어야 한다.
- **FR-008**: 하단 액션 영역은 본문 스크롤과 분리되어 safe area 위에 고정되어야 하며, 스크롤 콘텐츠의 터치 영역을 가리지 않도록 bottom inset을 확보해야 한다.
- **FR-009**: 출처 Sheet는 현재 문제 수명 안에서 그 문제의 Feature가 소유해야 하며 Router의 화면 전환으로 취급해서는 안 된다. 표시 여부 외의 상태를 갖지 않으므로 Destination을 요구하지 않는다.
- **FR-010**: 출처 Sheet를 닫으면 열기 직전의 문제 상태가 그대로 복원되어야 한다.
- **FR-010a**: 출처를 여는 컨트롤은 객관식과 서술형의 편집·결과 상태에 동일하게 제공해야 하며, 출처 목록이 비어 있는 문제에서는 노출하지 않아야 한다.
- **FR-010b**: 한 문제에 출처가 여러 개 있으면 출처 Sheet는 서버가 반환한 배열 전체를 목록으로 표시해야 하며 일부만 표시하거나 임의로 병합해서는 안 된다.
- **FR-010c**: 출처 URL 행 선택은 화면이나 Feature가 URL을 직접 열지 않고 외부 URL 열기 의도를 상위로 전달해야 하며, 실제 열기는 App이 주입받은 단일 경로에서 수행해야 한다.

### 기능 요구사항 - 객관식

- **FR-011**: 객관식 편집 상태에서 사용자는 한 번에 하나의 선택지만 선택할 수 있어야 한다.
- **FR-012**: 선택 상태는 UIComponent에 Feature State를 전달하지 않고 표현 값과 콜백으로 연결해야 한다.
- **FR-013**: 제출 전 선택지 표현과 제출 후 결과 선택지 표현은 서로 다른 의미 상태이므로 기존 `ChoiceAnswerOption`·`ChoiceResultRow` 계약을 우선 검토해 사용해야 한다.
- **FR-014**: 답안 제출은 명시적인 View Action에서 시작해야 하며 Binding 변경만으로 mutation을 시작해서는 안 된다.
- **FR-014a**: 선택지를 하나도 고르지 않은 상태에서는 제출이 시작되지 않아야 한다.
- **FR-015**: 제출이 진행 상태에 들어간 뒤에는 중복 제출과, 진행 중인 결과를 잃게 만드는 취소·이탈을 차단해야 한다.
- **FR-016**: 정답 결과는 정답 선택지의 결과 역할과 AI 해설을 표시해야 한다.
- **FR-017**: 오답 결과는 사용자가 고른 오답 역할과 실제 정답 역할을 서로 구별되는 의미 상태로 동시에 표시해야 한다.
- **FR-018**: 결과의 의미 역할은 서버 채점 결과에서 판정해 상태로 전달해야 하며, 화면과 컴포넌트가 옵션의 배열 위치나 `A`/`B`/`C`/`D` 문자로 정답·오답을 추론해서는 안 된다.

### 기능 요구사항 - 서술형

- **FR-019**: 서술형 draft는 Feature State가 소유해야 한다.
- **FR-020**: 입력 영역은 최대 400자를 허용하고 `현재 글자 수 / 400`을 표시해야 한다.
- **FR-020a**: 상태에 400자를 넘는 draft가 저장되어서는 안 되며, 상한을 넘긴 답안이 제출되는 경로가 존재해서는 안 된다.
- **FR-020b**: 공백만 입력된 상태에서는 제출이 시작되지 않아야 한다.
- **FR-021**: 제출이 성공하기 전에는 사용자 draft를 결과 표현으로 바꾸지 않아야 한다.
- **FR-022**: 제출 결과 상태에서는 사용자 답안과 AI 답안을 각각 구분된 읽기 전용 영역으로 표시해야 한다.
- **FR-023**: 결과 상태에서 사용자가 입력한 답안 문자열을 제출 당시 값 그대로 보존해야 한다.

### 기능 요구사항 - 북마크

- **FR-024**: 북마크는 기존 `BookmarkButton` 표현 계약을 우선 사용해야 한다.
- **FR-025**: 북마크 mutation은 Reducer가 명시적인 사용자 Action을 해석해 Effect로 처리해야 하며, 진행 중 중복 입력과 결과 유실이 발생하지 않아야 한다.
- **FR-025a**: 북마크 mutation 결과는 요청 대상 문제 ID와 일치할 때만 표시에 반영해야 한다.
- **FR-025b**: 세트 조회 응답에는 북마크 여부가 없으므로, 시스템은 흐름 진입 시 북마크 목록을 1회 조회해 세트 문제의 초기 북마크 표시를 결정해야 한다. 문제 화면이 바뀔 때마다 다시 조회해서는 안 된다.
- **FR-025c**: 북마크 목록 조회 실패는 풀이 흐름을 막지 않아야 한다. 이 경우 모든 문제의 초기 표시를 미북마크로 두고 북마크 토글은 계속 허용한다.

### 기능 요구사항 - 다음 문제와 완료

- **FR-026**: 다음 문제 진행 입력은 결과 상태에서만 처리해야 한다.
- **FR-027**: 다음 문제가 있으면 다음 문제의 편집 상태를 표시하고 이전 문제의 선택·입력·결과 표시를 남기지 않아야 한다.
- **FR-028**: 마지막 문제의 결과에서 진행하면 Router가 활성 화면을 완료 화면으로 전환해야 한다.
- **FR-029**: 완료 화면은 정답 수와 문제 수를 상태에서 계산하거나 수신한 값으로 표시해야 하며 고정값으로 대체해서는 안 된다.
- **FR-029a**: 카운터의 분모는 세트 전체의 객관식 문제 수이고, 분자는 이번 세션에서 정답으로 채점된 객관식 수와 건너뛴 객관식 중 기존 답변이 정답인 수의 합이어야 한다.
- **FR-029b**: 건너뛴 객관식의 정답 여부는 서버가 준 기존 답변 값에서만 판정해야 하며, 값이 없는 문제는 정답으로 세지 않는다.
- **FR-030**: 완료 화면의 일러스트는 Feature가 asset 이름을 직접 해석하지 않고 UIComponent의 표현 API로 렌더링해야 한다.

### 기능 요구사항 - Navigation

- **FR-031**: 화면이 둘 이상인 흐름은 순차 Router-Feature가 화면 Feature의 조합과 전환을 소유해야 한다. 이 규칙은 풀이 흐름과, 프로젝트 상세·저장한 문제 목록·단일 문제를 포함하게 된 프로젝트 상세 흐름에 모두 적용한다.
- **FR-032**: 각 Router State는 자신이 조합하는 화면 Feature의 child State를 항상 함께 보유하고 별도의 활성 화면 값으로 현재 화면을 선택해야 한다. 같은 배타 상태를 여러 개의 Bool로 표현해서는 안 되며, 활성 화면 값에 "완료"처럼 상위로 나감을 뜻하는 case를 두어서는 안 된다.
- **FR-032a**: 동시에 진행할 수 있는 조회·mutation은 하나의 상태 값에 합치지 않고 각각의 상태로 분리해야 한다. 세트 상세 조회와 북마크 목록 조회, 답안 제출과 북마크 mutation이 여기에 해당한다.
- **FR-032b**: 실패 상태는 오류의 의미와 사용자가 실행할 수 있는 재시도·복구 경로를 보존해야 하며, 실패 여부만 남기는 Bool로 대체해서는 안 된다.
- **FR-032c**: 새 요청이 진행 중인 요청을 대체할 수 있는 조회는 요청 식별 값을 보존하고 현재 요청과 일치하는 결과만 반영해야 한다. 상태 전이로 재요청 입력을 차단하는 경우에는 그 차단 규칙을 명시한다.
- **FR-033**: 흐름 안의 화면 전환에 `NavigationStack`·`StackState`를 사용해서는 안 된다.
- **FR-034**: Router는 실제 활성 화면 값이 바뀔 때만 화면 이동 이벤트를 기록해야 하며, 각 이벤트는 전환 이전 화면, 전환 이후 화면과 전환을 유발한 Action을 식별할 수 있는 값을 함께 담아야 한다.
- **FR-034a**: 이동 이벤트는 테스트가 상태에서 직접 조회하는 검증 수단으로만 사용해야 하며, 화면은 읽기 전용으로만 참조하고 production 로깅·analytics로 내보내서는 안 된다.
- **FR-035**: 흐름 밖으로 나가는 의도는 delegate로 상위에 전달해야 하며, Router가 push·present 같은 App Navigation 방식을 명령해서는 안 된다.
- **FR-035a**: 흐름 안의 뒤로가기는 활성 화면 값을 이전 값으로 되돌리는 상태 전이여야 하며, 화면 Feature의 State를 새로 만들거나 화면을 pop해서는 안 된다. 문제 화면의 뒤로가기는 세트 시작 화면으로 되돌아간다.
- **FR-035b**: 되돌아갈 이전 화면이 없는 뒤로가기와 완료 화면의 닫기는 흐름 이탈이므로 Router의 delegate로 상위에 전달해야 한다. 세트 시작 화면의 뒤로가기가 여기에 해당한다.
- **FR-035c**: 답안 제출이 진행 중일 때는 뒤로가기를 무시해야 한다(FR-015).
- **FR-035d**: 뒤로가기로 세트 시작 화면에 돌아온 뒤 다시 `시작하기`를 입력하면, 직전까지 진행하던 문제와 그 입력·결과 상태를 그대로 이어서 표시해야 한다. 보유 중인 child State를 버리고 첫 미응답 문제부터 다시 구성해서는 안 된다.

### 기능 요구사항 - 채점과 데이터 정합

- **FR-036**: 정답 여부·정답 선택지·해설은 서버 제출 응답 값만 사용해야 하며 클라이언트가 정오를 계산해서는 안 된다.
- **FR-037**: 완료 화면의 정답 카운터는 객관식 문제만 집계해야 한다. 서버가 서술형에 정오를 반환하지 않으므로 서술형을 분자·분모 어느 쪽에도 포함해서는 안 된다. 이 조건은 이번 세션에서 푼 문제와 건너뛴 문제 모두에 동일하게 적용한다.
- **FR-038**: 객관식 문제가 하나도 없는 세트에서는 카운터를 표시하지 않고 완료 메시지만 표시해야 한다.
- **FR-039**: 시스템은 세트 설명, 출처의 줄 번호·심볼·설명, 기존 답변의 선택 index·정답 여부를 화면까지 전달할 수 있도록 보존해야 한다. 기존 답변의 정답 여부는 FR-004와 FR-029a가 시작 지점과 카운터 판정에 직접 사용한다. 이 값들은 Data DTO에 이미 존재하므로 Domain 모델과 Composition 매핑에서 복원해야 한다.
- **FR-040**: 시스템은 서버가 반환한 문제·선택지·세트 배열의 순서를 재정렬하지 않아야 한다.

### 기능 요구사항 - 프로젝트 상세 진입 화면

- **FR-041**: 프로젝트 상세 화면은 저장소 정보와 전체 진행률, 세트 목록을 표시하고 세트 선택 액션을 제공해야 한다.
- **FR-041a**: 저장소 영역의 시작(play) 컨트롤은 첫 미완료 세트의 세트 시작 화면으로 진입해야 하며, 세트 항목의 시작 컨트롤과 같은 진입 규칙을 사용한다. 미완료 세트가 없으면 이 컨트롤을 비활성으로 둔다.
- **FR-042**: 세트 목록의 각 항목은 세트 라벨과 제목, 그리고 그 세트의 실제 문제 수와 완료 수를 반영한 진행 표시를 보여야 하며 고정값으로 대체해서는 안 된다. 라벨은 제목과 구별되는 표현으로 항목 안에 함께 표시한다.
- **FR-042a**: 세트 항목에서 탭할 수 있는 컨트롤은 항목 우측의 시작(play) 아이콘 버튼 하나뿐이어야 하며, 항목 본문 전체를 버튼으로 만들어서는 안 된다. 세트 선택은 이 버튼에서만 시작한다.
- **FR-042b**: 세트 항목의 진행 표시는 그 세트의 문제 수만큼의 세그먼트로 구성하고 완료한 문제 수만큼 채워야 한다. 연속 막대나 비율 텍스트로 대체해서는 안 된다.
- **FR-043**: 학습 완료 화면의 닫기와 하단 CTA는 그 세트가 속한 프로젝트 상세 화면으로 이동해야 한다.
- **FR-044**: 프로젝트 상세의 메뉴 컨트롤은 `저장한 문제`, `GitHub에서 보기`, `삭제하기` 세 항목을 펼쳐 보여야 하며, 파괴적 동작인 `삭제하기`는 나머지와 구별되는 표현으로 표시해야 한다.
- **FR-044a**: `저장한 문제`는 그 프로젝트의 저장한 문제 목록 화면으로 이동해야 하며, 목록에 다른 프로젝트의 문제를 포함해서는 안 된다.
- **FR-044a-1**: 이 목록은 저장한 문제를 조회·필터링하는 기존 책임을 재사용해야 하며, 같은 목적의 Reducer를 새로 만들어서는 안 된다. 진입 시 그 프로젝트로 필터를 고정한다.
- **FR-044a-2**: 저장한 문제 목록의 각 항목은 그 문제로 진입하는 `문제 풀기` 컨트롤을 제공해야 하며, 문제 진입은 이 컨트롤에서만 시작해야 한다.
- **FR-044a-3**: 단일 문제 진입은 세트 시작 화면과 완료 화면 없이 그 문제의 문제 화면만 표시해야 한다. 문제 데이터는 그 문제가 속한 세트의 조회 결과에서 해당 문제를 찾아 사용하며, 세트의 다른 문제로 이동하는 경로를 만들어서는 안 된다.
- **FR-044a-4**: 단일 문제의 결과 상태 하단 컨트롤은 저장한 문제 목록으로 돌아가는 `완료` 의미여야 하며, 다음 문제로 이어지는 진행을 만들어서는 안 된다.
- **FR-044a-5**: 단일 문제는 기존 답변이 있어도 편집 상태로 열어야 하며, 기존 답안·결과를 복원해 표시해서는 안 된다.
- **FR-044a-6**: 저장한 문제 목록의 각 항목은 문제 본문과 `문제 풀기` 컨트롤만 표시해야 하며, 세트 제목·라벨을 얻기 위한 추가 조회를 해서는 안 된다.
- **FR-044a-7**: 목록이 비어 있으면 빈 상태 표현을, 조회에 실패하면 다시 시도할 수 있는 실패 표현을 제공해야 한다. 두 표현 모두 프로젝트의 기존 공통 표현을 재사용한다.
- **FR-044b**: `GitHub에서 보기`는 프로젝트 상세가 보유한 저장소 URL의 외부 열기 의도를 만들어야 하며, 화면이 URL 문자열을 임의로 조립하거나 직접 열어서는 안 된다. 열기는 FR-010c와 같은 App의 단일 경로를 사용한다.
- **FR-044c**: `삭제하기`는 되돌릴 수 없으므로 확인 단계를 거친 뒤에만 삭제를 실행해야 하고, 확인 전 취소가 가능해야 하며, 진행 중 중복 실행이 발생해서는 안 된다. 삭제에 성공하면 프로젝트 상세를 닫는다.
- **FR-044d**: 위에서 정의하지 않은, 동작 근거가 확정되지 않은 컨트롤은 이번 범위에서 노출하지 않아야 한다.

### 기능 요구사항 - 구조와 범위 제약

- **FR-045**: 각 화면의 상태와 액션은 그 화면을 책임지는 독립 Reducer가 소유해야 하며, 하나의 Reducer가 여러 화면의 상태를 함께 소유해서는 안 된다.
- **FR-045a**: 여러 흐름이 같은 화면을 사용하면 그 화면과 Feature는 한 흐름만 소유해야 하고, 다른 흐름은 Router가 그 Feature를 조합해 사용해야 한다. 같은 화면을 흐름마다 복제해서는 안 된다.
- **FR-045b**: 조합되는 화면 Feature는 자신을 사용하는 흐름이 무엇인지 알지 않아야 하며, 종료 의미는 delegate로만 알리고 흐름별 분기를 화면 Feature 안에 두어서는 안 된다.
- **FR-046**: 각 Reducer는 자신이 사용하는 UseCase만 생성자 주입으로 받아야 하며 전역 컨테이너나 Service Locator를 사용해서는 안 된다.
- **FR-047**: 계획 단계 산출물은 Reducer별로 주입되는 UseCase 목록과 그 사용 지점을 명시해야 한다.
- **FR-048**: 화면 구현은 기존 UI 패키지 컴포넌트와 디자인 토큰을 사용해야 하며, 색·치수·타이포 값을 화면 코드에 직접 적어서는 안 된다.
- **FR-049**: 구현은 Feature·App·Composition·Domain·UI 패키지만 변경해야 하며 Data 패키지 파일을 변경해서는 안 된다.
- **FR-050**: Domain·Composition·UI 변경은 FR-039와 FR-042 계열이 요구하는 데이터·컴포넌트 정합에 필요한 범위로 한정해야 한다.
- **FR-050a**: 기존 UI 컴포넌트의 공개 계약을 바꿀 때는 조작 중심인지 정보 표시 중심인지를 다시 판정하고 그 결과에 맞는 역할 분류를 적용해야 한다. 외형이 같다는 이유로 기존 분류를 유지해서는 안 된다.
- **FR-051**: 패키지 간 의존 방향은 기존 아키텍처 문서의 허용 방향을 유지해야 한다.

### 기능 요구사항 - 접근성

- **FR-052**: 선택지는 보조 기술에서 옵션 식별자와 선택 여부를 읽을 수 있어야 한다.
- **FR-053**: 결과 상태의 각 선택지는 정답, 선택한 오답 등 의미를 색 이외의 수단으로도 구별할 수 있어야 한다.
- **FR-054**: 북마크는 현재 저장 상태를, 출처 URL 행은 링크임을 보조 기술에 전달해야 한다. URL 행이 SwiftUI `Link`가 아니라 App으로 의도를 올리는 컨트롤이므로(FR-010c) 링크 특성을 명시적으로 부여해야 한다.
- **FR-055**: 완료 점수는 시각 형식과 별개로 한 문장으로 읽을 수 있는 접근성 레이블을 제공해야 한다.
- **FR-056**: 버튼·링크·선택지의 터치 대상은 실제 hit area 기준 최소 44pt를 확보해야 한다.

### 핵심 엔터티 *(기능에 데이터가 포함되면 작성)*

- **학습 세트**: 하나의 학습 단위. 식별자, 라벨, 제목, 설명과 순서가 있는 문제 목록을 가진다.
- **문제**: 세트를 구성하는 항목. 식별자, 순번, 질문, 형식(객관식·서술형), 선택지 목록(객관식만), 출처 목록, 기존 답변을 가진다. 북마크 여부는 문제에 포함되지 않고 별도의 북마크 목록과 문제 ID를 대조해 얻는다.
- **선택지**: 객관식 문제의 답안 후보. 식별 수단과 표시 내용을 가지며 표시 순서는 서버 응답 순서를 따른다.
- **서술형 draft**: 제출 전 사용자 입력 문자열. 최대 400자.
- **기존 답변**: 이전에 제출한 답. 선택 index(객관식) 또는 작성 텍스트(서술형)와 정답 여부를 구분해 가진다. 정답 여부는 서술형에서 비어 있다.
- **객관식 제출 결과**: 정답 여부, 정답 선택지 위치, 해설로 구성된다.
- **서술형 제출 결과**: 해설과 자가채점 기준으로 구성되며 정답 여부를 포함하지 않는다.
- **출처**: 문제가 유래한 코드 위치. 파일 경로, 시작 줄, 심볼, 설명, 외부 링크를 가진다. 한 문제는 출처를 0개 이상 가질 수 있다.
- **세트 진행**: 세트별 전체 문제 수와 완료 수. 프로젝트 상세의 세트 목록 표시에 사용한다.
- **저장한 문제**: 학습자가 북마크한 문제. 프로젝트 단위로 조회하며 문제 화면의 북마크 표시와
  저장한 문제 목록 화면이 같은 출처를 사용한다.
- **학습 완료 결과**: 세트 전체의 객관식 문제 수와, 이번 세션 정답 수에 건너뛴 객관식의 기존 정답 수를 더한 값. 완료 표시를 만들 수 있는 값을 함께 가진다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 화면 자료 `s01`~`s13`의 각 기준 상태를 Preview 또는 자동화 검증에서 파일 식별자와 1:1로 추적할 수 있다.
- **SC-002**: 학습자가 프로젝트 상세에서 세트를 선택해 표시된 모든 문제를 풀고 학습 완료 화면까지 도달하는 흐름을 중단 없이 완료한다.
- **SC-003**: 흐름 안의 화면 전환이 Router의 활성 화면 값으로만 결정되며, 흐름 코드에 `NavigationStack`·`StackState` 사용이 0건이다.
- **SC-004**: 답안 제출 중 연속 입력으로 같은 mutation이 두 번 실행되는 사례가 0건이다.
- **SC-005**: 상태에 400자를 초과한 서술형 draft가 저장되는 경로가 0건이다.
- **SC-006**: 출처 Sheet를 열고 닫기 전후에 선택 답안·서술 draft·채점 결과가 손실되지 않는다.
- **SC-007**: 정답 여부·정답 선택지·해설 표시가 100% 서버 응답 값에서 비롯되며, 클라이언트가 정오를 계산하거나 옵션 위치·문자로 결과 의미를 추론하는 코드 경로가 0건이다.
- **SC-008**: 세트 목록의 진행 표시와 완료 화면 카운터가 서버가 준 값과 일치하며, 고정값으로 표시되는 사례가 0건이다.
- **SC-009**: 변경된 파일 중 Data 패키지 경로가 0건이다.
- **SC-010**: UI production target에 TCA·Feature·Domain 타입이 노출되지 않고, 화면에 Store를 복제하는 ViewModel이나 Feature State를 복제하는 화면 로컬 상태가 0건이다.
- **SC-011**: 새로 추가된 raw RGB·hex 색상 리터럴과 화면 임의 Typography 선언이 0건이다.
- **SC-012**: 각 화면 Reducer의 단위 테스트가 다른 화면의 상태를 준비하지 않고 독립 실행되며, 정상 상태 전이·제출 중 중복 차단·결과 상태·Router delegate를 검증한다.
- **SC-013**: 계획 산출물의 Reducer별 주입 UseCase 목록과 구현된 각 Reducer의 생성자 인자가 일치한다.
- **SC-014**: 객관식·서술형이 섞인 세트, 서술형만 있는 세트, 앞쪽 객관식이 이미 답변되어 건너뛴 세트 각각에 대해 완료 화면 카운터 표시를 검증하는 테스트가 존재하고 통과한다.
- **SC-015**: 전체 공유 scheme 빌드와 테스트가 변경 전후 모두 통과한다.
- **SC-016**: 기존 답변이 앞쪽에 있는 세트, 전부 답변된 세트, 답변이 없는 세트 각각에서 시작 문제가 명세대로 결정되는 사례가 테스트로 검증된다.
- **SC-017**: 프로젝트 상세의 시작 컨트롤(저장소 영역과 각 세트 항목)이 모두 세트 시작 화면으로 진입하며, 세트 시작 화면을 건너뛰는 진입 경로가 0건이다.
- **SC-018**: 확인 단계를 거치지 않고 삭제가 실행되는 경로가 0건이고, 삭제 진행 중 중복 실행이 0건이다.
- **SC-019**: 세트 항목에서 탭 가능한 컨트롤이 시작 버튼 하나이며, 항목 본문 전체를 버튼으로 감싼 구현이 0건이다.
- **SC-020**: 저장한 문제 목록에 표시된 문제가 모두 해당 프로젝트에 속하며, 목록을 표시하기 위한 세트 조회가 0건이다.
- **SC-021**: 화면 또는 Feature가 외부 URL을 직접 여는 코드 경로가 0건이며, 열기는 App의 단일 경로에서만 일어난다.
- **SC-022**: 흐름 안의 뒤로가기가 활성 화면 값만 되돌리며, 화면 Feature의 State를 새로 만들거나 pop하는 코드 경로가 0건이다.

## 가정

- 화면 자료 `s01`~`s13`의 렌더 이미지가 레이아웃 정본이다. 기존 UI 컴포넌트의 현재 구현이 렌더와 다르면 렌더를 따르며, 그에 필요한 UI 패키지 변경은 FR-049가 허용하는 범위 안에 있다.
- 원본 명세와 화면 자료(`private/**`)는 저장소에 포함되지 않는 로컬 자료다. 이 명세가 서술한 내용이 이후 작업의 근거이며, 원본 자료가 갱신되면 이 명세를 다시 정렬한다.
- 원본 명세는 서술형 상한을 300자로 적었고 현재 파일의 해당 문단은 상한 300과 카운터 400이 섞여 있다. 사용자 재확인에 따라 이 명세는 400자로 통일한다.
- 원본 명세가 제품 결정이 필요하다고 표시한 항목 중 미선택 객관식과 빈 서술형의 제출 조건은 제출 불가로, 서술형 결과 상태의 하단 CTA는 객관식 결과와 같은 다음 진행 의미로 기본값을 정했다. 화면 자료의 `정답 확인` 표기는 결과가 이미 노출된 상태와 모순되므로 자료 오류로 본다.
- 완료 메시지의 점수별 문구 규칙은 자료가 만점 사례만 제공하므로 단일 완료 메시지를 사용하고 점수별 분기를 두지 않는다.
- 세트 라벨은 프로젝트 상세의 세트 요약(`LearningProjectSetProgress.label`)에서 오고 세트 상세 응답에는 없다. 세트 시작 화면의 라벨은 진입 시 전달된 값을 사용한다.
- 서버 API는 기존 계약대로 동작하며 이 기능에서 서버 계약을 변경하지 않는다. 서술형 답안의 서버 상한은 2000자이므로 400자 제한은 그 안에 들어간다.
- 문제 풀이에 필요한 UseCase 6종은 이미 구현되어 있고 Composition이 공개하고 있어 새로 만들지 않는다.
- 서술형은 서버가 채점하지 않으며 학습자가 AI 답안과 비교해 스스로 판단한다.
- 로딩·실패·제출 중 상태는 화면 자료가 없으므로 프로젝트의 기존 상태 표현을 재사용한다.
- 답안은 문제마다 즉시 서버에 제출되고 결과를 확인한 뒤 다음 문제로 넘어가므로, 세트 단위로 답안을 모아 한 번에 제출하는 경로는 없다.
- 재풀이로 같은 문제에 답안을 다시 제출했을 때 서버가 기존 답변과 진행 값을 어떻게 갱신하는지는 서버 계약의 책임이며, 클라이언트는 진행 표시를 임의로 낮추지 않는다.
- 구현 폴더 이름은 원본 명세가 제안한 `LearningSet`이 아니라 저장소에 이미 있는 `Quiz` 책임 이름을 우선한다. 원본 명세 §4의 "기존 코드베이스에 동일 책임의 타입이 있으면 기존 이름을 우선한다"는 규칙을 따른 결과이며, 최종 배치는 계획 단계에서 확정한다.

## 범위 밖

- 학습 세트·문제·정답을 생성하는 서버 또는 AI 로직.
- 서버 API 계약 변경과 Data 패키지 DTO 변경.
- 이미 답변한 문제의 답안·결과를 화면에 다시 표시하는 복원. 시작 지점만 첫 미응답 문제로 이동하며, 이번 세션에서 지나간 문제로 되돌아가 열람하는 경로도 만들지 않는다. 흐름 차원의 뒤로가기(FR-035a)는 문제 사이 이동이 아니라 세트 시작 화면으로의 복귀만을 뜻한다.
- 세트 시작 화면을 건너뛰고 곧바로 특정 문제로 이어 풀기로 진입하는 경로. 홈과 프로젝트 상세의 시작 컨트롤 모두 세트 시작 화면을 거친다(FR-041a). 저장한 문제 목록의 단일 문제 풀기는 세트 진행이 아니라 개별 복습이므로 이 제외에 해당하지 않는다(FR-044a-3).
- 완료 화면 이후 프로젝트 상세를 넘어선 최종 목적지 결정과 앱 전체 Navigation 정책.
- 서술형 자가채점 기준을 화면에 표시하는 기능.
- 비만점 완료 상태의 점수별 문구·일러스트 규칙.
- 네트워크 오류 전용 시각 디자인.
- 프로젝트 목록, 프로젝트 등록, 마이·설정 화면. 저장한 문제 목록은 FR-044a가 요구하는 프로젝트 한정 화면만 이번 범위에 포함하며, MainShell `saved` 탭의 전체 목록 화면은 범위 밖이다.
- 오프라인 캐시와 재시도 정책 일반화.
