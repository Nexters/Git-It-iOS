### 시나리오 1 - 객관식 문제를 풀고 결과를 확인한다 (우선순위: P1)

학습자가 세트의 객관식 문제에서 선택지 하나를 고르고 제출하면, 정답 여부와 정답 선택지, AI 해설을
확인한 뒤 다음 문제로 넘어간다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 세트 문제의 기본 형식이며, 이 흐름 하나만 완성해도 학습자가 "코드를 문제로 학습한다"는
제품의 핵심 가치를 처음부터 끝까지 경험할 수 있다.

**독립 테스트**: 객관식 문제 1개를 가진 세트로 진입해 선택 → 제출 → 결과 확인 → 다음까지 수행하면
전체를 검증할 수 있고, 학습자에게 즉시 채점과 해설이라는 가치를 제공한다.

**수용 시나리오**:

1. **전제** 객관식 문제가 미답변 상태로 표시된 상태, **실행** 선택지 하나를 탭하면, **결과** 그 선택지만 선택 상태로 표시되고 이전 선택은 해제된다.
2. **전제** 선택지 하나가 선택된 상태, **실행** 제출 버튼을 누르면, **결과** 제출 결과의 정오·정답 index·해설이 화면에 반영되고 선택지는 결과 표현으로 전환된다.
3. **전제** 제출이 완료된 상태, **실행** 다음 버튼을 누르면, **결과** 세트의 다음 문제가 표시되고 이전 문제의 선택·결과 표시는 초기화된다.
4. **전제** 아직 선택하지 않은 상태, **실행** 제출 버튼을 누르면, **결과** 제출이 일어나지 않고 화면 상태가 변하지 않는다.
5. **전제** 제출이 실패한 상태, **실행** 화면을 확인하면, **결과** 선택 상태가 유지되어 사용자가 다시 제출할 수 있다.

### 시나리오 2 - 서술형 문제에 답안을 작성하고 AI 답안과 비교한다 (우선순위: P1)

학습자가 서술형 문제에 자유 서술로 답안을 작성해 제출하면, 자신의 답안과 AI가 제시한 답안을 나란히
비교한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 세트에는 객관식과 서술형이 함께 들어오므로, 객관식만 구현하면 서술형 문제에서 흐름이
끊긴다. 두 형식이 모두 동작해야 세트를 끝까지 풀 수 있다.

**독립 테스트**: 서술형 문제 1개를 가진 세트로 진입해 입력 → 제출 → 비교 확인까지 수행하면 검증할 수 있다.

**수용 시나리오**:

1. **전제** 서술형 문제가 빈 입력 상태, **실행** 답안을 입력하면, **결과** 입력한 글자 수가 상한과 함께 표시된다.
2. **전제** 답안이 입력된 상태, **실행** 제출하면, **결과** 사용자의 답안과 서버가 반환한 해설이 각각 구분된 영역에 표시된다.
3. **전제** 공백만 입력된 상태, **실행** 제출하면, **결과** 제출이 일어나지 않는다.
4. **전제** 답안이 400자에 도달한 상태, **실행** 계속 입력하면, **결과** 더 이상 글자가 추가되지 않고 글자 수 표시가 400에 머문다.

### 시나리오 3 - 세트를 시작하고 완료까지 도달한다 (우선순위: P2)

학습자가 세트 시작 화면에서 세트의 제목·설명을 확인하고 시작해, 마지막 문제를 푼 뒤 학습 완료 화면에서
성과를 확인한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 개별 문제 풀이(P1)를 하나의 학습 단위로 묶어 시작과 끝을 만든다. 완료 화면이 없으면
학습자가 세트를 끝냈다는 사실을 알 수 없다.

**독립 테스트**: 문제 2개짜리 세트를 시작해 둘 다 풀면 학습 완료 화면에 도달하는지로 검증한다.

**수용 시나리오**:

1. **전제** 세트를 선택한 상태, **실행** 세트 시작 화면에 진입하면, **결과** 세트 라벨·제목·설명이 표시된다.
2. **전제** 세트 시작 화면, **실행** 시작하면, **결과** 아직 답변하지 않은 첫 문제가 표시된다.
3. **전제** 세트의 마지막 문제를 제출한 상태, **실행** 다음으로 진행하면, **결과** 학습 완료 화면에 객관식 정답 수와 객관식 문제 수가 표시되고, 객관식이 없는 세트에서는 카운터 없이 완료 메시지만 표시된다.
4. **전제** 모든 문제에 기존 답변이 있는 세트, **실행** 진입하면, **결과** 첫 문제부터 다시 푸는 재풀이로 시작한다.

### 시나리오 4 - 문제의 출처 코드를 확인한다 (우선순위: P2)

학습자가 문제를 풀거나 결과를 본 뒤, 그 문제가 어떤 코드에서 나왔는지 출처를 열어 확인하고 필요하면
GitHub에서 실제 코드를 연다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: "오픈소스 코드를 학습한다"는 제품 정체성을 문제와 실제 코드로 연결하는 기능이다.
풀이 흐름과 독립적으로 열고 닫히므로 분리해 검증할 수 있다.

**독립 테스트**: 문제 화면에서 출처를 열어 파일 경로·설명이 표시되고 닫으면 원래 화면으로 돌아오는지로 검증한다.

**수용 시나리오**:

1. **전제** 출처 정보가 있는 문제, **실행** 출처를 열면, **결과** 문제 번호가 포함된 제목과 출처 파일 위치, 설명이 표시된다.
2. **전제** 출처가 열린 상태, **실행** 닫으면, **결과** 출처를 열기 직전 화면과 그 상태가 그대로 복원된다.
3. **전제** 출처가 열린 상태, **실행** 코드 위치를 선택하면, **결과** 해당 위치의 외부 코드 페이지가 앱 밖에서 열린다.

### 시나리오 5 - 프로젝트 상세에서 학습 세트를 선택해 진입한다 (우선순위: P2)

학습자가 프로젝트 상세 화면에서 저장소 정보와 전체 진행률, 세트별 진행 상태를 확인하고 세트를 선택해
풀이를 시작한다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 풀이 화면으로 들어가는 진입 경로다. 현재 이 경로가 없어 풀이 화면에 도달할 수 없다.

**독립 테스트**: 프로젝트 상세에 진입해 세트 목록과 진행 상태가 표시되고, 세트를 선택하면 그 세트의 풀이
흐름이 시작되는지로 검증한다.

**수용 시나리오**:

1. **전제** 프로젝트를 선택한 상태, **실행** 상세 화면에 진입하면, **결과** 저장소 이름·스타 수·기술 스택·전체 진행률과 세트 목록이 표시된다.
2. **전제** 세트 목록이 표시된 상태, **실행** 확인하면, **결과** 각 세트의 진행 상태가 그 세트의 실제 문제 수와 완료 수를 반영해 표시된다.
3. **전제** 세트 목록이 표시된 상태, **실행** 세트 하나를 선택하면, **결과** 그 세트의 시작 화면으로 이동한다.
4. **전제** 홈에서 이어 풀기를 선택한 상태, **실행** 진입하면, **결과** 세트 시작 화면을 거치지 않고 서버가 지정한 이어 풀 문제로 바로 이동한다.
5. **전제** 미완료 세트가 있는 프로젝트 상세 화면, **실행** 바로 시작을 누르면, **결과** 세트 시작 화면을 거치지 않고 첫 미완료 세트의 아직 답변하지 않은 첫 문제가 표시된다.

---

### 시나리오 6 - 개발자가 화면별 책임이 분리된 Feature 구성을 확인한다 (우선순위: P2)

개발자가 이 기능의 코드를 열었을 때, 각 화면의 상태와 액션이 책임 단위로 분리된 Reducer에 담겨 있고
상위 Reducer가 이들을 조합하며, 화면 간 이동이 Delegate로 위임되는 구조를 확인한다.

**주요 행위자**: 개발자

**우선순위 이유**: 사용자가 명시적으로 요구한 구조 제약이다. 화면 수가 8개로 많아 단일 Reducer로 구현하면
상태·액션이 뒤섞여 이후 화면 추가·수정 비용이 커진다.

**독립 테스트**: 각 화면 Reducer의 단위 테스트가 그 화면의 상태 전이만으로 독립 실행되고, 상위 Reducer
테스트가 조합과 위임만 검증하는지로 확인한다.

**수용 시나리오**:

1. **전제** 구현이 완료된 상태, **실행** 각 화면 Reducer를 확인하면, **결과** 그 화면이 소유하는 상태와 액션만 포함하고 다른 화면의 상태를 직접 변경하지 않는다.
2. **전제** 구현이 완료된 상태, **실행** 화면 간 이동을 확인하면, **결과** 하위 Reducer는 Delegate로 의도만 알리고 실제 이동은 상위가 수행한다.
3. **전제** 구현이 완료된 상태, **실행** 의존성 주입을 확인하면, **결과** 각 Reducer가 자신이 실제로 사용하는 UseCase만 생성자로 주입받는다.

---

### 시나리오 7 - 이미 답변한 문제와 북마크 상태가 유지된다 (우선순위: P3)

학습자가 중간에 나갔다가 돌아오거나 문제를 북마크하면, 그 상태가 서버 기준으로 유지된다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 풀이 흐름 자체는 P1~P2로 완결되며, 이 시나리오는 재방문 경험을 개선한다.

**독립 테스트**: 문제를 북마크한 뒤 다시 진입해 북마크가 유지되는지, 이미 답변한 문제가 있는 세트에서
이어 풀 지점이 올바른지로 검증한다.

**수용 시나리오**:

1. **전제** 문제가 표시된 상태, **실행** 북마크를 누르면, **결과** 서버 반영이 끝난 뒤 북마크 상태가 화면에 반영된다.
2. **전제** 일부 문제에 기존 답변이 있는 세트, **실행** 진입하면, **결과** 답변이 없는 첫 문제부터 시작한다.
3. **전제** 북마크 반영이 진행 중인 상태, **실행** 다시 누르면, **결과** 중복 요청이 발생하지 않는다.

---

### 예외·경계 사례

- 세트 조회에 실패하면 화면은 실패 상태를 표시하고 사용자가 다시 시도할 수 있어야 한다.
- 답변 제출에 실패하면 입력·선택 내용이 사라지지 않고 유지되어야 한다.
- 문제가 하나도 없는 세트로 진입하면 풀이 화면을 열지 않고 세트에 문제가 없음을 사용자에게 알려야 한다(표현 방식은 계획 단계에서 기존 빈 상태 표현을 재사용해 결정한다).
- 선택지 수가 4개가 아닌 객관식 문제도 서버가 준 개수 그대로 표시해야 한다.
- 문제 본문이나 선택지가 길어 화면을 넘칠 때 잘리지 않고 스크롤로 모두 읽을 수 있어야 한다.
- 서술형 입력 중 키보드가 올라와도 제출 버튼과 글자 수 표시가 가려지지 않아야 한다.
- 출처 정보가 없는 문제에서는 출처를 여는 수단이 노출되지 않아야 한다. 이 규칙은 객관식과 서술형 화면에 동일하게 적용된다.
- 서술형 문제만으로 구성된 세트를 마치면 학습 완료 화면에 카운터 없이 완료 메시지만 표시되어야 한다.
- 북마크 요청이 실패하면 표시가 되돌아간 상태로 남고 사용자가 다시 시도할 수 있어야 한다.
- 제출 요청이 진행 중일 때 같은 문제에 중복 제출이 발생하지 않아야 한다.
- 풀이 도중 뒤로 나가면 확인 없이 즉시 나가고 미제출 입력·선택은 사라지며, 같은 문제로 다시 들어오면 빈 상태로 시작해야 한다.

## 요구사항 *(필수)*

### 기능 요구사항 - 진입과 흐름

- **FR-001**: 시스템은 홈의 이어 풀기 요청(프로젝트·세트·문제 식별자를 포함)을 받아 해당 세트의 지정된 문제로 진입시켜야 한다. 이 경로에서는 세트 시작 화면을 거치지 않아야 한다.
- **FR-002**: 시스템은 프로젝트 상세의 세트 목록에서 선택한 세트로 세트 시작 화면을 거쳐 풀이를 시작시켜야 한다. 세트 시작 화면은 이 경로에서만 나타나야 한다.
- **FR-002a**: 시스템은 세트 풀이를 시작할 때 아직 답변하지 않은 첫 문제부터 시작해야 한다. 모든 문제에 답변이 있는 세트는 첫 문제부터 다시 푸는 재풀이로 처리해야 한다(유스케이스 명세 006 FR-025).
- **FR-002b**: 답변 제출은 문제 단위로 이루어지며 제출 즉시 그 문제의 채점 결과를 표시해야 한다. 세트 전체를 제출하는 동작을 두어서는 안 된다.
- **FR-003**: 시스템은 문제 형식(객관식·서술형)에 따라 해당 형식의 풀이 화면을 표시해야 한다.
- **FR-004**: 시스템은 마지막 문제를 제출하고 다음으로 진행할 때 학습 완료 화면을 표시해야 한다.
- **FR-005**: 시스템은 풀이 중 어느 화면에서든 이전 화면으로 돌아가는 수단을 제공해야 한다.
- **FR-005a**: 뒤로 나가기는 확인 절차 없이 즉시 수행해야 하며, 제출하지 않은 입력과 선택은 버려야 한다. 미제출 답안을 기기에 임시 저장해서는 안 된다.

### 기능 요구사항 - 화면별 상태와 액션

- **FR-006**: 프로젝트 상세 화면은 저장소 이름·썸네일·스타 수·기술 스택·전체 진행률과 세트 목록을 표시하고, 세트 선택 액션을 제공해야 한다.
- **FR-006a**: 프로젝트 상세 화면의 바로 시작 액션은 첫 미완료 세트에서 아직 답변하지 않은 첫 문제의 풀이 화면으로 바로 이동해야 하며, 세트 시작 화면을 거쳐서는 안 된다. 미완료 세트가 없으면 이 액션을 제공하지 않아야 한다.
- **FR-006b**: 동작 근거가 확정되지 않은 상단 메뉴 버튼은 이번 범위에서 노출하지 않아야 한다. 동작하지 않는 버튼을 화면에 두어서는 안 된다.
- **FR-007**: 세트 목록의 각 항목은 세트 라벨·제목과 함께 그 세트의 문제 수와 완료 수를 반영한 진행 상태를 표시해야 한다.
- **FR-008**: 세트 시작 화면은 세트 라벨·제목·설명을 표시하고 시작 액션을 제공해야 한다.
- **FR-009**: 객관식 풀이 화면은 문제 번호·본문·선택지 목록을 표시하고, 선택지 선택과 제출 액션을 제공하며, 선택은 항상 최대 1개만 유지해야 한다.
- **FR-010**: 객관식 결과 화면은 제출 응답의 정답 여부·정답 선택지·해설을 표시하고, 정답과 사용자가 고른 오답을 서로 구분해 표시해야 한다.
- **FR-010a**: 결과 화면의 모든 선택지는 펼치고 접을 수 있어야 하며, 정답도 사용자가 고른 오답도 아닌 선택지는 정답·오답 어느 쪽으로도 오인되지 않는 중립 표현으로 펼쳐야 한다.
- **FR-011**: 서술형 풀이 화면은 문제 번호·본문과 답안 입력 영역, 현재 글자 수와 상한을 표시하고 제출 액션을 제공해야 한다.
- **FR-011a**: 서술형 답안의 글자 수 상한은 400자여야 하며, 상한에 도달하면 추가 입력이 반영되지 않아야 한다. 상한을 넘긴 답안이 제출되는 경로가 존재해서는 안 된다.
- **FR-012**: 서술형 결과 화면은 사용자가 제출한 답안과 서버가 반환한 해설을 각각 구분된 영역에 표시해야 한다.
- **FR-013**: 출처 화면은 문제 번호가 포함된 제목, 출처 파일 위치와 설명을 표시하고, 외부 코드 열기와 닫기 액션을 제공해야 한다.
- **FR-013a**: 출처를 여는 수단은 객관식 풀이·결과 화면뿐 아니라 서술형 풀이·결과 화면에도 같은 형태로 제공해야 한다.
- **FR-014**: 학습 완료 화면은 정답 수 카운터와 완료 메시지를 표시하고 다음 단계로 나가는 액션을 제공해야 한다.
- **FR-014b**: 학습 완료 화면의 카운터는 객관식 문제만 집계해야 한다. 분모는 세트의 객관식 문제 수, 분자는 그중 서버가 정답으로 판정한 문제 수여야 하며, 서술형 문제는 서버가 채점하지 않으므로 분자·분모 어느 쪽에도 넣어서는 안 된다.
- **FR-014c**: 카운터 집계는 이번 풀이에서 받은 제출 응답과 FR-020이 보존하도록 요구한 기존 답변의 정답 여부를 함께 사용해 세트 전체를 기준으로 산출해야 한다.
- **FR-014d**: 객관식 문제가 하나도 없는 세트에서는 카운터를 표시하지 않고 완료 메시지만 표시해야 한다.
- **FR-014a**: 학습 완료 화면의 `다음`과 닫기 액션은 모두 그 세트가 속한 프로젝트 상세 화면으로 이동해야 하며, 이동 후 상세 화면의 진행률과 세트 진행 상태는 갱신된 값을 표시해야 한다.
- **FR-015**: 모든 풀이 화면은 현재 문제의 북마크 토글 액션을 제공해야 한다.
- **FR-015a**: 북마크 표시는 서버가 성공을 응답한 뒤에만 바뀌어야 한다. 요청이 진행 중인 동안 같은 문제의 추가 요청은 무시하고, 실패하면 이전 표시를 유지해야 한다.
- **FR-016**: 각 화면은 조회 중·조회 실패·제출 중 상태를 사용자가 구분할 수 있게 표시해야 한다.

### 기능 요구사항 - 데이터 정합

- **FR-017**: 시스템은 정답 여부를 클라이언트에서 계산하지 않고 서버 제출 응답의 값만 사용해야 한다.
- **FR-018**: 시스템은 세트별 문제 수와 완료 수를 서버 응답 값으로 표시해야 하며, 고정값으로 대체해서는 안 된다.
- **FR-019**: 시스템은 세트 설명을 서버 응답에서 가져와 세트 시작 화면에 표시해야 한다.
- **FR-020**: 시스템은 기존 답변을 선택 index·작성 텍스트·정답 여부를 구분할 수 있는 형태로 보존해, 답변 여부 판단과 결과 복원에 사용할 수 있어야 한다.
- **FR-021**: 시스템은 출처의 파일 경로·시작 줄·설명·외부 링크를 보존해 출처 화면에 표시해야 한다.
- **FR-022**: 시스템은 서버가 반환한 문제·선택지·세트 배열의 순서를 재정렬하지 않아야 한다.
- **FR-023**: 시스템은 답변 제출 이후 최신 진행률이 필요한 화면에서 진행률을 다시 조회해 반영해야 한다.

### 기능 요구사항 - 구조 제약

- **FR-024**: 각 화면의 상태와 액션은 그 화면을 책임지는 독립 Reducer가 소유해야 하며, 하나의 Reducer가 여러 화면의 상태를 함께 소유해서는 안 된다.
- **FR-025**: 하위 Reducer는 화면 이동을 직접 수행하지 않고 상위에 의도를 위임해야 하며, 실제 이동은 상위 Reducer가 수행해야 한다.
- **FR-026**: 각 Reducer는 자신이 사용하는 UseCase만 생성자 주입으로 받아야 하며, 전역 컨테이너나 Service Locator를 사용해서는 안 된다.
- **FR-027**: 계획 단계 산출물은 Reducer별로 주입되는 UseCase 목록과 그 사용 지점을 명시해야 한다.
- **FR-028**: 화면 구현은 기존 UI 패키지 컴포넌트와 디자인 토큰을 사용해야 하며, 색·치수·타이포 값을 화면 코드에 직접 적어서는 안 된다.

### 기능 요구사항 - 범위 제약

- **FR-029**: 구현은 Feature·App·Composition·Domain·UI 패키지만 변경해야 하며, Data 패키지 파일을 변경해서는 안 된다.
- **FR-030**: Domain·Composition·UI 패키지 변경은 이 명세가 식별한 데이터 정합(FR-017~FR-022)과 컴포넌트 정합(FR-007)에 필요한 범위로 한정해야 한다.
- **FR-031**: 패키지 간 의존 방향은 기존 아키텍처 문서의 허용 방향을 유지해야 한다.

### 핵심 엔터티 *(기능에 데이터가 포함되면 작성)*

- **학습 세트**: 하나의 학습 단위. 식별자, 라벨, 제목, 설명, 그리고 순서가 있는 문제 목록을 가진다.
- **문제**: 세트를 구성하는 항목. 식별자, 본문, 형식(객관식·서술형), 선택지 목록(객관식만), 출처, 기존 답변을 가진다.
- **기존 답변**: 사용자가 이전에 제출한 답. 선택 index(객관식) 또는 작성 텍스트(서술형)와 정답 여부를 구분해 가진다. 정답 여부는 서술형에서 비어 있다.
- **출처**: 문제가 유래한 코드 위치. 파일 경로, 시작 줄, 대상 심볼, 설명, 외부 링크를 가진다. 한 문제가 여러 출처를 가질 수 있다.
- **객관식 제출 결과**: 정답 여부, 정답 선택지 index, 해설로 구성된다.
- **서술형 제출 결과**: 해설과 자가채점 기준으로 구성되며 정답 여부를 포함하지 않는다.
- **세트 진행**: 세트별 전체 문제 수와 완료 문제 수. 프로젝트 상세의 세트 목록 표시에 사용한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 학습자가 프로젝트 상세 또는 홈의 이어 풀기에서 시작해 세트의 모든 문제를 풀고 학습 완료 화면까지 도달하는 흐름을 중단 없이 완료한다.
- **SC-002**: Task 3 화면 8종 각각에 대해 정의된 상태 전이를 검증하는 자동화 테스트가 존재하고 통과한다.
- **SC-003**: 정답 여부·정답 선택지·해설 표시가 100% 서버 응답 값에서 비롯되며, 클라이언트가 정오를 계산하는 코드 경로가 존재하지 않는다.
- **SC-004**: 세트 목록의 진행 표시가 서버가 준 문제 수·완료 수와 일치하며, 고정값 `0`으로 표시되는 사례가 없다.
- **SC-005**: 변경된 파일 중 Data 패키지 경로가 0건이다.
- **SC-006**: 각 화면 Reducer의 단위 테스트가 다른 화면의 상태를 준비하지 않고 독립적으로 실행된다.
- **SC-007**: 계획 산출물에서 Reducer별 주입 UseCase 목록을 확인할 수 있고, 구현된 각 Reducer의 생성자 인자가 그 목록과 일치한다.
- **SC-008**: 전체 공유 scheme 빌드와 테스트가 변경 전후 모두 통과한다.
- **SC-009**: 답변 제출 실패 시 사용자가 입력하거나 선택한 내용이 유지되어 재시도할 수 있다.
- **SC-010**: 객관식·서술형이 섞인 세트와 서술형만 있는 세트 각각에 대해 학습 완료 화면의 카운터 표시를 검증하는 테스트가 존재하고 통과한다.

## 가정

- 서버 API는 유스케이스 명세(006) FR-020~FR-036과 `specs/011-server-data-api` 계약대로 동작하며, 이 기능에서 서버 계약을 변경하지 않는다.
- Data 패키지의 DTO는 세트 설명, 기존 답변의 선택 index·정답 여부, 출처의 줄 번호·심볼·설명, 세트별 문제 수·완료 수를 이미 모두 제공한다(2026-09-03 확인). 따라서 유실 복구는 Domain 모델과 Composition 어댑터 매핑에서 수행한다.
- 문제 풀이에 필요한 UseCase 6종(세트 조회, 객관식 제출, 서술형 제출, 북마크 설정, 북마크 목록 조회, 프로젝트 상세 조회)은 이미 구현되어 있고 `AppComposition`이 공개하고 있어 새로 만들지 않는다.
- 서술형 답안은 서버가 채점하지 않으며 학습자가 AI 답안과 비교해 스스로 판단한다.
- 화면 문구·레이아웃·색은 Figma 섹션 `4113:6395`를 정본으로 삼고, 원본에 근거가 없는 값은 계획 단계에서 확정하거나 미확정으로 표시한다. 예외로 서술형 글자 수 상한은 명확화 세션에서 400자로 확정했으며, 이는 Figma 표시값 300과 다르고 서버 상한 2000보다 작다.
- 로딩·실패·제출 중 상태는 Figma에 화면이 없으므로 프로젝트의 기존 상태 표현 방식을 재사용한다.
- 학습 완료 화면의 정답 집계는 세트 전체를 기준으로 하며, 기존 답변의 정답 여부가 보존된다는 FR-020 전제에 의존한다. FR-020이 충족되지 않으면 이번 풀이에서 제출한 문제만 집계된다.
- 프로젝트 상세 화면은 이 기능에서 구현하되, 화면 인벤토리상 G4 그룹의 다른 화면(프로젝트 목록·삭제 등)은 범위 밖이다.

## 범위 밖

- 프로젝트 목록, 프로젝트 등록, 저장한 문제 목록, 마이·설정 화면.
- 서버 API 계약 변경과 Data 패키지 DTO 변경.
- 서술형 자가채점 기준(rubric)을 화면에 표시하는 기능. Figma 원본에 해당 화면이 없다.
- 프로젝트 상세 화면의 상단 메뉴 버튼 동작. 동작 근거가 확정되지 않아 FR-006b에 따라 노출하지 않는다.
- 오프라인 캐시와 재시도 정책 일반화.
- 접근성·다이내믹 타입 전면 대응. 기존 컴포넌트가 제공하는 수준을 유지한다.
