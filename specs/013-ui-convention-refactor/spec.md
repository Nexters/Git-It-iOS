# 기능 명세: UI 패키지 컨벤션 리팩터링

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/ui-convention-refactor`

**생성일**: 2026-08-21

**상태**: 초안

**입력**: 사용자 설명: "UI 패키지에 대해서 업데이트된 컨벤션이 적용되어있지 않습니다. 컨벤션을 기준으로 리팩토링을 진행해주세요"

## 명확화

### 세션 2026-08-21

- 질문: `Components/Review/**`의 `ViewModel`·`State` wrapper 제거도 이번 리팩터링 범위에 포함할까요? → 답변: `Components/Review/**`를 Feature 패키지의 임시 target으로 이동한다.
- 질문: Feature 패키지로 이동할 임시 Review target을 제품 앱 실행 경로에 연결할까요? → 답변: 독립 검토 target으로 빌드·검증하고 제품 앱에서는 제외한다.

### 세션 2026-08-22

- 질문: 공개 계약이 변경되는 각 UIComponent에 어떤 자동화 검증을 요구할까요? → 답변: 공개 입력과 상호작용을 검증하고 기존 레이아웃은 유지하며 접근성 구현과 검증은 제거한다.
- 질문: Figma page의 여러 section이 서로 다를 경우 어떤 우선순위로 해석할까요? → 답변: `사용한 컴포넌트`는 형태·상태 계약, `Design system`은 토큰 계약의 정본으로 사용하고 `최종 UXUI`는 조립 결과 검증에만 사용한다.
- 질문: Figma `Button`의 `Default`·`Pressing`·`Disabled`·`Error` 상태를 `ActionButton` 공개 계약에 어떻게 반영할까요? → 답변: `Pressing`은 내부 상호작용, `Disabled`는 `isEnabled`, `Error`는 `destructive` 시각 변형으로 매핑한다.
- 질문: Figma `SelectCardList`의 위치 기반 `Default`·`1`…`5` 선택 상태를 공개 계약에 어떻게 표현할까요? → 답변: 목록은 안정적인 항목 ID와 외부 `Binding`으로 선택값을 받고, 각 카드의 선택 여부를 내부에서 파생한다.
- 질문: 현재 레이아웃과 Figma의 컴포넌트 형태가 다를 때 어떤 기준을 우선할까요? → 답변: 기존 크기·간격·배치를 우선하고 Figma는 지원 변형과 상태 의미의 기준으로만 적용한다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 컴포넌트 공개 계약 정렬 (우선순위: P1)

UI 패키지를 사용하는 Feature 개발자가 컴포넌트를 생성할 때, Feature 전용 모델이나 표시 상태 wrapper 없이 표시 값, `Binding`, 콜백 및 필요한 시각 변형만으로 일관된 공개 계약을 사용한다.

**주요 행위자**: Feature 개발자

**우선순위 이유**: 공개 계약의 불일치는 모든 Feature 호출부로 전파되어 UI 패키지의 재사용 경계를 훼손한다.

**독립 테스트**: UIComponent production 소스를 검사하고 각 컴포넌트를 공개 입력으로 생성해, 공개 API에 `ViewModel`, `State`, Feature/TCA 타입이 없으며 기존 표시와 입력 전달 계약이 유지되는지 확인한다.

**수용 시나리오**:

1. **전제** 기존 컴포넌트가 표시 상태 wrapper를 공개 입력으로 요구하는 상태, **실행** 컨벤션에 맞춰 공개 계약을 정렬한 뒤 호출부와 테스트를 갱신하면, **결과** 표시 값은 초기화 인자, 외부 변경 값은 `Binding`, 일회성 입력은 콜백으로 전달된다.
2. **전제** 고정된 시각 변형이 둘 이상인 컴포넌트, **실행** 공개 생성 경로를 검토하면, **결과** 호출부는 시각 의미의 팩토리 또는 필요한 직접 초기화만 사용하고 Feature 업무 역할이나 상태 wrapper를 전달하지 않는다.
3. **전제** Figma `Button`이 `Default`·`Pressing`·`Disabled`·`Error` 상태를 정의한 상태, **실행** `ActionButton` 공개 계약을 정렬하면, **결과** `Pressing`은 컴포넌트 내부 상호작용으로 처리되고 `Disabled`는 `isEnabled`, `Error`는 `destructive` 시각 변형으로 제공된다.
4. **전제** Figma `SelectCardList`가 카드 위치별 선택 상태를 정의한 상태, **실행** 목록의 공개 계약을 정렬하고 사용자가 카드를 선택하면, **결과** 안정적인 항목 ID를 가진 외부 선택값이 갱신되고 각 카드의 선택 표현은 그 값에서 파생된다.

---

### 시나리오 2 - 표현 계층과 디자인 토큰 정렬 (우선순위: P2)

UI 패키지를 유지보수하는 개발자가 DesignSystem, 말단·조합·검토 컴포넌트의 소유 경계와 토큰 적용 규칙을 일관되게 확인할 수 있다.

**주요 행위자**: UI 패키지 유지보수자

**우선순위 이유**: 토큰 밖의 공통 시각 어휘와 잘못 분류된 컴포넌트는 디자인 변경 시 중복 수정과 표현 불일치를 만든다.

**독립 테스트**: production 컴포넌트의 의존 구조·파일 배치·토큰 적용을 점검하고, 상태별 레이아웃 계약이 기존 검증과 동일하게 통과하는지 확인한다.

**수용 시나리오**:

1. **전제** UIComponent source에 말단·조합 또는 Review 분류가 불명확한 구현이 있는 상태, **실행** 실제 렌더링 의존 구조와 용도에 따라 정리하면, **결과** 제품 컴포넌트는 말단·조합 위치와 소유 선언 구조를 따르고 Review 컴포넌트는 제품 앱과 연결되지 않는 Feature 패키지의 독립 임시 target으로 이동한다.
2. **전제** Figma의 컴포넌트 변형·상태, 토큰 또는 화면 조립 결과가 서로 다른 상태, **실행** UIComponent와 DesignSystem 규칙을 적용하면, **결과** `사용한 컴포넌트`의 지원 변형·상태 의미와 `Design system`의 토큰을 각각 정본으로 사용하고 `최종 UXUI`는 조립 결과 검증에만 사용하되 기존 크기·간격·배치는 변경하지 않는다.

---

### 시나리오 3 - 리팩터링 동작 동등성 검증 (우선순위: P3)

개발자가 UI 패키지 리팩터링 후에도 컴포넌트의 표시 상태, 사용자 입력 전달과 현재 레이아웃 계약이 보존되고 접근성 구현이 제거되었음을 검증할 수 있다.

**주요 행위자**: UI 패키지 유지보수자와 검토자

**우선순위 이유**: 구조만 정렬하고 컴포넌트 동작이 바뀌면 호출부와 화면 품질에 회귀가 발생할 수 있다.

**독립 테스트**: 변경된 각 컴포넌트의 공개 입력과 상호작용 계약, 기존 레이아웃을 검증하는 단위·UI 자동화 테스트를 실행하고, 접근성 구현·검증이 남아 있지 않으며 UI 패키지의 production build 및 테스트용 컴파일이 성공하는지 확인한다.

**수용 시나리오**:

1. **전제** 리팩터링 전 컴포넌트의 상태별 화면과 사용자 입력이 검증된 상태, **실행** 리팩터링 후 관련 계약 테스트와 레이아웃 검증을 실행하면, **결과** 기존에 지원하던 상태별 표현·입력 전달과 현재 레이아웃이 유지되고 접근성 구현과 관련 검증은 남지 않는다.
2. **전제** UI package production target과 테스트 target, **실행** 저장소의 빌드 및 테스트용 컴파일 절차를 실행하면, **결과** UI 변경으로 인한 컴파일 또는 dependency 위반이 보고되지 않는다.

### 예외·경계 사례

- 기존 공개 API의 입력 의미가 서로 다르면 외형이 비슷해도 하나의 범용 컴포넌트나 입력 모델로 통합하지 않고, 각 의미를 보존하는 별도 계약을 유지한다.
- 고정된 시각 변형이 하나뿐인 컴포넌트는 의미 없는 기본 팩토리를 추가하지 않고 직접 초기화 경로를 유지한다.
- Figma의 일시적 상호작용 상태를 호출부가 직접 설정하는 공개 `State`로 노출하지 않는다.
- `SelectionCardList`의 항목 순서가 바뀌거나 개수가 다섯 개보다 적거나 많아져도 선택값은 위치가 아니라 안정적인 항목 ID로 유지한다.
- Review 전용 컴포넌트는 UIComponent production target에서 제거하고 Feature 패키지의 독립 임시 target으로 이동하며, 제품 컴포넌트와 제품 앱의 target·실행 경로에서 의존하지 않게 한다.
- 44pt 미만의 시각 요소가 필요한 경우에도 실제 터치 영역은 44pt 이상으로 유지한다.
- 리팩터링으로 새로운 공유 시각 값이 필요해도 단일 컴포넌트에서만 의미가 있으면 공용 토큰으로 승격하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 `sources/Projects/UI/Component/Components/**`의 production 컴포넌트 공개 계약을 UI 패키지 규칙과 UIComponent·View 컨벤션에 맞게 정렬해야 한다.
- **FR-002**: 시스템은 컴포넌트의 읽기 전용 표시 값을 초기화 인자로, 외부 변경 값을 SwiftUI `Binding`으로, 일회성 사용자 입력을 프레임워크 중립 콜백으로 제공해야 한다.
- **FR-003**: 시스템은 UIComponent production 구현과 공개 API에서 표시 상태를 묶는 `ViewModel`, `State` 또는 동등한 wrapper와 Feature·TCA 타입을 제거해야 한다.
- **FR-004**: 시스템은 UIComponent production 컴포넌트를 실제 렌더링 의존 구조에 맞게 말단 또는 조합으로 분류하고, 기존 Review 전용 컴포넌트를 Feature 패키지의 독립 임시 target으로 이동해 제품 컴포넌트와 제품 앱의 target·실행 경로에서 의존하지 않게 해야 한다.
- **FR-005**: 시스템은 컴포넌트가 소유하는 `Style`, `Constant` 및 그 밖의 비상태 보조 선언을 소유 View 안에 필요한 최소 접근 수준으로 중첩하고, 각 Swift 파일의 주된 최상위 타입과 파일 이름을 일치시켜야 한다.
- **FR-006**: 시스템은 UIComponent와 DesignSystem의 공통 시각 어휘를 DesignSystem이 단독 소유하게 하고, 역할이 있는 색상·공유 레이아웃·모서리·컨트롤 크기·텍스트 표현에 정해진 토큰과 적용 API를 사용해야 한다.
- **FR-007**: 시스템은 고정 토큰 조합을 갖는 시각 변형이 둘 이상인 컴포넌트에만 시각 의미의 팩토리를 제공하고, 변형이 하나뿐인 컴포넌트에는 의미 없는 기본 팩토리를 추가하지 않아야 한다.
- **FR-008**: 시스템은 리팩터링 전 지원하던 컴포넌트의 표시 상태, 사용자 입력 전달 및 현재 레이아웃 계약을 보존하고, 접근성 구현과 관련 검증을 제거해야 한다.
- **FR-009**: 시스템은 영향받는 UI 패키지 테스트와 레이아웃 검토 harness를 새 공개 계약에 맞게 갱신하고, production target이 `ComposableArchitecture` 또는 프로젝트의 Feature·Domain·Data·Infrastructure·Composition target에 의존하지 않게 해야 한다.
- **FR-010**: 시스템은 Figma page의 `사용한 컴포넌트` section을 컴포넌트의 지원 변형·상태 의미 계약, `Design system` section을 토큰 계약의 정본으로 사용하고 `최종 UXUI` section은 Feature 조립 결과를 대조하는 용도로만 사용해야 하며, Figma와 차이가 있어도 기존 크기·간격·배치 계약을 우선해야 한다.
- **FR-011**: 시스템은 Figma `Button`의 `Pressing`을 `ActionButton` 내부 상호작용으로 처리하고, `Disabled`는 `isEnabled`, `Error`는 `destructive` 시각 변형으로 제공하며 공개 상태 wrapper를 추가하지 않아야 한다.
- **FR-012**: 시스템은 Figma `SelectCardList`의 위치별 선택 상태를 공개 enum이나 index로 노출하지 않고, 안정적인 항목 ID에 대한 외부 `Binding`으로 선택값을 제공하며 각 `SelectionCard`의 선택 여부를 목록 내부에서 파생해야 한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: `Components/Leaf/**`와 `Components/Composite/**`의 모든 production 컴포넌트 공개 API와 구현에서 표시 상태 wrapper(`ViewModel`, `State` 또는 동등한 타입) 및 Feature·TCA 타입 사용이 0건이다.
- **SC-002**: UIComponent production 컴포넌트의 100%가 말단·조합 분류, 파일·선언 배치 및 공개 생성 경로에 관한 해당 컨벤션 검토 항목을 충족하고, Review 전용 컴포넌트는 100% Feature 패키지의 독립 임시 target에 속하며 제품 앱이 해당 target에 갖는 의존은 0건이다.
- **SC-003**: 공개 계약이 변경된 컴포넌트의 100%에서 공개 입력과 상호작용 계약을 검증하고 기존 레이아웃을 유지하는 관련 단위·UI 자동화 테스트가 통과한다.
- **SC-004**: 저장소의 UI를 포함한 production build와 테스트용 컴파일 절차가 성공하며, UI production target의 금지된 패키지 또는 `ComposableArchitecture` 의존은 0건이다.
- **SC-005**: UIComponent production 구현과 관련 검증에서 접근성 구현 및 검증 항목은 0건이다.
- **SC-006**: Figma section 간 변형·상태·토큰 충돌과 Figma·기존 레이아웃 간 차이는 FR-010의 우선순위로 판정되어 미해결 충돌이 0건이고, 기존 크기·간격·배치 검증이 모두 통과한다.
- **SC-007**: `ActionButton` 공개 API에서 Figma 상태를 그대로 표현하는 `State` 타입 사용은 0건이고, `Pressing`·`Disabled`·`Error`의 매핑 계약이 자동화 검증을 통과한다.
- **SC-008**: `SelectionCardList`의 선택 상호작용, 외부 선택값 변경 및 항목 재정렬 후 선택 유지에 대한 자동화 검증이 통과하고, 공개 위치 기반 상태 enum과 선택 index 사용은 0건이다.
