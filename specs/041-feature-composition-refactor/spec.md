## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 분해 기준 확립과 중복 관심사 전수 식별 (우선순위: P1)

개발자가 "무엇이 하나의 Feature인가"를 판단할 수 있는 기준을 갖고, 그 기준으로 Feature 패키지의
모든 Reducer를 대조해 중복된 기능 관심사를 빠짐없이 식별한다. 현재 Feature 패키지의 Reducer는
화면과 라우팅 단위로 나뉘어 있어, 같은 기능 관심사가 여러 Reducer에 따로 선언되어 있는지를
판단할 공통 기준이 없다.

**주요 행위자**: 개발자

**우선순위 이유**: 기준과 식별 결과가 없으면 어떤 Feature를 통합할지, 통합하지 않을지를 매번
즉흥적으로 결정하게 된다. 이후 모든 시나리오가 이 결과물을 입력으로 사용한다.

**독립 테스트**: 확립된 기준을 Feature 패키지의 각 Reducer에 적용했을 때, 제3자가 같은 기준으로
같은 분류 결과에 도달하는지 검토한다. 통합을 한 건도 수행하지 않아도, 중복 범위와 작업량을
확인 가능한 형태로 제공한다.

**산출물**: `specs/041-feature-composition-refactor/research.md`에 기록된 기준과 전수 식별
결과.

**착수 조건**: 없음. 이 시나리오는 읽기 전용 분석이므로 다른 시나리오의 완료를 기다리지 않고
진행한다.

**수용 시나리오**:

1. **전제** 분해 기준이 문서화되어 있지 않고, **실행** 기능 관심사와 상태 소유를 기준으로
   판단 규칙을 정의하면, **결과** 임의의 Reducer에 대해 기능 Feature, 화면 합성 Feature, 전환
   계층 중 어디에 해당하는지 판정할 수 있다.
2. **전제** Feature 패키지에 여러 Reducer가 존재하고, **실행** 모든 Reducer를 기준에 대조하면,
   **결과** 중복 선언된 기능 관심사와 그 선언 위치가 누락 없이 목록으로 확인된다.
3. **전제** 어떤 중복이 식별되었으나 통합이 적절하지 않다고 판단되면, **실행** 그 판단을
   기록하면, **결과** 제외 사유가 남아 이후 작업에서 다시 판단하지 않는다.

### 시나리오 2 - 식별된 기능 관심사를 단일 Feature로 추출 (우선순위: P1)

개발자가 식별된 각 중복 관심사에 대해, 그 상태 모델과 전이 규칙을 소유하는 Feature를 하나만
남긴다. 하나의 독립 단위는 관심사 하나의 추출과, 그 관심사를 선언하던 모든 화면 Feature의 합성
전환을 함께 포함하며, 식별된 관심사 수만큼 반복된다. 단위 완료 시점에 저장소에 중복 선언이
남지 않는다.

**주요 행위자**: 개발자

**우선순위 이유**: 이 시나리오가 중복 제거라는 목적을 직접 달성한다. 관심사 단위로 쪼개져
있어 하나만 완료해도 그만큼의 효과가 확정된다.

**독립 테스트**: 관심사 하나를 추출하고 그 관심사를 쓰던 화면들을 합성으로 전환한 뒤, 그
관심사의 상태 전이를 화면과 무관하게 검증하는 테스트를 작성하고, 화면 테스트는 합성 지점
검증만 남긴 채 이관 전후로 단언이 소실되지 않았는지 확인한다.

**착수 조건**: UIComponent 팩토리 제거가 이 브랜치에 반영되어 있어야 한다. 그 변경은 UI 공개 API
제거와 Feature·App 호출부 수정이 불가분하고 대상 호출부가 Feature 전반에 걸쳐 있어, 먼저
추출하면 같은 파일을 두 번 수정하게 되기 때문이다. 이 조건은 현재 HEAD에서 이미 충족되어 있다.

**수용 시나리오**:

1. **전제** 한 기능 관심사의 상태 유형과 전이 규칙이 둘 이상의 Reducer에 선언되어 있고,
   **실행** 이를 하나의 기능 Feature로 추출하면, **결과** 해당 선언이 저장소에 한 벌만 남는다.
2. **전제** 추출 대상 Reducer들의 현재 동작이 서로 미세하게 다르고, **실행** 통합을 수행하면,
   **결과** 정본으로 선택한 동작과 그로 인해 달라지는 화면 동작이 `research.md`의 해당 관심사
   항목에 기록된다.
3. **전제** 어떤 화면만 사용하는 부가 동작이 관심사에 섞여 있고, **실행** 추출을 수행하면,
   **결과** 그 부가 동작은 기능 Feature가 아니라 해당 화면 쪽 책임으로 남는다.

### 시나리오 3 - 화면 Feature를 기능 Feature의 합성으로 재구성 (우선순위: P1)

개발자가 각 화면 Feature를 직접 구현된 상태 덩어리가 아니라, 필요한 기능 Feature들의 합성과
화면 고유 결정만으로 구성한다. 기능 관심사의 합성 전환 자체는 시나리오 2의 관심사 단위에
포함되며, 이 시나리오는 그 전환이 끝난 화면에 남은 화면 고유 정리(잔여 전환 책임 축소, Router
성격 Feature의 기능 상태 반납, 화면 고유 후속 동작 정리)를 화면 단위로 완료한다.

**주요 행위자**: 개발자

**우선순위 이유**: 기능 상태가 빠져나간 뒤에도 화면 Feature에 정리되지 않은 책임이 남으면
합성 구조의 이점이 드러나지 않는다. 이 정리는 화면 단위로 독립 완료가 가능하므로 별도
시나리오로 분리한다.

**독립 테스트**: 화면 하나의 정리를 마친 뒤, 해당 화면의 테스트가 합성 지점과 화면 고유 후속
동작을 동일하게 검증하고 그 화면이 기능 상태를 직접 선언하지 않는지 확인한다.

**착수 조건**: 시나리오 2와 동일한 기준선을 전제로 하며, 화면별로는 그 화면이 쓰던 관심사들의
시나리오 2 단위가 모두 끝난 뒤에 착수한다.

**수용 시나리오**:

1. **전제** 화면 Feature가 기능 상태를 직접 소유하고 있고, **실행** 기능 Feature를 자식으로
   합성하면, **결과** 화면 Feature에는 표시 범위·후속 동작·전환 결정만 남는다.
2. **전제** 화면 Feature가 자식의 결과를 수신해야 하고, **실행** 자식이 결과를 확정하면,
   **결과** 부모는 화면 고유 후속 동작만 수행하고 자식의 내부 상태를 직접 바꾸지 않는다.
3. **전제** 같은 기능 Feature가 한 화면에 둘 이상 필요하고, **실행** 두 번 합성하면, **결과**
   각 인스턴스의 상태가 서로 간섭하지 않는다.
4. **전제** 화면 전환만 담당하던 Router 성격의 Feature가 있고, **실행** 기능 상태가 빠져나가면,
   **결과** 전환 책임만 남고 기능 상태를 다시 소유하지 않는다.

---

### 시나리오 4 - 분해 기준을 컨벤션 문서로 확립 (우선순위: P3)

개발자가 이후 새 Feature를 추가하거나 기존 Feature를 수정할 때, 분해 기준과 현재 분류 결과를
문서에서 확인하고 리뷰에서 대조할 수 있다. 검증 수단은 컨벤션 문서와 리뷰이며, 자동 검사는
도입하지 않는다.

**주요 행위자**: 개발자

**우선순위 이유**: 리팩토링 결과가 시간이 지나며 되돌아가는 것을 막지만, 통합이 끝나기 전에는
문서화할 확정된 분류 결과가 없다.

**독립 테스트**: 기준을 의도적으로 위반하는 변경을 가정했을 때, 문서만 읽고 그 변경이 기준을
벗어났다고 판정할 수 있는지 검토한다.

**착수 조건**: 시나리오 2·3의 결과가 확정되어야 최종 분류 결과를 문서화할 수 있다.

**수용 시나리오**:

1. **전제** 분해 기준이 코드에만 암묵적으로 존재하고, **실행** 기준을
   `docs/conventions/tca/feature.md`에, 분류 결과를 그 하위 문서에 남기면, **결과** 새 Feature를
   추가하려는 개발자가 문서만으로 기능 Feature, 화면 합성 Feature, 전환 계층 중 어디에 해당하는지
   판정할 수 있다.
2. **전제** 한 기능 관심사의 상태를 새 화면 Feature가 중복 선언하는 변경이 제안되고, **실행**
   리뷰에서 컨벤션 문서와 대조하면, **결과** 그 변경이 기준을 벗어났다고 지적할 근거가 문서에
   존재한다.
3. **전제** 통합하지 않기로 한 중복이 있고, **실행** 문서를 확인하면, **결과** FR-016의 제외
   사유를 찾을 수 있어 같은 판단을 반복하지 않는다.

### 예외·경계 사례

- 두 화면이 같은 기능을 쓰지만 필요한 의존성 집합이 다를 때, 사용하지 않는 의존성을 주입하도록
  강제되면 어떻게 하는가? — 기능 Feature의 의존성 경계를 그 기능이 실제로 요구하는 범위로
  한정하고, 화면 고유 동작은 화면 Feature에 남긴다.
- 겉보기에 비슷하지만 상태 전이 규칙이 실제로 다른 두 Reducer를 어떻게 처리하는가? — 같은
  관심사로 보지 않는다. 통합 근거는 명칭 유사성이 아니라 상태 모델과 전이 규칙의 동일성이다.
- 통합했을 때 특정 화면만을 위한 분기가 기능 Feature 내부에 늘어나면 어떻게 하는가? — 화면
  식별자에 따른 분기를 기능 Feature 안에 두지 않고, 그 차이를 화면 Feature의 책임으로
  되돌리거나 통합 대상에서 제외한다.
- 통합 대상들의 현재 동작이 서로 미세하게 다를 때(예: 재시도 조건, 실패 표시 범위) 어떤 동작을
  정본으로 삼는가? — 차이를 먼저 기록하고 정본 동작을 명시적으로 선택하며, 선택으로 인해
  달라지는 화면 동작을 변경 사항으로 남긴다.
- 중복이 두 곳뿐이고 통합 비용이 중복 유지 비용보다 클 때는 어떻게 하는가? — 통합하지 않되
  식별 결과와 제외 사유를 기록해 판단이 반복되지 않게 한다.
- 한 Reducer가 기능 상태와 화면 전환을 모두 소유해 어느 쪽으로도 분류되지 않으면 어떻게
  하는가? — 기능 상태를 분리해 기능 Feature로 추출하고, 남은 전환 책임은 전환 계층으로 둔다.
- 한 화면만 쓰던 기능 Feature를 나중에 다른 화면도 쓰게 되면 어떻게 하는가? — 그 시점에 해당
  기능 Feature를 공용 디렉터리로 옮긴다. 화면 디렉터리 사이에 새 참조를 만들지 않는다.
- 두 화면이 같은 기능 Feature를 합성했을 때 한 화면의 적재·실패 결과가 다른 화면에도 나타나야
  하는가? — 나타나지 않는다. 각 화면은 독립 인스턴스를 가지며 현행처럼 화면별로 적재·실패를
  처리한다(FR-026).

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: Feature 분해 기준은 화면이나 라우팅 단위가 아니라 "동일한 기능 관심사와 그
  기능이 소유하는 상태 모델"이어야 한다. 하나의 기능 Feature는 하나의 기능 관심사와 그 상태
  전이만 소유한다.
- **FR-002**: 관심사가 둘 이상인 화면에 대응하는 Feature는 자신이 필요한 기능 Feature들을
  자식으로 합성해 구성해야 하며, 자식 Feature가 이미 소유한 상태 유형과 전이 규칙을 다시 선언하지
  않아야 한다. 관심사가 하나뿐인 화면은 별도 합성 Feature를 두지 않고 그 기능 Feature를 화면이
  직접 관찰한다.
- **FR-003**: 하나의 기능 관심사에 대한 상태 유형과 전이 규칙은 저장소 전체에서 단 하나의
  Feature에만 선언되어야 한다.
- **FR-004**: 기능 Feature는 그 기능 수행에 실제로 필요한 의존성만 요구해야 하며, 특정 화면에서만
  쓰이는 동작을 위한 의존성을 모든 합성 지점에 강제하지 않아야 한다.
- **FR-005**: 기능 Feature는 자신을 합성한 화면이 무엇인지에 따라 동작을 분기하지 않아야 한다.
  화면별 차이는 화면 Feature가 결정한다.
- **FR-006**: 화면 Feature는 자식 기능 Feature의 결과를 수신해 화면 고유의 후속 동작만 수행해야
  하며, 자식의 내부 상태를 직접 변경하지 않아야 한다.
- **FR-007**: 같은 기능 Feature가 한 화면에 둘 이상 합성되는 경우 각 인스턴스의 상태는 서로
  독립적으로 유지되어야 한다.
- **FR-008**: 리팩토링은 최종 사용자에게 관찰되는 화면 동작과 화면 전환 결과를 변경하지 않아야
  한다. 통합 과정에서 기존 동작 간 차이를 해소하기 위해 정본 동작을 선택한 경우, 그로 인해
  달라지는 동작을 `research.md`에 관심사별로 누적 기록하고, 확정된 최종 목록을
  `docs/conventions/tca/feature/`의 분류 문서에 함께 남겨야 한다.
- **FR-009**: 각 기능 Feature는 자신의 상태 전이를 화면 Feature를 거치지 않고 독립적으로
  검증하는 테스트를 가져야 한다.
- **FR-010**: 합성 구조로 전환된 뒤 화면 단위 테스트는 합성 지점만 검증해야 한다. 즉 화면
  Feature가 해당 동작을 자식 기능 Feature에 위임하는지, 그리고 자식이 결과를 확정했을 때 화면
  고유의 후속 동작과 화면 전환이 기존과 동일한지를 단언한다. 관심사 내부의 상태 전이 단언은
  FR-009의 기능 Feature 테스트로 이관하고 화면 테스트에서는 제거해, 같은 전이를 두 곳에서
  검증하지 않는다. 이관 과정에서 어떤 단언도 소실되지 않아야 한다.
- **FR-011**: 리팩토링은 아키텍처 문서에 정의된 패키지 의존 방향을 위반하지 않아야 하며,
  Domain/Data/Core가 Feature에 의존하지 않는 제약을 유지해야 한다.
- **FR-012**: 의존성 전달은 생성자 주입을 유지해야 하며, 기능 Feature 도입을 이유로 전역
  컨테이너나 Service Locator를 도입하지 않아야 한다.
- **FR-013**: 리팩토링은 기능 관심사 단위와 화면 단위로 나누어, 각 단위가 독립적으로
  빌드·테스트 가능한 상태로 완료될 수 있어야 한다. 기능 관심사 단위는 추출과, 그 관심사를
  선언하던 모든 화면의 합성 전환을 함께 포함해 단위 완료 시점에 FR-003을 만족해야 하며,
  화면 단위는 그 뒤에 남은 화면 고유 정리를 대상으로 한다.
- **FR-014**: 적용 범위는 Feature 패키지의 모든 Reducer여야 한다. 특정 화면이나 특정 관심사만
  대상으로 한정하지 않는다.
- **FR-015**: 모든 Reducer를 FR-001의 기준에 대조해 중복된 기능 관심사와 그 선언 위치를 누락
  없이 식별해야 한다. 식별 결과는 `specs/041-feature-composition-refactor/research.md`에
  기록되어 시나리오 2·3의 작업 단위를 나누는 입력이 된다.
  같은 문서가 FR-008의 동작 차이 기록을 관심사별로 누적하는 위치이기도 하다.
- **FR-016**: 중복으로 식별되었으나 통합하지 않기로 한 대상은 제외 사유를 함께 기록해야 한다.
- **FR-017**: 통합 판단 근거는 이름이나 화면 유사성이 아니라 상태 모델과 전이 규칙의 동일성이어야
  한다. 규칙이 실제로 다른 대상은 같은 관심사로 묶지 않는다.
- **FR-018**: 리팩토링 완료 후 Feature 패키지의 모든 Reducer는 기능 Feature, 화면 합성 Feature,
  전환 계층 중 하나로 분류될 수 있어야 한다.
- **FR-019**: 시나리오 2·3(추출과 합성)은 UIComponent 팩토리 제거가 반영된 호출부를 기준선으로
  삼아야 한다. 이 조건은 현재 브랜치 HEAD에서 이미 충족되므로 시나리오 1~4의 착수를 가로막는
  외부 선행 기능은 남아 있지 않다.
- **FR-020**: 분해 기준은 `docs/conventions/tca/feature.md`에 기록되어야 하고, 통합이 완료된
  뒤의 최종 분류 결과와 FR-016의 제외 사유, FR-008의 확정된 동작 차이 목록은 같은 컨벤션 체계의
  하위 문서(`docs/conventions/tca/feature/`)에 기록되고 `feature.md`에서 링크되어야 한다. `research.md`의 식별 결과는 확정 전의 중간
  산출물이며, 컨벤션 문서가 최종 정본이다. 기준 준수 여부는 리뷰에서 그 문서와 대조해
  판정하며, 이를 강제하는 자동 검사는 이번 범위에 포함하지 않는다.
- **FR-021**: 시나리오 1~4는 모두 `feature/feature-composition-refactor` 브랜치에서 진행되어야
  하며, 이 기능은 한 번의 PR로 닫는다. 시나리오를 별도 브랜치나 별도 PR로 분리하지 않는다.
- **FR-022**: Feature 패키지는 단일 target을 유지하며, 공용 경계는 디렉터리로 실현한다. 둘 이상의
  화면 Feature가 합성하는 기능 Feature는 공용 디렉터리에 배치되어야 하고, 화면 디렉터리는 그
  공용 디렉터리의 타입만 참조해야 한다. 한 화면 디렉터리가 다른 화면 디렉터리의 타입을 참조하는
  구성은 허용하지 않는다. 한 화면만 사용하는 기능 Feature는 그 화면 디렉터리에 남을 수 있다.
  단, 화면 전환만 담당하는 Router·Shell 디렉터리는 화면 디렉터리가 아니라 "전환 계층"으로
  분류하며, 여러 화면 디렉터리의 타입을 참조할 수 있다. 디렉터리 간 참조 방향은 전환 계층 →
  화면 → 공용의 단방향이어야 하고, 화면 디렉터리나 공용 디렉터리가 전환 계층의 타입을 참조하는
  구성은 허용하지 않는다. 이 제약은 컴파일러가 아니라 리뷰에서 FR-020의 문서와 대조해 판정한다.
- **FR-023**: 화면 View와 그 하위 View 수정은 합성 전환에 필요한 최소 범위로 한정해야 한다.
  허용 범위는 자식 기능 Feature로의 store 스코핑, 그에 따른 자식 View 분리, 그리고 기능 상태를
  보유하던 `ViewModels/` 계열 타입의 소유권을 기능 Feature로 옮기는 것이다. 레이아웃, 표현,
  사용하는 UIComponent와 디자인 토큰은 이번 리팩토링에서 바꾸지 않는다.
- **FR-024**: 자식 기능 Feature는 그것을 합성하는 상위 Feature(화면 Feature 또는 전환 계층)가
  `body`에서 직접 생성한다. 상위 Feature는 자식이 실제로 사용하는 최소 subset 의존성만 생성자로
  받아 그대로 전달하며, 구현을 교체하거나 새로 만들지 않는다. Composition 패키지는 Feature
  Reducer를 생성하지 않고, 최상위 Feature의 의존성 주입은 App이 담당한다.
- **FR-025**: 기능 Feature와 화면 Feature를 이름으로 구분하는 일괄 접두어·접미어 규칙을
  도입하지 않아야 한다. 이름은 [네이밍 컨벤션](../../docs/conventions/naming.md)을 그대로 따르며,
  분류는 FR-020의 컨벤션 문서와 FR-022의 디렉터리 위치로 표현한다.
- **FR-026**: 기능 Feature 추출로 공유되는 것은 상태 유형과 전이 규칙의 선언뿐이어야 한다. 같은
  기능 Feature를 합성한 화면들은 각자 독립 인스턴스를 보유하며, 한 화면 인스턴스의 상태 변화가
  다른 화면 인스턴스에 반영되지 않아야 한다. 화면 간 런타임 상태 공유를 위해 `@Shared` 등 공유
  상태 수단을 도입하지 않는다.
- **FR-027**: 기능 Feature는 Reducer(상태 유형과 전이 규칙)만 소유하고 View를 소유하지 않아야
  한다. 기능 상태를 렌더링하는 View는 그 기능 Feature를 합성한 화면 디렉터리에 남아 스코핑된
  자식 store를 받아 표시한다. FR-023의 "자식 View 분리"로 생기는 View도 화면 디렉터리에 둔다.

### 핵심 엔터티

- **기능 관심사**: 하나의 목적을 가진 기능과 그것이 소유하는 상태 모델·전이 규칙. 분해의 기본
  단위이며, 화면 경계와 무관하게 정의된다.
- **기능 Feature**: 하나의 기능 관심사를 소유하는 Feature. 그 기능에 필요한 의존성만 요구하고,
  결과를 부모에게 전달한다.
- **화면 Feature**(화면 합성 Feature): 관심사가 둘 이상인 한 화면에 대응하는 합성 단위. 필요한
  기능 Feature들을 자식으로 보유하고, 화면 고유의 표시 범위·후속 동작·전환 결정을 소유한다.
  관심사가 하나뿐인 화면에는 두지 않으며, 그 화면은 기능 Feature를 직접 관찰한다.
- **전환 계층**: 화면 전환만 담당하는 Router·Shell 성격의 Feature와 그 디렉터리. 여러 화면
  Feature를 자식으로 보유할 수 있으나 기능 상태를 소유하지 않으며, 화면·공용 디렉터리가 이를
  참조하지 않는다.
- **중복 관심사 식별 결과**: 기준을 전체 Reducer에 적용해 얻은, 중복된 기능 관심사와 그 선언
  위치, 그리고 통합·제외 판단의 목록.

*기준을 설명하기 위한 예시*(범위 정의가 아니며, 실제 대상은 FR-015의 식별 결과로 확정한다):
프로필 조회 상태가 `HomeFeature`·`ProfileFeature`·`SettingsFeature`에 각각 선언된 경우,
프로젝트 요약 목록 적재 상태가 `HomeFeature`와 `ProjectListFeature`에 나뉘어 선언된 경우,
로그인·약관 동의 흐름이 여러 진입 지점에 나뉘어 구현된 경우, 직군·연차 선택이 온보딩과 설정에
서로 다른 상태 모델로 존재하는 경우.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: FR-015로 식별된 중복 기능 관심사 각각에 대해, 상태 유형과 전이 규칙을 선언한
  Feature가 저장소에 정확히 하나씩 존재하거나, 통합하지 않은 경우 제외 사유가 기록되어 있다.
- **SC-002**: 최종 사용자에게 관찰되는 화면 동작·화면 전환 결과의 불변은 단위 테스트로 판정한다.
  리팩토링 후 Feature 패키지의 전체 테스트가 통과하고, 이관 전 화면 테스트의 모든 단언이 SC-011에
  따라 기능 Feature 테스트나 합성 지점 검증에 대응되어 있으면 불변으로 본다. Simulator 수동 확인과
  UI 자동화 테스트 추가는 판정 수단으로 요구하지 않는다. 정본 동작 선택으로 의도한 차이는 FR-008에
  따라 기록된 항목에 한정된다.
- **SC-003**: 통합된 각 기능 관심사에 대해, 그 기능의 동작을 바꾸려 할 때 수정해야 하는 Feature
  선언 지점이 단 한 곳이다.
- **SC-004**: 통합된 기능 Feature 각각이 화면 Feature를 거치지 않고 자신의 상태 전이를 검증하는
  테스트를 가진다.
- **SC-005**: 리팩토링 이후에도 프로젝트의 전체 공유 scheme 빌드, build-for-testing,
  test-without-building이 모두 성공한다.
- **SC-006**: 어떤 기능 Feature도 자신을 합성한 화면의 식별자에 따라 동작을 분기하지 않는다.
- **SC-007**: Feature 패키지의 모든 Reducer가 기능 Feature, 화면 합성 Feature, 전환 계층 중
  하나로 분류되며, 어느 쪽으로도 분류되지 않는 Reducer가 없다.
  분류 판정은 이름이 아니라 FR-020의 문서와 FR-022의 디렉터리 위치로 수행한다.
- **SC-008**: 화면 Feature 중 기능 관심사의 상태 유형을 직접 선언하는 것이 없다.
- **SC-009**: 분해 기준이 `docs/conventions/tca/feature.md`에, 최종 분류 결과와 제외 사유가
  `docs/conventions/tca/feature/`의 하위 문서에 존재하고 서로 링크되며, 그 문서만 읽고 임의의
  Feature가 기준을 따르는지 판정할 수 있다.
- **SC-010**: 화면 디렉터리 사이에 직접 타입 참조가 존재하지 않고, 화면·공용 디렉터리에서 전환
  계층(Router·Shell) 디렉터리로의 타입 참조가 존재하지 않으며, 둘 이상의 화면이 쓰는 기능
  Feature는 모두 공용 디렉터리에 위치한다.
- **SC-011**: 화면 Feature의 테스트 중 자식 기능 Feature의 내부 상태 전이를 직접 단언하는 것이
  없으며, 이관 전 화면 테스트가 검증하던 단언은 모두 기능 Feature 테스트나 합성 지점 검증 중
  한 곳에 남아 있다.
- **SC-012**: View 변경은 store 스코핑·자식 View 분리·`ViewModels/` 소유권 이동에 한정되며,
  레이아웃 값·사용 컴포넌트·디자인 토큰의 변경이 없다.
- **SC-015**: 공용 디렉터리에 View 타입이 존재하지 않으며, 기능 상태를 렌더링하는 모든 View는
  화면 디렉터리에 위치한다.
- **SC-013**: 상위 Feature가 자식 기능 Feature에 전달하는 의존성은 자식 생성자가 요구하는 것과
  정확히 같은 subset이며, 상위가 자식을 위해 받은 의존성 중 자식에 전달되지 않거나 구현이
  교체되는 것이 없다. Composition 패키지에는 Feature Reducer 생성 코드가 없다.
- **SC-014**: 추출된 기능 Feature 중 화면 간 런타임 상태 공유 수단(`@Shared` 등)을 사용하는 것이
  없으며, 같은 기능 Feature를 합성한 두 화면 중 한쪽의 상태 전이가 다른 쪽 상태를 바꾸지 않는다.

## 가정

- 이 리팩토링은 개발자와 이후 기능 작업의 유지보수 비용을 대상으로 하며, 최종 사용자에게
  새로운 기능 가치를 제공하지 않는다.
- 기존 TCA 기반 Feature 합성 방식과 프로젝트의 TCA 컨벤션을 그대로 사용하며, 새로운 상태 관리
  방식을 도입하지 않는다.
- 사용자 입력에 등장한 네 가지 항목은 기준을 설명하는 예시이며 범위 정의가 아니다. 실제 통합
  대상은 FR-015의 전수 식별 결과로 확정한다.
- 적용 범위는 Feature 패키지로 한정하며, UI 컴포넌트·디자인 토큰·Domain·Data 계층의 공개 계약은
  이번 리팩토링에서 변경하지 않는다. Feature 패키지 안의 View는 FR-023이 정한 최소 범위에서만
  수정한다.
- Composition 패키지는 변경하지 않는다. 기능 Feature의 생성과 의존성 전달은 FR-024에 따라 상위
  Feature가, 최상위 Feature로의 주입은 App이 담당하며, 생성자 주입이라는 조립 방식 자체를 바꾸는
  것은 이번 범위가 아니다. App은 다음 두 경우에만 함께 수정하며, 해당 단위는 Feature와 App을
  묶은 integration unit으로 둔다. 하나는 최상위 Feature 생성자가 바뀔 때다. 다른 하나는 App이
  직접 참조하는 Feature 상태 경로가 바뀔 때다. 예를 들어 `AppRootFeature`가 읽는
  `mainShell.home.projectLoad`와, App 테스트가 읽는 `projectDetail.loadStatus`가 있다.
- Feature 패키지의 Tuist target 구성은 이번 범위에서 바꾸지 않는다. 현재의 단일 `Feature` target을
  유지하고 경계는 디렉터리로 표현한다.
- 화면 전환만 담당하는 Router 성격의 Feature는 제거 대상이 아니며, 기능 상태 소유를 내려놓는
  것까지가 이번 범위다.
- `feature/guest-mode`에서 진행한 비로그인 관련 변경이 이 브랜치의 기준선에 포함되어 있으며,
  식별과 통합은 그 결과를 전제로 한다.
- 인증 토큰 전달 방식 교체(UseCase Request 모델이 토큰을 입력받고 Feature가 이를 중재하는 변경)는
  이 기능의 선행 조건이 아니며 범위에도 포함하지 않는다. 이 리팩토링은 현재의 토큰 전달 방식을
  그대로 둔 채 진행하고, 그 교체는 별도 시점에 독립적으로 다룬다.
- UIComponent 팩토리 제거([리뷰 문서](../../docs/review/ui-component-factory-removal-requirements.md))는
  이 기능의 범위가 아니라 **이미 완료되어 이 브랜치에 병합된 기준선**이다. 041은 전환이 끝난
  호출부를 전제로 하며, 그 기능의 내부 결정(`StyledText` 팩토리 유지 여부, `ScreenEdgeScrim`의
  가장자리 enum 정의, Typography 컨벤션 개정)은 041에서 다루지 않는다.
- 이 브랜치에 이미 반영된 UIComponent 관련 커밋(`ActionButton` 햅틱의 Feature 이전, design-rules
  위반 정리)은 041의 변경이 아니라 기준선의 일부다. FR-008의 동작 불변은 그 커밋들이 반영된
  상태를 기준으로 판정한다.
- 이 브랜치의 현재 HEAD가 041의 기준선이며, 시나리오 1~4의 모든 작업은 이 브랜치에서 진행한다.
