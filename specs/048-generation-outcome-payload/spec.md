# 기능 명세: 생성 결과 원격 알림을 서버의 실제 payload 형식으로 인식하고 로컬 결과 알림 제거

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/generation-outcome-payload`

**브랜치 상태**: `생성` (2026-09-30 갱신 시 `재사용`)

**생성일**: 2026-09-29

**상태**: 초안

**입력**: 사용자 설명: "생성 결과 원격 알림 payload를 서버 실제 형식에 맞춰 파싱한다. 실기기 관찰(2026-09-29) 결과 서버는 `status` 키를 보내지 않고 `type` 키로 결과를 보낸다: 생성 완료는 `type: "QUIZ_READY"`(알림 문구 "프로젝트 준비 완료 / 새 문제가 도착했어요"), 생성 불가는 `type: "QUIZ_REJECTED"`(알림 문구 "문제를 만들 수 없는 저장소예요 / 다른 저장소로 등록해 주세요"), 두 경우 모두 최상위에 `projectId`가 있다. 현재 `QuizGenerationOutcomeDTO`는 `status: completed|failed`만 인정해 모든 생성 결과 알림이 파싱 실패로 버려지고, 그 결과 생성 기록이 진행 중으로 남아 메인 앱(홈 잠금·목록 갱신·실패 안내)과 공유 확장(생성 중 등록 차단)이 모두 갱신되지 않는다. `QUIZ_READY`는 완료, `QUIZ_REJECTED`는 실패로 반영해 백그라운드 수신·알림 표시·알림 탭·알림 센터 복귀 경로 모두에서 기록이 갱신되어야 한다. 관찰된 원본 payload 예: [\"projectId\": \"6abbb1b4f55054fd8fbb4ca3\", \"type\": \"QUIZ_READY\", \"aps\": {alert...}, \"gcm.message_id\": ..., \"google.c.*\": ...], [\"projectId\": \"6abbacabf55054fd8fbb479d\", \"type\": \"QUIZ_REJECTED\", ...]. 046 명세의 서버 payload 가정(`status: completed/failed`)과 실기기 검증 기록(device-verification.md \"서버 payload\" 관찰 대기)을 이 관찰로 바로잡는다."

**갱신 입력**(2026-09-30): "2026-09-30 결정을 반영해 범위를 넓힌다. (1) FR-010을 개정: 로컬 결과 알림은 결과 입력이 원격 알림뿐이라 예약만 막으면 도달 불가 코드가 되므로 048에서 기능 전체를 제거한다 — 생성 요청 시 결과 대기 등록, 공유 저장소의 결과 대기 대기열, 결과 반영 시 예약·취소, 알림 유효 시간(300초), 로컬 알림 예약·취소 능력, 로컬 알림 문구. 공유 저장소에 이미 남아 있는 결과 대기 대기열 값의 처리도 정한다. (2) 유지: 원격 알림 수신·기기 등록, 설정 화면의 알림 권한 조회·요청, 원격 결과 반영. (3) '홈에서 기다리기'의 알림 권한 시트는 유지하되 목적을 서버 결과 알림 권한 요청으로 바꾼다: 권한이 없을 때만 시트를 띄워 권한을 요청하고, 선택값 전달은 제거한다. 시트 문구는 유지한다. (4) 알림 권한 조회·요청 계약은 남기되 'Reminder' 이름을 권한 책임 이름으로 바꾼다. 네이밍 컨벤션 8에 따라 동작 변경과 분리된 커밋으로 진행한다. (5) 로컬 결과 알림을 기술한 이전 명세(020·021·023 등)는 역사 기록으로 두고, 이 명세가 대체함을 기록한다."

## 배경

앱은 서버가 보내는 생성 결과 원격 알림으로 학습 세트 생성의 완료·실패를 판정한다(019 이후, 046
FR-002·FR-015·FR-023). 판정 결과는 공유 저장소의 생성 기록에 반영되고, 메인 앱의 홈 잠금·목록 갱신·
생성 진행 화면과 공유 확장의 생성 중 등록 차단(047)이 모두 이 기록을 읽는다.

지금까지 앱은 알림 payload가 최상위 `projectId`와 `status`(`completed` 또는 `failed`)를 담는다고
가정했다(021 외부 계약 고정, 046 가정). 이 가정은 실기기에서 한 번도 확인되지 않았다(046
device-verification.md "서버 payload" 관찰 대기).

2026-09-29 실기기(iPhone 12 mini) 관찰에서 서버 payload는 다음과 같았다. 알림 문구는 `aps.alert`에
있고, 나머지 `gcm.*`·`google.c.*` 키는 전달 계층 메타데이터다.

| 결과 | `projectId` | `type` | `status` | 사용자에게 보인 알림 문구 |
|---|---|---|---|---|
| 생성 완료 | `6abbb1b4f55054fd8fbb4ca3` | `QUIZ_READY` | 없음 | 프로젝트 준비 완료 / 새 문제가 도착했어요 |
| 생성 불가 | `6abbacabf55054fd8fbb479d`, `6abbaf3ef55054fd8fbb4a78` | `QUIZ_REJECTED` | 없음 | 문제를 만들 수 없는 저장소예요 / 다른 저장소로 등록해 주세요 |

세 알림 모두 앱의 진단 로그에 "생성 결과 payload 파싱 실패"로 남았다. 따라서 현재 앱은 서버의 생성
결과를 **하나도** 기록에 반영하지 못한다. 생성 기록은 대기 보관 기한이 지날 때까지 진행 중으로 남고,
그동안 다음이 모두 갱신되지 않는다.

- 메인 앱: 홈 불러오기 잠금이 풀리지 않고, 생성 진행 화면이 결과로 넘어가지 않으며, 결과 도착에 따른
  목록 자동 갱신(046 FR-002)이 일어나지 않는다.
- 공유 확장: 생성 중 등록 차단(047)이 풀리지 않는다.

### 로컬 결과 알림(2026-09-30 추가)

앱은 생성 요청마다 결과 대기 대상을 등록하고, 결과가 기록에 반영된 뒤 300초 안이고 알림 권한이 있으면
로컬 알림("준비 완료" 또는 "생성 실패")을 예약한다(020·021·023). 결과가 기록에 반영되는 입력은 원격
알림뿐이므로, 이 기능이 동작하면 서버 알림과 같은 결과의 로컬 알림이 한 번 더 보인다. 원격 알림으로 반영한
결과의 예약만 막으면 예약 경로에 도달하는 입력이 없어져 로컬 결과 알림 전체가 도달 불가 코드가 된다.

"홈에서 기다리기"의 알림 권한 시트는 알림 권한이 없을 때 권한을 요청한다. 사용자가 고른 값은 앱 루트까지
전달되지만 어디에도 쓰이지 않는다. 설정 화면 밖에서 알림 권한을 요청하는 유일한 흐름이므로, 서버 결과
알림을 사용자에게 보여 주려면 이 요청은 필요하다.

알림 권한 조회·요청은 로컬 결과 알림과 같은 계약(`LocalReminderNotifier` 등 이름에 "Reminder"가
들어간 계약)을 거쳐 설정 화면에서도 쓰인다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 생성 불가 알림으로 진행 중 상태 해제 (우선순위: P1)

사용자가 문제를 만들 수 없는 저장소를 등록하면 서버가 생성 불가 알림을 보낸다. 앱은 이 알림을 그 프로젝트의
생성 실패로 기록해, 사용자가 곧바로 다른 저장소를 등록할 수 있게 한다.

**주요 행위자**: 회원 사용자

**우선순위 이유**: 실패가 반영되지 않으면 사용자는 대기 보관 기한이 지날 때까지 앱과 공유 확장 어디서도
새 저장소를 등록할 수 없다. 서버가 "다른 저장소로 등록해 주세요"라고 안내하는데 앱이 그 행동을 막는
모순이 생긴다.

**독립 테스트**: 진행 중 기록이 있는 상태에서 `type: QUIZ_REJECTED` payload를 각 수신 경로로 주입하고,
기록이 실패로 바뀌며 홈 잠금과 공유 확장 차단이 풀리는지 확인한다.

**수용 시나리오**:

1. **전제** 프로젝트 P의 생성이 진행 중이다, **실행** 앱이 포그라운드에서 P의 `QUIZ_REJECTED` 알림을
   받는다, **결과** P의 생성 기록이 실패가 되고 홈의 "문제 생성 중" 잠금이 풀린다.
2. **전제** 사용자가 P의 생성 진행 화면에서 기다리고 있다, **실행** P의 `QUIZ_REJECTED` 알림이
   도착한다, **결과** 진행 화면이 생성 실패 상태로 바뀐다.
3. **전제** P의 생성이 진행 중이고 앱은 백그라운드다, **실행** P의 `QUIZ_REJECTED` 알림이 도착한 뒤
   사용자가 공유 확장에서 다른 저장소를 공유한다, **결과** 공유 확장이 생성 중 안내로 막지 않고 등록을
   진행한다.

### 시나리오 2 - 생성 완료 알림으로 결과 반영 (우선순위: P1)

서버가 생성 완료 알림을 보내면 앱은 그 프로젝트의 생성 완료로 기록하고, 사용자가 새 프로젝트로 학습을
시작할 수 있게 한다.

**주요 행위자**: 회원 사용자

**우선순위 이유**: 완료도 지금은 반영되지 않아 생성 진행 화면이 끝나지 않고 홈 잠금과 공유 확장 차단이
유지된다. 핵심 등록 흐름이 끝나지 않는 결함이다.

**독립 테스트**: 진행 중 기록이 있는 상태에서 `type: QUIZ_READY` payload를 주입하고, 기록이 완료로
바뀌며 진행 화면·홈 잠금·목록 갱신이 결과를 따르는지 확인한다.

**수용 시나리오**:

1. **전제** P의 생성 진행 화면에서 기다리고 있다, **실행** P의 `QUIZ_READY` 알림이 도착한다,
   **결과** 진행 화면이 완료 흐름으로 넘어간다.
2. **전제** 회원 사용자가 메인 화면에 있고 앱이 포그라운드다, **실행** P의 `QUIZ_READY` 알림이
   도착한다, **결과** 홈 잠금이 풀리고 프로젝트 목록을 다시 받아온다.

---

### 시나리오 3 - 모든 수신 경로에서 같은 해석 (우선순위: P2)

생성 결과는 백그라운드 수신, 알림 표시, 알림 탭(종료 상태 실행 포함), 앱 활성화 시 알림 센터 읽기 네
경로로 들어온다. 네 경로 모두 같은 payload 해석을 써서 같은 결과를 기록한다.

**주요 행위자**: 회원 사용자, 연동 시스템(서버 원격 알림)

**우선순위 이유**: 한 경로만 고치면 알림을 누르지 않고 앱 아이콘으로 돌아온 경우(046 FR-023) 같은
복구 경로가 여전히 결과를 놓친다.

**독립 테스트**: 같은 `QUIZ_READY`·`QUIZ_REJECTED` payload를 네 경로 각각으로 넣어 기록 결과가 같은지
확인한다.

**수용 시나리오**:

1. **전제** P의 생성이 진행 중이고 P의 `QUIZ_REJECTED` 알림이 알림 센터에 남아 있다, **실행** 사용자가
   알림을 누르지 않고 앱 아이콘으로 앱을 연다, **결과** P의 기록이 실패가 된다.
2. **전제** 앱이 종료되어 있다, **실행** 사용자가 P의 `QUIZ_READY` 알림을 눌러 앱을 연다, **결과**
   P의 기록이 완료가 된다.

### 시나리오 4 - 서버 알림 계약 기록 정정 (우선순위: P3)

개발자는 서버 알림 payload의 실제 형식을 문서에서 확인할 수 있어야 한다. 잘못된 가정이 남아 있으면 이후
명세가 같은 가정을 다시 따른다.

**주요 행위자**: 개발자

**우선순위 이유**: 동작 결함은 시나리오 1~3이 해결하고, 이 시나리오는 재발 방지를 위한 기록이다.

**독립 테스트**: 046 명세의 payload 가정과 실기기 검증 기록의 "서버 payload" 표가 이 명세의 관찰과
일치하는지 검토한다.

**수용 시나리오**:

1. **전제** 046 명세가 `status: completed/failed`를 가정한다, **실행** 이 기능을 완료한다, **결과**
   046 문서의 해당 가정이 관찰된 `type` 형식으로 정정되거나 이 명세로 대체되었음이 표시된다.
2. **전제** 046 device-verification.md의 "서버 payload" 표가 관찰 대기다, **실행** 이 기능을
   완료한다, **결과** 2026-09-29 관찰 결과(키·값 형식)가 기록된다.

### 시나리오 5 - 같은 결과에 알림은 한 번만 (우선순위: P2)

생성 결과가 나오면 사용자는 서버 알림 하나만 본다. 앱은 같은 결과로 로컬 알림을 더 보내지 않는다.

**주요 행위자**: 회원 사용자

**우선순위 이유**: 시나리오 1·2가 결과를 반영하기 시작하면 로컬 결과 알림이 실제로 예약되어 같은 결과의
알림이 두 번 보인다. 파싱 수정과 함께 들어가야 중복이 사용자에게 노출되지 않는다.

**독립 테스트**: 알림 권한이 있는 상태에서 생성 요청 뒤 결과 원격 알림을 주입하고, 로컬 알림 예약이
없는지 확인한다.

**수용 시나리오**:

1. **전제** 알림 권한이 있고 P의 생성이 진행 중이다, **실행** P의 `QUIZ_READY` 알림이 도착한다,
   **결과** 기록은 완료가 되고 앱은 로컬 알림을 예약하지 않는다.
2. **전제** 알림 권한이 있고 공유 확장에서 P의 생성을 요청했다, **실행** P의 `QUIZ_REJECTED` 알림이
   도착한다, **결과** 앱은 로컬 알림을 예약하지 않는다.

---

### 시나리오 6 - "홈에서 기다리기"는 서버 알림 권한을 요청 (우선순위: P2)

생성 진행 화면에서 "홈에서 기다리기"를 누른 사용자는, 알림 권한이 없으면 결과 알림을 받을지 묻는 시트를
보고 권한을 줄 수 있다. 권한이 있으면 바로 홈으로 간다.

**주요 행위자**: 회원 사용자

**우선순위 이유**: 권한이 없으면 서버 결과 알림이 보이지 않는다. 설정 화면 밖에서 권한을 얻는 유일한
흐름이므로, 로컬 알림 제거와 함께 이 흐름이 서버 알림을 위한 것으로 남아야 한다.

**독립 테스트**: 권한 상태별로 "홈에서 기다리기"를 눌러 시트 표시, 권한 요청, 홈 이동을 확인한다.

**수용 시나리오**:

1. **전제** 알림 권한이 있다, **실행** "홈에서 기다리기"를 누른다, **결과** 시트 없이 홈으로 간다.
2. **전제** 알림 권한이 정해지지 않았다, **실행** "홈에서 기다리기"를 누르고 시트에서 설정을 고른다,
   **결과** 시스템 알림 권한 요청이 뜨고 홈으로 간다. 요청 결과가 허용이 아니면 시스템 설정의 앱 알림
   화면을 연다.
3. **전제** 알림 권한을 거절한 적이 있다, **실행** 시트에서 설정을 고른다, **결과** 권한 요청 결과가
   허용이 아니므로 시스템 설정의 앱 알림 화면을 열고 홈으로 간다.
4. **전제** 알림 권한이 없다, **실행** 시트에서 "다시 보지 않기"를 고른다, **결과** 권한 요청 없이
   홈으로 간다.

---

### 시나리오 7 - 로컬 결과 알림 코드와 알림 권한 계약 정리 (우선순위: P3)

개발자는 도달하지 않는 로컬 결과 알림 코드 없이 생성 결과 흐름을 읽을 수 있고, 알림 권한 계약은 실제
책임(권한 조회·요청)을 이름으로 드러낸다.

**주요 행위자**: 개발자

**우선순위 이유**: 동작 결함은 시나리오 1~6이 해결하고, 이 시나리오는 유지보수 비용을 줄이는 정리다.

**독립 테스트**: 결과 대기 등록·대기열·예약·취소·유효 시간·로컬 알림 문구가 코드와 테스트에서 사라졌는지,
설정 화면의 알림 권한 조회·요청 테스트가 변경 전후 모두 통과하는지 확인한다.

**수용 시나리오**:

1. **전제** 이 기능을 완료했다, **실행** 로컬 결과 알림 관련 식별자를 검색한다, **결과** 운영 코드와
   테스트에 남아 있지 않다.
2. **전제** 이 기능을 완료했다, **실행** 설정 화면의 알림 권한 표시와 권한 요청을 사용한다, **결과**
   변경 전과 같이 동작한다.

### 예외·경계 사례

- `type`이 `QUIZ_READY`·`QUIZ_REJECTED`가 아닌 값(향후 추가 값, 오타, 대소문자 차이)이면 생성 기록을
  바꾸지 않고 목록 갱신 계기로도 쓰지 않는다(046 FR-015와 같은 방침).
- `projectId`가 없거나 빈 문자열이면 결과로 인정하지 않는다.
- `type`·`projectId` 외에 `aps`, `gcm.message_id`, `google.c.*` 같은 전달 계층 키가 함께 오거나 빠져도
  해석 결과는 같다.
- 결과 알림의 프로젝트가 생성 기록에 없으면(이미 정리됨, 다른 계정, 재설치 후) 기록을 바꾸지 않는다.
  포그라운드 중이면 목록 갱신 계기로는 쓴다(046 FR-002·FR-015 유지).
- 같은 프로젝트의 같은 결과가 여러 경로(표시 후 탭, 알림 센터 읽기)로 중복 도착해도 기록과 목록 갱신은
  한 번만 일어난다(기존 중복 도착 처리 유지).
- 기존 `status: completed|failed` 형식의 payload가 도착하면 지금과 같이 해석한다. 두 키가 모두 있으면
  `type`을 우선한다.
- 이전 버전이 공유 저장소에 남긴 결과 대기 대기열 값은 읽지도 예약에 쓰지도 않는다(FR-014).
- 이전 버전이 이미 예약해 두었으나 아직 표시되지 않은 로컬 결과 알림은 없다고 본다. 이전 버전은 결과
  반영 즉시(지연 없이) 예약했고, 결과 반영은 파싱 실패로 일어나지 않았기 때문이다.
- 알림 권한이 없는 사용자가 "다시 보지 않기"를 골라도 다음 생성 때 권한이 여전히 없으면 시트를 다시
  보여 준다(현재 동작 유지. 선택값을 저장하지 않는다).

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 원격 알림 payload의 최상위 `type`이 `QUIZ_READY`이고 최상위 `projectId`가
  비어 있지 않으면, 그 프로젝트의 생성 완료 결과로 인식해야 한다.
- **FR-002**: 시스템은 원격 알림 payload의 최상위 `type`이 `QUIZ_REJECTED`이고 최상위 `projectId`가
  비어 있지 않으면, 그 프로젝트의 생성 실패 결과로 인식해야 한다.
- **FR-003**: 시스템은 FR-001·FR-002의 인식 규칙을 백그라운드 수신, 알림 표시, 알림 탭(종료 상태 실행
  포함), 앱 활성화 시 알림 센터 읽기의 네 경로에 똑같이 적용해야 한다.
- **FR-004**: 시스템은 기존 `status: completed|failed` 형식도 계속 결과로 인식해야 하며, `type`과
  `status`가 함께 있으면 `type`의 해석을 따라야 한다.
- **FR-005**: 시스템은 `type`이 FR-001·FR-002의 값이 아니고 인식 가능한 `status`도 없으면 그 알림을
  생성 결과로 인식하지 않아야 하며, 생성 기록과 목록 갱신 계기에 쓰지 않아야 한다.
- **FR-006**: 시스템은 인식한 생성 결과를 기존 결과 반영 규칙(생성 기록 갱신, 중복 도착 제거, 기록에 없는
  프로젝트 처리, 포그라운드 목록 갱신)에 그대로 전달해야 하며, 이 규칙 자체는 바꾸지 않아야 한다.
- **FR-007**: 시스템은 결과로 인식하지 못한 payload를 진단 로그로 남겨, 개발자가 실기기에서 원인을
  확인할 수 있어야 한다.
- **FR-008**: 개발자는 046 명세의 서버 payload 가정과 046 실기기 검증 기록의 "서버 payload" 표를 이
  명세의 2026-09-29 관찰로 정정해야 한다.
- **FR-009**: 이 변경은 서버의 알림 payload와 API를 바꾸지 않아야 하며, 생성 상태를 주기적으로 조회하는
  폴링을 추가하지 않아야 한다(046 FR-020 유지).
- **FR-010** *(2026-09-30 개정)*: 시스템은 생성 결과에 대해 로컬 결과 알림을 예약하지 않아야 한다.
  로컬 결과 알림 기능 전체를 제거한다. 제거 대상은 생성 요청 시 결과 대기 등록, 공유 저장소의 결과 대기
  대기열, 결과 반영 시 로컬 알림 예약과 기록 정리 시 예약 취소, 결과 알림 유효 시간(300초), 로컬 알림
  예약·취소 능력, 로컬 결과 알림 문구다.
- **FR-011**: 시스템은 원격 알림 수신, 기기 등록, 원격 결과 반영, 설정 화면의 알림 권한 조회·요청·시스템
  설정 열기를 변경 전과 같이 유지해야 한다.
- **FR-012**: "홈에서 기다리기"는 알림 권한이 있으면 곧바로 홈으로 가야 하고, 권한이 없으면 알림 권한
  시트를 보여 줘야 한다. 시트에서 설정을 고르면 권한을 요청하고, 요청 결과가 허용이 아니면 시스템 설정을
  열며, 홈으로 가야 한다(현재 동작 유지). "다시 보지 않기"를 고르면 권한 요청 없이 홈으로 가야 한다. 시트의 문구는 바꾸지 않는다.
- **FR-013**: 시스템은 시트에서 사용자가 고른 값을 생성 진행 화면 밖으로 전달하지 않아야 한다(현재 앱
  루트에서 버려지는 전달 경로 제거).
- **FR-014**: 시스템은 이전 버전이 공유 저장소에 남긴 결과 대기 대기열 값을 읽지 않아야 하며, 그 값이
  남아 있어도 생성 기록·목록·알림 동작이 바뀌지 않아야 한다.
- **FR-015**: 개발자는 설정 화면이 계속 쓰는 알림 권한 조회·요청 계약의 이름을 권한 책임을 드러내는
  이름으로 바꿔야 하며, 이 이름 변경은 동작 변경과 분리된 커밋이어야 한다(네이밍 컨벤션 8).
- **FR-016**: 개발자는 로컬 결과 알림을 정의한 이전 명세(020·021·023과 그 계약 문서)가 이 명세로
  대체되었음을 기록해야 한다. 이전 명세 본문은 역사 기록으로 두고 고쳐 쓰지 않는다.

### 핵심 엔터티

- **생성 결과 원격 알림**: 서버가 한 프로젝트의 생성 결과를 알리는 원격 알림이다. 최상위 `projectId`와
  결과 종류(`type`: `QUIZ_READY` 완료, `QUIZ_REJECTED` 실패)를 담고, 사용자에게 보이는 문구는 별도로
  담는다.
- **생성 결과**: 알림에서 해석한 프로젝트 식별자, 완료·실패 구분, 도착 시각이다. 생성 기록 반영과 목록
  갱신 계기의 입력이다.
- **결과 대기 대기열** *(제거 대상)*: 생성 요청마다 공유 저장소에 쌓던 로컬 결과 알림 대상 프로젝트
  목록이다. 이 기능 이후에는 쓰지 않는다.
- **알림 권한 상태**: 설정 화면과 "홈에서 기다리기"가 읽는 시스템 알림 허용 여부(미결정·허용·거절)다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 2026-09-29에 관찰한 세 payload(`QUIZ_READY` 1건, `QUIZ_REJECTED` 2건)가 네 수신 경로
  모두에서 100% 올바른 결과(완료 1, 실패 2)로 인식된다.
- **SC-002**: 진행 중 기록이 있는 상태에서 생성 결과 알림이 도착하면, 대기 보관 기한을 기다리지 않고 알림
  반영 즉시 홈 잠금과 공유 확장의 생성 중 차단이 풀린다.
- **SC-003**: 인식하지 못하는 `type` 값과 `projectId`가 없는 payload는 생성 기록을 0건 바꾼다.
- **SC-004**: 기존 생성 결과 반영·중복 제거·목록 갱신 관련 자동 테스트가 변경 전후 모두 통과한다.
- **SC-005**: 실기기에서 서버의 실제 `QUIZ_READY`·`QUIZ_REJECTED` 알림을 받았을 때 진단 로그에 "파싱
  실패"가 남지 않고, 생성 진행 화면·홈 잠금·공유 확장 차단이 결과를 따른다.
- **SC-006**: 046 문서에 `status: completed/failed`를 서버 형식으로 단정하는 가정이 정정 없이 남아
  있지 않다.
- **SC-007** *(2026-09-30 개정)*: 알림 권한이 있는 상태에서 생성 결과 원격 알림이 도착해도 로컬 알림
  예약이 0건이다.
- **SC-008**: "홈에서 기다리기"의 권한 상태 4가지(허용, 미결정 후 설정, 거절 후 설정, 다시 보지 않기)
  모두에서 홈으로 이동하고, 권한 요청·시스템 설정 열기는 수용 시나리오와 100% 일치한다.
- **SC-009**: 설정 화면의 알림 권한 관련 자동 테스트가 변경 전후 모두 통과한다.
- **SC-010**: 운영 코드와 테스트에서 로컬 결과 알림 전용 타입·저장 키·문구 참조가 0건이다.

## 가정

- 서버는 생성 결과를 위 두 `type` 값으로만 보낸다고 본다. 서버의 생성 상태에는 `FAILED` 등 다른 값도
  있으나(006·007), 원격 알림에서 관찰되지 않은 값은 인식하지 않는다(FR-005). 새 값이 확인되면 별도
  변경으로 추가한다.
- `QUIZ_REJECTED`는 앱의 기존 "생성 실패"와 같은 결과로 다룬다. 거절과 일시적 실패를 구분하는 안내는
  이 기능의 범위가 아니다.
- 값 비교는 관찰된 표기(대문자, 밑줄)와 정확히 일치할 때만 인정한다.
- 기존 `status` 형식 인식을 유지하는 것은 서버 전환 기간이나 테스트용 payload와의 호환을 위한 것이며,
  서버가 그 형식을 보낸다는 근거는 없다.
- 생성 결과는 원격 알림으로만 들어오므로, 로컬 결과 알림을 제거해도 사용자가 결과를 알 수 있는 수단은
  서버 알림으로 유지된다. 원격 알림이 아닌 결과 경로가 생기면 그때 알림 방식을 다시 정한다.
  *(2026-10-01 갱신: 서버 프로젝트 목록 확인으로도 완료가 들어온다. 목록 경로에는 추가 알림을 두지
  않는다. [049 명세](../049-generation-list-completion/spec.md) FR-007 참조)*
- 공유 저장소에 남은 결과 대기 대기열 값은 최대 32개 항목의 작은 값이므로 지우는 이전 작업 없이 무시한다.
- 알림 권한 시트의 문구("세트 생성이 완료되면 리마인드 알림을 보내드려요.")는 서버 알림에도 맞는다고
  본다.
- 알림 권한이 꺼져 있으면 표시·탭 경로가 없으므로, 백그라운드 수신이 가능한 알림일 때만 수신이
  감지된다(046 가정 유지). `content-available` 포함 여부는 이번 관찰로 확인하지 못했다.
