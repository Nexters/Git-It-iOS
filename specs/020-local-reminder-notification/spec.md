# 기능 명세: 생성 완료 리마인드 알림의 실제 권한 요청과 로컬 알림 발송

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/local-reminder-notification`

**브랜치 상태**: `생성`

**생성일**: 2026-08-31

**상태**: 초안

**입력**: 사용자 설명: "생성 완료 리마인드 알림의 실제 권한 요청과 로컬 알림 예약 기능. 019-project-registration-flow는 알림 옵션 시트(수락/거절)의 UI와 intent 출력까지만 다루고, 실제 UNUserNotificationCenter 권한 요청·로컬 알림 예약·발송은 명시적으로 범위에서 제외해 후속 기능으로 남겨두었다(FR-014, FR-015, SC-009, "제외" 섹션 참고). 이번 기능은 그 후속 기능이다. 사용자가 프로젝트 등록 흐름의 생성 진행 화면에서 "홈에서 기다리기"를 누르고 알림 옵션 시트에서 "리마인드 알림 설정하기"(수락)를 선택하면, 앱이 실제로 iOS 알림 권한을 요청해야 한다. 권한이 아직 결정되지 않았다면 시스템 권한 요청 다이얼로그가 뜨고, 이미 거부한 상태라면 시스템 설정 앱의 알림 화면으로 안내한다. 권한이 허용되면, 서버가 FCM(content-available silent push)으로 보내는 학습 세트 생성 완료 신호를 수신했을 때 사용자에게 보이는 로컬 알림을 발송해야 한다. 알림 옵션을 거절했거나 권한을 거부한 경우에는 로컬 알림을 발송하지 않는다. 019가 이미 구현한 FCM 수신·완료 판정 로직은 변경하지 않고 재사용한다."

## 명확화 세션

### 세션 2026-08-31

- 질문: 사용자가 알림 수락과 권한 허용 이후 생성 진행 화면을 떠나 `홈에서 기다리기`로 Home에 복귀했는데, 그 뒤에 FCM 생성 완료 신호가 도착하면 로컬 리마인드 알림을 보내야 하는가? → 답변: 보내야 한다. 019가 이미 "진행 화면과 Home 모두 FCM 완료·실패 신호를 수신해 상태를 갱신"하도록 구현해 두었으므로, 리마인드 알림도 같은 두 지점(진행 화면에 머무는 경우와 Home으로 복귀한 이후) 모두에서 동작해야 일관적이다. 이를 위해 알림 옵션 수락 intent는 진행 화면의 일시적 상태가 아니라 해당 `projectID`에 연결된 형태로 앱 프로세스가 살아있는 동안 유지되어야 한다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 알림 옵션을 수락하면 실제 iOS 알림 권한을 요청한다 (우선순위: P1)

생성 완료를 기다리는 사용자가 알림 옵션 시트에서 리마인드 수락을 선택하면, 앱은 더 이상 시스템 설정 화면으로만 안내하지 않고 실제 알림 권한을 요청한다.

**주요 행위자**: 생성 완료까지 대기하며 리마인드를 원하는 사용자

**우선순위 이유**: 이 기능 전체의 진입점이며, 이 동작이 없으면 이후 실제 리마인드 알림 발송 자체가 불가능하다.

**독립 테스트**: 시스템 알림 권한이 `notDetermined`인 기기에서 알림 옵션을 수락하면 iOS 권한 요청 다이얼로그가 정확히 한 번 뜨는지 확인하는 것만으로 전체 가치를 검증할 수 있다.

**수용 시나리오**:

1. **전제** 시스템 알림 권한 상태가 `notDetermined`이다, **실행** 사용자가 알림 옵션 시트에서 수락을 선택한다, **결과** 시스템은 `UNUserNotificationCenter`를 통해 알림 권한 요청 다이얼로그를 표시하고, 사용자의 응답과 무관하게 이어서 기존 `홈에서 기다리기` 동작(등록 흐름 종료, Home 복귀)이 진행된다.
2. **전제** 시스템 알림 권한 상태가 이미 `denied`(과거에 거부함)다, **실행** 사용자가 알림 옵션 시트에서 수락을 선택한다, **결과** 시스템은 권한 요청 다이얼로그 대신 기존 `openNotificationSettings` 동작을 재사용해 시스템 설정 앱의 알림 화면으로 안내한다.
3. **전제** 시스템 알림 권한 상태가 이미 `authorized`(과거에 허용함)다, **실행** 사용자가 알림 옵션 시트에서 수락을 선택한다, **결과** 시스템은 추가 다이얼로그나 설정 화면 이동 없이 곧바로 해당 프로젝트를 리마인드 대상으로 등록한다.
4. **전제** 알림 옵션 시트가 표시되어 있다, **실행** 사용자가 거절을 선택하거나 시트를 닫는다, **결과** 시스템은 알림 권한을 요청하지 않으며 해당 프로젝트를 리마인드 대상으로 등록하지 않는다.

---

### 시나리오 2 - 권한이 허용된 사용자는 생성 완료 시 실제 로컬 알림을 받는다 (우선순위: P1)

알림 옵션을 수락하고 시스템 알림 권한을 허용한 사용자는, 서버가 보내는 생성 완료 신호를 계기로 사용자에게 보이는 로컬 알림을 실제로 받는다.

**주요 행위자**: 리마인드를 수락하고 권한을 허용한 사용자

**우선순위 이유**: 시나리오 1이 만든 권한 상태를 실제 사용자 가치(리마인드 수신)로 연결하는 핵심 경로다.

**독립 테스트**: 알림 옵션을 수락하고 권한을 허용한 프로젝트에 대해 완료 신호를 주입하면, 다른 자동화나 수동 조작 없이 로컬 알림이 정확히 1회 발송되는지 확인해 가치를 검증할 수 있다.

**수용 시나리오**:

1. **전제** 사용자가 특정 프로젝트에 대해 알림 옵션을 수락했고 시스템 알림 권한이 허용 상태다, **실행** 진행 화면에 머무는 동안 해당 프로젝트의 FCM 생성 완료 신호가 도착한다, **결과** 시스템은 생성 완료를 안내하는 사용자에게 보이는 로컬 알림을 정확히 1회 발송한다.
2. **전제** 사용자가 알림 옵션을 수락하고 권한을 허용한 뒤 `홈에서 기다리기`로 Home에 복귀했다, **실행** 실제 생성이 끝나 해당 프로젝트의 FCM 생성 완료 신호가 나중에 도착한다, **결과** 시스템은 진행 화면이 더 이상 존재하지 않아도 동일한 로컬 알림을 정확히 1회 발송한다.
3. **전제** 사용자가 알림 옵션을 거절했거나 시스템 알림 권한이 `denied`/제한 상태다, **실행** 해당 프로젝트의 FCM 생성 완료 신호가 도착한다, **결과** 시스템은 로컬 알림을 발송하지 않으며, 019가 이미 구현한 진행 화면·Home의 상태 갱신 자체는 정상적으로 이루어진다.
4. **전제** 여러 프로젝트를 등록했고 그중 일부만 알림 옵션을 수락했다, **실행** 각 프로젝트의 FCM 생성 완료 신호가 서로 다른 시점에 도착한다, **결과** 리마인드를 수락한 프로젝트에 대해서만 로컬 알림이 발송되며, 각 프로젝트의 알림은 서로 뒤섞이거나 중복되지 않는다.

---

### 시나리오 3 - 생성 실패 신호는 로컬 알림 대상이 아니다 (우선순위: P3)

생성이 실패한 경우에는 사용자에게 보이는 로컬 알림을 보내지 않으며, 기존 실패 처리 UI만 동작한다.

**주요 행위자**: 리마인드를 수락한 사용자

**우선순위 이유**: 실패 알림의 문구·정책이 확정되지 않았으므로 완료 알림과 동일하게 취급하지 않는 것이 안전하다.

**독립 테스트**: 리마인드를 수락한 프로젝트에 실패 신호를 주입했을 때 로컬 알림 발송이 0건인지 확인하는 것으로 검증한다.

**수용 시나리오**:

1. **전제** 사용자가 알림 옵션을 수락하고 권한을 허용했다, **실행** 해당 프로젝트의 FCM 생성 실패 신호가 도착한다, **결과** 시스템은 로컬 알림을 발송하지 않으며, 019가 이미 구현한 재시도 가능한 실패 상태 표시만 동작한다.

---

### 예외·경계 사례

- 사용자가 알림 옵션을 수락하고 권한도 허용했지만, 이후 시스템 설정에서 알림 권한을 직접 꺼버리면 어떻게 되는가? 시스템은 로컬 알림을 실제로 발송하는 시점에 현재 권한 상태를 다시 확인하고, 그 시점에 권한이 없다면 발송하지 않는다.
- `UNUserNotificationCenter.requestAuthorization` 호출 자체가 실패(에러 반환)하면 어떻게 되는가? 권한이 허용되지 않은 것과 동일하게 취급하며 리마인드 대상으로 등록하지 않는다. 별도의 오류 UI는 표시하지 않는다.
- 앱이 완전히 종료된 뒤(백그라운드 프로세스도 없음) FCM 완료 신호가 도착하면 어떻게 되는가? 이 기능은 019가 구축한 FCM 수신 인프라(앱 프로세스가 silent push를 받을 수 있는 조건)에 의존하며, 그 조건 자체를 확장하지 않는다. 앱이 신호를 수신할 수 있는 조건에서만 리마인드 판단이 이루어진다.
- 같은 프로젝트에 대해 완료 신호가 중복 도착하면 어떻게 되는가? 로컬 알림도 019의 완료 판정과 동일하게 프로젝트당 정확히 1회만 발송하고, 이미 리마인드를 발송했거나 완료 처리가 끝난 프로젝트에 대해서는 다시 발송하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 알림 옵션 시트에서 사용자가 리마인드 수락을 선택하면, 기존 `홈에서 기다리기` 동작을 이어서 수행하기 전에 현재 시스템 알림 권한 상태를 확인해야 한다.
- **FR-002**: 알림 권한 상태가 아직 결정되지 않은 경우, 시스템은 `UNUserNotificationCenter.requestAuthorization`을 호출해 사용자에게 시스템 권한 요청 다이얼로그를 표시해야 한다.
- **FR-003**: 알림 권한이 이미 거부된 경우, 시스템은 권한 요청 다이얼로그 대신 기존 `openNotificationSettings` 동작(시스템 설정 앱의 알림 화면 이동)을 재사용해야 한다.
- **FR-004**: 알림 권한이 이미 허용된 경우, 시스템은 추가 다이얼로그나 설정 화면 이동 없이 해당 프로젝트를 리마인드 대상으로 등록해야 한다.
- **FR-005**: 시스템은 알림 옵션을 거절했거나 권한 확인·요청 결과가 허용이 아닌 프로젝트를 리마인드 대상으로 등록하지 않아야 한다.
- **FR-006**: 시스템은 리마인드 대상으로 등록된 프로젝트에 대해 019가 이미 구현한 FCM(content-available silent push) 생성 완료 신호를 수신하면, 사용자에게 보이는 로컬 알림(생성 완료를 안내하는 제목·본문 포함)을 발송해야 한다.
- **FR-007**: 시스템은 리마인드 대상 등록 정보를 등록 흐름 화면(진행 화면)이 아니라 해당 `projectID`에 연결된 형태로 유지해, 사용자가 `홈에서 기다리기`로 등록 흐름을 닫고 Home으로 복귀한 뒤에 완료 신호가 도착해도 동일하게 로컬 알림을 발송해야 한다.
- **FR-008**: 시스템은 생성 실패를 의미하는 FCM 신호에 대해서는 이번 기능 범위에서 로컬 알림을 발송하지 않아야 한다.
- **FR-009**: 시스템은 로컬 알림을 실제로 발송하기 직전에 현재 알림 권한 상태를 다시 확인하고, 그 시점에 권한이 허용 상태가 아니면 발송하지 않아야 한다.
- **FR-010**: 시스템은 동일 프로젝트에 대해 로컬 알림을 정확히 1회만 발송해야 하며, 완료 판정이 이미 끝난 프로젝트에 대한 중복 신호로 추가 알림을 발송하지 않아야 한다.
- **FR-011**: production 코드는 `@Dependency`, dependency key, Service Locator 또는 전역 mutable container로 production dependency를 조회하지 않고 생성자 주입만 사용해야 한다.
- **FR-012**: 알림 권한 요청·상태 확인·로컬 알림 발송을 다루는 새 기술 API는 Domain/Data가 아니라 프로젝트 소유 Infrastructure 계층(기존 `PushMessaging` 등)에 위치해야 한다. Feature는 이 기술 API를 직접 참조하지 않고, Domain이 소유하는 UseCase·계약을 통해서만 간접적으로 사용해야 한다.
- **FR-013**: 이번 기능 구현 완료 후, 019-project-registration-flow의 spec.md가 FR-014/FR-015/SC-009에서 명시한 "실제 알림 권한 요청이나 로컬 알림 예약을 수행하지 않는다"는 제약은 더 이상 실제 동작과 일치하지 않으므로, 019 문서 자체의 갱신(별도 `speckit-clarify`/`speckit-specify` 실행)이 후속 조치로 필요하다는 점을 인지해야 한다. 이 문서 갱신 자체는 이번 기능의 산출물 범위 밖이다.

### 핵심 엔터티

- **알림 권한 상태**: `UNUserNotificationCenter`가 보고하는 사용자의 시스템 알림 권한 상태(예: 미결정/거부/허용)로, 리마인드 수락 시점과 로컬 알림 발송 직전 두 시점에서 각각 확인 대상이 된다.
- **리마인드 대상 등록**: 프로젝트 식별자(`projectID`)에 연결되어, 알림 옵션 수락과 권한 허용이 모두 충족된 프로젝트가 완료 신호 수신 시 로컬 알림 발송 대상임을 나타내는 이번 기능의 신규 상태다. 진행 화면의 생존 여부와 무관하게 유지된다.
- **생성 완료 로컬 알림**: 리마인드 대상으로 등록된 프로젝트의 FCM 생성 완료 신호를 계기로 발송되는, 사용자에게 보이는 알림이다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 알림 권한이 `notDetermined`인 상태에서 알림 옵션을 수락하는 자동화 시나리오의 100%에서 시스템 권한 요청 다이얼로그가 정확히 1회 트리거된다.
- **SC-002**: 알림 권한이 이미 `denied`인 상태에서 알림 옵션을 수락하는 자동화 시나리오의 100%에서 권한 요청 다이얼로그 없이 설정 앱 안내만 트리거된다.
- **SC-003**: 알림 옵션 수락과 권한 허용이 모두 충족된 프로젝트 표본의 100%에서, 진행 화면에 머무는 경우와 `홈에서 기다리기`로 Home 복귀한 경우 각각 완료 신호 수신 시 로컬 알림이 정확히 1회 발송된다.
- **SC-004**: 알림 옵션을 거절했거나 권한이 허용되지 않은 프로젝트 표본에서 로컬 알림 발송 발생은 0건이다.
- **SC-005**: 생성 실패 신호를 수신한 표본에서 로컬 알림 발송 발생은 0건이다.
- **SC-006**: 동일 프로젝트에 완료 신호가 중복 도착하는 자동화 시나리오에서 로컬 알림 중복 발송은 0건이다.
- **SC-007**: 이번 기능 구현 전후로 019가 검증한 FCM 완료·실패 판정 로직(진행 화면·Home 상태 갱신)의 기존 자동화 테스트는 100% 동일하게 통과한다.

## 가정

- 019가 구축한 FCM(content-available silent push) 수신·완료/실패 판정 인프라(Infrastructure/PushMessaging, `ProjectRegistrationFeature`, Home 상태 갱신)는 변경 없이 그대로 재사용 가능하다는 전제다.
- 로컬 알림은 예약된 미래 시각이 아니라 완료 신호 수신 시점에 즉시 발송하는 것으로 간주한다. 별도의 지연·예약 시각 요구가 없기 때문이다.
- 로컬 알림의 정확한 제목·본문 문구는 계획 단계에서 기존 `NotificationOptionSheet`의 안내 문구("세트 생성이 완료되면 리마인드 알림을 보내드려요")와 일관되게 확정한다.
- 리마인드 대상 등록 정보는 앱 프로세스가 메모리에 유지하는 동안만 유효하면 충분하며, 앱이 완전히 종료된 뒤 재실행되는 경우까지 영속적으로 복구해야 한다는 요구는 없다(019가 정의한 FCM 수신 조건 자체를 확장하지 않는다는 전제와 일치한다).
- 생성 실패에 대한 로컬 알림 정책(발송 여부·문구)은 이번 기능 범위 밖이며, 향후 별도 결정 사항으로 남긴다.

## 범위 경계와 의존성

### 포함

- 알림 옵션 시트 수락 시 실제 `UNUserNotificationCenter` 권한 상태 확인과 필요 시 권한 요청, 이미 거부된 경우의 설정 화면 안내
- 권한 허용과 알림 옵션 수락이 모두 충족된 프로젝트를 `projectID` 기준으로 리마인드 대상으로 등록하고, 진행 화면 생존 여부와 무관하게 유지
- 리마인드 대상 프로젝트의 FCM 생성 완료 신호 수신 시 사용자에게 보이는 로컬 알림 발송
- 로컬 알림 발송 직전 권한 재확인과 프로젝트당 중복 발송 방지

### 제외

- 019-project-registration-flow가 이미 구현한 FCM silent push 수신·완료/실패 판정 로직 자체의 변경
- 생성 실패 신호에 대한 로컬 알림 발송(문구·정책 미정)
- 배지·사운드 등 알림 부가 표시의 UI 설계
- 앱이 완전히 종료된 뒤에도 리마인드 대상 등록을 영속적으로 복구하는 저장소 설계
- 019 spec.md의 FR-014/FR-015/SC-009 문서 자체의 갱신(별도 후속 조치)

### 외부 의존성

- 019-project-registration-flow가 이미 구현한 `PushMessagingClient`, FCM 수신 파이프라인, `ProjectRegistrationFeature`의 알림 옵션 시트·delegate, Home의 FCM 상태 갱신 로직
- 기존 `openNotificationSettings` closure와 그 배선(`AppRootFeature`, `GitItApp`)
