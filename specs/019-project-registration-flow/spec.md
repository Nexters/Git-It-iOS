## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - Home에서 프로젝트 등록 흐름을 열고 레포지토리를 검증한다 (우선순위: P1)

Home의 `지금 불러오기`를 선택한 사용자는 실제 프로젝트 등록 화면으로 이동해 GitHub 레포지토리 링크를 입력하고, 시스템이 링크를 검증해 레포지토리 정보를 보여준다.

**주요 행위자**: 새 학습 프로젝트를 등록하려는 사용자

**우선순위 이유**: Home이 그동안 출력만 하던 등록 intent를 실제 화면으로 연결하는 것이 이 기능 전체의 진입점이다.

**독립 테스트**: `AppRootFeature`가 `mainShell(.delegate(.projectRegistrationRequested))`를 받았을 때 등록 흐름이 표시되는지, 그리고 `ProjectRegistrationFeature`의 `validateTapped` Action에 대해 성공·실패 결과로 상태가 전이되는지 reducer 테스트로 검증한다.

**수용 시나리오**:

1. **전제** 사용자가 Home에서 `지금 불러오기`를 선택했다, **실행** `AppRootFeature`가 `projectRegistrationRequested` intent를 받는다, **결과** 기존 `ProjectRegistrationFeature`가 소유하는 등록 화면(Figma node `986:13739`, `986:13646` 계열)이 표시되고 GitHub 레포지토리 링크 입력 필드가 비어 있는 초기 상태로 시작된다.
2. **전제** 사용자가 유효한 GitHub 레포지토리 URL을 입력했다, **실행** 검증을 요청한다, **결과** `FetchExternalRepositoryUseCase` 조회가 성공하면 Figma node `737:10890`(Task2_04)에 대응하는 레포지토리 확인 화면으로 전환되고 `ExternalRepository`의 저장소 이름·이미지·기술 스택이 표시된다.
3. **전제** 사용자가 유효하지 않거나 존재하지 않는 URL을 입력했다, **실행** 검증을 요청한다, **결과** 검증 실패 상태가 표시되고 재입력 또는 재시도로만 복구할 수 있으며 임의로 레포지토리 정보를 만들어 다음 화면으로 진행하지 않는다.
4. **전제** 검증이 진행 중이다, **실행** 사용자가 입력 필드를 다시 수정한다, **결과** 진행 중이던 검증 요청은 최신 상태를 덮어쓰지 않으며 이전 `validationRequestID`의 뒤늦은 응답은 무시된다.

### 시나리오 2 - 기술 이해도를 선택하고 학습 세트 생성을 요청한다 (우선순위: P1)

레포지토리 확인을 마친 사용자는 해당 레포지토리와 기술 스택에 대한 자신의 이해도를 선택하고, 선택을 확정해 학습 세트 생성을 시작한다.

**주요 행위자**: 레포지토리 검증을 완료한 사용자

**우선순위 이유**: `QuizLevel` 선택은 생성될 학습 세트의 난이도를 결정하는 필수 입력이며 제출 이전 마지막 사용자 결정이다.

**독립 테스트**: `quizLevelSelected` Action이 `QuizLevel`의 세 값 각각에 대해 상태를 갱신하는지, `submitTapped`가 검증된 레포지토리가 없을 때는 아무 효과도 내지 않는지 reducer 테스트로 검증한다.

**수용 시나리오**:

1. **전제** 레포지토리 검증이 성공했다, **실행** 사용자가 Figma node `737:10882`(Task2_05)의 선택 카드 목록에서 기술 이해도를 하나 선택한다, **결과** `QuizLevel.l1`~`l3` 중 선택한 값이 상태에 반영되고 선택 카드의 시각적 선택 상태가 표시된다.
2. **전제** 기술 이해도를 선택했다, **실행** 다음 단계로 진행해 Figma node `737:10830`(Task2_09)에서 생성 시작을 확정한다, **결과** `createLearningProject(githubRepoURL:quizLevel:)`가 검증된 레포지토리의 `canonicalURL`과 선택된 `QuizLevel`로 정확히 한 번 호출된다.
3. **전제** 레포지토리가 아직 검증되지 않았거나 검증이 실패했다, **실행** 사용자가 생성 제출을 시도한다, **결과** 제출은 실행되지 않고 사용자는 레포지토리 확인 단계로 돌아가야 함을 알 수 있다.
4. **전제** 제출이 이미 진행 중이다(`submission == .committing`), **실행** 사용자가 제출을 다시 시도한다, **결과** 중복 제출 요청은 발생하지 않는다.

### 시나리오 3 - 학습 세트 생성 진행 화면을 확인하고 진행 화면에 머무르거나 Home에서 기다린다 (우선순위: P1)

제출을 마친 사용자는 학습 세트가 만들어지는 동안 진행 화면을 보고, 그 화면에 머무르며 실제 생성 완료·실패를 기다리거나 `홈에서 기다리기`를 선택해 Home으로 먼저 돌아갈 수 있다. 실제 생성 완료·실패는 서버가 보내는 FCM 알림으로 판정한다.

**주요 행위자**: 학습 세트 생성을 요청한 사용자

**우선순위 이유**: 생성에는 수 분이 걸리므로 사용자가 진행 상태를 신뢰하며 대기하거나, 화면을 벗어나 다른 작업으로 전환한 뒤에도 결과를 안전하게 알 수 있어야 한다.

**독립 테스트**: 제출 성공이 도착하면 항상 진행 화면으로 전이하는지, `홈에서 기다리기` 선택 시 실제 생성 완료 여부와 무관하게 `delegate(.projectRegistered)`가 정확히 한 번 출력되는지, 진행 화면에 머무는 동안 FCM 완료·실패 페이로드 수신에 따라 완료 또는 재시도 가능한 실패 상태로 전이되는지 reducer/Effect 테스트로 검증한다.

**수용 시나리오**:

1. **전제** 생성 제출이 성공적으로 접수되었다, **실행** 사용자가 진행 화면을 확인한다, **결과** Figma node `737:10800`(로딩(완))에 대응하는 5단계 체크리스트(`프로젝트 정보 확인`, `코드 구조 분석`, `학습 개념 구성`, `문제 생성`, `세트 검증`)와 예상 소요 시간 문구가 정적으로 표시되며, 서버 진행률을 조회하는 추가 폴링 API 호출은 발생하지 않는다.
2. **전제** 진행 화면이 표시되어 있다, **실행** 사용자가 `홈에서 기다리기` CTA를 탭한다, **결과** (알림 옵션이 아직 꺼져 있으면 알림 옵션 시트를 먼저 거친 뒤) `delegate(.projectRegistered(receipt))`가 상위에 정확히 한 번 전달되고, 상위는 등록 흐름을 닫고 MainShell의 Home 탭으로 복귀한다. 이 시점에 실제 학습 세트 생성이 끝나 있음을 전제하지 않는다.
3. **전제** 사용자가 `홈에서 기다리기`를 누르지 않고 진행 화면에 머무른다, **실행** 서버가 해당 프로젝트의 생성 완료를 의미하는 FCM 알림을 보낸다, **결과** 진행 화면은 이 FCM 알림 수신을 완료 판정 근거로 삼아 완료 상태로 전이하고 `delegate(.projectRegistered(receipt))`를 정확히 한 번 전달한 뒤 등록 흐름을 닫고 Home 탭으로 복귀한다.
4. **전제** 사용자가 진행 화면에 머무른다, **실행** 서버가 해당 프로젝트의 생성 실패를 의미하는 FCM 알림을 보낸다, **결과** 재시도 가능한 단일 실패 상태가 표시되고, 사용자는 같은 입력으로 재시도하거나 이전 단계로 돌아갈 수 있다.
5. **전제** 생성이 실패해 재시도 가능한 상태다, **실행** 사용자가 재시도를 선택한다, **결과** 동일한 `githubRepoURL`과 `quizLevel`로 `createLearningProject`가 다시 정확히 한 번 호출된다.
6. **전제** 사용자가 `홈에서 기다리기`로 Home에 복귀했고 실제 생성은 아직 진행 중이다, **실행** 서버가 해당 프로젝트의 생성 완료 또는 실패를 의미하는 FCM 알림을 보낸다, **결과** Home은 이 알림을 수신해 목록에서 해당 프로젝트의 상태를 갱신하며, 별도의 상태 조회 폴링은 발생하지 않는다.

### 시나리오 4 - 생성 완료 알림 옵션을 선택한다 (우선순위: P2)

생성이 끝나기를 기다리는 사용자는 완료 시 리마인드를 받을지 선택할 수 있으며, 이 선택은 실제 알림 예약 없이 상위에 의도로만 전달된다.

**주요 행위자**: 생성 완료까지 대기하는 사용자

**우선순위 이유**: 대기 경험을 보완하는 부가 기능이며 핵심 등록·생성 흐름의 성공에는 영향을 주지 않는다.

**독립 테스트**: 알림 옵션 시트의 수락·거절 각각에 대해 실제 `UNUserNotificationCenter` 권한 요청이나 알림 예약 없이 delegate intent만 출력되는지 검증한다.

**수용 시나리오**:

1. **전제** 생성 진행 화면이 표시되어 있고 알림 옵션이 아직 꺼져 있다, **실행** 사용자가 `홈에서 기다리기` CTA를 탭한다, **결과** Figma node `824:12149`의 알림 옵션 시트가 표시되고 `세트 생성이 완료되면 리마인드 알림을 보내드려요` 문구와 수락·거절 선택지가 표시된다.
2. **전제** `홈에서 기다리기`를 눌러 알림 옵션 시트가 표시되어 있다, **실행** 사용자가 알림 수락을 선택한다, **결과** 알림 희망 intent가 상위에 정확히 한 번 전달되고 실제 알림 권한 요청이나 로컬 알림 예약 없이, 이어서 `홈에서 기다리기` 동작이 진행되어 등록 흐름이 닫히고 Home으로 복귀한다.
3. **전제** 사용자가 알림 거절을 선택하거나 시트를 닫는다, **실행** `홈에서 기다리기` 동작이 이어진다, **결과** 알림 옵션 선택과 무관하게 등록 흐름은 닫히고 Home으로 복귀하며, 진행 중이던 생성의 완료·실패는 이후 Home이 FCM 알림을 수신해 반영한다.

### 시나리오 5 - Figma 근거와 접근성을 갖춘 등록 흐름을 검증한다 (우선순위: P2)

개발자와 리뷰어는 등록 흐름의 각 화면을 지정된 Figma node와 비교하고, 사용자는 Dynamic Type과 VoiceOver에서도 입력과 진행 상태를 이해할 수 있다.

**주요 행위자**: 앱 사용자, 개발자, 리뷰어

**우선순위 이유**: 여러 단계로 이어지는 입력 흐름에서 상태 손실이나 접근성 누락은 등록 자체를 완료할 수 없게 만든다.

**독립 테스트**: 각 화면의 deterministic Preview 또는 동등한 렌더를 `360×800` 기준 Figma node와 비교하고, 접근성 라벨·오류 안내·터치 영역과 `xSmall`~`accessibility5` 전체 Dynamic Type을 검사한다.

**수용 시나리오**:

1. **전제** 등록 흐름의 각 화면을 검토한다, **실행** 대응 Preview를 연다, **결과** 링크 입력, 레포 확인, 이해도 선택, 생성 진행, 생성 완료 각 상태를 지정된 Figma node로 식별할 수 있다.
2. **전제** VoiceOver를 사용한다, **실행** 링크 입력 필드, 검증·제출·재시도 버튼, 이해도 선택 카드, 진행 체크리스트를 탐색한다, **결과** 각 요소의 의미·현재 상태·선택 여부를 중복 없이 알 수 있다.
3. **전제** 사용자가 iOS 26 `DynamicTypeSize` 중 `xSmall`, `small`, `medium`, `large`, `xLarge`, `xxLarge`, `xxxLarge`, `accessibility1`, `accessibility2`, `accessibility3`, `accessibility4`, `accessibility5` 중 하나를 사용한다, **실행** 각 화면을 확인한다, **결과** 입력 필드, 선택 카드, 진행 체크리스트, CTA가 잘리거나 서로 가리지 않는다.

### 예외·경계 사례

- 레포지토리 URL이 비어 있으면 검증 요청 자체를 시작하지 않는다.
- 레포지토리 검증 요청이 진행 중일 때 입력이 다시 바뀌면 진행 중이던 검증은 취소하거나 결과를 무시하고 최신 입력 기준으로만 다시 검증한다.
- 검증된 레포지토리가 없거나 제출이 이미 진행 중이면 생성 제출을 실행하지 않는다.
- 생성 요청 제출 자체가 실패(네트워크 오류·서버 오류)하면 원인을 구분하지 않고 동일한 재시도 가능 실패 상태로 표현한다.
- 진행 화면에 머무는 동안 생성 실패를 의미하는 FCM 알림을 받아도 동일한 단일 재시도 가능 실패 상태로 표현하며, 실패 원인(네트워크·서버·AI 중단 등)별로 문구를 분기하지 않는다.
- 완료·실패 판정은 서버가 보내는 FCM 알림 수신을 근거로만 내리며, 알림을 받기 전에는 `ProjectRegistrationReceipt.requestStatus` 값이나 임의 타이머로 완료·실패를 추정하지 않는다.
- 진행 화면과 Home이 동일한 프로젝트에 대해 중복된 FCM 알림을 받아도 완료·실패 처리는 정확히 한 번만 반영한다(멱등 처리).
- `홈에서 기다리기`로 등록 흐름을 이미 닫은 뒤에는 진행 화면이 더 이상 존재하지 않으므로, 이후 도착하는 FCM 알림은 Home에서만 수신·반영한다.
- 사용자가 등록 흐름을 중간에 닫으면(뒤로 가기 등) 진행 중이던 검증·제출 요청은 취소하고 Home 상태에는 어떤 부작용도 남기지 않는다.
- 등록 흐름 완료(홈에서 기다리기 선택 또는 진행 화면에서의 FCM 완료 수신)로 Home에 복귀할 때는 정확히 한 번만 프로젝트 목록을 다시 조회하며, 반복 복귀로 중복 조회를 일으키지 않는다.
- 알림 옵션 선택은 등록·생성 상태 전이에 영향을 주지 않으며, 시트를 보지 않고 흐름이 완료되어도 생성 결과 처리는 동일하게 동작한다.
- 등록 흐름이 전체 화면으로 표시되는 동안 사용자는 MainShell의 다른 탭이나 화면으로 이동할 수 없으며, 진행 화면을 벗어나는 유일한 방법은 `홈에서 기다리기` 선택 또는 명시적 취소뿐이다.
- 생성 완료 후 Home 복귀는 조용한 화면 전환으로만 처리하며, Figma `홈 - 생성 완료` 프레임에 나타나는 자리표시자 Modal(제목/설명 미확정)은 이번 기능에서 렌더링하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 MainShell의 `projectRegistrationRequested` delegate를 받으면 기존 `ProjectRegistrationFeature`가 소유하는 등록 화면을 전체 화면으로 실제로 표시해야 한다.
- **FR-001a**: 등록 흐름이 표시되는 동안에는 완료되거나 사용자가 명시적으로 취소하기 전까지 MainShell 탭 전환과 다른 화면 접근을 차단해야 한다.
- **FR-002**: 등록 화면은 GitHub 레포지토리 URL 입력을 받고, `view(.repositoryURLChanged)`로 상태를 갱신하며 View에서 Use Case를 직접 호출하지 않아야 한다.
- **FR-003**: 시스템은 `view(.validateTapped)` 시 `FetchExternalRepositoryUseCase`를 통해 레포지토리를 검증하고, 성공하면 `ExternalRepository`의 저장소 이름·이미지·기술 스택을 레포지토리 확인 화면에 표시해야 한다.
- **FR-004**: 시스템은 검증 실패를 재시도 가능한 단일 실패 상태로 표시해야 하며, 실패 시 임의의 레포지토리 정보를 생성해 다음 단계로 진행하지 않아야 한다.
- **FR-005**: 시스템은 진행 중인 검증 요청보다 늦게 도착한 응답이 최신 상태를 덮어쓰지 않도록 `validationRequestID` 기준으로 최신 요청만 반영해야 한다.
- **FR-006**: 사용자는 `QuizLevel.l1`, `l2`, `l3` 중 하나를 이해도로 선택할 수 있어야 하며 선택 상태가 시각적으로 구분되어야 한다.
- **FR-007**: 시스템은 레포지토리가 검증되지 않았거나 제출이 이미 진행 중이면 `view(.submitTapped)`가 `createLearningProject`를 호출하지 않아야 한다.
- **FR-008**: 시스템은 제출 시 검증된 레포지토리의 `canonicalURL`과 선택된 `QuizLevel`로 `createLearningProject(githubRepoURL:quizLevel:)`를 정확히 한 번 호출해야 한다.
- **FR-009**: 시스템은 제출이 성공적으로 접수되면 항상 생성 진행 화면에 5단계 체크리스트(`프로젝트 정보 확인`, `코드 구조 분석`, `학습 개념 구성`, `문제 생성`, `세트 검증`)와 예상 소요 시간 문구를 표시해야 하며, 진행률(%)을 조회하는 새 폴링 API를 추가하지 않아야 한다.
- **FR-010**: 시스템은 생성 진행 화면의 `홈에서 기다리기` CTA가 선택되면 실제 학습 세트 생성 완료 여부와 무관하게 `delegate(.projectRegistered(receipt))`를 정확히 한 번 출력하고 등록 흐름을 닫아야 한다.
- **FR-010a**: 사용자가 `홈에서 기다리기`를 선택하지 않고 진행 화면에 머무르는 경우, 시스템은 해당 프로젝트의 생성 완료를 의미하는 FCM 알림을 수신했을 때만 `delegate(.projectRegistered(receipt))`를 정확히 한 번 출력해야 하며, 알림을 받기 전에는 `requestStatus` 값이나 임의 타이머로 완료를 가정하지 않아야 한다.
- **FR-011**: 시스템은 생성 요청 제출 자체가 실패하면 원인(네트워크·서버)을 구분하지 않는 단일 재시도 가능 실패 상태를 표시하고, 재시도 시 동일한 `githubRepoURL`과 `quizLevel`로 다시 정확히 한 번 제출해야 한다.
- **FR-011a**: 시스템은 진행 화면에 머무는 동안 생성 실패를 의미하는 FCM 알림을 수신하면 FR-011과 동일한 단일 재시도 가능 실패 상태로 전이해야 한다.
- **FR-012**: `projectRegistered` delegate를 받은 상위(MainShell 또는 App)는 등록 흐름을 닫고 MainShell의 Home 탭으로 복귀해야 한다.
- **FR-013**: Home은 등록 흐름 완료(홈에서 기다리기 선택 또는 진행 화면에서의 FCM 완료 수신)로 복귀했을 때 프로젝트 목록을 정확히 한 번 다시 조회해 최신 상태를 반영해야 하며, 반복 복귀로 중복 조회를 일으키지 않아야 한다. 실제 생성이 아직 끝나지 않은 채 복귀했다면 해당 프로젝트는 생성 중 상태로 목록에 나타날 수 있다.
- **FR-014**: 생성 진행 화면은 `홈에서 기다리기` CTA를 제공해야 하며, 알림 옵션이 아직 꺼져 있는 상태에서 사용자가 이 CTA를 탭하면 완료 알림 옵션 시트를 표시해야 한다. 시트에서의 수락·거절 선택은 상위가 해석할 intent로만 출력하고 실제 알림 권한 요청이나 로컬 알림 예약을 수행하지 않아야 하며, 선택 직후 `홈에서 기다리기` 동작(FR-010)을 이어서 수행해야 한다.
- **FR-015**: 알림 옵션 시트에서의 선택은 등록·생성 상태 전이나 완료 판정에 영향을 주지 않아야 한다.
- **FR-016**: 사용자가 등록 흐름을 중간에 닫으면 진행 중인 검증·제출 요청을 취소하고 Home이나 다른 화면 상태에 부작용을 남기지 않아야 한다.
- **FR-017**: production 코드는 `@Dependency`, dependency key, Service Locator 또는 전역 mutable container로 production dependency를 조회하지 않고 생성자 주입만 사용해야 한다.
- **FR-018**: 등록 흐름의 시각 구현은 기존 UIComponent와 DesignSystem 토큰을 먼저 대조해 재사용하고, 의미가 맞지 않는 표현만 UI 패키지의 공개 계약으로 확장해야 한다.
- **FR-019**: 각 화면은 의미가 분명한 접근성 라벨·trait·선택 상태를 제공하고 모든 조작 요소의 유효 터치 영역을 최소 `44pt × 44pt`로 유지해야 한다.
- **FR-020**: 각 화면은 iOS 26 `DynamicTypeSize` 전체 12단계(`xSmall`, `small`, `medium`, `large`, `xLarge`, `xxLarge`, `xxxLarge`, `accessibility1`, `accessibility2`, `accessibility3`, `accessibility4`, `accessibility5`)에서 핵심 입력과 동작을 사용할 수 있어야 한다.

### 핵심 엔터티

- **등록 흐름 상태**: 레포지토리 URL 입력값, 검증 상태(`idle`/`validating`/`validated`/`failed`), 선택된 `QuizLevel`, 제출 상태(`idle`/`committing`/`failed`)와 최신 검증 요청 식별자를 소유하는 기존 `ProjectRegistrationFeature.State`이다.
- **외부 레포지토리**: 검증된 GitHub 레포지토리의 정본 URL, 소유자, 이름, 이미지, 스타 수, 기술 스택을 제공하는 기존 Domain 정본(`ExternalRepository`)이다.
- **프로젝트 등록 영수증**: 생성된 프로젝트 식별자, 서버가 부여한 진행 상태 문자열, 선택된 `QuizLevel`을 담는 기존 Domain 정본(`ProjectRegistrationReceipt`)이며, 생성 요청이 서버에 접수되었음을 나타내는 근거다. 실제 생성 완료·실패의 판정 근거는 아니다.
- **생성 완료 FCM 알림**: 프로젝트 식별자와 생성 완료 또는 실패 여부를 담아 서버가 push로 전달하는 이번 기능의 신규 신호다. 진행 화면과 Home 모두 이 신호를 수신해 해당 프로젝트 상태를 갱신하는 근거로 사용한다.
- **알림 옵션 intent**: 생성 완료 리마인드 수락 여부를 상위가 해석할 수 있게 나타내는 이번 기능의 delegate payload다.

## 가정

- 구현 기준은 이 기능 브랜치를 만들기 직전의 `feature/home-screen` HEAD `86da69d7333261172ba821fa31f27c8373074aa1`이다.
- Figma 파일 `mCRt0ejmzI4EFW3UnC9Bzb`의 section `4113:6394`에 포함된 스플래시(`986:13739`, `986:13646` 계열), Task2_04(`737:10890`), Task2_05/06(`737:10882`, `737:10874`), Task2_09(`737:10830`), 로딩(완)(`737:10800`, `824:12149`), 홈 - 생성 완료(`737:10726` 계열)는 모두 `360×800` 화면이며 이번 명세 세션에서 metadata를 직접 확인했다.
- 서버는 학습 세트 생성을 비동기로 처리하며, 진행 화면에 머무는 동안과 Home 복귀 이후의 실제 완료·실패 여부는 서버가 보내는 FCM 알림으로만 판단하고, 별도의 진행률 조회(폴링) API는 이번 기능 범위에서 신설하지 않는다.
- `createLearningProject`가 즉시 반환하는 `ProjectRegistrationReceipt.requestStatus`는 요청이 서버에 접수되었음을 나타내는 값(예: 접수됨)으로만 쓰이며, 이번 기능은 이 값을 실제 생성 완료·실패의 판정 근거로 사용하지 않는다.
- FCM payload가 담을 프로젝트 식별자·완료/실패 상태의 정확한 필드 형식과, FCM 수신을 위한 Firebase Messaging 등록 처리의 패키지 배치(Infrastructure 계층 등)는 계획 단계에서 백엔드 계약과 기존 의존성 방향을 확인해 확정한다.
- 백엔드는 생성 완료·실패 FCM payload를 `content-available` silent push로 전송하며, 이는 사용자의 시스템 알림 권한(`UNUserNotificationCenter` authorization) 승인 여부와 무관하게 앱이 수신할 수 있다는 전제다. 사용자가 알림 권한을 이미 허용했다면 동일 payload에 배지·사운드 등 부가 표시가 함께 전달될 수 있으나, 그 부가 표시의 UI와 권한 요청 자체는 이번 기능에서 구현하지 않는다.
- 로컬 리마인드 알림(시나리오 4)의 권한 요청과 예약 인프라는 이 저장소에 아직 존재하지 않으며, 이번 기능은 알림 옵션 UI와 intent 출력까지만 다루고 실제 알림 구현은 후속 기능으로 남긴다. 이는 이번 기능에서 새로 구축하는 FCM 완료·실패 수신 인프라와는 별개다.
- 기존 `ProjectRegistrationFeature`의 State·Action·Reducer 계약은 이번 기능의 요구를 충족하며, 계획 단계에서 화면 연결과 FCM 판정 로직 추가 위치를 구체화한다.
- `AppRootFeature`가 이미 소유한 `mainShell(.delegate(.projectRegistrationRequested))` 등 관련 delegate 케이스는 현재 `.none`으로 처리되며, 이 기능이 실제 화면 표시와 완료 후 복귀 로직으로 대체한다.
- 018-home-screen 기능이 정의한 Home의 최초 조회 정책(다른 탭에서 복귀 시 재조회하지 않음)은 등록 완료로 복귀하는 경우에 한해 예외적으로 1회 재조회하도록 확장된다. FCM 알림 수신에 따른 프로젝트 상태 갱신은 이 재조회 정책과 별개의 메커니즘(수신 payload 기반의 로컬 상태 갱신)으로 처리하며, 그 외 일반 탭 전환 동작은 변경하지 않는다.
