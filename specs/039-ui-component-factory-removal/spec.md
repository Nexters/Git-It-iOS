- 질문: 개정 대상 문서가 정확히 어디까지인가 → 답변: 계획 단계의 전수 조사에서 팩토리를 규정·전제하는 문장이 여섯 문서에 있음을 확인했다. 최초에 열거한 네 문서에 `docs/conventions/view-tokens.md`와 `docs/conventions/view-declarations/style.md`를 더하고, 폐기된 개념을 가리키게 되는 `docs/conventions/view/screen-init.md`의 문구 정리도 같은 변경 단위에 포함한다.

- 정정: `/speckit-analyze` 교차 검증으로 세 건을 바로잡았다. (1) `factory-criteria.md`는 전문이
  팩토리 규칙이므로 개정이 아니라 삭제하고, 팩토리와 무관한 두 규칙만 `component-init.md`로
  옮긴다. (2) `view.md` §3.2의 제목과 링크 텍스트가 "생성 경로는 두 가지"를 단언하고 있어
  개정 대상에 추가했다. 같은 문장이 `component-init.md`의 제목이기도 하다. (3) FR-004c의
  "같은 변경 단위"는 커밋이 아니라 브랜치 수준이다. FR-010의 컴포넌트 단위 커밋 요구와
  양립하도록 문구를 정정했다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 단일 변형 축 컴포넌트의 팩토리 제거 (우선순위: P1)

개발자가 `ActionButton`, `IconGlassButton`, `TagBadge`, `LabeledCard`를 생성할 때 경로가 하나뿐이다.
앞의 세 컴포넌트는 초기화 메서드가 `style:` 파라미터를 받는데도 같은 변형을 이름으로 고정한
정적 팩토리가 함께 공개돼 있고, 호출부는 대부분 팩토리를 쓴다. 기본값과 인자 순서가 두 경로에
중복되며, 변형이 늘어날 때마다 팩토리가 `String`·`StyledText` 변형으로 2배씩 늘어난다.
`LabeledCard`는 사정이 다르다. 공개 초기화 메서드가 없고 `Style`이 `private`이라 생성 경로가
팩토리 둘뿐이므로, 제거 전에 공개 계약을 먼저 만들어야 한다.

**주요 행위자**: 개발자

**우선순위 이유**: `ActionButton`·`IconGlassButton`·`TagBadge`는 이미 대응하는 `Style` enum과
초기화 메서드를 갖고 있어 새로 정의할 축이 없다. 가장 적은 설계 결정으로 중복을 제거할 수 있고,
시나리오 2·3의 판단 근거가 되는 전환 방식을 먼저 확정한다. `LabeledCard`는 공개 계약을 신설해야
하므로 앞의 셋으로 전환 방식이 확정된 뒤에 진행한다.

**독립 테스트**: 네 컴포넌트의 정적 팩토리를 제거하고 호출부를 초기화 메서드로 전환한 뒤,
전체 build·compile·test가 통과하고 프리뷰의 화면 표현이 이전과 같은지 확인한다. 컴포넌트
하나씩 독립적으로 검증할 수 있으며, 시나리오 2·3을 진행하지 않아도 이 네 컴포넌트의 중복은
완전히 사라진다.

**수용 시나리오**:

1. **전제** 한 컴포넌트에 초기화 메서드와 정적 팩토리가 함께 공개돼 있고, **실행** 팩토리를
   제거하고 호출부를 초기화 메서드로 옮기면, **결과** 그 컴포넌트의 공개 생성 경로가 하나만
   남는다.
2. **전제** 팩토리마다 기본값과 인자 순서가 중복돼 있고, **실행** 전환을 완료하면, **결과**
   기본값과 인자 순서가 초기화 메서드 한 곳에만 선언된다.
3. **전제** 전환 전후의 화면이 있고, **실행** 같은 프리뷰를 렌더링하면, **결과** 표현이
   달라지지 않는다.
4. **전제** UI의 공개 API를 제거하는 변경이고, **실행** 커밋 단위를 구성하면, **결과** UI 변경과
   Feature·App 호출부 수정이 같은 단위에 들어가 중간 상태에서도 compile된다.

### 시나리오 2 - ScreenEdgeScrim의 변형 축 정의와 전환 (우선순위: P2)

개발자가 `ScreenEdgeScrim`을 다른 컴포넌트와 같은 방식으로 생성한다. 이 컴포넌트는 `top`·`bottom`
팩토리만 공개돼 있고 대응하는 enum도 공개 초기화 메서드도 없어, 파라미터로 표현할 축을 먼저
정의해야 한다.

**주요 행위자**: 개발자

**우선순위 이유**: 시나리오 1과 달리 새 공개 타입(가장자리 축 enum)을 정의하는 설계 결정이
필요하다. 전환 방식이 확정된 뒤에 진행해야 축의 이름과 형태를 일관되게 정할 수 있다.

**독립 테스트**: 가장자리 축 enum과 이를 받는 초기화 메서드를 추가하고 팩토리를 제거한 뒤,
호출부 전환과 전체 검증이 통과하며 위·아래 스크림의 표현이 이전과 같은지 확인한다.

**수용 시나리오**:

1. **전제** 변형이 팩토리 이름으로만 구분되고 대응하는 타입이 없고, **실행** 가장자리 축을
   나타내는 enum을 정의하면, **결과** 두 변형이 같은 타입의 값으로 표현된다.
2. **전제** 축 enum이 정의되고, **실행** 이를 받는 초기화 메서드를 공개하고 팩토리를 제거하면,
   **결과** 다른 컴포넌트와 같은 형태의 생성 경로만 남는다.

### 시나리오 3 - StyledText 팩토리 제거 (우선순위: P2)

개발자가 `StyledText`도 다른 컴포넌트와 같은 방식으로 생성한다. Typography 팩토리 10개는 모두
같은 private `styled`를 거쳐 동일한 public init을 호출하는 한 줄 위임이며, 그 init은 이미
`TextStyleToken`을 파라미터로 받는다. 따라서 다른 컴포넌트와 구조가 같고 같은 근거로 제거된다.
[Typography 컨벤션](../../docs/conventions/view-tokens/typography.md)이 이 팩토리 사용을
규칙으로 정하고 있으나, 그 개정은 시나리오 4가 관련 문서를 함께 다룬다.

**주요 행위자**: 개발자

**우선순위 이유**: 이 기능에서 가장 큰 전환 단위다. 팩토리 호출이 168곳으로 나머지 다섯
컴포넌트 합계(60곳)의 세 배에 가깝다. 전환 방식이 앞선 시나리오로 확정된 뒤 진행해야 168곳을
한 번에 옳게 옮길 수 있다.

**독립 테스트**: 팩토리 10개를 제거하고 호출부를 초기화 메서드로 전환한 뒤, 전체 검증이
통과하고 텍스트의 타이포그래피·색·정렬 표현이 이전과 같은지 확인한다.

**수용 시나리오**:

1. **전제** Typography 팩토리 10개가 공개돼 있고, **실행** 이를 제거하고 호출부를 초기화
   메서드로 옮기면, **결과** `StyledText`의 공개 생성 경로가 하나만 남는다.
2. **전제** 전환 전후의 텍스트가 있고, **실행** 같은 화면을 렌더링하면, **결과** 자간·행간·
   폰트·색·정렬이 달라지지 않는다.
3. **전제** 호출부가 168곳이고, **실행** 전환을 수행하면, **결과** 프리뷰와 테스트의
   호출부까지 포함해 남은 팩토리 호출이 없다.

### 시나리오 4 - 생성 경로 컨벤션 개정 (우선순위: P1)

개발자가 컴포넌트를 새로 만들 때 참조하는 규칙이 이번 전환 결과와 일치한다. 현재 View
컨벤션은 팩토리를 호출부의 기본 선택 수단으로 규정하고 있어, 코드만 바꾸면 컨벤션이 되살리라고
지시하는 경로를 코드가 없앤 상태가 된다. 이 시나리오는 그 규칙을 개정해 문서와 코드를
일치시킨다.

**주요 행위자**: 개발자

**우선순위 이유**: 시나리오 1~3의 코드 변경이 개정 전 컨벤션을 위반하므로, 개정이 함께 들어가지
않으면 어떤 전환도 규칙에 어긋난 상태로 남는다. 코드 전환과 같은 브랜치여야 한다.

**독립 테스트**: 개정 대상 문서에서 `팩토리` 토큰이 0건이고, `component-init.md`가 공개 생성
경로를 단수로 규정하며 그 호출 예시가 모두 초기화 호출인지 확인한다(SC-006a). 삭제한 문서를
가리키는 링크와 끊어진 앵커가 없는지도 함께 확인한다.

**수용 시나리오**:

1. **전제** 컨벤션이 생성 경로를 초기화 메서드와 팩토리 둘로 규정하고 있고, **실행** 이를
   초기화 메서드 하나로 개정하면, **결과** 새 컴포넌트를 설계하는 개발자가 문서만으로 단일
   경로에 도달한다.
2. **전제** 컨벤션에 팩토리 정의 기준과 검토 체크리스트 항목이 있고, **실행** 개정을 수행하면,
   **결과** 팩토리를 요구하거나 전제하는 문장이 남지 않는다.
3. **전제** 코드 전환과 컨벤션 개정이 있고, **실행** 브랜치의 커밋 순서를 구성하면,
   **결과** 개정이 코드 전환과 같은 브랜치의 마지막 커밋에 들어가, 병합 시점에 문서와 코드가
   어긋난 상태가 남지 않는다.

### 예외·경계 사례

- 팩토리와 초기화 메서드의 기본값이 서로 다르면 어떻게 하는가? — 전환 전에 차이를 확인하고,
  호출부가 실제로 얻던 값을 유지한다. 기본값 차이로 화면 표현이 바뀌면 안 된다.
- 팩토리가 `String`과 `StyledText` 두 변형으로 나뉘어 있을 때 초기화 메서드가 두 변형을 모두
  제공하지 않으면 어떻게 하는가? — 호출부가 쓰던 입력 형태를 초기화 메서드가 받을 수 있어야
  전환이 성립한다. 부족하면 초기화 메서드를 먼저 보완한다.
- 프리뷰와 테스트의 호출부는 어떻게 하는가? — 같은 전환 범위에 포함한다. 제외하면 공개 API
  제거 시 compile되지 않는다.
- 전환 중간 상태에서 compile이 깨지면 어떻게 하는가? — UI 공개 API 제거와 호출부 수정을 같은
  커밋 단위에 두어 중간 상태를 만들지 않는다.
- 되돌려야 할 때는 어떻게 하는가? — 공개 API 제거는 되돌리기 비용이 높으므로, 컴포넌트 단위로
  단위를 나누어 한 컴포넌트의 전환이 끝날 때마다 검증이 통과하는 상태를 남긴다.
- 컨벤션 개정과 코드 전환의 순서가 어긋나면 어떻게 하는가? — 같은 브랜치에 넣고 개정을
  마지막 커밋에 둔다. 개정만 먼저 들어가면 코드가 규칙을 위반한 상태가, 개정이 빠진 채
  병합되면 문서가 없앤 경로를 지시하는 상태가 된다. 브랜치 내부의 일시적 불일치는 허용한다.
- 개정 대상 문서가 서로를 참조하고 있으면 어떻게 하는가? — `view.md`가 §3.2·§3.3으로 하위
  문서를 가리키므로 §3.3 절과 그 링크를 함께 삭제한다. `package-rules/ui.md`, `ui-component.md`,
  `ui-component/public-contract.md` 세 문서는 §3 자체(`view.md#3-공개-생성-경로`)만 가리키므로,
  FR-004b-1대로 §3 제목과 앵커를 유지하면 셋 다 수정 대상이 아니다.
- 생성 팩토리가 아닌 정적 선언은 어떻게 하는가? — `TabShellItem.tabColor(isSelected:)`와
  `ResourceImage.resizable(_:)`은 값을 변환해 돌려주는 계산이므로 이 기능의 대상이 아니다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: `ActionButton`, `IconGlassButton`, `TagBadge`, `LabeledCard`는 정적 팩토리를 공개하지
  않아야 하며, 변형을 `Style`·`Size` 같은 enum 파라미터로 받는 초기화 메서드만 공개해야 한다.
- **FR-001a**: `LabeledCard`는 `Style`을 `public`으로 올리고 이를 받는 `public` 초기화 메서드를
  추가한 뒤 팩토리를 제거해야 한다. 기준선에서 이 컴포넌트는 공개 초기화 메서드가 없고
  `Style`이 `private`이다.
- **FR-002**: 각 대상 컴포넌트의 기본값과 인자 순서는 초기화 메서드 한 곳에만 선언되어야 한다.
- **FR-003**: `ScreenEdgeScrim`은 위·아래 변형을 나타내는 공개 enum을 정의하고, 이를 파라미터로
  받는 초기화 메서드를 공개한 뒤 팩토리를 제거해야 한다.
- **FR-004**: `StyledText`의 Typography 팩토리 10개를 제거하고, 변형을 `TextStyleToken`
  파라미터로 받는 초기화 메서드만 공개해야 한다.
- **FR-004a**: 컴포넌트의 공개 생성 경로를 규정하는 컨벤션을 개정해, 초기화 메서드 하나만
  공개 경로로 규정하고 시각 변형을 enum 파라미터로 받도록 해야 한다. 개정 대상은 다음 여섯
  문서다.
  - [docs/conventions/view/component-init.md](../../docs/conventions/view/component-init.md) —
    제목 "컴포넌트의 공개 생성 경로는 두 가지입니다", "공개 생성 경로는 다음 둘뿐입니다"와
    팩토리 호출을 정본으로 제시한 예시
  - [docs/conventions/view/factory-criteria.md](../../docs/conventions/view/factory-criteria.md) —
    문서 전문이 팩토리 정의 기준이므로 **문서를 삭제한다**. 팩토리와 무관한 두 규칙
    (`@ViewBuilder` 자식을 받는 컴포넌트의 기본 생성 경로, 기본값을 초기화 인자에 두는
    규칙)은 `component-init.md`로 옮겨 보존한다. Constitution 원칙 5는 `/speckit-implement`에

    세션에서 승인을 받았다. PR에 원칙 3 예외로 기록한다
  - [docs/conventions/view.md](../../docs/conventions/view.md) — §3.2의 제목과 링크 텍스트
    "컴포넌트의 공개 생성 경로는 두 가지입니다", §3.3(팩토리를 정의하는 기준) 절과 그 링크
    삭제, §6 검토 체크리스트의 팩토리 전제 항목 2개
  - [docs/conventions/view-tokens/typography.md](../../docs/conventions/view-tokens/typography.md) —
    "문자열 렌더링은 `StyledText`의 Typography 팩토리를 사용합니다"
  - [docs/conventions/view-tokens.md](../../docs/conventions/view-tokens.md) — §2.4 본문의 같은
    규칙과 §3 검토 체크리스트의 "문자열이 `StyledText` Typography 팩토리를 통과하는가?"
  - [docs/conventions/view-declarations/style.md](../../docs/conventions/view-declarations/style.md) —
    "호출부는 … 시각 변형 팩토리를 기본 선택 수단으로 사용합니다"
- **FR-004b**: 개정 후 위 문서에 팩토리 정의를 요구하거나 전제하는 문장이 남아 있지 않아야
  하며, 팩토리를 허용하는 예외 조건을 새로 정의하지 않아야 한다.
- **FR-004b-1**: `docs/conventions/view.md` §3의 제목 "공개 생성 경로"와 그 앵커

  삭제하더라도 세 링크가 모두 끊기지 않아야 한다.

  - [docs/conventions/ui-component.md](../../docs/conventions/ui-component.md)

- **FR-004b-2**: 삭제하는 문서를 가리키는 링크가 저장소에 남아 있지 않아야 한다.
- **FR-004b-3**: `docs/conventions/view.md` §3.3을 삭제한 뒤 §3.4·§3.5의 번호를 다시 매기지
  않아야 한다. `docs/retrospective/31-quiz-solving-flow.md`가 §3.5를 절 번호로 인용하고 있어,
  재번호는 과거 기록의 참조를 조용히 어긋나게 한다. 번호 공백은 허용한다.
- **FR-004c**: 컨벤션 개정은 코드 전환과 같은 브랜치에 포함되어야 하며, 그 브랜치가
  develop에 병합되는 시점에 문서와 코드가 일치해야 한다. FR-010이 컴포넌트 단위로 커밋을
  나누도록 요구하므로 개정을 코드 커밋 하나에 합칠 수는 없고, 코드 전환을 모두 마친 뒤의
  마지막 커밋에 둔다. 브랜치 내부의 중간 커밋에서 문서와 코드가 일시적으로 어긋나는 것은
  허용하되, 브랜치 밖으로는 그 상태를 내보내지 않는다.
- **FR-004d**: [docs/conventions/view/screen-init.md](../../docs/conventions/view/screen-init.md)의

  정리해, 폐기된 개념을 가리키지 않아야 한다. 화면이 `Style`을 정의하지 않는다는 규칙 자체는
  유지한다.
- **FR-005**: 전환 후 화면 표현이 변하지 않아야 한다. 색·크기·간격·타이포그래피가 전환 전과
  동일해야 한다.
- **FR-006**: UI 공개 API 제거와 Feature·App 호출부 수정은 같은 커밋 단위에 포함되어야 하며,
  각 커밋 단위는 그 자체로 compile되어야 한다.
- **FR-007**: 프리뷰와 테스트의 호출부도 전환 범위에 포함되어야 한다.
- **FR-008**: 전환 후 전체 공유 scheme 빌드, build-for-testing, test-without-building이 모두
  통과해야 한다.
- **FR-009**: 생성 팩토리가 아닌 정적 선언(`TabShellItem.tabColor(isSelected:)`,
  `ResourceImage.resizable(_:)`)은 이 기능의 대상이 아니며 변경하지 않아야 한다.
- **FR-010**: 컴포넌트 단위로 작업을 나누어, 한 컴포넌트의 전환이 끝날 때마다 검증이 통과하는
  상태가 남아야 한다.
- **FR-011**: 변경 범위는 UI 패키지의 대상 컴포넌트와 그 호출부, 그리고 FR-004a·FR-004d가 지정한
  컨벤션 문서로 한정되어야 한다. 호출부의 화면 구성이나 Feature 구조는 변경하지 않아야 한다.

### 핵심 엔터티

- **변형 축**: 한 컴포넌트가 가질 수 있는 표현 변형의 집합을 나타내는 enum. `ActionButton.Style`,
  `IconGlassButton`·`TagBadge`·`LabeledCard`의 대응 enum, 그리고 FR-003이 새로 정의하는
  `ScreenEdgeScrim`의 가장자리 축이 여기 해당한다.
- **공개 생성 경로**: 컴포넌트를 만들기 위해 외부에 공개된 방법. 이 기능의 목표는 컴포넌트마다
  이것이 초기화 메서드 하나만 남는 상태다.
- **의미 축과 표현 축**: `TextStyleToken`은 자간·행간·언어별 폰트 선택을 함께 결정하는 의미
  축이고, `ActionButton.Style`은 배경·글자색을 고르는 표현 축이다. 이 구분은 토큰이 무엇을
  결정하는지에 대한 설명이며, 생성 경로를 다르게 둘 근거는 아니다. 두 경우 모두 초기화 메서드가
  이미 그 축을 파라미터로 받는다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: FR-001·FR-003·FR-004의 대상 여섯 컴포넌트에서 공개된 정적 생성 팩토리가 0개다.
- **SC-002**: 여섯 컴포넌트 각각의 공개 생성 경로가 초기화 메서드 하나뿐이며, 기본값 선언이
  중복되지 않는다.
- **SC-003**: 전환 전후로 대상 컴포넌트를 사용하는 화면의 표현이 동일하다.
- **SC-004**: 전체 공유 scheme 빌드, build-for-testing, test-without-building이 모두 통과한다.
- **SC-005**: 전환 과정의 각 커밋이 단독으로 compile된다.
- **SC-006**: FR-004a가 열거한 문서 중 남는 다섯 문서와 FR-004d의 `screen-init.md`가 기술한
  공개 생성 경로가 실제 코드와 일치하며, 팩토리 정의를 요구하거나 전제하는 문장이 남아 있지
  않다. 삭제한 문서를 가리키는 링크와 끊어진 앵커도 없고, `view.md` §3.4·§3.5의 절 번호가
  그대로다.
- **SC-006a**: 개정된 컨벤션만 읽고 새 컴포넌트를 설계하면 초기화 메서드 하나만 공개하는
  결론에 도달한다. 판정은 두 조건으로 한다. (1) 개정 대상 문서 전체에서 `팩토리` 토큰이
  0건이다. (2) `component-init.md`가 공개 생성 경로를 단수로 규정하고, 그 문서가 제시하는
  호출 예시가 모두 초기화 호출이다.
- **SC-007**: 새 변형을 추가할 때 수정해야 하는 선언 지점이 컴포넌트마다 한 곳이다.

## 가정

- 이 변경은 개발자의 유지보수 비용과 UI 공개 API의 일관성을 대상으로 하며, 최종 사용자에게
  새로운 기능 가치를 제공하지 않는다.
- 기준선은 `feature/feature-composition-refactor`의 `2b994f2`이며, `ActionButton` 햅틱을 Feature의
  `FeedbackActionButton`으로 옮긴 작업(`8ab9e08`)이 이미 반영되어 있다. 햅틱 소유권 이전은 이
  기능의 범위가 아니다.
- 팩토리 호출은 `StyledText` 168곳, 나머지 다섯 컴포넌트 60곳으로 전환 대상은 228곳이다.
  패키지별로는 UI 111곳, Feature 117곳이며 App에는 없다. 고유 파일은 UI 42개, Feature 51개다.
  계획 단계 실측은 166곳·226곳이었고, 구현 단계에서 줄바꿈으로 나뉜 호출 2곳을 추가로
  확인했다.
- 초기화 메서드로 옮기면서 생기는 호출부의 가독성 차이는 초기화 메서드의 파라미터 레이블로
  조정할 수 있으며, 그 형태는 계획 단계에서 정한다.
- `ActionButton`, `IconGlassButton`, `TagBadge`, `StyledText`는 이미 대응하는 변형 축과 이를 받는
  공개 초기화 메서드를 갖고 있어 새 축을 정의하지 않는다. `LabeledCard`는 `Style` 승격과 초기화
  메서드 추가가, `ScreenEdgeScrim`은 변형 enum 신규 정의가 필요하다.
- 팩토리를 `@available(*, deprecated)`로 먼저 표시한 뒤 제거하는 2단계 전환은 선택지로 남기되,
  기본은 컴포넌트 단위의 단일 전환으로 본다.
- 이 기능은 `feature/feature-composition-refactor`의 Feature 분해·합성보다 먼저 완료되어야 하는
  선행 기능이다. 두 기능은 형제 브랜치이며 서로의 완료를 기다리지 않는다.
- 컨벤션 개정은 생성 경로 규칙에 한정하며, 표시 값·`Binding`·콜백 구분이나 상태 wrapper 금지
  같은 나머지 규칙은 그대로 둔다.
- UI 컴포넌트의 내부 구현, DesignSystem 토큰, 화면 구성은 변경하지 않는다.
