# 기능 명세: 생성 리마인드 명명·경계 리팩터링

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/generation-reminder-refactoring`

**브랜치 상태**: `생성`

**생성일**: 2026-09-01

**상태**: 초안

**입력**: 사용자 설명: "코드 리뷰 리포트에 따라 로컬 리마인드 알림 기능의 명명·경계·죽은 코드를 리팩터링한다. Infrastructure에서 서비스 개념(알림 문구·generation-completed 식별자)을 제거하고, 생성 결과 어휘를 GenerationOutcome으로 통일하며, AppComposition의 조립과 실행을 분리하고, 사용처 0인 컴포넌트와 죽은 delegate·중복 테스트를 제거하고, InfrastructurePushMessaging 테스트 target을 신설한다. 동작 변경 없이 구조와 어휘만 정리한다."

## 변경 시나리오와 테스트 *(필수)*

이 기능은 최종 사용자에게 관찰되는 동작을 바꾸지 않는다. 이해관계자는 이 저장소를
유지보수하는 iOS 개발자와 PR 리뷰어이며, 확인 가능한 결과는 패키지 규칙 준수, 이름으로
책임을 식별하는 비용, 테스트 신뢰도다. 사용자 가치를 꾸며내지 않는다.

### 시나리오 1 - Infrastructure가 서비스 개념을 모르게 한다 (우선순위: P1)

`InfrastructurePushMessaging`이 "학습 세트", "세트 생성 완료" 같은 서비스 고유 개념과
사용자에게 보이는 한국어 문구를 직접 소유하고 있다. 개발자가 알림 문구를 바꾸려면 범용
기술 패키지를 열어야 하고, 이 패키지는 교체 불가능한 도메인 지식을 갖게 된다.
`docs/package-rules/infrastructure.md`가 명시적으로 금지하는 상태를 해소한다.

**주요 행위자**: 개발자

**우선순위 이유**: 유일하게 문서화된 패키지 규칙을 직접 위반하는 항목이다. 이후 알림
문구가 늘어나거나 로컬라이제이션이 붙으면 되돌리는 비용이 급격히 커진다.

**독립 테스트**: `InfrastructurePushMessaging` 소스 전체에서 서비스 고유 용어와 사용자
문구를 검색해 0건임을 확인하고, 알림 발송 경로가 상위 계층이 만든 값만 전달받는지
테스트로 검증한다. 다른 시나리오 없이 단독으로 규칙 위반을 해소한다.

**수용 시나리오**:

1. **전제** 알림 문구가 Infrastructure에 하드코딩된 상태, **실행** 알림 발송 계약을 범용
   요청 값을 받는 형태로 바꾼다, **결과** Infrastructure 소스에 "세트", "학습",
   "generation-completed" 문자열이 남지 않는다.
2. **전제** 알림 문구 변경 요청, **실행** 문구를 수정한다, **결과** Infrastructure 패키지를
   열지 않고 상위 계층 한 곳에서만 변경이 끝난다.
3. **전제** 한 파일이 최상위 타입 둘을 정의한 상태, **실행** 파일·형태 어휘 규칙에 맞게
   정리한다, **결과** 해당 패키지의 모든 파일이 파일 하나에 파일 밖 참조 타입 하나 규칙을
   충족한다.

### 시나리오 2 - 생성 결과를 한 어휘로 부른다 (우선순위: P2)

같은 사건("학습 세트 생성이 끝났다")이 Domain·Data·Composition에서 서로 다른 세 어휘로
불린다. 개발자가 세 패키지를 오가며 같은 개념을 다른 이름으로 재해석해야 하고, 가장 긴
타입 이름은 49자다. 어휘를 하나로 통일하고 이미 문맥이 제공하는 접두어를 제거한다.

**주요 행위자**: 개발자

**우선순위 이유**: 이후 모든 변경이 이 이름들을 통과한다. 뒤로 미룰수록 참조 지점이 늘어
비용이 커진다. 시나리오 1과 파일이 겹치지 않아 독립 진행이 가능하다.

**독립 테스트**: 생성 결과를 표현하는 공개 타입을 세 패키지에서 나열해 단일 어휘를 쓰는지,
그리고 이름 길이 상한을 만족하는지 확인한다. 기존 테스트가 이름만 바꾸어 전부 통과하면
동작이 보존된 것이다.

**수용 시나리오**:

1. **전제** 세 패키지가 서로 다른 어휘를 쓰는 상태, **실행** 단일 어휘로 통일한다,
   **결과** 생성 결과 관련 공개 타입 이름에서 어휘가 한 종류만 관측된다.
2. **전제** 관찰용 UseCase 이름에 수명 정보가 없는 상태, **실행** 조회와 관찰을 이름에서
   구분한다, **결과** 스트림을 반환하는 UseCase와 1회 조회 UseCase를 이름만으로 구별할 수
   있다.
3. **전제** 이름 변경 완료, **실행** 기존 테스트를 실행한다, **결과** 통과·실패 구성이
   변경 전과 동일하다.

### 시나리오 3 - 조립과 실행을 분리한다 (우선순위: P3)

`AppComposition`의 생성자가 의존성 그래프 조립을 넘어 네트워크 호출, 전역 상태 쓰기,
취소 핸들 없는 무기한 관찰을 시작한다. 이 타입을 만드는 것만으로 서버에 기기가 등록되어,
테스트가 공개 표면만 검증할 수 없고 관찰 Task를 멈출 방법도 없다.

**주요 행위자**: 개발자

**우선순위 이유**: 테스트가 실제 부작용 경로를 건드리는 상태라 신뢰도에 직접 영향을 준다.
다만 시나리오 1·2보다 참조 범위가 좁아 뒤에 두어도 재작업이 발생하지 않는다.

**독립 테스트**: 조립 타입을 생성하고 부작용이 관측되지 않음을 확인한 뒤, 명시적 실행
진입점을 호출했을 때만 관찰과 등록이 시작되는지 검증한다.

**수용 시나리오**:

1. **전제** 생성자가 부작용을 수행하는 상태, **실행** 실행을 명시적 진입점으로 분리한다,
   **결과** 조립 타입 생성만으로는 네트워크 호출과 전역 상태 쓰기가 발생하지 않는다.
2. **전제** 관찰 Task에 취소 수단이 없는 상태, **실행** 실행 진입점이 취소 가능한 핸들을
   제공한다, **결과** 시작한 관찰을 외부에서 종료할 수 있다.
3. **전제** production 타입이 테스트 전용 대기 함수를 소유한 상태, **실행** 테스트가 실행
   진입점의 반환값으로 완료를 기다리게 한다, **결과** production 공개 API에 테스트 지원
   목적만 가진 연산이 남지 않는다.
4. **전제** 조립 계층이 기술 계층 구체 타입을 공개 API로 재노출하는 상태, **실행** 그 노출을
   제거하거나 소유 계층을 옮긴다, **결과** 조립 계층 공개 API에서 기술 계층 구체 타입을
   참조할 수 없다.
5. **전제** 형태 폴더에 그 어휘가 규정하지 않는 종류의 선언이 놓인 상태, **실행** 어휘에
   맞는 위치로 옮기거나 어휘 표를 갱신한다, **결과** 각 선언의 위치가 형태 어휘 정본과
   일치한다.

---

### 시나리오 4 - 죽은 코드와 중복 테스트를 제거한다 (우선순위: P4)

production 사용처가 0인 UI 컴포넌트, 아무도 소비하지 않는 delegate, 선언만 되고 쓰이지
않는 상수, 그리고 본문이 동일하고 상수만 다른 테스트가 남아 있다. 유지보수 대상은 늘지만
검증하는 동작은 늘지 않는다.

**주요 행위자**: 개발자

**우선순위 이유**: 앞 시나리오들이 파일을 이동·개명한 뒤에 수행해야 재작업이 없다.
제거 자체는 위험이 낮다.

**독립 테스트**: production 참조 수가 0인 공개 선언을 나열해 0건임을 확인하고, 테스트
제거 전후로 검증되는 동작 분기 수가 줄지 않았음을 확인한다.

**수용 시나리오**:

1. **전제** production 참조가 0인 공개 컴포넌트가 존재, **실행** 제거하거나 대체 컴포넌트에
   흡수한다, **결과** 해당 선언과 그 전용 테스트·프리뷰가 함께 사라진다.
2. **전제** 수신부가 무시하는 delegate가 존재, **실행** delegate와 빈 수신 분기, 이를
   검증하던 테스트 구문을 함께 제거한다, **결과** 발행되지만 아무 동작도 유발하지 않는
   출력이 남지 않는다.
3. **전제** 본문이 동일하고 입력 상수만 다른 테스트 셋이 존재, **실행** 하나의 파라미터화
   테스트로 합친다, **결과** 검증되는 입력 조합 수가 유지되면서 테스트 코드 길이가 줄어든다.
4. **전제** 대상 필드를 한 번도 설정하지 않고 기본값만 확인하는 테스트가 존재, **실행**
   제거한다, **결과** 항상 통과하는 테스트가 남지 않는다.
5. **전제** 프로젝트가 소유한 enum을 다루는 `switch`가 라이브러리 전용 미지 케이스 처리를
   포함한 상태, **실행** 그 처리를 제거한다, **결과** 해당 enum에 케이스를 추가하면
   컴파일러가 누락된 분기를 보고한다.

---

### 시나리오 5 - 검증 공백을 닫는다 (우선순위: P5)

`InfrastructurePushMessaging`에는 테스트 target 자체가 없어 권한 상태 매핑과 payload 변환이
검증 없이 들어간다. Composition의 권한 결과 매핑도 세 분기를 뒤바꿔도 실패하는 테스트가
없다.

**주요 행위자**: 개발자

**우선순위 이유**: 앞 시나리오들이 만든 새 구조 위에서 작성해야 재작성이 없다. 다른
시나리오의 완료를 막지 않는다.

**독립 테스트**: 테스트 target이 공유 scheme의 테스트 실행에 포함되는지 확인하고, 매핑
분기를 의도적으로 뒤바꿨을 때 테스트가 실패하는지 확인한다.

**수용 시나리오**:

1. **전제** 해당 기술 패키지에 테스트 target이 없는 상태, **실행** 다른 기술 패키지와 같은
   구성으로 테스트 target을 추가한다, **결과** 프로젝트 테스트 실행에 그 target이 포함된다.
2. **전제** 권한 결과 매핑에 테스트가 없는 상태, **실행** 각 입력 결과가 대응하는 출력으로
   변환되는지 검증한다, **결과** 매핑 분기를 뒤바꾸면 테스트가 실패한다.

---

### 예외·경계 사례

- 이름 변경 도중 한 패키지만 갱신되어 빌드가 깨지면 어떻게 하는가? 어휘 통일은 참조하는
  모든 패키지를 하나의 커밋 단위로 함께 변경한다.
- Infrastructure에서 문구를 걷어낸 뒤 알림 식별자 형식이 바뀌면 이미 예약된 알림은
  어떻게 되는가? 이 기능의 알림은 즉시 발송이며 예약 큐를 사용하지 않으므로 기존 식별자를
  참조하는 상태가 남지 않는다.
- 조립과 실행을 분리한 뒤 실행 진입점 호출을 누락하면 어떻게 드러나는가? 리마인드 관찰과
  기기 등록이 시작되지 않는다. 앱 시작 경로가 진입점을 호출하는지 검증하는 테스트가 필요하다.
- 죽은 코드로 판단한 선언이 실제로는 다른 브랜치에서 사용 중이면 어떻게 하는가? 제거 대신
  사용처가 생길 때까지 보류하고 판단 근거를 PR에 남긴다.
- 테스트 target 추가가 기존 빌드 시간을 크게 늘리면 어떻게 하는가? 외부 라이브러리 링크가
  필요 없는 검증부터 추가하고, 링크 비용이 문제가 되면 폴더 분리 후 target 분리를 재검토한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 로컬 알림 발송 기술 계약은 알림 식별자와 표시 문구를 호출자로부터 값으로
  전달받아야 하며, 서비스 고유 개념을 계약 이름이나 구현에 포함해서는 안 된다.
- **FR-002**: 로컬 알림에 사용하는 사용자 표시 문구와 식별자 형식은 상위 계층 한 곳에서만
  정의되어야 한다.
- **FR-003**: 각 소스 파일은 파일 밖에서 참조되는 최상위 타입을 하나만 정의해야 하며 파일
  이름이 그 타입 이름과 일치해야 한다.
- **FR-004**: 생성 결과를 표현하는 공개 타입과 계약은 Domain·Data·Composition에서 동일한
  단일 어휘를 사용해야 한다.
- **FR-005**: 공개 타입 이름은 소속 모듈과 관심사 폴더가 이미 제공하는 문맥을 반복해서는
  안 된다.
- **FR-006**: 스트림을 반환하는 관찰 UseCase는 1회 조회 UseCase와 이름으로 구분되어야 한다.
- **FR-007**: 하나의 UseCase 계약은 그 이름이 설명하는 책임만 제공해야 하며, 이름이 설명하지
  않는 연산은 별도 계약으로 분리해야 한다.
- **FR-008**: 의존성 그래프 조립 타입의 생성자는 네트워크 호출, 전역 상태 쓰기, 무기한 백그라운드
  작업 시작을 수행해서는 안 된다.
- **FR-009**: 조립 타입은 부작용을 시작하는 명시적 실행 진입점을 제공해야 하며, 그 진입점이
  시작한 작업은 취소 가능해야 한다.
- **FR-010**: production 공개 API는 테스트 지원만을 목적으로 하는 연산을 포함해서는 안 된다.
- **FR-011**: Composition의 공개 API는 Infrastructure 구체 타입을 노출해서는 안 된다.
- **FR-012**: 형태 폴더에는 그 폴더의 어휘가 규정한 종류의 선언만 두어야 하며, 어휘 표에 없는
  형태 폴더를 추가할 때는 같은 변경에서 어휘 표를 갱신해야 한다.
- **FR-013**: production 참조가 0인 공개 선언과 소비되지 않는 delegate 출력은 제거되어야 한다.
- **FR-014**: 본문이 동일하고 입력 상수만 다른 테스트는 검증 조합을 유지한 채 하나의
  파라미터화 테스트로 합쳐야 한다.
- **FR-015**: 대상 값을 한 번도 설정하지 않고 기본값만 확인하는 테스트는 제거해야 한다.
- **FR-016**: `InfrastructurePushMessaging`은 다른 Infrastructure 기술 패키지와 동일한 구성의
  테스트 target을 가져야 하며, 프로젝트 테스트 실행에 포함되어야 한다.
- **FR-017**: 계층 간 값 변환(권한 결과 매핑, payload 변환)은 각 입력이 대응 출력으로 변환되는지
  검증하는 테스트를 가져야 한다.
- **FR-018**: 이 기능의 모든 변경은 최종 사용자에게 관찰되는 동작을 바꾸어서는 안 되며,
  변경 전 통과하던 테스트는 변경 후에도 통과해야 한다.
- **FR-019**: 프로젝트가 소유한 enum에 대한 `switch`는 새 케이스 추가 시 컴파일러 경고를 얻을 수
  있어야 하며, 라이브러리 non-frozen enum 전용 처리를 적용해서는 안 된다.

### 핵심 엔터티

이 기능은 새 데이터를 도입하지 않는다. 아래는 이름이 바뀌는 기존 개념과 그 소유 경계다.

- **생성 결과**: 특정 학습 프로젝트의 학습 세트 생성이 완료 또는 실패했다는 사실. 프로젝트
  식별자와 완료·실패 상태를 갖는다. Domain 모델, Data 전송 모델, 두 경계를 잇는 변환이 각각
  존재하며 현재 서로 다른 어휘를 쓴다.
- **생성 결과 관찰 계약**: 생성 결과가 도착할 때마다 이를 전달하는 무한 수명 계약. 1회 조회
  계약과 수명이 다르며 이름에서 구분되어야 한다.
- **리마인드 등록 대상**: 사용자가 알림 수신을 수락한 프로젝트 식별자 집합. 생성 결과가 도착하면
  이 집합과 대조해 발송 여부를 결정한다.
- **알림 권한 결과**: 허용, 방금 거부, 이미 거부 세 상태. Infrastructure와 Domain이 각각 자신의
  타입으로 소유하며 경계에서 변환된다.
- **로컬 알림 요청**: 알림 식별자와 표시 문구를 담아 기술 계층에 전달하는 값. 이 기능에서 새로
  분리되는 경계 값이다.

## 가정

기능 설명이 정하지 않은 항목에 대해 선택한 기본값이다. 굵게 표시한 세 항목은
`/speckit-clarify`에서 우선 재검토할 후보다.

- **기준선**: 현재 작업 트리 상태(미커밋 15건 포함)를 리팩터링 기준선으로 삼는다. 커밋된
  HEAD는 자기 일관적이지만 작업 트리가 더 진행된 상태이며, 그중 로컬 알림 클라이언트 이름
  변경은 이 기능이 지향하는 방향과 이미 일치한다. 이 미커밋 묶음을 이 기능의 첫 커밋으로
  정리한 뒤 시나리오를 시작한다.
- **리마인드 정책의 소유 경계**: 생성 결과 판정과 발송 여부 결정 로직은 현재 위치(Composition)에
  유지하고, 그 판단 근거를 PR과 세션 지식 기록에 남긴다. 이 정책을 Domain UseCase로 올리는
  안은 범위가 크게 늘고 동작 무변경 보장이 어려워지므로 이번 범위에서 제외한다.
- **관찰 UseCase 이름 복원 범위**: 조회·관찰 구분을 이름에 되살리는 변경은 이번 기능이 다루는
  생성 결과 계열에만 적용한다. 같은 문제를 가진 인증 결과 계열은 별도 기능으로 분리한다.
- **Home 목록 갱신 경로**: 등록 완료 트리거와 생성 완료 트리거 두 경로를 모두 유지한다.
  하나로 합치면 갱신 시점이 바뀌어 동작 무변경 원칙에 어긋나므로, 대신 두 트리거가 겹칠 때의
  동작을 고정하는 테스트를 추가한다.
- **알림 관심사의 위치**: 알림 권한 관련 계약과 모델은 별도 Domain target으로 분리하지 않고
  현재 관심사 안에서 폴더 배치만 일관되게 정리한다. target 분리는 알림 관련 UseCase가 하나 더
  늘어날 때 재검토한다.
- **기술 패키지 분리**: 원격 푸시와 로컬 알림은 같은 target 안에서 하위 폴더로 분리하고,
  target 자체는 쪼개지 않는다. 링크 비용이 실제 문제로 관측될 때 승격한다.
- **검증 수단**: 저장소가 이미 제공하는 build·test 실행기와 pre-commit 검증을 사용하며 새로운
  검증 도구를 도입하지 않는다.
- **외부 계약**: 서버가 보내는 push payload의 키와 값 형식은 변경하지 않는다. 이름 변경은
  프로젝트 내부 타입에만 적용한다.
- **동작 무변경의 범위**: 사용자에게 관찰되는 화면 전이, 알림 발송 시점과 문구 내용은
  변경하지 않는다. 알림 식별자 문자열의 생성 위치는 바뀌지만 형식은 보존한다.
