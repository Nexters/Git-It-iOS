**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/async-stream-redesign`

**브랜치 상태**: `생성`

**생성일**: 2026-09-15

**상태**: 초안

**입력**: 사용자 설명: "docs/review/async-stream-redesign-requirements.md 의 요구사항을 기능 명세로 정의한다. 프로덕션에서 이벤트를 내지 않는 Apple 자격 증명 변경 관측 파이프라인을 제거하고, 기기 토큰 갱신 신호를 콜백으로 대체하며, 퀴즈 생성 상태를 구독 시점과 무관하게 최신 상태를 먼저 전달하는 단일 관측 대상으로 통합한다. 또한 스트림 구독 해제 시 구독 레지스트리에서 제거되도록 보장한다."

**근거 문서**: [AsyncStream 재설계 요구사항](../../docs/review/async-stream-redesign-requirements.md)

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 구독 시점과 무관한 생성 상태 관측 (우선순위: P1)

학습 세트 생성 결과는 서버 푸시로 도착한다. 현재는 각 화면이 화면 진입 시점에 이벤트 구독을 시작하므로, 그 이전에 도착한 결과는 해당 화면에 전달되지 않는다. 생성 상태를 최신값을 보유하는 단일 관측 대상으로 바꿔, 언제 관측을 시작하든 현재 상태를 먼저 받고 이후 변경을 이어서 받도록 한다.

**주요 행위자**: 최종 사용자 (생성 완료를 기다리는 학습자), 개발자

**우선순위 이유**: 사용자가 실제로 겪는 결함이다. 앱이 백그라운드에 있거나 다른 화면에 있는 동안 생성이 완료되면 홈 화면과 진행 화면이 완료를 반영하지 못한다. 현재는 이를 메우려고 두 개의 별도 로컬 저장소가 존재하며, 그 두 저장소와 푸시 이벤트 사이의 정합성을 보장하는 지점이 없다.

**독립 테스트**: 생성 완료가 관측 시작보다 먼저 발생한 상황을 구성하고, 이후 관측을 시작한 관측자가 완료 상태를 받는지 확인해 검증할 수 있다. 이 시나리오만 구현해도 사용자가 완료를 놓치는 결함이 해소된다.

**수용 시나리오**:

1. **전제** 생성 요청이 진행 중이고 완료 결과가 이미 도착한 상태, **실행** 새 관측자가 생성 상태 관측을 시작, **결과** 관측자는 첫 값으로 완료 상태를 받는다.
2. **전제** 생성 요청이 진행 중이고 아직 결과가 없는 상태, **실행** 새 관측자가 관측을 시작한 뒤 완료 결과가 도착, **결과** 관측자는 첫 값으로 진행 중 상태를, 이어서 완료 상태를 받는다.
3. **전제** 홈 화면에서 벗어나 있는 동안 생성이 완료됨, **실행** 홈 화면에 다시 진입, **결과** 목록이 완료를 반영한다.
4. **전제** 생성 요청을 보내기 전, **실행** 요청을 보내고 결과를 기다림, **결과** 요청 이전에 미리 관측을 시작해 두지 않아도 결과를 받는다.
5. **전제** 관측자가 여럿인 상태, **실행** 결과가 한 번 도착, **결과** 모든 관측자가 같은 상태를 받는다.

### 시나리오 2 - 동작하지 않는 자격 증명 관측 경로 제거 (우선순위: P2)

Apple 자격 증명 변경을 관측하는 경로는 프로덕션에서 값을 전달하는 진입점이 없어 한 번도 동작하지 않는다. 그럼에도 Infrastructure·Domain·Composition·App 네 패키지에 걸쳐 유지되고 있다. 이 경로를 제거하고, 그 경로가 담당한다고 기술되어 있던 재인증 필요 판정을 실제로 동작하는 방식으로 대체한다.

**주요 행위자**: 개발자, 최종 사용자 (Apple 계정 인증이 취소된 사용자)

**우선순위 이유**: 동작하지 않는 코드가 네 패키지에 걸쳐 있어 모든 인증 관련 변경의 검토 범위를 부풀린다. 동시에 "자격 증명이 취소되면 세션을 정리한다"는 보장이 실제로는 없는 상태이므로, 제거만 하고 대체하지 않으면 명시된 동작이 여전히 없는 채로 남는다.

**독립 테스트**: 제거 후 인증 관련 테스트가 모두 통과하고, 자격 증명이 재인증 필요 상태일 때 세션이 정리된다는 보장이 대체 경로의 테스트로 존재하는지 확인해 검증한다.

**수용 시나리오**:

1. **전제** 앱이 실행 중이고 사용자의 Apple 자격 증명이 외부에서 취소됨, **실행** 앱이 다시 활성 상태가 됨, **결과** 저장된 세션이 정리되고 사용자는 재인증이 필요한 상태가 된다.
2. **전제** 자격 증명이 유효함, **실행** 앱이 다시 활성 상태가 됨, **결과** 세션이 유지되고 화면 흐름이 바뀌지 않는다.
3. **전제** 자격 증명 상태를 일시적으로 확인할 수 없음, **실행** 앱이 다시 활성 상태가 됨, **결과** 세션을 정리하지 않는다.

---

### 시나리오 3 - 기기 토큰 갱신 신호 전달 방식 정정 (우선순위: P3)

기기 푸시 토큰 갱신은 값을 싣지 않는 신호이며 앱 수명 동안 드물게 발생한다. 현재는 이를 값 없는 연속 스트림으로 표현하고, 주입이 누락돼도 조용히 동작하는 기본값을 갖고 있다.

**주요 행위자**: 개발자

**우선순위 이유**: 단독으로 적용 가능하고 범위가 좁다. 주입 누락이 런타임에 조용히 무시되는 현재 형태는 기기 등록 실패를 감추는 경로이기도 하다.

**독립 테스트**: 토큰 갱신이 발생했을 때 기기 재등록이 일어나는지, 그리고 의존성을 주입하지 않으면 컴파일이 실패하는지로 검증한다.

**수용 시나리오**:

1. **전제** 앱이 실행 중, **실행** 푸시 토큰이 갱신됨, **결과** 기기 재등록이 수행된다.
2. **전제** 토큰 갱신 전달 수단을 주입하지 않고 화면 상태 타입을 구성하려 함, **실행** 빌드, **결과** 컴파일이 실패한다.

---

### 예외·경계 사례

- 관측을 시작한 직후 취소하면 어떤 결과가 발생하는가 — 관측 등록이 해제되고 이후 값 전달 대상에서 제외되어야 한다.
- 같은 관측 대상을 반복해서 구독하고 해제하면 어떤 결과가 발생하는가 — 내부 구독 목록이 누적되지 않아야 한다.
- 생성 요청이 만료 시간을 넘겨도 결과가 오지 않으면 어떤 결과가 발생하는가 — 기존 만료 처리 동작이 유지되어야 한다.
- 앱이 종료된 뒤 다시 실행되면 진행 중이던 생성 상태는 어떻게 되는가 — 기존과 동일하게 복원되어야 한다.
- 계정 삭제로 로컬 상태가 초기화되면 생성 상태는 어떻게 되는가 — 초기화되어야 한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 생성 상태를 관측하는 대상은 관측 시작 시 현재 상태를 먼저 1회 전달하고, 이어서 이후의 변경을 전달해야 한다.
- **FR-002**: 생성 상태는 하나의 정본만 존재해야 하며, 진행 중 정보와 결과 정보가 분리된 저장소로 나뉘어 존재해서는 안 된다.
- **FR-003**: 관측자는 관측 시작 순서와 무관하게 동일한 생성 상태를 얻어야 한다. 정확성을 위해 특정 작업보다 먼저 관측을 시작해야 하는 호출 순서 제약이 남아 있어서는 안 된다.
- **FR-004**: 생성 상태 관측 계약은 Domain이 소유해야 한다.
- **FR-005**: 프로덕션 실행 경로에서 값을 전달하는 진입점이 없는 관측 경로를 유지해서는 안 된다.
- **FR-006**: Apple 자격 증명이 재인증 필요 상태일 때 저장된 세션을 정리하는 동작은 앱이 활성 상태로 전환되는 시점에 수행되어야 한다.
- **FR-007**: 자격 증명 상태를 일시적으로 확인할 수 없는 경우 세션을 정리해서는 안 된다.
- **FR-008**: 기기 푸시 토큰 갱신은 값 없는 연속 스트림이 아니라 갱신 시점을 통지하는 수단으로 전달되어야 한다.
- **FR-009**: 기기 토큰 갱신 전달 수단은 필수 의존성이어야 하며, 주입 누락이 런타임에 무시되는 기본값을 가져서는 안 된다.
- **FR-010**: 값을 여러 관측자에게 전달하는 모든 타입은 관측 종료 시 자신의 관측자 목록에서 해당 관측을 제거해야 한다.
- **FR-011**: 값이 패키지 경계를 넘을 때 변환이 필요 없는 구간에서 전달 수단을 다시 감싸서는 안 된다.
- **FR-012**: 저장소 호출 결과를 변환 없이 그대로 반환하기만 하는 Domain 계층을 생성 상태 관측 경로에 두어서는 안 된다.

### 핵심 엔터티

- **생성 상태**: 특정 학습 프로젝트의 생성 요청이 현재 어떤 단계에 있는지를 나타내는 값. 요청 대상 식별자, 요청 시각, 진행 중·완료·실패 구분을 포함한다. 관측 대상의 정본이며 앱 재실행 후에도 복원된다.
- **생성 상태 관측 대상**: 생성 상태의 최신값을 보유하고, 관측자에게 현재 상태와 이후 변경을 전달하는 대상. 관측자 수와 무관하게 동일한 값을 전달한다.
- **자격 증명 상태**: Apple 계정 인증이 유효한지, 재인증이 필요한지, 일시적으로 확인 불가한지를 구분하는 값.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 생성 완료가 관측 시작보다 먼저 발생한 경우에도 관측자가 완료 상태를 받는다는 것이 자동화 테스트로 증명된다.
- **SC-002**: 생성 상태를 보관하는 로컬 저장소가 1개다. 변경 전 2개에서 줄어든다.
- **SC-003**: 프로덕션 코드에서 관측자에게 값을 전달하는 진입점 중 실제 호출 경로가 없는 것이 0개다.
- **SC-004**: 생성 상태 관측 경로에서 값이 거치는 변환 계층 수가 변경 전보다 줄어든다.
- **SC-005**: 관측을 반복 등록·해제한 뒤 내부 관측자 목록의 크기가 증가하지 않는다는 것이 자동화 테스트로 증명된다.
- **SC-006**: 변경 전 인증·생성 흐름 테스트가 보장하던 항목이 변경 후에도 모두 통과한다. 보장 항목 수가 줄어들지 않는다.
- **SC-007**: 프로젝트 등록, 홈 목록 갱신, 생성 완료 리마인드 알림 세 흐름이 변경 후에도 동일하게 동작한다.

## 가정

- 서버 푸시 페이로드의 스키마는 변경하지 않는다. 생성 결과 통지는 현재와 동일한 형태로 도착한다.
- Domain↔Data 경계 구조(Domain 계약을 Composition Adapter가 구현하고 Data API에 위임)는 현행을 유지한다. 이 명세는 그 경계를 바꾸지 않는다.
- Feature는 단일 target을 유지한다.
- 생성 상태의 영속 위치는 현재와 같이 앱과 확장 프로그램이 공유하는 로컬 저장소를 사용한다.
- 앱이 활성 상태로 전환되는 시점을 감지하는 기존 수단을 재사용한다. 새로운 생명주기 감지 수단을 도입하지 않는다.
- 생성 대기 시간 정책과 만료 기준의 값 자체는 변경하지 않는다. 소유 위치만 이 명세의 범위에 포함될 수 있다.
- 로컬 알림 문구와 리마인드 정책의 소유 위치 정리는 이 명세의 범위가 아니다. 별도 요구사항 문서가 소유한다.
