# 기능 명세: 관심사별 Domain UseCase 재설계와 호출부 전환

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/domain-usecase-redesign`

**브랜치 상태**: `생성`

**생성일**: 2026-09-18

**상태**: 초안

**입력**: 사용자 설명: "docs/review/domain-usecase-redesign.md 의 결정 1–27에 따라 Domain UseCase를 관심사별 7개 UseCase(Account, UserInfo, AppSetting, ExternalRepository, QuizDetail, Project, ProjectGeneration)와 관심사별 Domain 타깃 + DomainIdentifier 기반 타깃으로 재설계하고, Data 요청 인증 정보(RequestCredentialProvider), Composition, Feature/App 호출부를 새 API로 전환한다."

## 배경

설계 근거는 [Domain UseCase 재설계 문서](../../docs/review/domain-usecase-redesign.md)(이하 "재설계 문서")이며,
결정 1–27과 공통 API 규칙 R1–R11, [기존 기능 대응표](../../docs/review/domain-usecase-redesign.md#기존-기능-대응표)가
이 명세의 기준입니다. 명세 작성 시점(`760e1e3`)에 관찰한 근거는 다음과 같습니다.

- Domain에는 UseCase 프로토콜 20개가 `DomainAuthentication`·`DomainLearningProject`·`DomainMember`
  세 타깃에 흩어져 있고, 같은 관심사의 동작이 여러 UseCase와 App·Composition·Feature 코드로 나뉘어 있습니다
  (예: 생성 대기 해제 타이머는 `AppRootFeature`, 약관 동의 판정은 `LegalAgreementFeature`).
- Home과 프로젝트 목록 화면이 목록을 각자 조회해 서로 다른 상태를 보여줄 수 있고, 퀴즈를 마친 뒤 목록을
  갱신하지 않아 Home의 "이어 학습"이 이미 끝낸 세트를 다시 열 수 있습니다.
- 목록의 생성 중 필터와 Home 생성 배너가 서로 다른 기준을 씁니다. 생성이 실패해도 준비 시각까지
  "생성 중"으로 보입니다.
- 메인 앱은 서버 요청 토큰을 Composition이 저장소에서 직접 읽고 만료를 확인하지 않습니다.
  `RefreshSession`은 소비처가 없고 어댑터가 항상 실패하는 미구현 상태입니다.
- Domain 공개 API에 `Session`, `Tokens` 같은 구현 수단 이름과 `Bool`·`String` 반환, 저장소 연산 이름이 섞여 있습니다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 관심사별 UseCase와 타깃으로 Domain API 일원화 (우선순위: P1)

개발자는 기능 하나를 구현할 때 관심사 이름 하나로 UseCase와 모델을 찾고, 같은 규칙(식별자·입력 모델·결과 모델·
오류·스트림)을 따르는 API로 호출합니다. 현재 제공되는 모든 동작은 새 API에서 빠짐없이 제공됩니다.

**주요 행위자**: 개발자 (Feature·Composition·App 구현자, 코드 리뷰어)

**우선순위 이유**: 나머지 모든 시나리오가 새 UseCase와 타깃 구성 위에서 동작합니다.

**독립 테스트**: 각 관심사 타깃의 UseCase 단위 테스트와, 기존 기능 대응표의 모든 행이 새 API 호출로 대체되었는지
대응표 대조로 검증합니다.

**수용 시나리오**:

1. **전제** Domain 패키지, **실행** 공개 UseCase 프로토콜을 나열, **결과** `AccountUseCase`, `UserInfoUseCase`,
   `AppSettingUseCase`, `ExternalRepositoryUseCase`, `QuizDetailUseCase`, `ProjectUseCase`,
   `ProjectGenerationUseCase` 7개만 존재한다.
2. **전제** 관심사 타깃 7개와 `DomainIdentifier`, **실행** 타깃 의존성을 확인, **결과** 관심사 타깃은
   `DomainIdentifier` 외 다른 Domain 타깃에 의존하지 않고, `DomainIdentifier`는 식별자 `typealias`만 가진다.
3. **전제** 재설계 문서의 기존 기능 대응표, **실행** 각 행의 현재 동작을 호출하던 코드를 확인, **결과** 모든 호출부가
   대응표의 새 API 또는 내부 책임으로 대체되었고, 대체된 기존 UseCase·계약·모델은 제거되었다.

---

### 시나리오 2 - 모든 화면이 같은 프로젝트 목록을 보여준다 (우선순위: P2)

학습자는 Home과 프로젝트 목록 화면에서 같은 목록을 봅니다. 생성 중인 프로젝트는 준비될 때까지 보이지 않고,
준비되거나 삭제되거나 퀴즈를 마치면 두 화면이 함께 바뀝니다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 현재 화면 간 불일치와 "이어 학습"이 끝낸 세트를 여는 결함을 해소합니다.

**독립 테스트**: `ProjectUseCase` 테스트에서 목록 구독자 둘이 같은 값을 받는지, 생성 중 식별자 필터·준비 완료 시
갱신·삭제 반영·로그아웃 정리를 검증하고, Feature 테스트에서 퀴즈 닫기 시 목록·상세 갱신 요청을 검증합니다.

**수용 시나리오**:

1. **전제** Home과 프로젝트 목록이 모두 목록을 구독, **실행** 한 화면에서 새로고침, **결과** 두 화면이 같은 목록을 받는다.
2. **전제** 생성 요청이 진행 중 또는 준비 중, **실행** 목록을 구독, **결과** 해당 프로젝트는 목록에 없다.
3. **전제** 준비 중이던 프로젝트, **실행** 준비 시각이 지남, **결과** 목록이 서버에서 다시 받아지고 새 프로젝트가 나타난다.
4. **전제** 퀴즈를 풀던 학습자, **실행** 퀴즈를 닫음, **결과** 목록이 첫 페이지부터 다시 받아지고, 열려 있던 상세 화면이
   다시 조회되며, 답안 제출마다 상세를 다시 조회하지 않는다.
5. **전제** 프로젝트 상세, **실행** 프로젝트 삭제 성공, **결과** 모든 목록 구독 화면에서 그 프로젝트가 사라진다.

---

### 시나리오 3 - 생성 요청과 상태가 한 기준으로 동작한다 (우선순위: P3)

학습자는 앱 또는 공유 확장에서 생성을 요청하고, Home 배너와 목록은 같은 준비 기준으로 동작합니다. 완료 시 알림을
받고, 실패하면 준비 시각을 기다리지 않고 바로 실패 알림을 받습니다.

**주요 행위자**: 최종 사용자(학습자)

**우선순위 이유**: 목록과 배너의 기준 불일치, 실패가 "생성 중"으로 남는 동작을 해소합니다.

**독립 테스트**: `ProjectGenerationUseCase` 테스트에서 단계 전이(`inProgress`→`preparing`→`ready`, `failed`),
중복 요청 거부, 완료·실패 알림 예약, 보관 기한 정리, 로그아웃 정리를 시계 주입으로 검증합니다.

**수용 시나리오**:

1. **전제** 같은 저장소 주소의 요청이 진행 중, **실행** 다시 요청, **결과** 서버 요청 없이 중복 요청 오류가 발생한다.
2. **전제** 요청 성공, **실행** 서버 생성 완료 후 요청 시각으로부터 300초 전, **결과** 단계는 `preparing`이고 배너는 켜져 있다.
3. **전제** `preparing`, **실행** 300초 경과, **결과** 앱 코드의 타이머 없이 단계가 `ready`로 방출되고 배너가 꺼진다.
4. **전제** 진행 중 요청, **실행** 서버가 실패를 알림, **결과** 즉시 `failed`로 방출되고 실패 알림이 예약되며 배너가 꺼진다.
5. **전제** 공유 확장, **실행** 로그인 사용 가능 상태에서 생성 요청, **결과** 요청과 알림 등록만 수행하고 상태 구독·타이머·
   알림 설정 시트는 실행하지 않는다.
6. **전제** 앱 시작, **실행** 보관 기한(3600초)이 지난 완료·실패 기록이 있음, **결과** 초기화 시 제거된다.

---

### 시나리오 4 - 로그인 무효와 로그아웃이 모든 관심사에 일관되게 반영된다 (우선순위: P4)

학습자의 접근 토큰이 만료되었거나 서버가 요청을 인증 실패(401)로 거부하면 로그인 정보가 지워지고 로그아웃 상태가
됩니다. 로그아웃·탈퇴·로그인 무효 시 프로젝트 목록과 생성 요청 상태가 스스로 정리됩니다.

**주요 행위자**: 최종 사용자(학습자), 개발자

**우선순위 이유**: 현재 메인 앱은 만료 토큰으로 계속 요청하고, 로그아웃 시 생성 기록이 남습니다.

**독립 테스트**: Data 요청 인증 정보 테스트(만료·401·로그인 정보 없음), `AccountUseCase` 테스트(`.unknown` 초기 상태,
무효 신호 처리), `ProjectUseCase`·`ProjectGenerationUseCase`의 로그아웃 신호 정리 테스트로 검증합니다.

**수용 시나리오**:

1. **전제** 앱 실행 직후 로그인 복원 전, **실행** 로그인 상태를 구독, **결과** 첫 값은 `.unknown`이고 로그아웃 정리가 일어나지 않는다.
2. **전제** 접근 토큰 만료, **실행** 서버 요청, **결과** 요청을 보내지 않고 로그인 정보를 지우며, 계정 상태가 `.signedOut`이 되고
   공유 로그인 표시가 로그아웃으로 바뀐다. 서버 로그아웃은 요청하지 않는다.
3. **전제** 유효한 토큰, **실행** 서버가 401 응답, **결과** 재요청 없이 인증 오류로 끝나고 2와 같은 정리가 일어난다.
4. **전제** 로그인 상태에서 생성 요청과 목록이 있음, **실행** 로그아웃 또는 탈퇴, **결과** 목록과 생성 요청 상태가 비워진다.
5. **전제** 공유 확장, **실행** 접근 토큰이 만료된 상태에서 열림, **결과** 로그인이 필요하다고 판정하고 토큰 갱신을 시도하지 않는다.

---

### 시나리오 5 - 설정·회원 정보·퀴즈 동작이 새 API로 동일하게 동작한다 (우선순위: P5)

학습자는 알림 권한 확인·요청, 기기 등록, 큐레이션·포지션·경력 변경, 퀴즈 세트 조회·채점·북마크, 외부 저장소 조회,
약관 동의를 현재와 같은 결과로 사용합니다.

**주요 행위자**: 최종 사용자(학습자), 개발자

**우선순위 이유**: 동작 변경 없이 API만 바뀌는 영역이며 회귀 방지가 목적입니다.

**독립 테스트**: 각 UseCase 단위 테스트와 해당 Feature 테스트가 전환 전과 같은 결과를 검증합니다.

**수용 시나리오**:

1. **전제** 알림 권한 거부 상태, **실행** 설정의 알림 항목 선택, **결과** 시스템 설정 이동을 안내한다(현재와 동일).
2. **전제** 서술형 답안이 공백뿐, **실행** 채점 요청, **결과** 서버 요청 없이 입력 오류가 발생한다.
3. **전제** 설정 화면, **실행** 상세 정보와 큐레이션을 함께 조회, **결과** 서버 요청은 한 번만 보낸다.
4. **전제** 필수 약관 버전이 바뀜, **실행** 약관 동의 상태 조회, **결과** 동의가 충족되지 않았다고 판정한다.

### 예외·경계 사례

- 목록 필터로 한 페이지의 항목 수가 줄어도 다음 페이지 존재 여부는 서버 응답 기준을 따른다.
- 목록 새로고침·다음 페이지 요청이 실패하면 동작이 오류를 던지고 스트림은 마지막으로 성공한 목록을 유지한다.
- 2페이지 이상 불러온 목록에서 퀴즈를 닫으면 목록은 첫 페이지로 교체된다(수용한 동작).
- 서버가 늦게 끝나 준비 시각이 이미 지났으면 `inProgress`에서 `ready`로 바로 넘어간다.
- 실패한 프로젝트는 서버 목록 응답에서 제외되므로 클라이언트는 실패 단계를 필터링하지 않는다.
- 로그인 정보가 이미 지워진 상태에서 401이 다시 오면 무효 신호를 중복 방출하지 않는다.
- 알림 권한이 없어도 기기 등록은 토큰 없이 수행한다.
- 공유 확장은 로그아웃 신호·로그인 무효 신호에 빈 스트림을 연결해 정리를 수행하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

**구조**

- **FR-001**: Domain은 재설계 문서의 관심사별 UseCase 프로토콜 7개와 각 구현 하나만 공개해야 한다. 현재 UseCase 프로토콜 20개와
  그 구현은 제거되어야 한다.
- **FR-002**: Domain은 관심사마다 타깃 하나(`DomainAccount`, `DomainUserInfo`, `DomainAppSetting`, `DomainExternalRepository`,
  `DomainQuizDetail`, `DomainProject`, `DomainProjectGeneration`)와 기반 타깃 `DomainIdentifier`로 구성되어야 하며, 기존 세 타깃은
  제거되어야 한다.
- **FR-003**: 관심사 타깃은 `DomainIdentifier` 외 다른 Domain 타깃에 의존하지 않아야 한다. `DomainIdentifier`는 둘 이상의 관심사가
  공개 API에 쓰는 식별자 `typealias`(`ProjectID`, `QuizSetID`, `QuizID`, `ExternalRepositoryURL`)만 가져야 한다.
- **FR-004**: 각 관심사 공개 API는 재설계 문서의 공통 API 규칙 R1–R11(식별자 타입, 입력 모델, 결과 모델, 관심사 오류, 첫 값을
  현재 상태로 보내는 스트림, 저장소 연산·구현 수단 이름 배제, UseCase 간 직접 의존 금지)을 따라야 한다.
- **FR-005**: UseCase는 다른 UseCase를 생성자로 받지 않아야 하며, 다른 관심사의 상태는 Composition이 연결한 스트림 클로저로만
  받아야 한다.
- **FR-006**: 재설계 문서 기존 기능 대응표의 모든 행은 새 API 또는 UseCase 내부 책임으로 대체되어야 하고, App·Composition·Feature의
  호출부는 새 API를 사용해야 한다.
- **FR-007**: 저장소 계약이 여러 관심사에 걸치는 경우(`MemberRepository`, `LearningProjectRepository` 등) 관심사 타깃마다 필요한
  동작만 가진 계약으로 나누어야 하며, Data·Composition 구현이 새 계약을 충족해야 한다.
- **FR-008**: 아키텍처 문서와 Domain 패키지 규칙 문서는 새 타깃 구성과 `DomainIdentifier` 예외 규칙을 반영해야 하며, 패키지 의존성
  검사 규칙이 있다면 같은 구성을 검사해야 한다.

**Account**

- **FR-010**: `AccountUseCase`는 로그인, 로그아웃, 로그인 상태 구독, 로그인 복원, 로그인 유효성 확인, 공유 확장용 로그인 사용 가능
  여부, 약관 동의 상태 조회·동의, 계정 탈퇴를 제공해야 한다.
- **FR-011**: 로그인 상태 스트림은 로그인 복원이 끝나기 전 `.unknown`을 보내고, 로그인 상태에는 계정 식별자만 담아야 한다.
  큐레이션 필요 여부는 로그인·복원 결과에만 담아야 한다.
- **FR-012**: 로그인 사용 가능 여부는 공유 로그인 표시 없음 → 앱 실행 필요, 로그아웃 표시 또는 로그인 기록 없음 또는 접근 토큰 만료 →
  로그인 필요, 그 외 → 로그인됨으로 판정하고 토큰 값을 반환하지 않아야 한다.
- **FR-013**: 로그인 무효 신호를 받으면 공유 로그인 표시를 로그아웃으로 바꾸고 `.signedOut`을 방출해야 하며, 서버 로그아웃은 요청하지
  않아야 한다.
- **FR-014**: 약관 동의 충족 판정(필수 문서의 식별자·버전 일치)은 Account가 수행해야 하며, 탈퇴 성공 시 동의 기록을 지우고
  `.signedOut`을 방출해야 한다.
- **FR-015**: 세션·토큰 관련 타입(`SessionTokens`, `SessionRecord`, `AuthenticationGrant`, `LocalOnboardingState`)은 Domain 공개 API에서
  제외되어야 하고, `RefreshSession` 관련 UseCase·계약 동작·모델과 `SingleFlightCoordinator`는 제거되어야 한다.

**요청 인증 정보 (Data)**

- **FR-020**: Data는 서버 요청 인증 정보를 공급하는 단일 구성요소를 제공하고, 앱과 공유 확장의 모든 인증 요청이 이를 사용해야 한다.
  Composition이 저장소에서 토큰을 직접 읽는 경로는 제거되어야 한다.
- **FR-021**: 저장된 접근 토큰이 만료되었으면 요청을 보내지 않고 로그인 정보를 지운 뒤 로그인 무효 신호를 한 번 방출하고 인증 오류로
  끝나야 한다. 로그인 정보가 없으면 요청을 보내지 않고 인증 오류로 끝나야 한다.
- **FR-022**: 서버가 401을 돌려주면 재요청하지 않고 로그인 정보를 지운 뒤 로그인 무효 신호를 방출하고 인증 오류로 끝나야 한다.
- **FR-023**: 토큰 갱신은 수행하지 않아야 한다.

**UserInfo · AppSetting · ExternalRepository · QuizDetail**

- **FR-030**: `UserInfoUseCase`는 상세 정보 조회, 큐레이션(포지션+경력 한 쌍) 조회·변경, 포지션 변경, 경력 변경을 제공하고, 상세 정보와
  큐레이션을 함께 조회해도 서버 요청을 한 번만 보내며, 변경 동작을 하나의 직렬화 단위로 처리해야 한다.
- **FR-031**: `AppSettingUseCase`는 알림 권한 확인·요청(`notDetermined`/`authorized`/`denied`), 기기 등록, 기기 토큰 업데이트를 제공해야
  하며, 알림 권한이 없어도 토큰 없이 기기를 등록해야 한다.
- **FR-032**: `ExternalRepositoryUseCase`는 주소로 외부 저장소를 조회하고, 주소를 해석하지 못하면 조회 없이 형식 오류를 던져야 한다.
- **FR-033**: `QuizDetailUseCase`는 퀴즈 세트 조회, 선택형·서술형 채점, 문제 북마크 등록·해제, 북마크 목록 조회(전체 또는 프로젝트별)를
  제공하고, 채점 전 입력 검증(선택 인덱스 0 이상, 서술형 공백 제거 후 1–2000자)과 같은 문제의 북마크 변경 순서 보장을 유지해야 한다.

**Project**

- **FR-040**: `ProjectUseCase`는 목록 스트림, 새로고침, 다음 페이지 요청, 상세 조회, 삭제를 제공하고, 앱에서 인스턴스 하나를 모든 화면이
  공유해야 한다.
- **FR-041**: 목록 스트림은 구독 즉시 현재 목록(미수신 시 로드 전 빈 목록)을 보내고, 첫 구독이 첫 페이지 요청을 시작해야 한다.
  새로고침은 첫 페이지로 교체, 다음 페이지는 이어 붙여야 한다.
- **FR-042**: 목록은 생성 상태에서 받은 제외 식별자 집합(진행 중·준비 중)을 서버 재요청 없이 적용해야 하고, 집합에서 식별자가 빠지면
  새로고침해야 한다.
- **FR-043**: 삭제 성공 시 목록에서 제거해 방출하고, 로그아웃 신호 수신 시 목록과 페이지 상태를 비워야 한다.
- **FR-044**: 퀴즈를 닫을 때 화면 흐름은 목록 새로고침과 열린 상세 화면의 재조회를 요청해야 하며, 답안 제출마다 보내던 진행률 무효화
  신호는 제거되어야 한다. 앱 활성화 시 목록 새로고침은 유지되어야 한다.

**ProjectGeneration**

- **FR-050**: `ProjectGenerationUseCase`는 생성 요청과 생성 상태 스트림만 공개하고, 상태 정리와 알림 등록은 내부에서 수행해야 한다.
- **FR-051**: 요청 상태 단계는 `inProgress(readyAt)`, `preparing(readyAt)`, `ready`, `failed`이며, 준비 시각은 요청 시각 + 300초이고,
  `preparing`→`ready` 전환은 UseCase 내부 타이머로 방출해야 한다.
- **FR-052**: 같은 저장소 주소(정규화 후)의 요청이 진행 중이면 서버 요청 없이 중복 요청 오류를 던져야 한다.
- **FR-053**: 요청 성공 시 완료 알림 대상에 항상 등록하고, 완료 시 준비 시각에 완료 알림을, 실패 시 즉시 실패 알림을 예약해야 한다.
- **FR-054**: `ready`·`failed` 기록은 3600초 후 제거하고, 초기화 시 기한이 지난 기록을 정리해야 한다. 로그아웃 신호 수신 시 모든 요청
  상태와 알림 대상을 비워야 한다.
- **FR-055**: 공유 확장은 로그인 사용 가능 여부가 로그인됨일 때만 생성 요청을 호출하고, 상태 구독·결과 수신·타이머·로그아웃 정리를
  수행하지 않아야 한다.
- **FR-056**: `AppRootFeature`의 생성 대기 해제 타이머·만료 판정과 Composition의 탈퇴 시 생성 기록 정리, 공유 확장의 알림 대기열 직접
  기록은 제거되어야 한다.

### 핵심 엔터티

- **관심사 UseCase**: 한 관심사의 공개 동작 묶음. 재설계 문서 각 섹션의 프로토콜과 모델 표가 정의한다.
- **식별자**: 여러 관심사가 공유하는 `ProjectID`, `QuizSetID`, `QuizID`, `ExternalRepositoryURL`과 관심사 전용 식별자.
- **로그인 상태**: `unknown`, `signedIn(계정 식별자)`, `signedOut`.
- **프로젝트 목록**: 지금까지 받은 목록 전체, 다음 페이지 존재 여부, 로드 여부.
- **생성 요청 상태**: 저장소 주소, 프로젝트 식별자, 요청 시각, 단계. 전체 상태는 요청 목록과 목록 제외 식별자 집합.
- **요청 인증 정보**: 사용 가능(토큰) 또는 로그아웃. 토큰 값은 Data 안에서만 다룬다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: Domain의 공개 UseCase 프로토콜 수가 20개에서 7개가 되고, Domain 타깃이 재설계 문서의 8개 구성과 일치한다.
- **SC-002**: 관심사 타깃 간 import가 0건이다(`DomainIdentifier` 제외).
- **SC-003**: 재설계 문서 기존 기능 대응표의 행 100%가 새 API 호출 또는 내부 책임 테스트로 대응된다.
- **SC-004**: Domain 공개 선언 이름에 `Session`, `Token`(기기 토큰 `DeviceToken` 제외), `load`, `save`, `fetch`가 0건이다.
- **SC-005**: 시나리오 2–4의 수용 시나리오 각각에 대응하는 자동 테스트가 1개 이상 존재하고 통과한다.
- **SC-006**: 프로젝트 빌드·테스트 실행기(`build`, `compile`, `test`)가 모두 성공한다.
- **SC-007**: App·Composition·Feature 코드에서 제거된 UseCase·계약 이름(`RefreshSession`, `TrackGeneration`, `FetchLearningProjects`,
  `LearningLibrary`, `MemberAccount` 등 대응표의 현재 이름) 참조가 0건이다.

## 가정

- 서버에는 토큰 갱신 API가 없다(재설계 문서 결정 22).
- 서버 프로젝트 목록 응답은 실패한 프로젝트를 포함하지 않는다(결정 23).
- 실패 알림 문구는 기존 완료 알림과 같은 로컬 알림 방식을 사용하며, 문구는 기존 알림 문구 규칙을 따른다.
- 서버 API와 Data의 원격 요청 형식은 변경하지 않는다. 요청 인증 헤더 공급 방식과 401 처리만 바뀐다.
- 화면 UI와 디자인은 변경하지 않는다. 동작 변경은 재설계 문서 "새로 생기는 동작" 목록으로 한정한다.
- 계약 이름 `SignInRepository`·`WithdrawalRepository` 등 재설계 문서가 "이름 제안"으로 표시한 이름과 Data 구성요소의 생성자 형태는
  계획 단계에서 확정한다.
- 규모가 크므로 구현은 의존성 위상 순서(Domain → Data → Composition → Feature → App)의 논리 단위로 나누되, 공개 API 이전으로
  중간 상태가 compile되지 않는 구간은 다중 패키지 통합 단위로 묶는다.
