## 배경

프로젝트 등록 흐름과 홈 화면을 실제로 사용하며 확인된 UX 결함 8건이다.
`022-registration-flow-review-fixes`가 다룬 리뷰 리포트(BR/NR 계열)와 겹치지 않는 새 라운드이며,
대상은 사용자가 직접 관찰하는 화면 동작과 알림 타이밍이다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 링크 입력 중 키보드가 화면을 흔들지 않는다 (우선순위: P1)

사용자가 GitHub 레포지토리 링크를 붙여넣는 동안, 하단 "다음" 버튼이 키보드에 밀려 올라오지
않고 원래 위치에 남는다. 입력 필드와 키보드 밖 영역을 터치하면 키보드가 닫힌다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 등록 흐름의 첫 화면이자 모든 사용자가 반드시 통과하는 지점이다. 버튼이
키보드와 함께 튀어 오르면 오탭과 레이아웃 붕괴가 발생하고, 키보드를 닫을 수 없으면 화면
하단 내용과 버튼에 접근할 수 없다.

**독립 테스트**: 링크 입력 화면에서 필드를 포커스해 키보드를 올린 뒤 하단 버튼의 화면 내
위치가 변하지 않는지, 빈 영역 터치로 키보드가 닫히는지 확인한다. 다른 항목과 독립적으로
검증·배포할 수 있다.

**수용 시나리오**:

1. **전제** 링크 입력 화면이 표시되고 키보드가 내려가 있다, **실행** 링크 입력 필드를 탭해
   키보드를 올린다, **결과** 하단 액션 버튼의 화면 내 위치가 키보드가 없을 때와 동일하게
   유지된다.
2. **전제** 키보드가 올라온 상태다, **실행** 입력 필드와 키보드가 아닌 영역(제목, 안내 패널
   여백, 하단 여백)을 터치한다, **결과** 키보드가 닫히고 입력한 텍스트는 그대로 남는다.
3. **전제** 키보드가 올라온 상태다, **실행** "불러오기 방법" 안내 패널을 터치한다, **결과**
   키보드가 닫히고 안내 패널의 펼침·접힘 동작도 정상 수행된다.
4. **전제** 키보드가 올라온 상태다, **실행** 입력 지우기 버튼을 탭한다, **결과** 입력이
   지워지는 기존 동작이 그대로 수행된다.

### 시나리오 2 - 생성 중에는 홈에서 새 불러오기를 시작할 수 없다 (우선순위: P1)

학습 세트 생성이 진행 중인 동안 홈 화면의 불러오기 패널이 Figma `1859:21645`의 진행 중
상태로 바뀌고, 새 레포지토리 불러오기를 시작할 수 없다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 생성 중 재진입을 막지 않으면 중복 생성 요청과 결과 수신 경로 혼선이
발생한다. 사용자에게도 현재 무엇이 진행 중인지 알리는 유일한 지점이다.

**독립 테스트**: 생성을 요청하고 "홈에서 기다리기"로 홈에 복귀한 뒤, 불러오기 패널이 진행 중
표기로 바뀌고 버튼이 눌리지 않는지 확인한다. 생성 결과 도착 후 원래 상태로 복귀하는지도
같은 흐름에서 검증한다.

**수용 시나리오**:

1. **전제** 사용자가 생성을 요청하고 "홈에서 기다리기"로 홈에 복귀했다, **실행** 홈 화면을
   본다, **결과** 불러오기 패널의 버튼이 "문제 생성 중" 진행 표기(진행 인디케이터 포함)로
   바뀌고 비활성 스타일로 표시된다.
2. **전제** 불러오기 패널이 진행 중 상태다, **실행** 버튼 영역을 탭한다, **결과** 등록 화면이
   열리지 않고 아무 전환도 일어나지 않는다.
3. **전제** 불러오기 패널이 진행 중 상태다, **실행** 요청 시각으로부터 300초가 지나고 생성
   완료가 확정된다, **결과** 버튼이 "지금 불러오기" 활성 상태로 복귀하고 학습 중인 레포지토리
   목록이 갱신된다.
4. **전제** 불러오기 패널이 진행 중이고 생성 결과가 300초가 지나기 전에 도착했다, **실행** 홈
   화면을 본다, **결과** 300초가 지나기 전까지 진행 중 표기가 그대로 유지된다.
5. **전제** 불러오기 패널이 진행 중 상태다, **실행** 요청 시각으로부터 300초가 지나고 생성
   실패가 확정된다, **결과** 버튼이 활성 상태로 복귀해 사용자가 다시 시도할 수 있다.
6. **전제** 생성이 진행 중인 상태에서 사용자가 앱을 완전히 종료한다, **실행** 앱을 다시
   실행한다, **결과** 불러오기 패널이 진행 중 표기로 복원되고, 남은 최소 대기 시간과 생성 결과
   관찰이 이어진다.
7. **전제** 진행 중인 생성이 없다, **실행** 홈 화면을 본다, **결과** 불러오기 패널은 기존
   "지금 불러오기" 활성 상태를 그대로 유지한다.

### 시나리오 3 - 생성 완료 알림이 안내한 대기 시간보다 먼저 오지 않는다 (우선순위: P1)

생성 요청 후 5분이 지나기 전에는 생성 완료 로컬 알림이 발송되지 않는다. 생성 진행 화면도
같은 기준을 따라 5분이 지나기 전에는 완료로 전이하지 않고, 알림이 발송되는 바로 그 시점에
완료로 전이한다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 진행 화면이 "약 5분의 시간이 소요돼요"라고 안내한 직후 수 초 만에 완료
알림이 도착하면 안내가 거짓이 되고, 생성이 실제로 수행됐는지 신뢰를 잃는다.

**독립 테스트**: 생성 결과를 즉시 반환하도록 만든 뒤 알림 발송 시각이 요청 시각 + 5분 이후인지
확인한다. 알림 경로만 격리해 검증할 수 있다.

**수용 시나리오**:

1. **전제** 사용자가 리마인드 알림을 허용하고 생성을 요청했다, **실행** 요청 후 5분이 지나기
   전에 생성 완료 결과가 도착한다, **결과** 알림은 즉시 발송되지 않고 요청 시각으로부터 5분이
   지난 뒤에 정확히 1회 발송된다.
2. **전제** 같은 상태다, **실행** 요청 후 5분이 이미 지난 뒤에 생성 완료 결과가 도착한다,
   **결과** 알림이 추가 지연 없이 발송된다.
3. **전제** 사용자가 생성 진행 화면에 머물러 있고, 요청 후 5분이 지나기 전에 생성 완료 결과가
   도착했다, **실행** 화면을 계속 본다, **결과** 진행 화면은 완료로 전이하지 않고 진행 표시를
   유지하다가, 요청 시각으로부터 5분이 지난 시점에 즉시 완료로 전이한다.
4. **전제** 진행률 시뮬레이션이 최소 대기 시간보다 먼저 끝났다, **실행** 남은 시간 동안 화면을
   본다, **결과** 마지막 단계가 진행 중 상태로 유지되고 완료 표시나 화면 전환이 일어나지 않는다.
5. **전제** 생성 결과가 도착한 뒤 사용자가 앱을 백그라운드로 보내거나 종료한다, **실행**
   예정 시각이 된다, **결과** 알림이 예정 시각에 도착한다.
6. **전제** 진행 화면이 완료로 전이하고 알림도 발송됐다, **실행** 같은 생성 결과가 다시
   전달된다, **결과** 중복 알림이 발송되지 않는다.
7. **전제** 생성이 실패로 끝났다, **실행** 요청 후 5분이 지나기 전에 실패 결과가 도착한다,
   **결과** 완료 알림은 발송되지 않으며, 진행 화면은 최소 대기 시간이 지난 뒤 실패 화면으로
   전이한다.

### 시나리오 4 - 카드를 불러오는 동안 빈 카드 형태가 보이고 로드 후 교체된다 (우선순위: P2)

학습 중인 레포지토리를 조회하는 동안 카드 자리에 빈 카드 형태가 표시되고, 조회가 끝나면
실제 카드로 교체된다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 홈 진입 시 카드 영역이 비거나 높이가 튀면 화면 전체가 흔들린다. 빈 형태를
먼저 배치하면 최종 레이아웃과 동일한 공간이 유지된다.

**독립 테스트**: 조회를 지연시킨 상태로 홈에 진입해 카드 영역의 표시와 높이를 확인하고,
조회 완료 후 실제 카드로 교체되며 영역 높이가 변하지 않는지 확인한다.

**수용 시나리오**:

1. **전제** 학습 프로젝트 조회가 진행 중이다, **실행** 홈 화면을 본다, **결과** 카드 자리에 빈
   데크 실루엣과 로딩 인디케이터가 함께 표시된다.
2. **전제** 조회가 진행 중이다, **실행** 조회가 성공으로 끝난다, **결과** 빈 데크 실루엣이 실제
   카드 목록으로 교체되고 카드 영역의 높이가 로딩 중과 동일하게 유지된다.
3. **전제** 조회가 진행 중이다, **실행** 조회 결과가 빈 목록이다, **결과** 빈 상태 안내가
   표시된다.
4. **전제** 조회가 진행 중이다, **실행** 조회가 실패한다, **결과** 실패 안내와 다시 시도 수단이
   표시된다.

### 시나리오 5 - 첫 카드가 기준 위치에서 기울어지지 않는다 (우선순위: P2)

홈 화면 카드 목록의 첫 카드가 초기 배치에서 기울기 0으로, 원본 디자인과 같은 수직 상태로
표시된다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 첫 카드는 홈 화면에서 가장 크게 보이는 요소다. 미세하게 기울어져 있으면
정렬이 어긋나 보이지만, 기능 사용을 막지는 않는다.

**독립 테스트**: 홈 진입 직후 첫 카드의 회전각을 확인한다. 배치 각도 계산은 화면과 분리해
단위 테스트할 수 있고, 화면 결합 부분은 스크린샷으로 확인한다.

**수용 시나리오**:

1. **전제** 학습 프로젝트가 1개 이상이다, **실행** 홈 화면에 진입해 스크롤하지 않은 초기 배치를
   본다, **결과** 첫 카드의 기울기가 정확히 0이다.
2. **전제** 카드가 1장뿐이다, **실행** 홈 화면을 본다, **결과** 그 카드의 기울기가 0이다.
3. **전제** 카드 목록을 가로로 스크롤했다가 처음 위치로 되돌린다, **실행** 첫 카드가 기준
   위치로 복귀한다, **결과** 기울기가 다시 정확히 0이 된다.
4. **전제** 카드 목록을 가로로 스크롤한다, **실행** 카드가 기준 위치를 지나 이동한다, **결과**
   기울기가 스크롤 위치에 따라 끊김 없이 변하고, 두 번째 이후 카드의 기존 배치는 유지된다.

### 시나리오 6 - GitHub 앱 공유로 링크가 입력된 상태로 진입한다 (우선순위: P3)

GitHub 앱에서 레포지토리를 공유하면 Git It의 링크 입력 화면이 해당 URL이 입력된 상태로 열리고
"다음"이 즉시 실행되어 다음 단계로 이어진다.

**주요 행위자**: 최종 사용자

**우선순위 이유**: 링크를 복사해 앱을 전환하고 붙여넣는 여러 단계를 한 번의 공유로 줄인다.
기존 복사·붙여넣기 경로가 그대로 동작하므로 우선순위는 가장 낮다.

**독립 테스트**: GitHub 앱(또는 URL을 공유하는 임의의 앱)의 공유 시트에서 Git It을 선택해
링크 입력 화면이 해당 URL이 채워진 상태로 열리고 "다음"이 자동 실행되는지 확인한다.

**수용 시나리오**:

1. **전제** 사용자가 로그인 상태이고 GitHub 앱에서 레포지토리 페이지를 보고 있다, **실행**
   공유 시트에서 Git It을 선택한다, **결과** Git It이 실행되고 링크 입력 화면이 공유된 URL이
   입력된 상태로 표시된다.
2. **전제** 위와 같다, **실행** 사용자가 아무 조작도 하지 않는다, **결과** "다음"이 즉시 1회
   자동 실행되어 사용자가 직접 붙여넣고 눌렀을 때와 동일하게 레포지토리 확인 단계로 진행된다.
3. **전제** 사용자가 로그인하지 않은 상태다, **실행** 공유로 앱에 진입한다, **결과** 기존 진입
   흐름(온보딩·로그인)을 먼저 마친 뒤 링크 입력 화면이 공유된 URL이 입력된 상태로 표시되고
   "다음"이 즉시 자동 실행된다.
4. **전제** 이미 생성이 진행 중이다, **실행** 공유로 앱에 진입한다, **결과** 새 등록 화면을 열지
   않고 홈 화면의 진행 중 상태(시나리오 2)를 보여주며, 공유된 URL은 보관하지 않고 버린다.
   진행 중 상태가 해제된 뒤에도 그 URL이 자동으로 채워지지 않는다.
5. **전제** 미인증 상태로 공유 진입한 사용자가 로그인을 마치지 않고 앱을 종료한다, **실행**
   앱을 다시 실행한다, **결과** 공유된 URL은 채워지지 않고 기존 진입 흐름만 표시된다.
6. **전제** GitHub 레포지토리 링크가 아닌 URL(예: 일반 웹페이지)을 공유한다, **실행** 앱에
   진입한다, **결과** 링크 입력 화면이 해당 URL이 채워진 상태로 열리고 자동 실행된 "다음"의
   결과로 기존과 동일한 검증 실패 안내가 같은 화면에 제공된다.
7. **전제** URL이 포함되지 않은 항목(사진, 순수 텍스트)을 공유한다, **실행** 공유 시트를 연다,
   **결과** Git It이 공유 대상 목록에 나타나지 않는다.

### 예외·경계 사례

- 키보드가 올라온 상태에서 화면이 회전하거나 기기 텍스트 크기가 큰 경우, 하단 버튼과 입력
  필드가 모두 조작 가능한 상태로 남아야 한다.
- 생성 진행 중에 앱을 완전히 종료했다가 다시 실행하면 보존된 진행 중 상태를 복원한다. 종료
  중에 도착했어야 할 생성 결과는 복원 후 재개된 관찰이나 홈의 학습 프로젝트 목록으로 해소한다.
- 생성 결과를 받기 전에 사용자가 앱을 강제 종료하면 그동안은 결과를 수신하지 못해 알림이
  지연되거나 발송되지 않을 수 있다. 재실행하면 복원된 진행 중 상태로 관찰을 재개해 남은 대기
  시간에 맞춰 알림을 예약한다. 결과를 받은 뒤에는 앱 상태와 무관하게 예정 시각에 도착해야 한다.
- 진행률 시뮬레이션이 최소 대기 시간보다 최대 120초 먼저 끝날 수 있다. 이 구간에서 진행률이
  더 이상 오르지 않는 것은 결함이 아니라 의도된 동작이다.
- 카드 조회가 매우 빠르게 끝나면 빈 카드 형태가 순간적으로만 보였다가 사라질 수 있으며,
  깜빡임으로 인식될 정도의 잔상이 남지 않아야 한다.
- Git It은 URL 항목이 포함된 공유에만 노출되므로 URL 없는 공유는 정상 경로에서 도달하지
  않는다. 그럼에도 URL을 얻지 못하면 빈 링크 입력 화면을 열고 "다음"을 자동 실행하지 않는다.
  URL이 여러 개면 첫 번째만 사용한다.
- 공유 진입 후 인증을 마치지 못한 채 앱이 종료되면 URL은 버려진다. 사용자는 다시 공유하거나
  직접 붙여넣어야 한다.
- 알림 권한이 없으면 대기 시간과 무관하게 알림은 발송되지 않는다.
- 화면 폭이 달라져도 첫 카드의 기준 위치 판정이 어긋나 기울기가 0에서 벗어나지 않아야 한다.

## 요구사항 *(필수)*

### 기능 요구사항

#### 링크 입력 화면 키보드 (항목 1, 2)

- **FR-001**: 링크 입력 화면의 하단 액션 버튼은 소프트 키보드가 나타나거나 사라져도 화면 내
  위치가 변하지 않아야 한다.
- **FR-002**: 사용자는 입력 필드와 키보드가 아닌 화면 영역을 터치해 키보드를 닫을 수 있어야
  한다.
- **FR-003**: 키보드를 닫아도 입력한 링크 텍스트와 검증 상태는 그대로 유지되어야 한다.
- **FR-004**: 키보드를 닫기 위한 터치는 같은 위치의 기존 조작(안내 패널 펼치기, 입력 지우기,
  액션 버튼)을 가로채지 않아야 한다.

#### 생성 중 홈 진입점 (항목 4)

- **FR-005**: 홈 화면은 학습 세트 생성이 진행 중인지 여부를 알 수 있어야 하며, 그 상태는
  생성 요청을 제출한 시점에 시작해야 한다. 이 상태는 대상 `projectID`와 요청 시각을 포함해
  기기에 보존되어야 하며, 앱을 완전히 종료했다 다시 실행해도 복원되어 남은 최소 대기 시간과
  생성 결과 관찰이 이어져야 한다.
- **FR-006**: 생성이 진행 중인 동안 홈 화면의 불러오기 패널은 Figma `1859:21645`의 진행 중
  표기("문제 생성 중" 문구와 진행 인디케이터, 비활성 스타일)로 표시되어야 한다.
- **FR-007**: 생성이 진행 중인 동안 홈 화면에서 새 레포지토리 불러오기를 시작할 수 없어야
  하며, 동시에 진행 가능한 생성은 1건으로 제한되어야 한다.
- **FR-008**: 생성 진행 상태는 요청 시각으로부터 최소 대기 시간이 지난 시점과 생성
  결과(완료 또는 실패)가 도착한 시점 중 **나중** 시점에 해제되어야 하며, 그때 불러오기 패널이
  기본 활성 상태로 복귀해야 한다. 복원된 진행 중 상태는 결과 도착 외에, 홈의 학습 프로젝트
  목록에 해당 `projectID`가 나타난 경우에도 해제되어야 한다.
- **FR-009**: 불러오기 패널 외 홈 화면의 다른 요소는 생성 진행 여부와 무관하게 동일하게
  동작해야 한다.

#### 생성 완료 알림 타이밍 (항목 5)

- **FR-010**: 생성 완료 로컬 알림은 생성 요청 시각으로부터 최소 대기 시간이 지나기 전에는
  발송되지 않아야 하며, 앱이 포그라운드에 없더라도 `요청 시각 + 최소 대기 시간`과 생성 결과
  도착 시점 중 나중 시점에 도착해야 한다.
- **FR-011**: 최소 대기 시간은 진행 화면의 안내 문구("약 5분의 시간이 소요돼요")와 같은 고정
  300초로 한다.
- **FR-012**: 최소 대기 시간이 이미 지난 뒤 생성 결과가 도착하면 알림은 추가 지연 없이
  발송되어야 한다.
- **FR-013**: 생성 진행 화면은 최소 대기 시간이 지나기 전에는 완료로도 실패로도 전이하지
  않아야 하며, 최소 대기 시간이 지나고 생성 결과가 확정된 시점(완료의 경우 완료 알림이
  발송되는 시점과 같다)에 즉시 해당 결과 화면으로 전이해야 한다. 진행률 표시가 완료 전이보다 먼저 끝나는 경우 마지막 단계를 진행 중
  상태로 유지해야 하며, 완료로 표시하거나 화면을 전환해서는 안 된다.
- **FR-014**: 하나의 생성 요청에 대해 완료 알림은 최대 1회만 발송되어야 한다.
- **FR-015**: 생성이 실패로 끝나면 완료 알림을 발송하지 않아야 한다.
- **FR-016**: 알림 권한이 없으면 알림을 발송하지 않는 기존 동작을 유지해야 한다.

#### 홈 카드 로딩 자리표시자 (항목 7)

- **FR-017**: 학습 프로젝트 조회가 진행 중인 동안 카드 영역에는 빈 데크 실루엣과 로딩
  인디케이터가 함께 표시되어야 한다.
- **FR-018**: 조회가 완료되면 빈 데크 실루엣은 실제 카드 목록으로 교체되어야 한다.
- **FR-019**: 로딩 중 카드 영역의 높이는 실제 카드가 표시될 때의 영역 높이와 같아야 하며,
  조회 완료 후 화면 나머지 요소가 이동하지 않아야 한다.
- **FR-020**: 조회 결과가 빈 목록이거나 실패인 경우의 기존 안내는 그대로 유지되어야 한다.

#### 홈 카드 배치 (항목 3)

- **FR-021**: 홈 화면 카드 목록의 첫 카드는 스크롤하지 않은 초기 배치와 기준 위치로 복귀했을
  때 기울기가 정확히 0이어야 한다.
- **FR-022**: 카드 기울기는 가로 스크롤 위치에 따라 불연속적으로 끊기지 않고 연속적으로
  변해야 하며, 두 번째 이후 카드의 기존 배치 값은 변하지 않아야 한다.
- **FR-023**: 카드 배치 각도는 화면을 실제로 렌더링하지 않고도 자동화 테스트로 검증할 수
  있어야 한다.

#### 공유 URL 랜딩 (항목 6)

- **FR-024**: 사용자는 GitHub 앱을 포함해 URL을 공유하는 앱의 공유 시트에서 Git It을 선택할
  수 있어야 한다. Git It은 URL 항목이 포함된 공유에만 노출되어야 하며, 텍스트·이미지만 있는
  공유에는 노출되지 않아야 한다.
- **FR-025**: 공유로 전달된 URL은 링크 입력 화면의 입력값으로 채워진 상태여야 하며, 사용자가
  직접 붙여넣었을 때와 동일한 검증·진행 경로를 따라야 한다.
- **FR-025a**: 공유된 URL로 링크 입력 화면에 랜딩하면 "다음" 액션이 사용자가 누른 것과
  동일하게 즉시 1회 실행되어야 한다. 이후 진행과 실패 처리는 사용자가 직접 누른 경우와
  구분되지 않아야 하며, 자동 실행은 공유된 URL 1건당 1회만 일어나야 한다.
- **FR-026**: 공유 진입 시 사용자가 인증되지 않았다면 기존 진입 흐름을 먼저 마친 뒤 링크 입력
  화면을 공유된 URL이 채워진 상태로 표시해야 한다. 공유된 URL은 해당 앱 실행 동안만 유효하며,
  앱이 종료되면 버려야 한다.
- **FR-027**: 공유 진입 시 이미 생성이 진행 중이면 새 등록 화면을 열지 않고 홈 화면의 진행 중
  상태를 표시해야 하며, 공유된 URL은 보관하지 않고 버려야 한다.
- **FR-028**: 공유 항목에 URL이 여러 개 있으면 형식과 무관하게 첫 번째 URL만 사용해야 한다.
- **FR-029**: 공유 경로는 전달받은 URL이 저장소 링크인지 판정하지 않고 링크 입력 화면으로
  넘겨야 한다. 유효성 판정과 실패 안내는 사용자가 직접 붙여넣었을 때와 동일하게 링크 입력
  화면의 기존 원격 조회 경로가 담당해야 하며, 공유 경로에 별도의 검증 규칙을 두어서는 안 된다.

#### 유저 프로필 이미지 (항목 8)

- **FR-030**: 홈 화면 프로필 영역의 아바타는 이번 변경에서 원격 이미지로 갱신하지 않고 현행
  고정 기본 이미지를 유지해야 한다.

### 핵심 엔터티

- **생성 진행 상태**: 생성 요청을 제출한 시점부터 요청 + 최소 대기 시간과 결과 도착 중 나중
  시점까지 유지되는 단일 슬롯 상태. 대상 `projectID`와 요청 시각을 속성으로 가지며 기기에
  보존되어 앱 재실행 후 복원된다. 생성 진행 화면의 완료 전이, 완료 알림 발송, 홈 화면
  불러오기 패널의 표시와 조작 가능 여부가 모두 이 하나의 수명을 공유한다.
- **완료 알림 예약**: 하나의 생성 요청에 대한 완료 알림 발송 자격. 요청 시각, 최소 대기
  시간(300초), 이미 발송했는지 여부를 함께 가진다.
- **공유 진입 링크**: 다른 앱의 공유 시트에서 전달받은 레포지토리 URL 1건. 수명은 그 앱
  실행(프로세스)으로 한정된다. 링크 입력 화면의 초기 입력값으로 1회 소비되면서 "다음" 액션을
  1회 자동 실행시키며, 소비되지 못하는 조건(생성 진행 중, 인증 미완료 상태에서 앱 종료)에서는
  보관하지 않고 버려진다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 링크 입력 화면에서 키보드를 올리고 내리는 동안 하단 액션 버튼의 화면 내 세로
  위치 변화가 0이다.
- **SC-002**: 키보드가 올라온 상태에서 입력 필드·키보드 밖 임의 지점을 터치하면 100% 키보드가
  닫히며, 같은 지점의 기존 조작이 동작하지 않게 되는 회귀가 0건이다.
- **SC-003**: 생성이 진행 중인 동안 홈 화면에서 새 등록 화면으로 진입하는 경로가 0개다.
- **SC-004**: 생성 결과가 즉시 반환되는 조건에서 완료 알림 발송 시각이 요청 시각 + 300초
  이상이며, 하나의 요청당 발송 횟수가 정확히 1회다. 결과 수신 후 앱을 백그라운드로 보내거나
  종료한 경우에도 동일하다.
- **SC-005**: 완료 알림 발송 시점에 진행 화면이 표시 중인 경우, 진행 화면이 완료로 전이하기까지
  추가 대기가 0초다.
- **SC-006**: 학습 프로젝트 조회 중과 조회 완료 후 카드 영역 높이 차이가 0이다.
- **SC-007**: 홈 진입 직후 첫 카드의 회전각이 0도이며, 스크롤 위치에 대한 각도 함수에 불연속
  지점이 0개다.
- **SC-008**: URL을 공유하는 앱의 공유 시트에서 Git It을 선택했을 때, 링크 입력 화면이 공유된
  URL이 채워진 상태로 열리고 "다음"이 추가 조작 없이 1회 실행되는 비율이 100%이며, 자동 실행
  횟수가 공유 1건당 정확히 1회다.
- **SC-009**: 하나의 생성 요청에 대해 진행 화면 완료 전이, 완료 알림 발송, 홈 불러오기 패널
  해제가 같은 시점에 일어나며 세 시점의 차이가 1초 이내다.
- **SC-010**: 생성 진행 중 앱을 완전히 종료한 뒤 다시 실행했을 때 진행 중 표기가 복원되는
  비율이 100%이며, 복원된 상태의 남은 대기 시간 오차가 1초 이내다.
- **SC-011**: 변경 전 통과하던 기존 자동화 테스트가 변경 후에도 100% 통과한다.

## 가정

- Figma 노드 `1859:21645`는 프레임 이름이 "홈 - 생성 완료"지만 실제 렌더링 내용은 불러오기
  버튼이 "문제 생성 중" 비활성 표기인 진행 중 상태다. 사용자 설명(항목 4)에 따라 이 노드를
  **생성 진행 중** 상태의 기준으로 삼는다.
- 항목 4의 "레포지토리 불러오기 기능"은 홈 화면 불러오기 패널의 진입 버튼을 뜻한다. 등록
  화면 내부의 단계 이동이나 다른 화면의 진입점은 대상이 아니다.
- 생성 진행 상태는 동시에 1건만 존재한다. 서버가 여러 건을 동시에 처리할 수 있더라도 앱은 한
  번에 하나의 생성만 시작할 수 있게 한다. 이 제한은 상태를 기기에 보존하므로 앱 재실행으로
  우회되지 않는다.
- 보존된 진행 중 상태가 결과 도착으로도, 학습 프로젝트 목록 확인으로도 해소되지 않는 경우의
  만료 정책(예: 보존 상한 시간)은 계획 단계에서 정한다. 이 명세는 상태가 영구히 남지 않아야
  한다는 요구만 남긴다.
- 최소 대기 시간은 완료와 실패 양쪽 결과에 모두 적용된다. 생성이 30초 만에 실패해도 사용자는
  300초가 지난 뒤에야 실패를 확인한다. 실패를 더 빨리 노출하는 예외는 두지 않으며, 완료·실패의
  수명 규칙을 하나로 유지하는 쪽을 택했다. 실패 경로에는 별도 알림을 발송하지 않으므로, 홈에서
  기다린 사용자는 불러오기 패널이 다시 활성화된 것으로 재시도 가능 시점을 알게 된다.
- 최소 대기 시간 300초는 완료 알림과 생성 진행 화면에 함께 적용한다. 생성 결과가 더 빨리
  도착해도 진행 화면은 완료로 전이하지 않고, 300초가 지난 시점에 화면 완료와 알림 발송이 함께
  일어난다. 실제 생성이 빨리 끝나는 경우 사용자는 최대 300초를 기다린다. 이는 진행 화면의
  안내와 알림이 어긋나지 않는 것을 대기 시간 단축보다 우선한 결정이다.
- 진행 화면의 180~300초 무작위 진행률 시뮬레이션은 이번 범위에서 변경하지 않는다. 시뮬레이션
  총 시간이 최소 대기 시간보다 짧게 뽑히면 마지막 단계가 진행 중 상태로 최대 120초 유지되며,
  이 정체를 감수하는 대신 시뮬레이션 구간 조정은 별도 결정으로 남긴다.
- 로딩 상태와 "프로젝트 없음" 상태는 같은 빈 데크 실루엣을 배경으로 쓰고 로딩 인디케이터
  유무로 구분한다. 두 상태에 서로 다른 그림을 주는 것은 이번 범위가 아니다.
- 항목 3의 배치 문제는 첫 카드 기울기로 한정한다. 두 번째 이후 카드의 각도 값과 카드 간
  간격은 현행 기준을 유지한다.
- 항목 6의 공유 진입은 iOS 공유 시트를 통한 URL 수신을 전제로 한다. GitHub 앱 전용 연동이나
  GitHub 계정 연동 확장은 범위가 아니다.
- 완료 알림은 생성 결과를 확인한 뒤에 예약한다. 결과를 확인하기 전에 미리 예약해 두고 나중에
  취소하는 방식은, 취소를 실행하지 못하는 상태에서 잘못된 완료 알림이 나갈 수 있어 채택하지
  않는다.
- 항목 5의 알림은 앱이 자체 발송하는 로컬 알림을 뜻한다. 서버가 보내는 원격 푸시의 발송
  시점 제어는 범위가 아니다.
- 항목 8은 신규 구현이 아니라 현행 유지 결정이다. 프로필 이미지 조회·표시 기능은 이번
  기능의 범위 밖으로 명시적으로 제외한다. 이름·직군 등 이미지 외 프로필 정보의 기존 동작은
  변경하지 않는다.
