# 조사: Figma UI 레이아웃 상수 검증

## 결정 1: Figma 근거 수준을 세 단계로 구분한다

- **결정**: `A`는 Figma 100% 화면 또는 직접 속성에서 확인한 값, `B`는 저장소가 Figma 실측이라고 명시한 값, `C`는 현재 코드에만 존재하는 기준선으로 구분한다.
- **근거**: Figma MCP 호출 한도로 모든 노드 속성을 직접 읽을 수 없었다. 근거 수준을 섞으면 현재 구현값을 디자인 확정값으로 오인할 수 있다.
- **검토한 대안**: 모든 현재 상수를 Figma 목표값으로 간주하는 방식은 순환 검증이 되므로 기각했다. 직접 확인되지 않은 모든 항목을 제외하는 방식은 전체 대응 현황을 잃으므로 기각했다.

## 결정 2: 제품 App이 아닌 UI 전용 검증 앱에서 XCUITest를 실행한다

- **결정**: `UIComponentLayoutHarness` 앱 타깃과 `UIComponentUITests` UI 테스트 타깃을 UI 프로젝트 안에 둔다.
- **근거**: 실제 `XCUIApplication` 프레임과 접근성 트리를 검증하면서도 제품 App·Feature에 검토 전용 라우팅과 표본 데이터를 유입시키지 않는다. UI 패키지 책임과도 일치한다.
- **검토한 대안**: 제품 `GitIt` 앱의 `ContentView`를 검증 카탈로그로 바꾸는 방식은 App 패키지 변경과 승인 게이트를 추가하고 제품 진입점을 오염시켜 기각했다. `UIHostingController.sizeThatFits` 단위 테스트만 쓰는 방식은 실제 UI 테스트 요청과 접근성 프레임 확인을 충분히 충족하지 못해 보조 검증으로만 허용한다.

## 결정 3: 고정 표면과 터치 영역을 별도 계약으로 검증한다

- **결정**: 시각 표면은 Figma 크기(`ActionButton LG 54pt·SM 40pt`, `IconGlassButton MD 40pt·SM 36pt`)를 따르고, 상호작용 프레임은 최소 44pt를 보장한다.
- **근거**: 작은 시각 컴포넌트가 Figma 값과 맞더라도 44pt 미만의 실제 터치 대상이면 접근성 요구를 위반한다. 현재 `IconGlassButton`의 `size + 2`는 38pt로 어느 계약도 충족하지 않는다.
- **검토한 대안**: 모든 아이콘 버튼을 시각적으로 44pt로 확대하는 방식은 Figma 변형을 훼손해 기각했다. 시각 크기만 검증하는 방식도 접근성 회귀를 놓치므로 기각했다.

## 결정 4: 적응형 시스템 UI는 픽셀 높이를 고정하지 않는다

- **결정**: `TabView`, Dynamic Type 텍스트와 화면 폭 의존 영역은 잘림 없음, 최소 터치 영역, 상태 간 외곽 크기 불변과 같은 조건을 검증한다.
- **근거**: 플랫폼이 소유하는 안전 영역과 시스템 컨트롤을 Figma 프레임 높이에 고정하면 기기·글꼴 크기별 회귀를 만든다.
- **검토한 대안**: 기준 기기 전체 스크린샷 픽셀 비교는 작은 OS 렌더링 차이에 취약하고 의미 있는 레이아웃 오류를 설명하기 어려워 주 검증 방식에서 제외했다.

## 결정 5: 크기 변형은 각 컴포넌트의 중첩 `Size`가 소유한다

- **결정**: 일반 버튼과 Liquid Glass 아이콘 버튼은 각각 자신의 `Size` 열거형과 기본값을 소유한다.
- **근거**: 크기값은 두 컴포넌트에서 의미와 구성 요소가 다르고, UI 패키지 규칙은 View가 소유하는 변형을 중첩하도록 요구한다.
- **검토한 대안**: 공용 `ControlSizeToken`에 36·40을 추가하는 방식은 44pt 미만 값을 공용 터치 크기로 오해하게 만들고 기존 토큰 검증 정책과 충돌해 기각했다. 임의 `CGFloat` 공개 입력은 지원하지 않는 크기를 허용하므로 기각했다.
