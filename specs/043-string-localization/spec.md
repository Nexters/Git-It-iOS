# 기능 명세: 사용자 노출 문자열 현지화 적용

**Git-flow 유형**: `feature`

**기능 브랜치**: `feature/string-localization`

**브랜치 상태**: `생성`

**생성일**: 2026-09-24

**상태**: 초안

**입력**: 사용자 설명: "Localize String 적용"

## 배경

현재 앱의 사용자 노출 문구는 Swift 소스에 한국어 문자열 리터럴로 직접 작성되어 있다. 2026-09-24
기준 `sources/Projects`의 테스트·생성 코드 제외 Swift 파일 중 한국어 리터럴을 포함한 파일은
`Feature` 87개, `UI/Component` 36개, `App` 5개이며, 저장소 어디에도 현지화 리소스
(String Catalog, `.strings`, `.stringsdict`)가 없다. 이 때문에 문구를 한곳에서 검토·수정할 수 없고,
다른 언어를 추가하려면 모든 호출부를 다시 수정해야 한다.

이 기능은 사용자 노출 문구를 현지화 리소스에서 조회하도록 바꾸고, 문구 추가·검토·번역 절차를
개발자가 반복 가능하게 만든다.

## 명확화

### 세션 2026-09-24

- 질문: 이번 범위에서 지원할 언어는 무엇인가? → 답변: 한국어만 리소스화한다. 영어 등 추가 언어 번역은
  이후 기능으로 미루며, 이번 변경은 한국어 사용자에게 보이는 결과를 바꾸지 않는다.
- 질문: 현지화 항목의 식별자(키)는 어떤 기준으로 정하는가? → 답변: 의미 기반 키(예: `settings.title`)를
  쓰고 한국어 문구는 그 키의 값으로 둔다. 한국어 문구를 고쳐도 키는 바뀌지 않는다.
- 질문: 표시 문구를 검증하는 기존 테스트는 무엇을 기대값으로 삼는가? → 답변: 한국어 최종 문구를 기대값으로
  유지한다. 테스트는 리소스에서 조회한 값이 변경 전 한국어 문구와 같은지 검증한다.
- 질문: 리소스에 등록되지 않은 문구나 쓰이지 않는 항목의 자동 검출을 어느 수준으로 강제하는가? → 답변:
  이번 범위에서 제외한다. 자동 검출·강제는 이후 기능으로 미루고, 이번에는 컨벤션 문서와 리뷰로 관리한다.
- 질문: `UIComponent` 내부에 고정된 문구(닫기·뒤로 가기, 정답·오답, 필수·선택, 접근성 레이블 등)는 누가
  소유하는가? → 답변: `UIComponent`가 자기 리소스로 소유한다. 컴포넌트 공개 API는 바꾸지 않는다.
- 정정: 2026-09-24 조사에서 `UIComponent` `TabShell`의 탭 이름은 프리뷰 전용 값(`TabShellPreviewItem`)으로
  확인되어 앞 답변의 예시에서 뺐다. 실제 탭 이름은 Feature `MainShellTab`이 소유한다.
- 질문: 새 문구를 추가할 때 수정하는 곳은 몇 곳인가? → 답변: 카탈로그, `LocalizedText` 멤버, 호출부 세 곳이다.
  모듈별 문구 전용 타입을 두기로 한 계획 결정(research.md 결정 7)을 반영한다. 기존 문구의 값만 바꿀 때는
  카탈로그 한 곳이다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 사용자 노출 문구를 현지화 리소스에서 제공 (우선순위: P1)

개발자는 화면·컴포넌트·알림에 보이는 모든 문구가 소스 리터럴이 아니라 현지화 리소스의 항목으로
관리되는 상태를 얻는다. 기본 언어(한국어) 사용자에게는 변경 전과 같은 문구가 같은 위치에 보인다.

**주요 행위자**: 개발자(문구를 추가·수정하는 사람), 최종 사용자(기본 언어 환경)

**우선순위 이유**: 이후 모든 번역·문구 검토 작업의 전제이며, 이 단계만으로도 문구를 한곳에서
검토할 수 있게 된다.

**독립 테스트**: 한국어 기기 설정에서 대표 화면(온보딩, 홈, 프로젝트 등록, 퀴즈, 저장, 설정)과
세트 생성 알림을 확인해 변경 전과 문구가 같고, 현지화 리소스에 해당 항목이 존재함을 확인한다.

**수용 시나리오**:

1. **전제** 기기 언어가 한국어, **실행** 앱의 각 화면을 연다, **결과** 모든 문구가 변경 전과 동일하게
   표시되고 현지화 키나 빈 문자열이 노출되지 않는다.
2. **전제** 현지화 리소스에서 특정 문구 항목의 한국어 값을 수정, **실행** 앱을 다시 빌드해 해당 화면을 연다,
   **결과** Swift 소스를 수정하지 않았는데도 수정한 문구가 표시된다.
3. **전제** 세트 생성 완료·실패 알림이 도착, **실행** 알림을 확인한다, **결과** 제목과 본문이 현지화
   리소스의 값으로 표시된다.
4. **전제** VoiceOver 사용, **실행** 버튼·아이콘 컨트롤에 초점을 맞춘다, **결과** 접근성 레이블도
   현지화 리소스의 값으로 읽힌다.

---

### 시나리오 2 - 보간·복수 표현 문구의 현지화 (우선순위: P2)

개수·번호·이름처럼 값이 끼어드는 문구(예: "\(count)개", "문제 \(number)")가 언어별 어순과 복수
규칙을 표현할 수 있는 형태로 현지화 리소스에 등록된다.

**주요 행위자**: 개발자, 번역 담당자

**우선순위 이유**: 값 보간 문구는 단순 치환만으로 번역할 수 없어, 언어 추가 전에 형태를 확정해야 한다.

**독립 테스트**: 보간 문구가 있는 화면(저장한 문제 필터 개수, 문제 번호 메타데이터 등)을 값 0·1·여러
개로 표시해 한국어 결과가 변경 전과 같고, 리소스 항목에 인자 자리표시자가 선언되어 있음을 확인한다.

**수용 시나리오**:

1. **전제** 보간 문구 항목, **실행** 여러 값으로 화면을 표시한다, **결과** 한국어 표시가 변경 전과
   동일하다.
2. **전제** 보간 문구 항목, **실행** 번역 담당자가 리소스를 연다, **결과** 인자 위치와 의미를 알 수 있는
   설명(주석)이 함께 제공된다.

### 예외·경계 사례

- 서버·GitHub에서 받은 콘텐츠(퀴즈 문제, 프로젝트 이름, 저장소 설명, 서버 오류 메시지)는 현지화
  대상이 아니며 받은 값 그대로 표시된다.
- 로그(`Logger`), `fatalError`·`precondition` 메시지, `#Preview` 이름과 미리보기 전용 샘플 데이터,
  테스트 픽스처는 사용자에게 노출되지 않으므로 대상이 아니다.
- 줄바꿈(`\n`)이 포함된 문구는 리소스화 후에도 같은 위치에서 줄이 바뀐다.
- 여러 화면에서 같은 한국어 문구(예: "잠시 후 다시 시도해 주세요.")가 쓰여도 의미·맥락이 다르면 서로
  다른 의미 기반 키를 가진 독립 항목으로 관리한다.
- `UIComponent` 내부에 고정된 문구(예: 닫기·뒤로 가기 레이블, 정답·오답, 필수·선택, 접근성 레이블·힌트)는
  `UIComponent` 자신의 리소스에서 조회되어, 앱 번들의 리소스 유무와 무관하게 올바르게 표시된다.
- 탭 이름(홈·프로젝트·저장·마이)은 `UIComponent`의 `TabShell`이 아니라 Feature의 `MainShellTab`이 제공하는
  값이므로 Feature가 현지화한다. `TabShell`의 탭 이름은 프리뷰 전용 값이라 대상이 아니다.
- 기기 언어가 한국어가 아니어도 문구는 한국어로 표시된다.
- Share Extension처럼 앱과 다른 번들에서 실행되는 화면도 같은 기준으로 문구가 표시된다.
- 컴포넌트가 외부에서 받은 문자열(서버 값 등)을 현지화 키로 오인해 조회하지 않는다.
- 표시 문구를 검증하는 기존 테스트는 한국어 최종 문구를 기대값으로 유지하며, 리소스 조회가 실패해 키가
  그대로 반환되면 실패한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 앱(`App`의 GitIt·ShareExtension), `Feature`, `UIComponent`가 사용자에게 보여 주는 모든
  고정 문구(화면 텍스트, 버튼·메뉴 제목, 빈 상태·오류 안내, 확인 대화상자, 로컬 알림 제목·본문,
  접근성 레이블·힌트)는 현지화 리소스에서 조회되어야 한다.
  Share Extension에는 자체 화면 문구가 없으며, 공유 등록 화면 문구는 Feature `ShareRegistration` 흐름이 소유한다.
- **FR-002**: 기본(개발) 언어는 한국어이며, 한국어 환경에서 표시되는 모든 문구는 변경 전과 글자 단위로
  동일해야 한다.
- **FR-003**: 각 현지화 항목은 사용 위치와 의미를 설명하는 번역용 주석을 가져야 한다. 값이 보간되는
  항목은 각 인자의 의미를 주석에 밝혀야 한다.
- **FR-004**: 개수·번호처럼 수량이 들어가는 문구는 언어별 복수 규칙과 어순을 표현할 수 있는 형태로
  등록되어야 한다.
- **FR-005**: 각 모듈의 문구는 그 문구를 소유한 모듈의 리소스에서 조회되어야 하며, 다른 모듈(특히 앱
  번들)의 리소스에 의존해 표시되지 않아야 한다.
- **FR-006**: 서버·외부에서 받은 동적 콘텐츠와 사용자가 입력한 값은 현지화 조회 없이 그대로 표시되어야
  한다.
- **FR-007**: 로그, 크래시 진단 메시지, 미리보기 전용 문자열, 테스트 픽스처는 현지화 대상에서 제외한다.
- **FR-008**: 이번 범위의 지원 언어는 한국어 하나다. 기기 언어가 한국어가 아닌 환경에서도 모든 문구는
  한국어로 표시되어야 하며, 현지화 키나 빈 문자열이 노출되지 않아야 한다.
- **FR-010**: 문구를 추가·수정·번역하는 규칙(의미 기반 키 작명 기준, 주석 작성, 모듈별 소유, 제외 대상)을 프로젝트
  컨벤션 문서에 기록해 이후 작업자가 같은 방식으로 따를 수 있어야 한다.
- **FR-011**: 이 변경은 레이아웃·색·타이포·동작을 바꾸지 않아야 하며, 기존 아키텍처의 의존 방향과
  생성자 주입 원칙을 유지해야 한다.
- **FR-012**: 이후 언어를 추가할 때 호출부 Swift 소스를 수정하지 않고 현지화 리소스에 해당 언어 값만
  추가하면 되도록 모든 사용자 노출 문구가 리소스 항목으로 조회되어야 한다.
- **FR-013**: 모든 현지화 항목의 키는 한국어 문구가 아니라 소유 모듈·화면·용도를 드러내는 의미 기반
  식별자여야 한다. 한국어 값을 수정해도 키는 유지되어야 하며, 같은 한국어 문구라도 맥락이 다르면 서로 다른
  키를 가진다.
- **FR-014**: 표시 문구를 검증하는 테스트는 현지화 키가 아니라 리소스에서 조회된 한국어 최종 문구를
  기대값으로 삼아야 한다. 기존 한국어 기대값은 변경 전 문구 그대로 유지되어야 한다.
- **FR-015**: `UIComponent` 내부에 고정된 문구는 `UIComponent`가 자기 리소스로 소유해야 하며, 이 변경으로
  `UIComponent`의 공개 초기화 인자·메서드 계약이 바뀌지 않아야 한다.

### 핵심 엔터티

- **현지화 리소스**: 모듈별로 소유되는 문구 모음. 항목마다 식별자, 언어별 값, 번역용 주석, 번역 상태를
  가진다.
- **현지화 항목**: 하나의 사용자 노출 문구. 의미 기반 키로 식별되며 키는 소유 리소스 안에서 유일하다. 고정 문구이거나 인자(개수·번호·이름)를 받는 보간 문구이며,
  수량 인자가 있으면 복수 변형을 가질 수 있다.
- **지원 언어**: 리소스가 값을 제공하는 언어 목록. 개발 언어(한국어)가 대체 언어다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: `App`·`Feature`·`UIComponent`의 production Swift 소스에서 사용자 노출 문구로 쓰이는 한국어
  문자열 리터럴이 0개가 된다(로그·진단·미리보기·테스트는 집계에서 제외).
- **SC-002**: 한국어 환경에서 대표 화면 6종(온보딩, 홈, 프로젝트 등록, 퀴즈, 저장, 설정)과 로컬 알림
  2종(생성 완료·실패)의 문구가 변경 전 대비 100% 동일하다.
- **SC-003**: 현지화 리소스의 모든 항목이 번역용 주석을 가지며, 보간 항목의 100%가 인자 의미를 설명한다.
- **SC-004**: 기존 테스트 전체와 프로젝트 build·compile·test 검증이 변경 전후 동일하게 통과한다.
- **SC-005**: 개발자가 새 문구 하나를 추가할 때 수정하는 곳이 소유 모듈의 리소스(카탈로그), 그 모듈의 문구
  전용 타입(`LocalizedText`) 멤버, 호출부, 최대 세 곳으로 한정된다. 기존 문구의 한국어 값만 바꿀 때는 리소스
  한 곳만 수정한다.
- **SC-006**: 기기 언어를 영어로 바꾼 환경에서 대표 화면 6종에 현지화 키나 빈 문자열이 0건 노출되고, 모든
  문구가 한국어로 표시된다.

## 가정

- 추가 언어(영어 등) 번역은 이후 별도 기능에서 다룬다.
- 리소스 누락·미사용 항목의 자동 검출과 pre-commit·CI 강제는 이후 별도 기능에서 다루며, 이번에는 FR-010의
  컨벤션 문서와 코드 리뷰로 관리한다.
- 기기(시스템) 언어 설정을 따르며, 앱 내부 언어 선택 설정은 이번 범위에 포함하지 않는다.
- 날짜·숫자 형식 현지화, 이미지·애니메이션 리소스 현지화, 오른쪽→왼쪽(RTL) 레이아웃 대응은 범위 밖이다.
- App Store 메타데이터와 스크린샷 현지화는 범위 밖이다.
- `Domain`·`Data`·`Infrastructure`에는 사용자 노출 문구가 없으며(2026-09-24 조사 기준 로그 문자열만 존재),
  사용자 노출 문구가 발견되면 표시 책임을 가진 `Feature`·`App` 쪽에서 현지화한다.
- Share Extension의 표시 이름(`CFBundleDisplayName`: "Git-It")은 브랜드 고유 명칭이므로 번역하지 않는다.
- Tuist 기반 멀티 패키지 구조와 iOS 26.0 최소 지원 버전에서 제공하는 표준 현지화 수단을 사용할 수 있다.
