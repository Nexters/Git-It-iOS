### 세션 2026-09-01

- 질문: BR-002의 생성 결과 유실을 프로세스 내 보존(버퍼)으로 막을 것인가, 서버 정본 재조정까지 포함할 것인가? → 답변: 둘 다 채택하지 않는다. 등록 흐름에서 생성 결과 구독을 먼저 확립하고 그 확립이 끝난 뒤에만 생성 요청을 전송하도록 직렬화한다. 코드 확인 결과 현재는 생성 요청 → 응답 → 구독 순서라 유실 구간이 존재하며, 구독은 `projectID` 없이도 시작할 수 있고 구독 확립 시점이 동기적으로 관찰 가능하므로 직렬화만으로 이 경로의 유실 구간이 사라진다.
- 질문: 생성 결과 개념의 canonical 용어를 무엇으로 확정하는가? → 답변: 경계별로 분리한다. Domain은 공급자 중립 용어인 `GenerationOutcome` 계열을 유지하고, Data 경계는 백엔드 실제 어휘인 `QuizGeneration*` 계열(`QuizGenerationOutcomeDTO` 등)을 사용하며, Composition adapter가 두 어휘 사이의 변환을 흡수한다. NR-002가 권장한 `LearningSetGenerationOutcome`은 채택하지 않는다. `LearningSet`이 이미 set 식별자로 조회되는 별개 Domain 모델(`Models/Quiz/LearningSet.swift`, `LearningSetRepository`, `FetchLearningSetUseCase`)로 존재하는데, 이 이벤트는 `projectID`로만 식별되어 이름과 식별자가 어긋나기 때문이다.
- 질문: 생성 결과 전달을 어떤 수명 범위까지 보장하는가? → 답변: 프로세스 실행 중에는 생성 요청 전 구독 선확립으로 전달을 보장하고, 프로세스 재시작 후에는 Home 서버 목록 조회로 정합성을 확보한다. 구독자가 없는 시점의 스트림 전달은 보장하지 않으며 메모리 버퍼와 영속 저장은 도입하지 않는다.
- 질문: 기기 등록 실패를 어떻게 재시도하는가? → 답변: 실패 상태를 인증 세션 소유자에게 보존하고 앱이 다시 활성화되거나 push 등록 token이 갱신되면 자동 재시도한다. 동시에 발생한 재시도 trigger는 하나의 기기 등록 요청으로 직렬화하고, 인증 종료 시 실패 상태와 진행 중인 Effect를 제거한다.

## 변경 시나리오와 테스트 *(필수)*

### 시나리오 1 - 생성 결과 구독을 확립한 뒤에 생성 요청을 보낸다 (우선순위: P1)

프로젝트를 등록한 사용자는 생성 완료·실패 신호를 놓치지 않고 진행 화면에서 확인할 수 있다.

**주요 행위자**: 프로젝트를 등록하고 생성 완료를 기다리는 최종 사용자

**우선순위 이유**: 현재는 생성 요청을 먼저 보내고 응답을 받은 뒤에야 구독을 시작하므로, 그 사이에
도착한 결과가 폐기된다. 신호 유실은 진행 화면 무기한 대기로 이어져 등록 흐름의 핵심 가치를
무너뜨린다.

**독립 테스트**: 생성 요청이 전송되기 전에 생성 결과 구독이 이미 확립돼 있는지를 관찰하는 것만으로
검증할 수 있다.

**수용 시나리오**:

1. **전제** 사용자가 생성 확정을 선택했다, **실행** 등록 흐름이 생성 요청을 전송한다, **결과** 생성
   결과 구독이 그 요청 전송 시점에 이미 확립돼 있다.
2. **전제** 생성 요청 응답이 도착하기 전에 해당 프로젝트의 생성 완료 신호가 먼저 도착한다,
   **실행** 이어서 생성 요청 응답이 도착한다, **결과** 진행 화면이 그 완료 결과를 반영하고 대기
   상태를 벗어난다.
3. **전제** 같은 프로젝트의 완료 신호가 중복 도착한다, **실행** 구독자가 이를 수신한다,
   **결과** 상태 반영 결과는 1회 수신과 동일하며 중복 재조회가 발생하지 않는다.
4. **전제** 앱이 종료된 상태에서 생성 완료 push가 도착해 cold launch가 일어났다, **실행** 세션
   복원과 Home 진입이 끝난다, **결과** Home 프로젝트 목록이 서버 조회 결과로 완료 상태를 반영한다.

### 시나리오 2 - 실패와 인증 종료에서 등록 흐름을 벗어날 수 있다 (우선순위: P1)

생성이 실패하거나 사용자가 로그아웃해도 등록 흐름이 화면을 점유한 채 남지 않는다.

**주요 행위자**: 생성 실패를 겪거나 등록 도중 로그아웃하는 최종 사용자

**우선순위 이유**: 현재는 알림 옵션 시트가 열린 채 생성이 실패하면 시트가 `interactiveDismissDisabled`
상태로 남고 이후 모든 Action이 no-op이 되어 사용자가 앱에 갇힌다. 복구 수단이 없는 결함이다.

**독립 테스트**: 시트가 열린 상태에서 실패 outcome을 주입하고, 사용자가 실패 화면을 확인하고
재시도 또는 종료할 수 있는지 reducer 테스트로 검증할 수 있다.

**수용 시나리오**:

1. **전제** 알림 옵션 시트가 표시된 상태다, **실행** 해당 프로젝트의 생성 실패 신호가 도착한다,
   **결과** 시트가 닫히고 사용자는 실패 상태를 확인하며 재시도 또는 등록 흐름 종료를 선택할 수 있다.
2. **전제** 등록 흐름이 표시된 상태다, **실행** 사용자가 로그아웃하거나 세션이 종료된다,
   **결과** 등록 흐름 화면이 사라지고 관련 생성 결과 관찰이 중단된다.
3. **전제** 로그아웃 뒤 다시 로그인한다, **실행** 앱이 첫 화면을 표시한다, **결과** 이전 세션의
   등록 흐름 화면이 다시 나타나지 않는다.

### 시나리오 3 - 시스템 설정 화면 이동이 UIKit 실행 조건을 지킨다 (우선순위: P1)

알림 권한이 이미 거부된 사용자가 리마인드를 수락하면, 설정 앱 이동이 UIKit이 요구하는 실행
문맥에서 수행된다.

**주요 행위자**: 알림 권한을 과거에 거부한 최종 사용자

**우선순위 이유**: 현재 호출은 Main Thread Checker 위반을 발생시키며 UIKit의 스레드 안전성 계약을
어긴다. 전환 성공을 보장할 수 없고 개발 중 다른 동시성 결함을 로그에 묻는다.

**독립 테스트**: 권한 거부 상태에서 리마인드를 수락하고 Main Thread Checker 경고가 발생하지 않는지
확인하는 것만으로 검증할 수 있다.

**수용 시나리오**:

1. **전제** 시스템 알림 권한이 거부 상태이고 Main Thread Checker가 활성화돼 있다, **실행** 사용자가
   알림 옵션 시트에서 리마인드 수락을 선택한다, **결과** 설정 앱 알림 화면으로 이동하며 UIKit
   메인 스레드 위반 경고가 발생하지 않는다.
2. **전제** 설정 화면 이동 의존성을 주입하는 지점이다, **실행** 잘못된 실행 문맥에서 호출을
   시도한다, **결과** 컴파일 단계에서 차단되거나 타입 선언만으로 실행 문맥 요구가 드러난다.

### 시나리오 4 - 푸시 부트스트랩과 기기 등록에 명시적 수명 소유자가 있다 (우선순위: P2)

개발자는 푸시 초기화와 기기 등록이 언제 시작되고 실패 시 어떻게 되는지를 코드 구조에서 읽을 수
있으며, 테스트에서 실제 Firebase·Keychain 부수효과 없이 대체할 수 있다.

**주요 행위자**: 이 경로를 수정하거나 테스트하는 개발자

**우선순위 이유**: 현재는 조립 시점의 unstructured `Task`가 오류를 로깅만 하고, 전역 static 저장소가
초기화 순서를 감춘다. 인증 세션 전, 네트워크 실패, token 갱신에서 기기 등록이 조용히 누락되며 이는
생성 결과 push가 도착하지 않는 원인이 된다.

**독립 테스트**: 조립만 수행했을 때 실제 Firebase 접근과 서버 호출이 일어나지 않고, 명시적 부트스트랩
호출 이후에만 등록이 시작되는지 확인해 검증할 수 있다.

**수용 시나리오**:

1. **전제** 애플리케이션 조립이 끝났다, **실행** 부트스트랩을 호출하지 않는다, **결과** 푸시 client
   초기화와 기기 등록 요청이 발생하지 않는다.
2. **전제** 사용자가 로그인해 인증 세션이 생겼다, **실행** 앱이 기기 등록을 수행한다, **결과** 등록이
   성공하거나, 실패 시 재시도 대상으로 남고 실패 사실이 소유자에게 전달된다.
3. **전제** 기기 등록이 이미 성공했다, **실행** 푸시 등록 token이 갱신된다, **결과** 갱신된 token으로
   서버 재등록이 이루어진다.
4. **전제** 테스트 환경이다, **실행** 조립 대상을 구성한다, **결과** 푸시 전달 경로를 테스트 대역으로
   교체할 수 있고 전역 가변 상태가 테스트 간에 누수되지 않는다.
5. **전제** 인증 세션에서 기기 등록이 실패해 재시도 가능한 상태다, **실행** 앱이 다시
   활성화되거나 push 등록 token이 갱신된다, **결과** 최신 token으로 기기 등록을 자동
   재시도하고 동시 trigger는 하나의 요청으로 직렬화된다.

### 시나리오 5 - 화면 단계와 목록 갱신을 Feature 상태가 소유한다 (우선순위: P2)

사용자는 View가 재생성돼도 등록 단계를 잃지 않고, Home은 조회 중에 도착한 생성 결과를 놓치지 않는다.

**주요 행위자**: 등록 흐름을 진행 중인 최종 사용자

**우선순위 이유**: 단계 상태가 SwiftUI 로컬 상태에 있어 View 재생성 시 사용자가 이전 단계로
되돌아간다. Home은 조회 중 도착한 결과를 폐기하면서 후속 갱신을 예약하지 않아 오래된 목록을 남긴다.

**독립 테스트**: 조회 중 outcome을 주입하고 조회 완료 후 목록이 최신 상태가 되는지 reducer 테스트로
검증할 수 있다.

**수용 시나리오**:

1. **전제** 사용자가 저장소 확인과 이해도 선택을 마쳤다, **실행** View가 재생성된다, **결과** 사용자는
   같은 단계에 머문다.
2. **전제** Home이 프로젝트 목록을 조회하는 중이다, **실행** 생성 완료 신호가 도착한다, **결과** 조회
   완료 뒤 목록이 그 결과를 반영한다.
3. **전제** 조회가 끝난 뒤 같은 완료 신호가 다시 도착한다, **실행** Home이 이를 수신한다, **결과**
   불필요한 반복 조회가 발생하지 않는다.

---

### 시나리오 6 - 공개 이름이 실제 책임과 범위를 드러낸다 (우선순위: P3)

개발자는 타입·Action·연산 이름만으로 그 대상과 부수효과를 파악할 수 있다.

**주요 행위자**: 이 코드를 읽고 수정하는 개발자

**우선순위 이유**: 동작 결함은 아니지만 잘못된 이름은 위 P1·P2 결함이 재발하는 조건을 만든다.
특히 모델은 `GenerationOutcome`으로 정리됐는데 Use Case만 `LearningProjectOutcomes`로 남아 같은
개념이 두 어휘로 존재한다.

**독립 테스트**: rename 후 이전 심볼이 저장소에서 검색되지 않고 빌드와 기존 테스트가 통과하는지로
검증할 수 있다.

**수용 시나리오**:

1. **전제** rename을 적용했다, **실행** 저장소 전체에서 이전 공개 심볼을 검색한다, **결과** 잔여
   참조가 없고 파일명·테스트·명세 참조가 함께 갱신돼 있다.
2. **전제** rename을 적용했다, **실행** production build와 기존 테스트를 실행한다, **결과** 동작
   변경 없이 모두 통과한다.

### 예외·경계 사례

- 앱이 완전히 종료된 상태에서 생성 완료 push가 도착하고 사용자가 알림을 탭하지 않은 채 앱을 열면
  어떻게 되는가? (FR-004에 따라 Home의 서버 목록 조회가 정본이 된다)
- 이미 반영한 생성 결과와 같은 결과가 다시 도착하면 어떻게 되는가?
- 알림 옵션 시트가 열린 상태에서 생성 실패와 사용자의 수락 탭이 거의 동시에 발생하면 어떤 상태가
  최종으로 남는가?
- 인증 세션이 없으면 기기 등록을 시작하지 않고, 다음 인증 세션 확립을 최초 등록
  trigger로 사용한다.
- 등록 흐름이 표시된 상태에서 세션 만료로 강제 로그아웃되면 진행 중인 생성 관찰은 어떻게 되는가?
- 설정 앱으로 이동한 뒤 사용자가 권한을 허용하고 앱으로 돌아오면 리마인드 등록은 어떻게 되는가?

## 요구사항 *(필수)*

### 기능 요구사항

#### 생성 결과 전달 신뢰성 (시나리오 1)

- **FR-001**: 시스템은 생성 결과 구독을 확립한 뒤에만 생성 요청을 전송해야 한다. 구독 확립과 생성
  요청은 순서가 보장되는 단일 실행 경로로 직렬화해야 하며, 순서 보장이 없는 병렬 실행으로 두지
  않아야 한다.
- **FR-002**: 생성 결과 구독은 생성 요청의 응답(프로젝트 식별자)에 의존하지 않고 시작할 수 있어야
  하며, 어떤 프로젝트의 결과인지는 구독 확립 이후 수신 측에서 프로젝트 식별자로 판별해야 한다.
- **FR-003**: 시스템은 같은 프로젝트의 동일 생성 결과를 중복 수신해도 최종 상태와 부수효과가 1회
  수신과 동일하도록 멱등하게 처리해야 한다.
- **FR-004**: 시스템은 프로세스가 재시작된 경우 생성 결과를 스트림으로 복원하지 않고 Home 진입 시의
  서버 프로젝트 목록 조회를 정본으로 사용해야 한다. 생성 결과의 프로세스 간 영속 저장과 서버 정본
  재조회 API는 이 명세에서 도입하지 않는다.
- **FR-005**: 시스템은 구독 확립과 생성 요청의 순서, 생성 요청 응답보다 먼저 도착한 결과의 반영,
  중복 수신 멱등성을 자동화 테스트로 검증해야 한다.

#### 흐름 탈출 가능성 (시나리오 2)

- **FR-006**: 시스템은 생성 실패로 전이할 때 표시 중인 알림 옵션 시트를 함께 닫아야 한다.
- **FR-007**: 사용자는 생성 실패 상태에서 재시도 또는 등록 흐름 종료를 항상 선택할 수 있어야 한다.
- **FR-008**: 시스템은 인증 종료·초기화 경로에서 등록 흐름 child 상태를 제거하고 그 child가 시작한
  생성 결과 관찰을 취소해야 한다.
- **FR-009**: 시스템은 재로그인 시 이전 세션의 등록 흐름 화면이 다시 표시되지 않도록 해야 한다.

#### 설정 화면 이동 (시나리오 3)

- **FR-010**: 시스템은 시스템 설정 앱 이동을 UIKit이 요구하는 메인 액터 문맥에서만 실행해야 한다.
- **FR-011**: 설정 화면 이동 의존성의 타입 선언이 메인 액터 실행 요구를 표현해, 잘못된 문맥의 호출이
  컴파일 단계에서 드러나야 한다.
- **FR-012**: 알림 권한이 거부 상태일 때의 설정 앱 이동 동작 자체는
  `specs/020-local-reminder-notification` FR-003이 정의한 대로 유지해야 한다.

#### 푸시 부트스트랩과 기기 등록 (시나리오 4)

- **FR-013**: 시스템은 푸시 전달 client 초기화를 외부 SDK 구성이 끝난 뒤 실행되는 명시적 단계로
  분리해야 하며, 조립 객체 생성만으로 시작되지 않아야 한다.
- **FR-013a**: 리마인드 발송을 담당하는 생성 결과 구독은 부트스트랩 단계에서 확립을 완료해야 하며,
  등록 흐름이 생성 요청을 전송할 수 있게 되기 전에 확립돼 있어야 한다. 조립 시점의 순서 보장 없는
  비동기 시작에 의존하지 않아야 한다.
- **FR-014**: 시스템은 기기 등록을 인증 세션과 앱 생명주기를 소유하는 조정 지점에서 수행해야 한다.
- **FR-015**: 시스템은 기기 등록 실패를 삼키지 않고 인증 세션 소유자에게 전달해 관찰 가능한

  요청으로 직렬화해야 한다. 인증 종료 시 실패 상태와 진행 중인 등록 Effect를 제거해야 한다.
- **FR-016**: 시스템은 푸시 등록 token이 갱신되면 서버에 재등록해야 한다.
- **FR-017**: 시스템은 푸시 콜백 전달을 전역 mutable 저장소가 아닌 소유자가 명시된 수명으로

- **FR-018**: 시스템은 테스트에서 실제 외부 푸시 SDK와 Keychain 부수효과 없이 이 경로를 대체할 수

### 핵심 엔터티

- **생성 결과(Generation Outcome)**: 특정 프로젝트의 학습 세트 생성이 완료됐는지 실패했는지를
  나타내는 프로세스 내 신호. 프로젝트 식별자와 상태를 가지며, 생성 요청 전에 필수 구독이
  확립된 경로에서는 유실 없이 전달돼야 한다. 구독자가 없는 시점의 스트림 전달은 보장하지 않고,
  프로세스 재시작 후의 정합성은 Home의 서버 목록 조회를 정본으로 확보한다.
- **생성 결과 구독(Outcome Subscription)**: 진행 화면과 Home이 각각 시작하는 관찰. 소유자의 수명이
  끝나면 함께 취소돼야 한다.
- **기기 등록 정보(Member Device Info)**: 기기 식별자, 기기 유형, 앱 버전, OS 버전, 푸시 등록 token.
  인증 세션이 있어야 서버에 등록할 수 있고 token 갱신 시 재등록 대상이 된다.
- **등록 흐름 단계(Registration Step)**: 저장소 확인 → 이해도 선택 → 생성 확정 → 생성 대기 →
  결과 판정으로 이어지는 배타적 단계.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 생성 요청 전송 시점에 생성 결과 구독이 확립돼 있는 비율이 100%이며, 생성 요청 응답보다
  먼저 도착한 생성 결과가 진행 화면에 반영되는 비율이 100%다.
- **SC-002**: 동일 생성 결과를 2회 이상 수신해도 프로젝트 목록 재조회 횟수와 최종 상태가 1회 수신과
  같다.
- **SC-002a**: 리마인드 구독이 부트스트랩 완료 시점에 확립돼 있는 비율이 100%다.
- **SC-003**: 알림 옵션 시트가 열린 상태에서 생성 실패가 도착하는 시나리오에서 사용자가 재시도 또는
  종료에 도달하는 비율이 100%이며, 조작 불가 상태가 0건이다.
- **SC-004**: 로그아웃 후 재로그인 시 이전 세션의 등록 흐름 화면 재표시가 0건이고, 인증 종료 후
  등록 흐름이 발생시키는 Home 갱신 요청이 0건이다.
- **SC-005**: 알림 권한 거부 상태에서 리마인드를 수락할 때 Main Thread Checker 경고가 0건이다.
- **SC-006**: 조립 객체 생성만 수행하는 테스트에서 외부 푸시 SDK 접근과 기기 등록 서버 호출이 0건이다.
- **SC-007**: 인증 세션 확립 이후 기기 등록이 성공하거나, 실패 시 관찰 가능한 재시도 상태로 남는
  비율이 100%이며 조용히 유실되는 실패가 0건이다. 실패 후 앱 활성화 또는 token 갱신 시나리오에서
  최신 token으로 재시도하는 비율이 100%이고, 동시 trigger에 대한 서버 등록 요청은 1회다.
- **SC-008**: View 재생성 후 등록 단계가 유지되는 비율이 100%다.
- **SC-009**: 목록 조회 중 도착한 생성 결과가 조회 완료 후 반영되는 비율이 100%다.
- **SC-010**: FR-022의 경계별 어휘 규칙 기준으로 이전 공개 심볼과 파일명의 잔여 참조가 0건이며,
  Domain 공개 surface에서 `QuizGeneration*` 어휘가 0건, 생성 결과 타입 이름에서 `LearningSet`
  어휘가 0건이다.
- **SC-011**: 변경 전후 모두 Swift formatter lint가 통과하고 위반이 0건이다.
- **SC-012**: `AllTests` scheme이 실제 테스트 case를 실행해 전부 통과하며, 이 명세가 요구하는 신규
  자동화 회귀 테스트(생성 요청 전 구독 확립, 요청 응답 전 결과 수신, 중복 수신, 시트 실패 전이,
  인증 종료 정리, 단계 유지, 조회 중 outcome 반영, bootstrap 반환 전 리마인드 구독 확립, 기기 등록
  실패 후 앱 활성화·token 갱신 재시도와 동시 trigger 직렬화)가 모두 포함된다. 실제 APNs
  cold launch 정합성은 FR-004의 수동 검증으로 분리한다.
- **SC-013**: 이 명세가 다루는 모든 변경 이후에도 기존 `ProjectRegistrationFeatureTests`,
  `HomeFeature` 테스트, `AppRootFeatureTests`의 기존 시나리오가 계속 통과한다.

## 범위

### 포함

- 위 대조 표에서 **유효** 또는 **부분 유효**로 표시한 지적의 해소
- 각 지적에 대응하는 회귀 테스트 추가
- 현재 실패 중인 formatter 위반 해소

### 제외

- 이미 **해소됨**으로 확인한 BR-001, BR-009, NR-001은 다시 다루지 않는다.
- `specs/019-project-registration-flow/spec.md`의 FR-014/FR-015/SC-009 갱신은
  `specs/020-local-reminder-notification` FR-013이 별도 후속으로 규정했으므로 이 명세의 산출물
  범위 밖이다.
- 서버 API 계약 변경과 신규 구현은 다루지 않는다. `QuizGenerationRemote.fetchGenerationStatus`
  (`GET /{projectID}/status`)의 production 구현·배선은 FR-004에 따라 이 명세 범위 밖이다.
- 리뷰 리포트 §5의 preview frame·`BottomActionBar`·토큰화 같은 UI 표현 컨벤션 정리는 동작 결함이
  아니므로 이 명세에 포함하지 않는다.
- 실제 기기에서의 APNs 발급·전달 인프라 구성(provisioning, APNs key)은 코드 변경 대상이 아니다.

## 가정

- 리뷰 리포트가 지적한 대상 브랜치의 변경은 현재 HEAD `b5070bb`에 이미 포함돼 있으며, 위 대조
  표가 현행 기준의 정본이다.
- 생성 결과 스트림의 구독 확립 시점은 관찰 가능하며(구독 요청이 반환된 시점에 등록이 끝난다),
  구독은 대상 프로젝트를 알기 전에 시작할 수 있다. 이 두 성질이 FR-001 직렬화의 전제다.
- cold launch 정합성은 Home 진입 시의 서버 프로젝트 목록 조회로 확보한다. 생성 결과 버퍼나 서버
  상태 재조회 API는 도입하지 않는다.
- 프로세스가 재시작되면 `specs/020-local-reminder-notification`의 설계에 따라 리마인드 등록 대상도
  함께 사라진다. 이 명세는 그 경계를 바꾸지 않는다.
- 리뷰 리포트가 기록한 `AllTests` runner `Early unexpected exit`은 이 명세 작성 시점에 재검증하지
  않았다. 구현 단계에서 실제 실행 결과로 원인을 확인한다.
- 실제 기기 APNs 수신 검증은 개발용 provisioning과 APNs key가 준비된 환경에서 수행할 수 있다.
- 백엔드는 이 과정을 `quiz-generation`으로 부른다고 본다. 근거는 저장소에 이미 존재하는
  `POST /{projectID}/quiz-generation/retry` 경로와 `QuizGenerationRemote`,
  `QuizGenerationStatusResponseDTO`, `QuizGenerationEndpoint` 계열이다. 백엔드 계약 문서가 다른
  어휘를 사용한다면 FR-022b의 Data 어휘를 그 문서에 맞춘다.
- 명세 산문이 사용하는 "학습 세트 생성"은 사람이 읽는 설명 어휘이며, FR-022의 코드 어휘 규칙을
  바꾸지 않는다.
- 이름 변경은 동작을 바꾸지 않으며, 기존 공개 테스트 시나리오는 이름 갱신 외에 수정하지 않는다.
